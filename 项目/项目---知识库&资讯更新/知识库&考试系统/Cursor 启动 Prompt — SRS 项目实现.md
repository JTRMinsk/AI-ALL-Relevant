## 工作流程(每步必须遵守)

### 规则 1:严格按 Roadmap 顺序

按设计文档**第十一节"实施路线图"**的 8 步顺序推进:

```
1. 项目骨架        2. 数据模型 + SQL    3. loader        4. scheduler
2. stats          6. CLI 复习核心       7. reporter+vis   8. graph
```

**不要跳步,不要并行**。每完成一步,告诉用户:"第 N 步 [模块名] 完成,关键决策点是 X,运行方法是 Y,下一步是 Z。"

### 规则 2:设计先行,代码在后

开始每一个新模块之前,**先输出一段简短的实现计划**:

- 模块的输入输出是什么
- 关键函数列表(函数名 + 一句话职责)
- 设计文档没明确覆盖的细节,你打算怎么处理

等用户回复 "go" 或具体反馈后,才开始写代码。

### 规则 3:不确定就问,不要编

设计文档里没写的细节,**禁止自行决策**。常见需要问的:

- 数据库字段的 nullable / default / 索引选择
- 异常处理策略(报错退出 / 警告继续 / 静默跳过)
- CLI 输出的具体措辞与配色
- 边界情况(空 YAML、ID 冲突、磁盘满等)

直接问用户,给 2-3 个选项让 ta 选。不要自己拍板,也不要假装"行业最佳实践"。

### 规则 4:一步一停

每完成一步,**不要主动开始下一步**。等用户说"继续"或"下一步"才推进。

## MVP 阶段的反模式禁令(严格执行)

❌ **不要写抽象基类、interface、Protocol** — 具体类够用就别抽象  
❌ **不要写依赖注入框架** — 构造函数传参就够了  
❌ **不要用 ORM**(SQLAlchemy/peewee/...) — `sqlite3` 标准库直接写 SQL  
❌ **不要先写测试** — 先把主流程跑通,关键模块的测试 MVP 末尾再补  
❌ **不要加缓存层、连接池、异步** — MVP 是单用户本地工具,同步代码足够  
❌ **不要"为未来扩展"留参数和钩子** — 用到再加  
❌ **不要把简单数据封装成类** — 能用 `TypedDict` / `dataclass` 别用 class with methods  
❌ **不要主动加 logging / docstring 装饰** — 保持精简  
❌ **不要写工厂方法、单例、Builder 模式** — 这是个人项目,不是企业框架  

✅ 函数能解决就别用类  
✅ 文件 < 300 行就别拆模块  
✅ 复制粘贴 3 次再考虑抽函数  
✅ 错了重写比"优雅设计"快

## 关键实现约束(摘自设计文档,务必遵守)

### 数据库
- `sqlite3` 标准库,**禁用** ORM
- 建表 SQL 写在 `schema.sql`,启动时执行
- 读写包成简短辅助函数,**不需要 repository 模式**

### upsert 与删除(文档 14.2、14.5)
- `srs sync` 默认 upsert 内容字段,**不动统计字段**
- 任何"删除"都是 `UPDATE SET disabled = true`,**禁止 `DELETE FROM`**
- `review_log` 永远 append,**禁止 UPDATE/DELETE**

### 题目 ID(文档 14.4)
- loader **必须忽略 Claude 给的 ID**,自己用 SHA-256 重算
- 输入:题干 + 所有选项 text,去除空白
- 取前 8 位,前缀 `q-`

### 配置(文档第六章)
- PyYAML 读,Pydantic 校验
- 配置错误时打印清晰错误信息**直接退出**,禁止静默 fallback

### CLI(文档第十章)
- Typer 框架
- Rich 做终端美化(颜色、表格、进度条)
- 答题循环支持快捷键:`1/2/3/4` 选项,`y/n` 二选一,`q` 退出(已答题保存)

### 报告(文档第七章)
- Jinja2 模板
- PyVis 生成图谱 HTML 片段,嵌入主报告
- **一份报告 = 一个独立 HTML 文件**,CSS/JS 全部内联,双击可看
