# 图片缩放与图片导出实现复盘

Date: 2026-05-19

本文记录 `betterversion` 分支中围绕“图片缩放”和“导出多张图片”做的一轮功能实现。它不是用户手册，而是一次工程复盘：需求是什么，做了哪些尝试，哪些方案被浏览器安全策略卡住，最后采用了什么技术路径。

## 目标

本次需求有两个核心目标。

第一，Markdown 预览中的图片需要能放大缩小。很多截图、产品图或长图在完整展示时会被压到预览区宽度，内部文字变小，用户无法阅读细节。因此需要一个预览查看器，让用户点击图片后能缩放、拖动、适应窗口和关闭。

第二，预览内容需要能导出为图片。导出时不能把 md-pew 自己的工具栏、编辑器、状态栏带进去，只能导出 Markdown 预览结果。普通文档应按页形成多张图片；如果遇到超宽图片、表格或图表，不能强行缩进 PDF/页面宽度里，而应该带着名称单独生成图片。

实现仍然遵守项目的早期约束：`md-pew.html` 是单文件、本地运行、无构建步骤、尽量离线可用。

## 最终结果

当前实现集中在 `md-pew.html`。

- 新增图片查看器：点击预览区图片后打开全屏浮层，支持放大、缩小、适应窗口、100%、拖拽平移和 Esc 关闭。
- 新增“导出图片”按钮。
- 导出时使用屏幕外的导出舞台，只处理 Markdown 预览内容，不截取应用工具栏。
- 普通内容会被分页绘制成 PNG。
- 超宽图片、表格和 Mermaid 图会从主分页中拆出来，带标题单独生成图片。
- 多张图片会打包成一个 ZIP 下载，ZIP 内部包含一个文件夹，所有 PNG 放在该文件夹中。
- 单张图片时仍直接下载 PNG。
- 外链图片如果无法安全读取，会在导出图里替换为占位框，保留图片名称和来源 URL，避免整次导出失败。

## 尝试过程

### 1. 初版方案：隐藏 DOM + SVG foreignObject + Canvas

最早采用的是常见的前端导出方案：

1. 克隆 `#preview` 内容到屏幕外的 `exportStage`。
2. 用导出专用 CSS 设置固定画布尺寸。
3. 把 DOM 包进 SVG 的 `foreignObject`。
4. 把 SVG 画到 Canvas。
5. 用 `canvas.toBlob()` 生成 PNG 并下载。

这个方案的优点是实现快，视觉效果接近真实预览，并且不需要引入外部库。

问题也很快暴露出来：在 `file://` 环境和 Edge/in-app browser 下，只要导出内容里包含外链图片，Canvas 就可能被浏览器标记为 tainted。此时调用 `toBlob()` 会触发安全错误。即使某些图片在预览区能显示，浏览器也不允许脚本把它们读回并重新写入 PNG。

最终这个方案被废弃。原因不是代码语法问题，而是浏览器安全模型限制。

### 2. 尝试文件夹选择：showDirectoryPicker

为了让多张图片进入一个文件夹，曾尝试使用 File System Access API 的 `showDirectoryPicker()`。

在本地 `file://` 页面里，Edge 弹出了“无法打开此文件夹，由于此文件夹包含系统文件，file:/// 无法将其打开”一类提示。用户体验很差，而且不同浏览器对此 API 的支持并不稳定。

这个方案也被放弃。浏览器网页不能可靠地在默认下载目录中创建任意文件夹，也不能静默写入用户文件系统。除非未来迁移到 Tauri 或其他桌面壳，否则不应该把它作为主路径。

### 3. 尝试逐张默认下载

之后改为不选择文件夹，而是生成每张 PNG 后直接触发浏览器下载，让浏览器放进默认下载目录。

这个方案避开了文件夹选择器，但带来两个问题：

- 多页导出会在下载目录散落很多 PNG。
- 浏览器可能拦截“一个点击触发多个下载”，需要用户额外允许。

因此它只适合作为兜底，不适合作为最终体验。

### 4. 尝试图片预处理

为了缓解 Canvas taint 问题，又加入了一层图片预处理：

- 如果图片是 `data:image`，直接保留。
- 如果图片能通过 `fetch()` 安全读取，就转成 data URL。
- 如果图片已经加载且 Canvas 允许读取，就用临时 Canvas 转 data URL。
- 如果仍然失败，就替换成占位框。

这能解决一部分外链图问题，但没有彻底解决。因为当导出底层仍然依赖 `foreignObject` 时，浏览器可能把整个 SVG/DOM 渲染链路判为不安全，而不只是某一张 `<img>` 不安全。

这说明问题根部在导出机制，而不只是图片资源。

### 5. 最终方案：手工 Canvas 渲染

最终实现改成直接用 Canvas 绘制 Markdown 内容，不再通过 `foreignObject` 截 DOM。

导出流程变成：

1. 根据当前 Markdown 生成预览 HTML。
2. 克隆预览内容到隐藏的 `exportStage`。
3. 测量普通内容和超宽内容。
4. 普通内容按固定画布尺寸分页。
5. 超宽图片、表格、Mermaid 图单独生成导出节点。
6. 导出前准备图片和 Mermaid 图，必要时替换为占位框。
7. 用 Canvas API 手工绘制标题、段落、列表、引用、代码块、表格、图片和占位框。
8. 生成 PNG Blob。
9. 多张 PNG 打包为 ZIP；单张 PNG 直接下载。

这条路径牺牲了一点“完全复刻浏览器排版”的精度，但换来了可靠性：它绕开了 DOM/SVG/foreignObject 这条最容易被本地文件安全策略拦截的路线。

## 当前技术路径

### 图片缩放

图片缩放使用应用内浮层，而不是改动 Markdown 文档流。

核心状态包括：

- 当前缩放比例
- 当前平移偏移
- 是否正在拖拽
- 拖拽起点和偏移量

用户点击预览区图片后，查看器读取图片 `currentSrc` 或 `src`，进入浮层。按钮控制缩放；滚轮也能缩放；鼠标拖动改变偏移；Esc 或关闭按钮退出。

这种方式不会影响原始 Markdown，也不会改变普通预览排版。

### 导出舞台

导出时不会截取整个应用界面。代码创建了一个屏幕外的 `exportStage`，把 Markdown 预览结果放进去测量和分页。

这样可以保证导出内容只来自 Markdown，而不是来自应用壳。工具栏、编辑器、状态栏、下载链接托盘都不会进入最终图片。

### 超宽内容识别

导出前会测量这些元素：

- `img`
- `table`
- `.mermaid-diagram`

如果实际宽度超过导出页的内容宽度，就把该元素所在的顶层块从主分页中移除，改成单独图片。

标题来源按优先级推断：

- 图片优先使用 `alt`
- 表格优先使用前一行类似“表 1：xxx”的文字
- 图表优先使用前一行类似“图 1：xxx”的文字
- 如果没有明确图表名，就使用最近的标题
- 再没有就使用“图”“表”“图片”的默认编号

### Canvas 手工绘制

最终 PNG 由 Canvas 手工绘制，而不是截图 DOM。

当前支持的块级内容包括：

- 标题
- 段落
- 无序列表
- 有序列表
- 引用块
- 代码块
- 表格
- 图片
- 分割线
- 图片/图表占位框

文字换行用 Canvas 的 `measureText()` 做宽度测量。中文按字符级 token 处理，英文按词组处理，避免长文本直接溢出画布。

表格会测量各列文本宽度，尽量保持可读。如果表格超宽，会被单独导出，不会被强行压缩到普通页面中。

### 图片与图表处理

导出前会预处理图片：

- 可安全读取的图片转成 data URL。
- 不能读取的外链图片替换成占位框。
- 占位框保留图片名称、来源 URL 和说明文字。

Mermaid 图会尝试把 SVG 序列化为 data URL 图片，再交给 Canvas 绘制。如果浏览器无法准备该 SVG，也会替换为占位框。

此外，在最终 `canvas.toBlob()` 时还有一层安全兜底。如果某页仍然触发 Canvas 安全错误，会把该页所有图片和图表换成占位框后重试一次。

### ZIP 打包

浏览器网页不能可靠地在默认下载目录创建文件夹。因此最终采用 ZIP：

- 多张图片时生成 `文档名-images.zip`
- ZIP 内部包含 `文档名-images/` 文件夹
- 所有 PNG 放在这个文件夹下
- 如果下载目录里已有同名 ZIP，由浏览器自动处理重名，例如追加 `(1)`

为了保持单文件离线可用，没有引入 JSZip 等外部库，而是直接生成无压缩 ZIP：

- 写 local file header
- 写 central directory
- 写 end of central directory record
- 计算 CRC32
- 使用 UTF-8 文件名标志

这种 ZIP 不做压缩，但 PNG 本身已经是压缩格式，因此体积损失通常可以接受。

## 为什么没有直接创建下载文件夹

网页运行在浏览器沙盒里。即使是本地 `file://` 页面，也不能默认拥有下载目录的写权限。

浏览器允许网页触发下载，但不允许网页静默选择下载路径、创建文件夹、检查下载目录是否已有同名文件夹，或者按自己的规则写多个文件到那个文件夹。

因此“自动创建文件夹并放入多张图片”在普通网页里不是可靠能力。ZIP 是更符合浏览器权限模型的方案：网页只下载一个文件，文件内部可以有文件夹结构。

如果未来迁移到 Tauri，原生应用可以获得更强的文件系统能力。到那时可以真正实现：

- 选择导出目录
- 自动创建子文件夹
- 重名时追加 `-1`、`-2`
- 直接写入多张 PNG

## 当前限制

当前实现优先保证“能导出”，而不是完全复刻 CSS 排版。

已知限制：

- Canvas 手工绘制的字体、间距和浏览器预览可能略有差异。
- 复杂 inline Markdown 样式在导出图里会被简化为纯文本。
- 外链图片如果被浏览器安全策略阻止读取，会显示占位框。
- 代码块目前按文本行绘制，不做语法高亮。
- 超复杂表格仍可能比较宽，但会被单独导出，避免挤压进普通页面。

## 验证

本轮实现使用了轻量检查：

```powershell
node -e "const fs=require('fs'); const html=fs.readFileSync('md-pew.html','utf8'); const match=html.match(/<script>([\s\S]*)<\/script>/); if(!match) throw new Error('script not found'); new Function(match[1]); console.log('script syntax ok');"
```

结果：

```text
script syntax ok
```

并执行：

```powershell
git diff --check
```

结果无空白错误输出。

浏览器侧验证由用户在 in-app browser 中反馈推动，主要发现并修正了：

- 文件夹选择器在 `file://` 下不可用。
- 外部图片导致 Canvas 安全错误。
- 多张图片散落下载体验不好。

## 后续建议

短期可以继续增强 Canvas 导出质量：

- 支持粗体、斜体、链接等 inline 样式。
- 表格自动重复表头。
- 给导出图片加页码。
- 增加导出尺寸选项，例如 A4、宽屏、长图。

中期可以考虑把导出功能抽成独立模块，便于未来从单文件 HTML 迁移到 Tauri/TypeScript。

长期如果进入桌面应用阶段，可以放弃 ZIP 兜底，改为真正写入用户选择的文件夹，并实现稳定的重名策略。
