## 0. 这篇讲什么

知识库是整套 RAG 的地基。本篇覆盖从"环境就绪"到"召回可用"的完整链路，并把检索背后的原理讲透——理解原理后，你调任何参数都知道自己在干什么，而不是照教程点按钮。

```
环境与插件 → 模型选型 → 分段策略 → 上传文档 → 召回测试与评估
                                          │
                                   背后的检索机制（原理层）
```

## 1. 环境与插件

### 1.1 Dify 运行途径选型

本地 Docker 自部署门槛高，按省心程度排序：

| 途径 | 难度 | 适合 |
|---|---|---|
| **官方云版（dify.ai）** | 0，注册即用 | 学习、demo、面试项目 |
| 云厂商一键部署 | 低，纯 Web 操作 | 要私有部署但不想折腾 Docker |
| GitHub Codespaces | 中 | 短期学习 |
| 本地 Docker | 高 | 真要做"踩坑经历" |

**结论**：学习阶段用云版最划算——省掉 80% 的基础设施麻烦，把精力花在调参和理解原理上。"自部署"在简历上的价值，远低于"你在 RAG 里做了什么实践"。

### 1.2 踩坑 A：PluginNotFound 报错

**现象**：节点（如 DIFY EXTRACTOR）运行 0.04 秒就 FAIL，报 `PluginNotFoundError: plugin not found`，0 token。

**根因**：Dify 1.0 之后把很多内置工具拆成了**插件**，由独立的 `plugin_daemon` 容器管理。工作流 DSL 里只存"插件引用"，不存插件本体——目标环境没装这个插件，节点就报错。

**判断信号**：0.04 秒 + 0 token + PluginNotFound = 根本没开始工作，卡在"找插件"这步。不是模型/网络/配额问题。

**解决**：去 Marketplace 找对应插件安装。注意看作者——`langgenius` 是 Dify 官方组织，它的插件不会下架，可放心装。

> **工程认知**：Dify 1.0+ 的"节点 ≠ 本体功能"。导出/分享的工作流 DSL 只是"引用清单"（类似前端的 package.json），依赖要在目标环境本地解析安装。这叫"声明分发，依赖本地解析"。

### 1.3 踩坑 B：插件安装极慢

**根因**：插件安装含两段网络操作——① 从 marketplace 拉插件包；② `plugin_daemon` 容器内 `pip install` 拉 Python 依赖（默认源 pypi.org，国内/跨境慢）。约 90% 的"卡半天"卡在第②步，超时后报安装失败。**更隐蔽的是**：WebUI 可能显示"已安装"，实际依赖没装好，用起来就报 PluginNotFound（静默失败）。

**解决**（自部署 Docker）：改 `<部署目录>/docker/.env`：

```bash
# 加速 pip（最关键）
PIP_MIRROR_URL=https://pypi.tuna.tsinghua.edu.cn/simple
# 延长超时
PLUGIN_PYTHON_ENV_INIT_TIMEOUT=600
PLUGIN_MAX_EXECUTION_TIMEOUT=600
```

改完**必须** `docker compose down && docker compose up -d`（不是 `restart`，restart 不重载 .env）。

用日志验证真假成功：`docker compose logs -f plugin_daemon | grep -iE "successfully|timeout|error"`。

> **工程认知**：LLM 工具栈（Dify/FastGPT/LangFlow）底层都依赖 pip/npm 装包，配镜像源是部署基本功，跟前端配 npm registry 同理。

### 1.4 踩坑 C：服务 API 入口位置 + 三种 key 区别

**踩坑**：知识库 API 入口不在单个知识库的左侧菜单，而在**知识库列表页右上角的"服务 API"**（新版挪了位置）。

**三种 API key 别搞混**：

| Key 类型 | 在哪拿 | 用途 |
|---|---|---|
| 应用 API | 进入某个应用 → 访问 API | 调用聊天/工作流应用 |
| **知识库 API（服务 API）** | 知识库**列表页**右上角 | **读写知识库**（文档三的图片入库用它） |
| 内部 API | 系统级 | Dify 内部用，不开放 |

知识库 API token 能操作账号下所有可见知识库，**敏感凭证，用完应吊销重建**。

## 2. 模型选型

一套知识库要挂三类模型：Embedding（向量化）、Rerank（精排）、LLM（生成，在应用层用）。

### 2.1 Embedding：选 text-embedding-v4

| 版本 | 架构 | 开源 | 备注 |
|---|---|---|---|
| v1/v2 | GTE 系 | 否 | 早期 |
| v3 | 基于 LLM | 否 | 支持 50+ 语言、8K 长文本 |
| **v4** | **基于 Qwen3** | 见下 | **当前最优，中文友好，默认 1024 维** |

阿里官方 Dify 集成文档现在举例就用 `text-embedding-v4` + `gte-rerank-v2`。

### 2.2 Rerank：选 qwen3-rerank（注意 gte-rerank 下线）

| 模型 | 状态 | 建议 |
|---|---|---|
| `gte-rerank`（v1） | **2026-05-30 下线** | ❌ 别选 |
| `gte-rerank-v2` | 在用 | 备选 |
| `qwen3-rerank` | 阿里钦定接任者，基于 Qwen3 | ✅ 首选 |

> **注意接口差异**：qwen3-rerank 与 gte-rerank-v2 的 API 格式不同，部分框架曾有适配 bug。若 Dify 里调用失败，降级到 gte-rerank-v2（系统模型设置里改下拉框，零成本）。

> **配置坑**：模型供应商页顶部有"系统模型设置"，Rerank 槽位默认是空的，必须手动指定，否则知识库选 Rerank 时找不到选项。

### 2.3 开源生态（重要认知）

阿里 API 背后的模型本质是开源的：
- `Qwen3-Embedding`（0.6B/4B/8B）和 `Qwen3-Reranker` 均开源，Apache 2.0，HuggingFace 可下载、可商用。
- 国内厂商 + 学术机构（阿里、智源 BGE、Jina）基本全开源；OpenAI、Cohere 继续闭源。

| 用法 | 适合 |
|---|---|
| 调阿里 API（v4 / qwen3-rerank） | 学习、量小、不想运维 |
| 自部署（Qwen3-Embedding-8B 等） | 生产、量大、数据敏感、省 API 费 |

> **工程认知**："开源喂养商业"模式——同一模型既开源打口碑，又包装成 API 收费。对你的影响：学习用 API（省心），生产评估自部署（省钱），别被 API 锁定。

### 2.4 为何放弃原生多模态 embedding

- 目标曾是用多模态 embedding 直接把图文映射到同一向量空间。
- **现实**：阿里官方明说 `multimodal-embedding-v1` 不支持在 Dify 当 Embedding 模型用；新一代 `qwen3-vl-embedding` 等尚未被 Dify 通义插件支持，且不支持 OpenAI 兼容接口。
- **结论**：纯阿里方案下，原生多模态走不通，图片改走 Caption-then-Index（详见文档三）。

> **工程认知**：模型发布速度 ≫ 框架适配速度。阿里发新模型后，Dify 插件由社区维护，存在 1-3 个月滞后。这是 LLM 工具链生态的典型痛点。

## 3. 分段策略（Chunking）

### 3.1 `\n## ` 是什么 + 单位陷阱

- `\n## ` = "换行 + 二级标题"，即在每个 Markdown `## 章节` 处切。末尾带空格（`\n## `）严格只匹配二级标题，避免误匹配 `###`。
- **踩坑 G：分段长度单位是 characters（字符），不是 tokens**。中文 1 token ≈ 1.5-2 字符。按 token 给的数值要乘约 2 倍换算。

### 3.2 父子分段：原理与参数

**核心思想**：把"匹配"和"阅读"解耦——同一内容存两个版本，小的（子块）用来被搜到、大的（父块）用来被读懂。

```
文档 → 切大块=父块（一个 ## 章节，完整语义）
        父块内再切小=子块（一个段落，精准匹配）
        建立映射：每个子块知道自己属于哪个父块

存储：只把子块向量化入库
检索：① 匹配子块（精准）→ ② Rerank → ③ 回溯取出对应父块 → 喂给 LLM（完整）
```

**它解决的矛盾**：普通分段里，块切小则匹配准但上下文缺，切大则上下文全但匹配糊。父子分段让子块负责"搜得准"、父块负责"读得懂"，互不妥协。

**推荐参数**（characters）：

| 位置 | 参数 | 值 | 理由 |
|---|---|---|---|
| 父块 | 分段标识符 | `\n## ` | 按二级标题章节切 |
| 父块 | 最大长度 | 3500 | 兜底，章节太长强行切，约 2000 token，LLM 上下文舒适占比 |
| 子块 | 分段标识符 | `\n\n` | 按空行（自然段）切 |
| 子块 | 最大长度 | 1000 | 子块越小匹配越精准，约一个完整段落 |
| 预处理 | 替换连续空白 | 开 | 去冗余提升向量质量 |
| 预处理 | 删 URL/邮箱 | 关 | 学习笔记里链接有价值 |

> **性能警告**：父子分段子块更多，若用本地小模型且算力不足，处理会明显变慢甚至超时。用阿里 API 不受此影响。

### 3.3 父子分段只在入库期配吗

**配置只在入库期**（建库时 UI / API 入库时 `doc_form: hierarchical_model`）。但**检索期它自动生效**——召回子块后自动回溯取父块，你无需配置。召回测试里看到的 `Parent-Chunk-02 → 命中子段落 C-3/C-4`，就是父子分段在检索期的可视化。

> **工程认知**：RAG 很多配置遵循"入库期决定，检索期消费"。embedding 模型也是——入库用哪个，查询必须用同一个，否则向量空间对不上。入库期的每个决定都约束检索期行为，所以入库期要慎重（改参数往往意味着整库重处理）。

### 3.4 踩坑 F：预览分段无显示

**根因**：分段标识符跟 MD 实际标题层级对不上（比如你填 `\n## ` 但文件用的是 `#` 或 `###`）。

**排查**：先把标识符改成 `\n\n`（任何 MD 都有空行）试——能切出来说明文件没问题、是层级不匹配；还空白则可能文件没上传成功。最快办法是直接打开 MD 看实际用几个井号。

> **工程认知**：RAG 项目失败常不是模型问题，而是"没人看原始文档真正长什么样"。成熟做法：先用 grep 看样本文档的标题分布，再定切块策略。

## 4. 检索机制（原理层）

### 4.1 全栈职责链

| 模块 | 时机 | 是什么 | 干什么 | 速度/成本 |
|---|---|---|---|---|
| Chunker | 入库前 | **代码**（非 AI） | 按规则切块 | 极快 / 0 |
| Embedding | 入库+查询 | AI 模型 | 文本→向量 | 快 / 低 |
| 向量数据库 | 查询时 | 数据库 | 算相似度找 Top-N | 极快 / 极低 |
| Rerank | 召回后 | AI 模型 | 候选精排 | 中 / 中 |
| LLM | 最后 | AI 模型 | 生成回答 | 慢 / 高 |

> **关键认知**：RAG 是"非 AI + AI"混合系统。最关键的 Chunker 和向量库都不是 AI，是经典软件工程。真实 RAG 调优时间分配：Chunker 30% + 数据预处理 25% + Query 理解 20% + 模型调参 15% + Prompt 10%——AI 模型本身只占约 25%。这就是 RAG 是工程岗而非算法岗的原因。

### 4.2 Chunker 是代码，不是 AI

切块由字符串处理代码完成（按分隔符切、按长度兜底），没有任何模型推理。推论：
- chunk 质量 100% 取决于你填的参数，换 embedding 模型不改变切块结果。
- 父子分段是 Chunker 层的优化（两次切割 + 父子映射），跟模型无关。
- Chunking 是整个 RAG 里**最可控**的一环（参数全在你手上、输入输出可见），所以调优时间大半花这。

### 4.3 入库期 vs 查询期的不对称

**查询时 Chunker 不工作，问题不切。**

```
入库：1 文档 → 切成 N 子块 → N 个向量
查询：1 问题 → 不切 → 1 个向量 → 去比对子块向量
```

为什么问题不切：① 问题本身就短（< 几百字符，embedding 一次能完美处理），不存在文档那种"太长"问题；② 切问题会破坏语义（"对比 A 和 B 哪个适合 RAG"切碎后丢失"对比意图"）；③ 训练时问题是完整问句，切碎会偏离训练分布、召回崩坏。

> 好的 embedding 模型对问题和文档用不同编码（如 `query:` / `passage:` 前缀），两者本就是不同的东西。

> **工程认知**：RAG 的不对称反映"读多写少，优化在写时做"——类比数据库索引在写入时建好、搜索引擎爬虫预处理建倒排索引。在每次查询时重新切/embedding 是经典反模式（贵 100 倍、慢 1000 倍）。

### 4.4 混合检索 + Bi/Cross-Encoder

- **混合检索**：向量检索（语义）+ 关键词检索（字面）同时跑，任一命中即成功，召回率比纯向量高 15-30%，且对错别字更健壮。
- **Bi-Encoder（向量召回）**：问题和文档分别编码成向量算余弦，快但糙，负责"广撒网"。
- **Cross-Encoder（Rerank）**：问题和候选块拼一起喂模型直接判断相关性，准但慢，负责"精挑"。
- 现代 RAG = Bi-Encoder 粗召回 Top-N + Cross-Encoder 精排 Top-K，兼顾速度、成本、准确。

### 4.5 Embedding 容错（错别字）

| 错误类型 | 能否容错 | 原因 |
|---|---|---|
| 拼写错位（cahce/cache） | ✅ 大概率 | 子词共享 + 整句编码 |
| 形近字 | ✅ 通常 | 训练语料里见过 |
| 漏字/多字 | ⚠️ 部分 | 看剩余信息量 |
| 错成另一真实词（epoch→epic） | ❌ 危险 | 会自信地编码成错词的语义，且无报错 |
| 专有名词错字（transformer→transmorder） | ❌ 大概率废 | 专名向量"锐"，错一点就跳出语义邻域 |

**机制**：① 子词切分——cache 和 cahce 共享子词，向量有相似度；② 上下文消歧——整句 embedding，错一两字符整句"语义指纹"大体还在。

> **工程认知**：Embedding 的容错 ≠ 拼写检查。它不知道对错，只是"觉得位置接近"。所以**不能靠 embedding 纠错，只能靠它宽容**。对错误敏感的应用（医疗、法律）必须在 embedding 前加显式纠错层（Query Rewriting）。

## 5. 召回测试与评估

### 5.1 召回测试方法

入口：知识库 → 召回测试 → 输入问题 → 看右侧召回块 + 相似度分数。

按三类问题系统测：
1. **明确事实型**（验证基础召回）："KV Cache 是什么"
2. **模糊概念型**（验证语义召回）："大模型为什么吃显存"（笔记里可能写"GPU 资源占用"）
3. **跨文档型**（验证全局召回）："Dify 有哪些部署方式"
4. **边界压力测试**："怎么做红烧肉"——好的库应敢返回空/低分，不硬召回凑数。

### 5.2 分数理解：相对排序 > 绝对值（重要）

**新手最大的坑**：把 Score 阈值提到 0.7 想过滤噪声。**这是错的。**

- 不同 embedding 模型分数分布不同——阿里 v4 的"完美匹配"上限约 0.8。把阈值设 0.7 会误杀大量相关内容。
- **要看的是相对梯度，不是绝对值**：Top-1 比 Top-2 高多少（明显的高+平稳下降 = 健康；全平 = 模型分不清；全顶部 = 过拟合）。
- **过滤交给 Rerank，不是阈值**。阈值的正确用途只有一个：让 RAG 敢说"我不知道"（守无关问题的下限）。调试阶段阈值留 0。

| 现象 | 调什么 |
|---|---|
| 块太长信息密度低 | 子块长度调小 |
| 块太碎看不出意思 | 子块长度调大 |
| 同义词召不出 | 启用混合检索 / 调大 Top-K |
| 不相关但分数高 | 启用/换强 Rerank |
| 多文档只命中一个 | 调大 Top-K |

> **mindset 转换**：新手问"多少分算高"，老手问"Top-1 比 Top-N 高多少"；新手"分低就砍"，老手"分低也留，让 Rerank/LLM 决定"；新手"提阈值"，老手"加 Top-K、开 Rerank"。

### 5.3 RAG 评估三层

| 层 | 维度 | 衡量 |
|---|---|---|
| **检索层** | Context Recall | 该召回的召全了吗 |
| | Context Precision | 召回的有多少真相关 |
| | Hit Rate@K | 正确块进 Top-K 了吗（0/1 判断） |
| | MRR | 正确块排名靠前吗（倒数排名平均） |
| **生成层** | Faithfulness ⭐ | 回答忠于上下文吗（防幻觉） |
| | Answer Relevancy | 回答切题吗 |
| | Correctness | 符合事实吗 |
| **工程层** | Latency / Cost / Stability | 快吗 / 贵吗 / 稳吗 |

- **命中率（Hit Rate）测法**：先建 Ground Truth（问题 + 正确来源块），跑召回看正确块是否在 Top-K，命中数/总数。没有 Ground Truth 无从测起。
- **工具**：Ragas（最主流）、TruLens、DeepEval。

> **核心评估理念**：检索层和生成层必须分开归因。一个错误答案可能是"检索的锅"（召回就错）或"生成的锅"（召回对但 LLM 没用好/幻觉）。只看最终答案分不清是哪层。专业做法：先测检索（Recall/Precision），再测生成（给定正确上下文 LLM 答得对不对），两层都好系统才好。

| F | 预览分段无显示 | 标识符与实际标题层级不匹配 | 先用 `\n\n` 排查，看 MD 真实井号数 |
| G | 分段长度不符预期 | 单位是 characters 非 tokens | 数值×约2 换算 |

### 7.2 专业缩写表如何让 embedding 理解（新问题 6 后半）

- **背景**：银行部门内部缩写，开发部门难懂，embedding 时模型可能不明白含义。
