# 多模态图片入库管道（ETL）

> 文档三 / 共三篇
> 主题：在 Dify 用 Workflow 搭建"图片自动转描述并写入知识库"的管道
> 主轴：**管道搭建** + **核心踩坑** + **数据治理** + 路线对比与规模化
> 配套：文档一《知识库构建与检索原理》、文档二《RAG 问答应用搭建》
> 注：模型可用性等为时间敏感信息，以撰写时（2026-05）为准。

---

## 0. 这篇讲什么

知识库底层是文本向量库，**图片不能直接被语义检索**。要让图片里的信息可被搜到，必须先把图变成"可索引的文本"。本篇搭的是一条 **ETL 管道**（Extract 提取 → Transform 转换 → Load 装载）：

```
图片 → [VLM 理解→描述] → [格式化+命名] → [写入知识库 API]
        Extract            Transform        Load
```

这是把"用 RAG"升级到"构建 RAG 的数据供给侧"。本篇也是三篇里踩坑最密集的——很多坑是"看起来成功、实际内容缺失"的静默失败。

## 1. 管道搭建

### 1.1 用 Workflow，不是 Chatflow

图片入库是**批处理任务**，不是对话。用"工作流（Workflow）"，开始节点选"用户输入（原始开始节点）"（不是"触发器"，触发器是后续自动化用）。

### 1.2 视觉模型选型

| 模型 | 代际 | 视觉 | 选择 |
|---|---|---|---|
| `qwen-vl-plus` | Qwen2.5-VL（老） | 有 | — |
| `qwen-vl-max` | Qwen2.5-VL（老） | 有，2.5代最强 | — |
| `qwen3.6-plus` | Qwen3.5-VL（最新） | **文本+视觉一体** | ✅ 本篇用 |

`qwen3.6-plus` 比 `qwen-vl-max/plus` 新一到两代，是"文本+视觉一体"模型，既能聊天又能看图。

> **工程认知**：视觉模型正在"消失"——不是技术倒退，是统一。新一代（Qwen3.5、GPT-5、Gemini）走向原生多模态，一个模型通吃文本/图像/视频。看模型时关注**代际**（Qwen2.5 vs Qwen3.5）比关注**是否带 -vl 后缀**更重要。

### 1.3 管道结构（4 节点）

```
[开始: image] → [LLM: VLM描述] → [代码执行: 解析+命名+生成body] → [HTTP: 写知识库]
```

> 注：早期版本中间还加过"模板转换"节点，后被代码节点取代——代码节点同时干"解析 JSON + 命名 + 包装文本 + 生成请求体"，更简洁。

### 1.4 各节点配置

**① 开始节点**
- 加输入变量 `image`，类型"**单文件**"（先单后批），限定图片格式，必填。
- 注意有个 `userinput.files [LEGACY]` 遗留默认字段，别用它，用自建的 `image`。

**② LLM 节点**
- 模型：`qwen3.6-plus`
- **视觉开关：打开**（命门！不开 LLM 就是瞎子），接入 `开始/image`
- SYSTEM 提示词：让它输出**严格 JSON**（见下），便于代码节点解析
- USER：`请分析这张图片`

LLM 的 SYSTEM 提示词（JSON 输出版）：

```
你是一个专业的图片内容分析专家。请分析这张图片，以严格的 JSON 格式输出，
不要有任何额外文字，不要用 markdown 代码块包裹。
{
  "title": "15字以内、能概括图片主题的标题",
  "doc_type": "图片类型（架构图/流程图/截图/代码/表格/手写笔记/其他）",
  "description": "详细结构化描述：核心内容、关键元素及关系、图中所有文字的完整提取、流程或数据流向说明",
  "keywords": "3-5个检索关键词，逗号分隔"
}
要求：title 有辨识度；description 详尽（检索核心）；第一个字符必须是 {。
```

**③ 代码执行节点**（管道大脑）—— 见第 2.4 节完整代码

**④ HTTP 请求节点**（写库）—— 见第 2.3、2.4 节

## 2. 核心踩坑（本篇精华）

这条管道经历了一连串"看起来成功、实际失败"的坑，每个都值得记。

### 2.1 踩坑 I：代码节点 `arg1` 报错

**现象**：`TypeError: main() got an unexpected keyword argument 'arg1'`

**根因**：代码里写了 `def main(llm_text)`，但 Dify 界面上输入变量名还是默认的 `arg1`，两边对不上。

**规则**：**界面声明的变量名 = 代码里的参数名**，一字不差。输出变量同理（代码 `return {"doc_name":..., "doc_text":...}`，界面就要声明 `doc_name`、`doc_text`）。

### 2.2 踩坑 J：入库只有 11 字符（静默失败）

**现象**：HTTP 返回成功、知识库多了文档，但**字符数只有 11**（应该几千）。

**根因**：HTTP Body 的 `text` 字段填的是占位文本 `"占位文本稍后替换成变量"`（约 11 字），**没换成真变量** `代码执行/doc_text`。API 忠实地把占位符写进了库。

**修复**：text 字段清空，用 `/` 插入变量胶囊 `代码执行/doc_text`。

> **工程认知（最重要的一条）**：**API 返回 200 成功 ≠ 业务逻辑正确**。从 API 角度这次调用完全成功（参数合法、文档创建），但存进去的是垃圾。这种"技术成功、业务失败"的**静默失败**最难发现，因为没有任何报错。能抓到它，全靠做了**召回验证**——如果当时直接相信"入库成功"就批量跑 20 张，会得到 20 条废文档。这就是"先单张验证再批量"的价值。

### 2.3 踩坑 K：doc_form 400

**现象**：`400 doc_form is different from the dataset doc_form`

**根因**：知识库用的是父子分段（doc_form = `hierarchical_model`），但 API 请求里写的是 `process_rule: {mode: automatic}`（对应普通分段），两者不匹配，知识库拒绝。

**修复**：Body 里显式声明父子分段：

```json
"doc_form": "hierarchical_model",
"process_rule": {
    "mode": "hierarchical",
    "rules": {
        "pre_processing_rules": [
            {"id": "remove_extra_spaces", "enabled": true},
            {"id": "remove_urls_emails", "enabled": false}
        ],
        "segmentation": {"separator": "\n## ", "max_tokens": 3500},
        "parent_mode": "paragraph",
        "subchunk_segmentation": {"separator": "\n\n", "max_tokens": 1000}
    }
}
```

> 参数要跟建库时一致（呼应文档一"入库期决定，检索期消费"）。响应头 `x-version: 1.14.2` 能看到 Dify 版本——遇 API 报错先看版本号，再查对应版本文档。最稳是去知识库"服务 API"面板抄你这个版本的确切示例。

### 2.4 踩坑 L：JSON 被换行/特殊字符破坏 400（最关键的解法）

**现象**：`400 The browser (or proxy) sent a request that this server could not understand.`

**根因**：这次不是参数问题，是 **JSON 本身坏了**。`doc_text` 里全是换行符 `\n`、`#`、`*`、中文引号。当这段文本被塞进 HTTP Body 的 `"text": "..."` 时，如果转义没做好，换行和特殊字符会撑破 JSON 结构，服务器收到非法 JSON，直接 400。

**失败的做法**：在 HTTP Body 里手拼 JSON + 手插变量——Dify 的变量插值对含换行的长文本转义不可靠。

**根治方案（方案 B）**：**把整个 JSON 交给代码节点用 `json.dumps` 生成**，HTTP 只发一个变量。

代码节点完整版（解析 + 命名 + json.dumps 生成 body）：

**输入变量（2 个）**：

| 变量名 | 接 | 说明 |
|---|---|---|
| `llm_text` | `LLM/text` | VLM 的描述输出（JSON 字符串） |
| `file_name` | `开始/image` 的文件名属性 | 用于命名锚点；由前置脚本保证已清洗（见 3.3） |

> 若 Dify 版本下文件变量取不到文件名子属性，可在**开始节点**额外加一个"文件名"文本输入字段，由用户上传时手动填，再接到代码节点。两种方式效果一致。

```python
import json
from datetime import datetime

def main(llm_text: str, file_name: str) -> dict:
    # 假设前置脚本已清洗文件名为安全字符，这里只去扩展名
    safe_name = file_name.rsplit(".", 1)[0] if "." in file_name else file_name

    # 解析 LLM 的 JSON（含去 markdown 包裹 + 容错兜底）
    cleaned = llm_text.strip()
    if cleaned.startswith("```"):
        cleaned = cleaned.split("```")[1]
        if cleaned.startswith("json"):
            cleaned = cleaned[4:]
        cleaned = cleaned.strip()
    try:
        data = json.loads(cleaned)
    except Exception:
        data = {"title": "未命名", "description": llm_text, "keywords": "", "doc_type": "未知"}

    title = data.get("title", "未命名")
    timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    doc_name = f"图片__{safe_name}__{title}__{timestamp}"  # 种类前缀写死"图片"

    full_text = f"""# {title}

**文件种类**: 图片
**原图文件**: {file_name}
**类型**: {data.get('doc_type','未知')}
**关键词**: {data.get('keywords','')}

## 详细内容

{data.get('description','')}"""

    # 关键：用 json.dumps 生成转义正确的完整 body
    body_payload = {
        "name": doc_name,
        "text": full_text,
        "indexing_technique": "high_quality",
        "doc_form": "hierarchical_model",
        "process_rule": {
            "mode": "hierarchical",
            "rules": {
                "pre_processing_rules": [
                    {"id": "remove_extra_spaces", "enabled": True},
                    {"id": "remove_urls_emails", "enabled": False}
                ],
                "segmentation": {"separator": "\n## ", "max_tokens": 3500},
                "parent_mode": "paragraph",
                "subchunk_segmentation": {"separator": "\n\n", "max_tokens": 1000}
            }
        }
    }
    body_json = json.dumps(body_payload, ensure_ascii=False)

    return {"doc_name": doc_name, "doc_text": full_text, "body_json": body_json}
```

输出变量声明三个：`doc_name`、`doc_text`、`body_json`（均 String）。

HTTP 节点改为：
- Body 类型 **raw / text**，内容**只填一个胶囊** `{{#代码执行.body_json#}}`
- Headers 保留 `Authorization: Bearer <知识库key>` 和 `Content-Type: application/json`

> **工程认知**：识别出工具的能力边界，用更可靠的方式绕过它。Dify 拼 JSON 不可靠 → 把 JSON 序列化交给 Python 标准库 `json.dumps`（转义的黄金标准），Dify 只当"传话筒"原样发送。这种判断力是高级工程师的标志。

### 2.5 踩坑结果：验证通过

修完后单张入库：文档名 `图片__test_image__阿里云通义千问大模型家族全景图__时间戳`，**字符数 1.4k**（不再是 11），分段模式"父子"。管道真正产出有效数据。

## 3. 数据治理

### 3.1 命名演进（一路被推着改）

```
写死 "图片描述-xxx"        → 批量会重名/无法溯源 ❌
纯 workflow_run_id        → 唯一但一串乱码，无法管理 ❌
LLM标题 + 时间戳           → 可读 + 唯一 ✓
文件种类__文件名__标题__时间戳 → 最终版，加种类前缀为未来扩展留位 ✓✓
```

最终格式：`图片__{文件名}__{LLM标题}__{时间戳}`，各段职责：

| 段 | 作用 | 解决 |
|---|---|---|
| `图片`（种类，写死） | 可扩展（未来有"文档__""音频__"） | 类型区分 |
| 文件名 | **可追溯**（删图时按它搜） | 数据血缘 |
| LLM标题 | **可读**（列表一眼认出） | 管理性 |
| 时间戳 | 唯一/版本 | 防重复 |

### 3.2 数据血缘（删图后怎么同步）

**关键洞察**：时间戳破坏了可追溯性——它是"生成时才有"的，无法从图片反推。所以光有时间戳，哪天想删某张图对应的知识点，找不到它。

**解法**：必须有一个"从图片能反推出来的稳定锚点"——**原图文件名**（或图片内容哈希）。文档名里带文件名，删图时按文件名搜知识库即可找到所有相关文档。

> **工程认知**：这是数据工程的"数据血缘（Data Lineage）"问题。任何"从源派生新数据"的系统都要解决：源变了/删了，派生数据怎么同步？标准答案三件事：① 稳定的源标识（不能用时间戳这种非确定性的做关联）；② 显式记录血缘（元数据/映射表）；③ 同步机制。大公司有专门的血缘系统（Apache Atlas、DataHub）。

> **诚实边界**：Dify 不会自动"删图→删文档"。要实现自动同步需另建一个删除管道（输入文件名→列表API找→删除API删），这是独立子项目，本次未做。

### 3.3 文件名清洗（职责分离）

**问题**：文件名含 `"` `\` 换行、空格、中文标点等会破坏 JSON 或文档名合法性（如 `图片1：RAG架构(最终版).PNG`）。

**决策**：清洗**不在 Dify 里做**，下放到本地**前置脚本**。

> **工程认知**：好的系统设计是"在正确的层做正确的事"——文件系统操作交给脚本，Dify 专注多模态理解和编排。这就是"职责分离"。真实数据系统都是多个专职组件的流水线（清洗→ETL脚本、编排→工作流、推理→模型服务、检索→向量库），每层解耦、单独可测可换。

前置脚本思路（本地 Python）：

```python
import os, re
def sanitize(filename):
    name, ext = os.path.splitext(filename)
    safe = re.sub(r'[^\w\u4e00-\u9fa5\-]', '_', name)  # 只留中文/字母/数字/_/-
    safe = re.sub(r'_+', '_', safe).strip('_')[:30]
    return (safe or "image") + ext.lower()
# 批量重命名为 001_xxx.png ... 并生成"原名→新名"映射表（映射表本身即血缘记录）
```

## 4. 技术路线对比

### 4.1 业界三条多模态路线

| 路线 | 怎么处理图 | 信息损失 | OCR依赖 | 复杂版面 | 成熟度 |
|---|---|---|---|---|---|
| **Caption-then-Index**（本篇走的） | VLM 转文字描述 | 大（降维） | 不需要 | 一般 | ⭐⭐⭐⭐⭐ |
| CLIP 联合嵌入 | 图文同向量空间 | 中 | — | 一般 | ⭐⭐⭐ |
| **ColPali** 纯视觉 | 整页当图，不转文字 | **几乎无** | **完全不需要** | **完美** | ⭐⭐ 新 |

- **Caption（本篇）**：VLM 生成描述→描述入库→文本检索。最成熟，普通文本向量库就能用，缺点是"图→文字"的降维损失。
- **ColPali**（2024底新范式）：把整个 PDF 页当图片，用视觉模型直接编码，Late Interaction（MaxSim）检索，VLM 看图回答。绕过 OCR/解析/caption，信息损失最小，但工程复杂、Dify 原生不支持，需自己写代码（colpali-engine + Qwen-VL）。

> **工程认知**：多模态 RAG 的演进史就是"减少信息损失"史——每代新方案砍掉一个有损的中间转换步骤。Caption 引入"图→文字"有损转换；ColPali 砍掉全部中间步骤直接"图→向量→VLM看图答"。每个中间转换都是信息泄漏点。

### 4.2 召回验证与发现的盲区

实测召回（用图片专属信息提问）：

| 问题 | 召回 | 说明 |
|---|---|---|
| 阿里有哪些 NEW 模型 | ✅ 0.91 | 图片描述精准命中，三子段全中 |
| Qwen3-Coder 是什么 | ✅ 0.64 | **只在图里有**，证明图片管道扩展了覆盖范围 |
| 万相是什么模型 | ❌ 未召回 | **盲区** |

**万相召回失败的根因**：图片本身以千问为主、万相只是被顺带提名（"基础模型（千问、万相）"），没展开。LLM 如实描述→万相在描述里信号弱→召回不到。

> **工程认知**：召回质量 = 原始内容质量 × 描述质量 × 检索质量。万相失败是**源头**的锅，不是检索的锅。这正是"离线诊断工作流"要系统性发现的盲区。改善方向：改 prompt 让描述对每个名词都简要说明（最低成本）/ 补文字笔记 / 多图覆盖。

## 5. 性能与工程优化

### 5.1 LLM 参数（针对图片描述任务）

图片描述是"提取/描述"类任务——要**准确、稳定**，不要创意。

| 参数 | 默认/初始 | 建议 | 理由 |
|---|---|---|---|
| 温度 Temperature | 0.7 | **0.1-0.3** | 要稳定准确，不要发挥 |
| Top P | — | 不动/默认 | 温度和 Top P 只调一个 |
| 随机种子 Seed | — | **固定** | 可复现，便于调试 |
| 思考模式 Thinking | — | **关** | 描述不需推理，省时间（你那 52s 延迟部分是它） |
| 回复格式 | — | **JSON**（如有） | 保证合法 JSON，可省代码里的清洗兜底 |
| Max Tokens | 8192 | 2000-4000 | 描述用不了那么长，省钱 |
| 重复惩罚 | 1.1 | 保持 | 轻度抑制重复，合理 |

> **⚠️ 开关默认关闭**：每个参数左边有开关，关着 = 用模型默认值。要调某参数先打开开关再设值。

> **工程认知**：参数无"最好值"，只有"适合任务的值"。提取/分类/描述类→低温+固定种子+结构化输出（求稳定可复现）；创意类→高温（求多样）；推理类→开思考。先保证"做对"，再追求"做快"。

### 5.2 flash + 精简 prompt（性价比优化）

- 模型 `qwen3.6-plus`（plus级，强但慢52s）→ 可换 `qwen3-vl-flash`（速度优先，快数倍、便宜得多）。
- prompt 从"详细描述"改成"200字以内核心描述"，输出短、快、省。
- **权衡**：召回分数可能从 0.91 降到 0.8 左右——够用但不如现在精。"更快"和"更好"有冲突，是"在可接受质量下尽量快"。
- 建议用 A/B 实验验证：同一张图测 plus+长prompt vs flash+短prompt 的召回分数对比。

> **工程认知**："杀鸡用牛刀"的解法不是"换小刀"，而是"先看清要杀的是不是鸡"。最初想用 OCR 替代 VLM 是错的——OCR 只读文字，读不懂图表的版面布局（你那张气泡图的位置语义 OCR 抓不到）。正确优化是：先定义任务真实需求，在满足需求的工具里选最轻的（VLM 里选 flash，而非降级到 OCR），再砍冗余（精简 prompt）。

## 6. 规模化（20 张 vs 2000 张）

### 6.1 规模改变架构

| | 20 张 | 2000 张 |
|---|---|---|
| 核心矛盾 | 单张质量（VLM vs OCR） | **吞吐量（并行）** |
| 串行耗时 | 可接受 | 52s×2000 = **28.9 小时** ❌ |
| 工具 | Dify 工作流 | **独立 Python 批处理脚本** |
| 新增问题 | 无 | 限流、断点续传、幂等、失败重试 |

### 6.2 2000 张的解决方案体系

- **并行**：串行→并发（asyncio/线程池），并行度 20 可把 28.9 小时压到约 1.4 小时（数量级提升）。
- **限流墙**：阿里 API 有 QPS/并发上限，超了报 429。要按配额设并行度 + 重试退避 + 申请提额。
- **flash + 短 prompt**：对 2000 张从"锦上添花"变"必须"。
- **分类路由（规模反转）**：20 张时不划算，2000 张时纯文字图走 OCR、图表走 VLM 能省 16+ 小时——搭分类逻辑是固定成本，收益随数量线性增长。
- **断点续传/幂等/失败队列**：跑几小时必出意外，不能从头再来。用文件名锚点判断是否已处理（去重），失败的单独记录重试。

### 6.3 该不该继续用 Dify

到几千张量级，**Dify 不一定最佳**：

| 规模 | 推荐工具 |
|---|---|
| 几十张 | Dify 工作流 |
| 几百张 | Dify 迭代节点（勉强） |
| 几千张+ | **独立 Python 批处理脚本** |

大批量 ETL 是脚本主场，Dify 擅长编排和单次交互。这又回到"职责分离"。

> **工程认知**：规模是架构的第一性变量——同一问题不同规模是完全不同的问题。20 张核心矛盾是"单张质量"，2000 张是"吞吐量"，最优解几乎没有共同点。资深工程师听需求先问"规模多大"，因为规模直接决定架构。扩展路径：串行单机（百级）→ 并发+限流（千级）→ 分布式任务队列 Celery（万级+）。

### 8.1 换 qwen3-vl-flash 报"无 user 角色"400（新问题 9）⚠️初步诊断未验证

- **报错**：`400 InvalidParameter: The input messages do not contain elements with the role of user`
- **初步诊断**：flash 模型比 qwen3.6-plus 更严格，要求请求里**必须有 user 角色的消息**。可能是 LLM 节点只有 SYSTEM 提示词、USER 框为空，或图片未作为 user 消息正确附加。
- **初步方向**：确保 USER 提示词框有内容（如"请分析这张图片"）、且图片接在 user 消息上。
- **状态**：未在对话中验证，需实测。

### 8.2 多模态 embedding 能否直接识图建库（新问题 1）

- 概念已在 4.1 三路线（CLIP/ColPali）讨论。具体到"阿里多模态 embedding 直接识图"：文档一 2.4 已说明阿里 Dify 插件当前不支持。若要走，需换 Jina-CLIP 等供应商或自建。
- **待验证**：换供应商后的 Dify 配置、与 Caption 路线的召回对比。

### 8.3 图片压缩加速 + 筛选（新问题 2）

- **设想**：压缩图片加快 VLM 处理；脚本批量压缩；筛选出需压缩的图。
- **待验证**：压缩对 VLM 速度的实际影响（VLM 内部会 resize，压缩收益可能有限）、压缩对识别精度的影响、按什么阈值（分辨率/文件大小）筛选。
- 注意：文档"保留图像分辨率"——过度压缩会降低 VLM 识别能力，需权衡。

### 8.4 缩写表在 caption 前注入（新问题 6 前半）

- **设想**：银行专业缩写，VLM 描述图片时可能不懂，先给一份对照表参考。
- **初步方向**：在 LLM 节点的 SYSTEM 提示词里附上缩写对照表，让 VLM 描述时按表展开。
- **待验证**：对照表多大合适（太长占 token）、注入 caption 阶段 vs embedding 阶段哪个更有效。
- 关联：文档一 7.2（embedding 侧的同一需求）。

### 8.5 逻辑判断：代码 vs Dify 判断节点（新问题 7）

- **设想**：判断逻辑交给代码节点是否比 Dify 条件分支节点更快、调试更顺手（本地测试数据）。
- **待验证**：两者性能对比、可维护性对比、什么场景该用哪个。
- 关联：分类路由（5.2 提及的方案 3）正需要这类判断。

### 8.6 多部门是否要建多个图片管道（新问题 3 后半）

- **背景**：多部门数据/名词易打架，可能每部门一个知识库。
- **疑问**：是否意味着要建很多个图片管道？
- **初步方向**：管道逻辑相同，可复用同一管道，只改"写入哪个知识库"的参数（dataset_id 做成可变）；不必每部门复制一条管道。
- **待验证**：如何参数化 dataset_id、能否一条管道按部门路由到不同库。
- 关联：文档二 7.1（应用侧挂多库）。
