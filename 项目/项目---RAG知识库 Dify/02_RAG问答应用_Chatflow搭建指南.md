# RAG 问答应用搭建指南（Chatflow）

> 文档二 / 共三篇
> 主题：在 Dify 用 Chatflow 搭建一个挂载知识库的 RAG 问答应用
> 主轴：**每个节点的配置细节** + 流程步骤 + 实战踩坑
> 配套：文档一《知识库构建与检索原理》、文档三《多模态图片入库管道》

---

## 0. 这篇讲什么

一个能用的 RAG 问答应用，本质是给知识库装一张"嘴"。知识库本身只能做召回测试（看"找到了什么"），要能**对话**，必须搭一条应用链路。

本篇目标链路（4 个节点）：

```
[开始] → [知识检索] → [LLM] → [直接回复]
  ↑          ↑          ↑          ↑
用户问题   召回知识库   生成回答   返回用户
```

看似简单，但每个节点的**变量怎么接、参数怎么配**，决定了它能不能真正工作——本篇大量篇幅在这上面。

---

## 1. 前置：为什么用 Chatflow，而不是"聊天助手"

Dify 创建应用时有多种类型，新版界面把基础类型**藏起来了**。

| 类型 | 特点 | 是否选 |
|---|---|---|
| 聊天助手（Chatbot） | 表单式配置，链路写死，最简单 | 藏在"新手适用"展开里 |
| **Chatflow** | 可视化节点编排，链路可见可改 | ✅ 本篇选它 |
| 工作流（Workflow） | 非对话的批处理 | 文档三用 |
| Agent | 能调工具的代理 | 暂不需要 |

**踩坑 D：创建应用时只看到"工作流"和"Chatflow"两个选项**——其他基础类型（聊天助手、Agent、文本生成器）被折叠进了左下角的"**新手适用**"展开项里。

**为什么本篇选 Chatflow 而非更简单的聊天助手：**
- 数据流**显式画在画布上**，每个步骤是独立节点，可调试、可扩展
- 后续要加 Query Rewriting、问题分类等进阶逻辑，直接拖节点即可，聊天助手做不到
- 节点级的输入/输出都可见，排错时能精确定位是哪一步出问题

**核心认知**：聊天助手是"黑盒"（你只能填参数），Chatflow 是"白盒"（链路摊开给你看）。

---

## 2. 节点配置详解

### 2.1 开始节点

Chatflow 创建后会预置 `[开始] → [LLM] → [直接回复]` 三个节点。开始节点承载用户输入。

| 配置项 | 说明 |
|---|---|
| 内置变量 | `sys.query` = 用户当前输入的问题（自动存在，无需手动建） |

开始节点通常不用额外配置——用户的提问自动进 `sys.query`。

---

### 2.2 知识检索节点（在开始和 LLM 之间插入）

**操作**：鼠标移到 `[开始]` 和 `[LLM]` 之间的连线上 → 出现 `+` → 选"知识检索"。插入后链路变成 `开始 → 知识检索 → LLM → 直接回复`。

**配置项：**

| 字段 | 填什么 | 说明 |
|---|---|---|
| 查询变量 | `sys.query` | 用用户的提问去检索 |
| 知识库 | 点 `+` 选你的知识库 | 可挂一个或多个（见第 5 节） |
| 召回设置 | 见下表 | 点设置图标进入 |

**召回设置（关键参数）：**

| 参数 | 推荐值 | 理由 |
|---|---|---|
| 召回方式 | **多路召回（混合检索）** | 向量+关键词同时搜，召回率比单纯向量高 15-30% |
| Top K | **8** | 召回阶段宁多勿漏，给 Rerank 留足候选 |
| Rerank 模型 | `qwen3-rerank` | 精排，把召回结果重新排序 |
| Rerank 后取 | **5** | 最终喂给 LLM 的数量 |
| Score 阈值 | **不开（0）** | 调试阶段不要在召回阶段过滤，让 Rerank 决定相关性 |

> **关于 Score 阈值为什么不开**（详见文档一）：阿里 embedding 的"完美匹配"分数上限约 0.8-0.9，把阈值提到 0.7 会误杀大量相关内容。正确做法是召回阶段"广撒网"、靠 Rerank 精排，而不是用绝对分数硬卡。看**相对排序**而非**绝对值**。

**知识检索节点的输出**：一个变量 `result`，类型是 `Array[Object]`——即"召回的块"组成的数组，每个块含 content、score、来源文档名等字段。下游 LLM 节点要接的就是这个 `result`。

---

### 2.3 LLM 节点（最关键，也最容易出 bug）

LLM 节点要配 4 样东西，**漏一样整条链路就废**。

#### ① 模型

下拉选 `deepseek-chat`（或你已配好的其他对话模型）。
- 不选 `deepseek-reasoner`：推理模型每次思考很久、贵，日常 RAG 问答用 chat 即可。

#### ② 上下文变量 ⭐ 最易翻车

LLM 节点有一个"**上下文**"字段，必须接 **`知识检索 / result`**。

**踩坑 H：应用回答"我的知识库里没有这方面的内容"，但召回测试明明能召回。**

- **根因**：上下文变量接错了——接成了一个名叫"上下文"的**会话变量**（默认空），而不是 `知识检索 / result`。
- **现象**：LLM 拿到的上下文是空的，于是严格按 prompt 规则回答"知识库里没有"。
- **修复**：删掉错误变量，重新插入 `知识检索 / result`。注意变量胶囊上会标明**来源节点**——正确的应显示带"知识检索"图标，错误的只显示"上下文"无来源。

> **识别变量对错的方法**：看胶囊的**来源节点名**，不要看显示名字。名字相似的变量（"上下文"会话变量 vs "知识检索/result"）极易混淆。

> **意外收获**：这次能快速定位，是因为 prompt 里写了"没召回到就说没有"。如果没有这条反幻觉规则，LLM 会用自己的训练知识硬编一个答案，你**根本看不出 RAG 没在工作**——这叫"静默失败"。好的 prompt 把沉默的 bug 变成了喧哗的 bug。

#### ③ 系统提示词（SYSTEM）

完整模板（含三层质量评估，详见第 4 节）：

```
# 角色
你是用户的"AI 学习助手"，基于用户的个人学习笔记回答问题。

# 知识库使用规则
## 基本原则
1. 你的回答必须优先基于"上下文"提供的内容。
2. 不要使用通用知识冒充笔记内容。如果知识库没有，就明说没有。

## 三层质量评估（先评估，再回答）
【1】相关性评估
- 高度相关：直接组织答案，不加额外提示
- 部分相关：正常回答 + 末尾加"⚠️ 提示：知识库只覆盖了问题的一部分（缺少 XXX）"
- 几乎不相关：不要硬答，直接说"我的知识库里没有这方面的内容"

【2】信息完整性
够用就答；只能部分回答就指出"上下文里说了 X，但 Y 部分没提到"。

【3】冲突检测
不同片段矛盾时，诚实指出两种说法及来源，不替用户做选择。

# 输出风格
- 中文回答，结构清晰，必要时用 ## 标题、列表
- 简短问题简短回答
- 代码用代码块格式
- 关键论点后用 [来源N] 引用

# 上下文
{{#context#}}
```

**关于 `{{#context#}}`**：这是把召回内容塞进提示词的占位符变量。
- 必须用 `/` 触发变量菜单插入，让它变成**高亮胶囊**。
- **不能手敲** `{{#context#}}` 文字——手敲是普通字符串，LLM 看到的就是字面这几个字符，召回内容不会被填进去。

#### ④ 用户提示词（USER）

填 `{{#sys.query#}}`（同样用 `/` 插入变量，不要手敲）。

---

### 2.4 直接回复节点

- 回复内容：用 `/` 插入 `LLM / text`，显示为 `{{#LLM.text#}}`。
- **踩坑 E：找不到"结束"节点**——新版 Dify 把它改名叫"**输出**"，且变为**可选**。Chatflow 末节点用"直接回复"，Workflow 才用"输出"。

---

## 3. 变量传递机制（贯穿全篇的核心）

Chatflow 的本质是**数据在节点间流动**，连线只是"路"，真正传数据靠**变量**。

```
[开始] sys.query
   │
   ▼
[知识检索] 查询=sys.query → 输出 result (Array[Object])
   │
   ▼
[LLM] 上下文=知识检索.result, 系统提示词含{{#context#}}, 用户={{#sys.query#}}
   │   → 输出 text
   ▼
[直接回复] {{#LLM.text#}}
```

**两条铁律：**
1. **每个节点的输入变量，必须"接"上游节点的输出**——连了线但没接变量，等于路通了但货没装上车。
2. **变量必须是胶囊，不能手敲**——手敲是字符串，不会被替换成实际值。

> 文档三里"代码节点 arg1 报错"和本篇"上下文接错"，本质是同一类问题：**变量名/变量来源对不上**。这是 Dify 编排最高频的翻车点。

## 4. Prompt 工程：三层质量评估 + 反幻觉

普通 RAG 的 prompt 只让 LLM"基于上下文回答"。本篇的增强版让 LLM **先自我评估召回质量，再回答**。

**三层评估：**

| 层 | 解决什么 | 表现 |
|---|---|---|
| 相关性 | 召回内容跟问题有多相关 | 高度相关直接答；部分相关加 ⚠️；不相关说"没有" |
| 完整性 | 上下文够不够回答 | 不完整时指出缺哪部分 |
| 冲突检测 | 多个片段是否矛盾 | 诚实列出两种说法及来源 |

**代价**：多消耗约 20-30% token。但换来回答可信度的飞跃——RAG 最大的失败模式是"自信地说错话"，这套规则直接堵住这个口子。

**反幻觉验证（必做）：**

| 测试问题 | 验证什么 | 期望 |
|---|---|---|
| KV Cache 是什么？ | 高度相关路径 | 直接答，无 ⚠️ |
| KV Cache 在分布式推理的问题？ | 部分相关路径 | 答 + ⚠️ 提示缺失 |
| **怎么炒土豆丝？** | **反幻觉底线** | **明确说"知识库里没有"** |

> "炒土豆丝"测试是整套 RAG 的生死线——如果 LLM 给了菜谱，说明反幻觉规则被穿透。实测：即使知识检索节点仍召回了 2 个低相关块（因没开 Score 阈值），LLM 也正确判断不相关并拒答。这正是"召回层广撒网 + LLM 层把关"分层协作的体现。

**运行时反思 vs 离线诊断（概念区分）：**
- **运行时反思**（本节做的）：每次提问时 LLM 自评召回质量，结果给用户。对应学术概念 Self-RAG / CRAG。
- **离线诊断**（文档一/独立项目）：周期性批量评估整个知识库覆盖度。对应 Ragas 等工具。
- 两者必须分开——运行时反思只给用户必要提示，不能把"元信息"噪声全暴露给用户。

## 5. 测试与发布

**测试时必看"引用展开"**：开启"引用和归属"功能后，每个回答下方显示召回了哪些块。
- 引用块跟回答内容对得上 → 真在用知识库
- 引用块跟回答不相关 → LLM 在自由发挥（幻觉风险）
- 无引用的论点 → 警惕幻觉

**建议开启的功能**：引用和归属（必开）、下一步问题建议、开场白。

**发布**：画布右上角"发布"→"更新发布"。发布后获得：公开聊天链接、API 接入点、网页嵌入代码。

## 6. 本篇踩坑总表

| 编号 | 现象 | 根因 | 解决 |
|---|---|---|---|
| D | 应用类型选项比预期少 | 基础类型折叠在"新手适用" | 展开"新手适用" |
| E | 找不到"结束"节点 | 新版改名"输出"且可选 | Chatflow 用"直接回复" |
| H | 回答"知识库里没有"但能召回 | 上下文变量接错（接成空的会话变量） | 重接 `知识检索/result` |
| — | `{{#context#}}` 不生效 | 手敲成字符串而非变量胶囊 | 用 `/` 插入胶囊 |

## 7. 本篇涉及但尚未展开的问题（待深入）

> 以下三个问题列在本篇范围内，但**截至目前尚未实操/深入讨论**，仅给初步方向，需后续专门展开。**请勿当作已验证内容整理。**

### 7.1 多部门多知识库防串台（新问题 3 前半）

- **背景顾虑**：不同部门数据/名词易"打架"，通用单库可能串台。
- **初步方向**：Dify 的"知识检索"节点支持**挂载多个知识库**；可以每部门建一个库，应用同时挂多个。
- **待验证**：多库召回时如何避免跨库混淆、是否需要按部门做查询路由、召回权重如何分配。
- 关联：文档三会讨论"是否要建多个图片管道"（这是同一想法的 ETL 侧）。

### 7.2 LLM 回答附带文件链接/出处（新问题 4）

- **需求**：回答时把来源文件链接一并给用户。
- **初步方向**：知识检索的 `result` 里含来源文档信息；结合文档元数据（metadata）可在 prompt 里要求 LLM 输出来源；若要可点击链接，需图片/文件托管到有公网 URL 的位置。
- **待验证**：具体在 Chatflow 里如何取出来源字段、如何稳定地让 LLM 输出正确链接、引用编号如何固定（目前是临时编号，每次会变）。

### 7.3 交付给同事使用 + 知识库权限（新问题 8）

- **需求**：搭好的应用/知识库如何给同事用？知识库是否只能本人访问？
- **初步方向**：涉及 Dify 的工作空间（Workspace）、团队成员、应用发布与访问控制。
- **⚠️ 重要**：这块涉及 Dify **当前版本的产品功能**（团队版/权限/共享），各版本差异大，**需在你的实际 Dify 版本里查证**，不要照搬旧资料。
