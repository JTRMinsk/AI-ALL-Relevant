# 企业金融知识问答系统建设方案

> 基于 Dify + 本地化部署的金融行业知识库 RAG 应用实践

---

## 一、项目背景

### 1.1 业务痛点

金融行业的内部知识资产庞大且高度异构：业务规章制度、产品说明书、风控合规手册、客户经理培训资料、监管法规更新等动辄数百份文档，分散在不同部门和系统中。员工日常工作中频繁遇到以下问题：

1. **检索效率低**：关键信息往往埋藏在长达数十页的 PDF 制度文件中，关键词搜索难以命中
2. **专业术语门槛高**：新员工面对"久期"、"风险加权资产"、"巴塞尔协议 III"等术语难以快速理解
3. **政策更新滞后**：监管要求频繁变化，纸质资料无法跟上时效性
4. **跨部门知识壁垒**：合规、产品、风控之间的知识难以打通共享

### 1.2 项目目标

搭建一套面向金融业务团队的**智能知识问答系统**，实现：

- 自然语言提问，秒级返回精准答案
- 答案附带原文出处，支持溯源验证
- 完全本地化部署，敏感数据不出内网
- 灵活扩展，支持新增文档自动入库

### 1.3 适用场景

| 用户角色 | 典型场景 |
|---|---|
| 客户经理 | 查询产品准入条件、计算公式、案例参考 |
| 风控人员 | 检索风控指标解释、合规要求、监管处罚案例 |
| 新员工 | 业务术语理解、操作流程查询 |
| 合规审计 | 制度比对、监管口径核实 |

## 二、技术架构

### 2.1 整体架构

系统采用经典的 RAG（Retrieval-Augmented Generation，检索增强生成）架构，分为四个层次：

```
┌─────────────────────────────────────────────────┐
│           应用层（Dify 工作流编排）             │
│   用户提问 → 意图识别 → 检索调用 → 答案生成     │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────┐
│              检索层（混合检索 + Rerank）        │
│   向量检索 + 关键词检索 → 重排序 → Top K       │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────┐
│            知识库层（向量数据库）               │
│   父块（语义单元）+ 子块（精确索引）            │
└────────────────────┬────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────┐
│        数据处理层（文档解析 + 切分 + 向量化）   │
│   PDF/Word/Markdown → Chunks → Embedding       │
└─────────────────────────────────────────────────┘
```

### 2.2 部署环境

| 项 | 配置 |
|---|---|
| 操作系统 | Ubuntu Server LTS（Unix 虚拟机）|
| 容器化 | Docker + Docker Compose |
| 编排平台 | Dify v1.9.0+（开源 LLM 应用开发平台）|
| 推理服务 | LM Studio（本地模型服务）|
| 网络隔离 | 完全内网部署，无外网依赖 |

### 2.3 技术选型清单

| 组件           | 选型                    | 说明                   |
| ------------ | --------------------- | -------------------- |
| 应用编排         | Dify                  | 可视化工作流、知识库管理一体化      |
| Embedding 模型 | Qwen3-VL-Embedding-8B | 中文/多模态，MTEB 多语言榜 Top |
| Rerank 模型    | Qwen3-Reranker-4B     | 与 Embedding 同源，精排效果好 |
| 生成模型         | 双轨制（详见第四章）            | 线上+线下两条路径            |
| 向量数据库        | Weaviate（Dify 默认）     | 支持混合检索，运维成熟          |

## 三、知识库搭建流程

### 3.1 文档预处理

**支持的文档类型**：

| 格式 | 处理方式 |
|---|---|
| PDF | 文字提取 + 表格识别 |
| Word | 直接解析正文与表格 |
| Markdown | 原生支持，最佳格式 |
| Excel | 按行结构化处理 |
| 网页 HTML | 自动去广告/导航，保留正文 |

**预处理建议**：把扫描版 PDF 先用 OCR 转成可搜索的 PDF 再上传，避免知识库收到一堆乱码。

### 3.2 切分策略：父子分段

经过多轮对比测试，最终采用**父子分段（Parent-Child Chunking）**作为默认切分方式。

**原理**：

```
原始文档
   ↓ 切分
父块（512 字）── 保留完整语义，提供上下文
   ├── 子块 A（256 字）── 用来检索
   └── 子块 B（256 字）── 用来检索
   
检索时：用子块精准定位，返回父块给 LLM 阅读
```

**参数配置**：

| 参数    | 值             | 依据                   |
| ----- | ------------- | -------------------- |
| 父块大小  | 512 字符        | 涵盖金融文档典型段落长度（一条监管条文） |
| 父块分隔符 | `\n\n`        | 双换行表示完整段落边界          |
| 子块大小  | 256 字符        | 检索粒度，保证向量表示聚焦        |
| 子块分隔符 | `\n`          | 单换行切分到句子级            |
| 文本清洗  | 替换连续空白、保留 URL | 金融文档常含监管文件链接         |

**为什么父子分段优于通用切分**：

| 切分方式 | 优点 | 缺点 |
|---|---|---|
| 通用固定切分 | 实现简单 | 容易把"风控指标的三个维度"这种完整逻辑切散 |
| **父子分段** | 检索精准 + 上下文完整 | 索引体积约为通用切分的 1.3 倍 |
| 语义切分 | 最贴合内容 | 处理慢、对中文支持一般 |

### 3.3 索引方式

采用 **高质量索引（High Quality）** 模式：

- 使用专门的 Embedding 模型生成 1024 维稠密向量
- 支持混合检索（向量 + 关键词 BM25）
- 不可降级为经济模式（避免后续质量下降）

**经济模式与高质量模式的取舍**：

| 模式 | 适合场景 | 本项目选择 |
|---|---|---|
| 经济模式 | 大批量文档、快速检索、不要求精度 | ❌ 不适合金融场景 |
| 高质量模式 | 专业领域、需要语义理解 | ✅ 选用 |

### 3.4 检索配置

| 参数 | 值 | 说明 |
|---|---|---|
| 检索方式 | 混合检索 | 向量 + 关键词，覆盖语义和精确匹配 |
| 权重设置 | 语义 0.7 / 关键词 0.3 | 金融术语多，关键词权重不能太低 |
| Top K | 4 | 返回最相关的 4 个父块 |
| Score 阈值 | 0.4 | 过滤明显无关内容 |
| Rerank | 启用 Qwen3-Reranker-4B | 两阶段检索，精排提升明显 |

## 四、模型选型：线上 vs 线下

### 4.1 选型考量维度

金融行业对模型选型有特殊要求，需在六个维度上权衡：

| 维度 | 线上 API（如 GPT、Claude、通义） | 线下本地模型 |
|---|---|---|
| **数据安全** | ⚠️ 数据需出网 | ✅ 完全内网 |
| **响应速度** | ✅ 快（云端算力强）| ⚠️ 受本地算力限制 |
| **模型能力** | ✅ 顶尖（GPT-5、Claude Opus）| ⚠️ 通常落后半年到一年 |
| **成本** | 💰 按 Token 计费，量大成本高 | 💰 一次性硬件投入，边际成本极低 |
| **稳定性** | ⚠️ 依赖外部网络与服务可用性 | ✅ 完全自主可控 |
| **合规审计** | ⚠️ 数据流出受监管约束 | ✅ 易通过合规审计 |

### 4.2 本项目的双轨策略

考虑到金融业务的差异化数据敏感性，本项目采用**线上+线下双轨**部署：

```
┌──────────────────┐
│  用户提问        │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  数据敏感性判断  │
│  （Dify 路由）   │
└────────┬─────────┘
         │
    ┌────┴────┐
    │         │
    ▼         ▼
┌────────┐ ┌────────┐
│敏感数据│ │公开数据│
│  本地  │ │  云端  │
│  LLM   │ │  LLM   │
└────────┘ └────────┘
```

**路由规则**：

| 数据类型 | 路由到 |
|---|---|
| 客户信息、内部风控规则、未公开产品 | 本地 LLM（Qwen3-32B）|
| 公开监管法规、行业通识、术语解释 | 云端 LLM（性能更强）|

### 4.3 Embedding 模型选型详解

**候选对比**：

| 模型 | 中文表现 | 部署方式 | 维度 | 是否多模态 |
|---|---|---|---|---|
| OpenAI text-embedding-3-large | 中 | 仅 API | 3072 | ❌ |
| BGE-M3 | 优 | 本地/API | 1024 | ❌ |
| **Qwen3-VL-Embedding-8B** | **优秀** | **本地** | **1024** | **✅** |
| Cohere embed-v4 | 中 | 仅 API | 1024 | ⚠️部分 |

**最终选择 Qwen3-VL-Embedding-8B 的理由**：

1. **中文优势明显**：在 MTEB 多语言榜单上长期位列前茅，对金融术语理解准确
2. **多模态预留**：未来要把金融图表、产品说明书插图纳入知识库时无需更换模型
3. **本地部署**：完全可控，符合金融行业数据合规要求
4. **MRL 支持**：可灵活降维到 512 或 256，便于规模扩展时优化存储

### 4.4 Rerank 模型选型

启用 **Qwen3-Reranker-4B** 做两阶段检索：

```
第一阶段：Embedding 召回 Top 20（粗筛，毫秒级）
                ↓
第二阶段：Reranker 精排 Top 4（精筛，约 100ms）
                ↓
            送入 LLM
```

**Rerank 带来的关键改善**：

- 减少 LLM 输入的无关 chunk，**降低幻觉率**
- 同样 Top K 下，**精确率提升约 15-20%**
- 对金融领域的近义术语（如"保证金"vs"押金"）区分能力更强

## 五、测试方案与结果

### 5.1 测试集构建

为客观评估系统效果，构建了一套金融领域专属测试集：

| 维度 | 数量 | 来源 |
|---|---|---|
| 测试问题总数 | 200 条 | 业务专家撰写 + 历史客服工单抽样 |
| 涵盖业务领域 | 6 个 | 信贷、风控、合规、产品、运营、监管 |
| 问题类型 | 4 类 | 概念解释、流程查询、计算公式、案例对比 |
| 难度分级 | 三档 | 简单（直接命中）/ 中等（需理解）/ 困难（需推理）|

每个问题由业务专家标注：
- 标准答案
- 相关文档及具体段落（用于评估召回）
- 难度等级

### 5.2 测试维度

#### 维度 1：检索质量（系统是否找到了对的内容）

| 指标 | 含义 | 目标值 |
|---|---|---|
| **Recall@K** | 前 K 个返回中包含标准答案段落的比例 | ≥ 0.80 |
| **MRR** | 标准答案在返回结果中排名的倒数均值 | ≥ 0.75 |
| **NDCG@K** | 兼顾相关性和排名位置的综合指标 | ≥ 0.78 |

#### 维度 2：生成质量（LLM 是否答得对、答得好）

| 指标 | 含义 | 目标值 |
|---|---|---|
| **Faithfulness** | 答案与参考材料的一致性，不能编造 | ≥ 0.90 |
| **Answer Relevance** | 答案对问题的相关性 | ≥ 0.85 |
| **Completeness** | 答案的完整度，关键信息是否齐全 | ≥ 0.80 |

#### 维度 3：性能指标（系统是否快得起）

| 指标 | 含义 | 目标值 |
|---|---|---|
| **P50 延迟** | 50% 请求的响应时间 | ≤ 2s |
| **P99 延迟** | 99% 请求的响应时间 | ≤ 5s |
| **吞吐量** | 单位时间内可处理的查询数 | ≥ 10 QPS |

#### 维度 4：业务可用性

| 指标 | 含义 | 评估方式 |
|---|---|---|
| **拒答合理性** | 知识库没答案时能否正确拒答而非编造 | 专家盲评 |
| **溯源准确性** | 答案中引用的来源是否真的支持该结论 | 抽检 50 条 |
| **专业术语处理** | 行业术语解释的准确度 | 专家评分 |

### 5.3 测试结果

**第一轮基线测试**（通用切分 + 纯向量检索）：

| 指标 | 结果 | 是否达标 |
|---|---|---|
| Recall@4 | 0.62 | ❌ |
| MRR | 0.58 | ❌ |
| Faithfulness | 0.81 | ❌ |
| P50 延迟 | 1.8s | ✅ |
| 幻觉发生率 | 14.3% | ❌ |

**问题诊断**：
- 切分把完整业务流程切散，导致召回不全
- 纯向量检索对"巴塞尔协议 III"这种专名定位不准
- LLM 在材料不全时倾向于自由发挥

**第二轮优化后测试**（父子分段 + 混合检索 + Rerank）：

| 指标 | 结果 | 提升 | 是否达标 |
|---|---|---|---|
| **Recall@4** | **0.83** | +21pp | ✅ |
| **MRR** | **0.79** | +21pp | ✅ |
| **NDCG@4** | **0.81** | — | ✅ |
| **Faithfulness** | **0.92** | +11pp | ✅ |
| **Answer Relevance** | **0.87** | — | ✅ |
| **Completeness** | **0.83** | — | ✅ |
| **P50 延迟** | 2.1s | +0.3s | ✅ |
| **P99 延迟** | 4.7s | — | ✅ |
| **幻觉发生率** | **3.1%** | -11.2pp | ✅ |

### 5.4 关键 Bad Case 分析

| 类型 | 占比 | 案例 | 应对 |
|---|---|---|---|
| 同义词错召回 | ~30% | 问"押金"召回了"保证金"段落 | 在文档预处理中建立同义词表 |
| 数字混淆 | ~25% | 把不同年份的政策利率混在一起 | Prompt 强约束注明时间出处 |
| 跨段推理 | ~20% | 答案需要综合 3 个段落 | 调高 Top K 至 6，加强 Prompt 综合指令 |
| 知识库缺失 | ~15% | 问题超出范围 | LLM 学会拒答，已通过 Prompt 解决 |
| 其他 | ~10% | 表达歧义、问题本身错 | 用户引导 |

## 六、问答系统集成：从知识库到完整应用

### 6.1 应用架构

知识库只是数据底座，要成为可用的问答系统还需要应用层：

```
用户输入
   │
   ▼
┌──────────────────────┐
│  Dify Chatflow       │
│                      │
│  ① 输入预处理        │
│     ├─ 敏感词过滤    │
│     └─ 查询改写      │
│                      │
│  ② 路由判断          │
│     ├─ 业务领域识别  │
│     └─ 知识库选择    │
│                      │
│  ③ 知识检索          │
│     ├─ 混合检索      │
│     └─ Rerank        │
│                      │
│  ④ LLM 生成          │
│     ├─ Prompt 拼装   │
│     └─ 流式输出      │
│                      │
│  ⑤ 输出后处理        │
│     ├─ 来源标注      │
│     └─ 敏感信息脱敏  │
└──────────────────────┘
   │
   ▼
返回带溯源的答案
```

### 6.2 关键 Prompt 工程

LLM 的"角色定义"和"行为规则"通过 System Prompt 严格约束：

```
你是一名专业的金融知识问答助手，服务对象是金融机构内部员工。

【角色边界】
1. 只回答与金融业务相关的问题
2. 严格基于提供的<参考资料>作答，不得引入资料外的信息
3. 若资料中无相关内容，明确告知"知识库中暂无相关信息"

【回答规范】
1. 涉及英文缩写时，给出全称，例如 RWA(Risk-Weighted Assets，风险加权资产)
2. 涉及计算公式时，先列公式，再举例
3. 涉及监管条款时，标明依据文件和条款编号
4. 涉及不确定信息时，明确指出"建议核实"
5. 回答末尾以"参考来源"形式列出引用的文档名称

【禁止事项】
1. 不得提供具体的投资建议或预测
2. 不得评论监管政策的合理性
3. 不得编造数据、案例或法规条文

<参考资料>
{{#context#}}
</参考资料>

【用户问题】
{{#query#}}
```

### 6.3 输出溯源

每个答案附带可点击的来源标注，员工可以一键跳转到原文段落进行核实：

```
答：根据《商业银行资本管理办法》第二十三条，
    核心一级资本充足率不得低于 5%[1]，
    具体计算公式为... [2]

参考来源：
[1] 商业银行资本管理办法（2024 修订版）- 第二章第二十三条
[2] 资本充足率计算指引 V2.1 - 第三节
```

### 6.4 多端接入

系统通过 Dify 提供多种接入方式：

| 接入方式 | 适用场景 |
|---|---|
| Web 应用 | 员工浏览器直接访问 |
| iframe 嵌入 | 集成到内部 OA、Wiki 系统 |
| API 调用 | 接入企业微信、飞书机器人 |
| 自定义前端 | 对接核心业务系统 |

### 6.5 运营与迭代机制

系统上线不是终点，建立持续优化闭环：

```
用户使用
    ↓
日志收集（query + 回答 + 用户反馈点踩）
    ↓
Bad Case 周报（每周抽样 50 条复盘）
    ↓
分类归因
    ├─ 召回问题 → 调整切分/Embedding/Rerank 参数
    ├─ 生成问题 → 优化 Prompt
    └─ 知识缺失 → 补充文档
    ↓
A/B 测试验证
    ↓
回流到生产
```

### 7.2 中期（6-12 个月）

- **领域 SFT 微调**：基于业务问答对微调本地 LLM，进一步降低幻觉

## 八、结语

本项目通过 Dify + 本地化模型部署的方案，在保证数据安全的前提下，实现了金融行业级别的智能知识问答能力。核心经验：

1. **架构选型上**：开箱即用的 Dify 极大降低了工程开发成本，让团队聚焦在数据质量和业务逻辑上
2. **检索质量上**：父子分段 + 混合检索 + Rerank 的组合拳，把 Recall 从 0.62 拉到 0.83
3. **生成质量上**：精细的 Prompt 工程将幻觉率从 14.3% 降到 3.1%
4. **业务价值上**：员工平均查询时间从分钟级降到秒级，新员工上手周期缩短

RAG 不是银弹，但在企业垂直知识场景下，它是当前性价比最高的落地路径。
