## 第一部分:AI 训练师工作流总览(上午第一节)

### 一、团队构成与上下游关系

进入公司后常接触的四个角色:

- **产品经理(上游)**:从用户出发提需,关注产品反馈、用户的点赞/点踩数据
- **算法工程师(上游)**:从模型能力出发提需,可能直接给出方法论
- **AI 训练师(中游 / 自己)**:承接需求 → 落地为规则文档 → 管理执行
- **数据标注师(下游)**:按规则文档执行数据生产

**核心定位**:AI 训练师 = 模型的"老师",核心职责是给模型投喂**优质数据**。
"优质"的定义不是数据本身好看,而是**满足需求方需求**的数据(例如"人像丑学"项目要的是普通、不好看的照片)。

不同公司的需求来源占比不同:
- 智谱时期:80% 算法需求 + 20% 产品需求
- 字节时期:产品 + 算法各占一半,需求承接链路非常复杂

### 二、AI 训练师工作流四大环节

```
需求承接 → 规则文档撰写 → 数据标注全流程管理 → 项目复盘与交付
```

每个项目都要带入这个工作流去思考。

### 三、需求承接:5W2H 法则

> ⚠️ 上班暗号级别的方法论。面试时不要无脑甩"5W2H"三个字,要能展开讲。

| 维度 | 含义 | 关键问题 |
|---|---|---|
| **What** | 项目目标 | 训练哪个模型?这次项目的目标是什么? |
| **Why** | 训练原因 | 为什么要训这批数据?希望模型产生什么效果? |
| **Where** | 作业方式 | 线上作业(标注平台)还是线下作业(Excel)? |
| **When** | 时间节点 | 交付 deadline?是否需要中间节点交付? |
| **Who** | 涉及人员 | 需求方几人?承接方几人?手下需要多少标注人员? |
| **How** | 实施方式 | 有没有现成规则?有什么卡点? |
| **How much** | 资源成本 | 项目预算多少?(走公司账,需要前置预估) |

**职场关键铁律:沟通留痕、结果留痕、量化留痕**
- 每次需求沟通完,做一个表单(项目名/数据量/准确率要求/额外要求),让需求方在群里确认
- 字节用飞书表单,智谱用问卷,公司没有就自己造一个 SOP —— 这本身就是"提效赋能"的产出

### 四、需求承接的关键检查项

需求方给你数据后,**第一件事:打开看一遍数据**。

经典踩坑案例:
- 给你 5 万条数据,打开是 6 层嵌套文件夹,每个底层只有 1 张图(用脚本/Cursor 处理)
- 给你 3000 条用户回流数据,实际去重后只有 300 条都是"猫/小猫/花猫"(必须留痕反馈给需求方,否则背锅)

需要明确的项目要素:
- 数据量、数据类型(文/图/视频/音频)
- 准确率要求(决定质检策略)
- 是否提供规则文档
- 周期与排期

### 五、规则文档撰写流程

```
初版规则文档 → 内部小范围试标 → 质量分析 → 优化规则 → 与需求方对齐 → 正式版
```

**两种试标策略**:
1. 内部 2-3 人小范围试标 → 自己调整 → 再与需求方对齐
2. 拉需求方一起试标 → 当场看 DIFF(分歧点)→ 直接调整

**试标的坑**:不能只标连续的前 10 条数据!要在前/中/后段各挑一些,避免数据有难度排布规律。
> 智谱有训练师因为只标前 10 条简单数据,后期发现规则覆盖不到难数据,导致全员重标 + 写检讨书。

**规则文档应包含的内容**:

最小必须项:
- 项目背景
- 标注概要(数据量、交付周期可选)
- 标注规则(打分维度 / 标签定义)
- 标注方案(打标签 / 打分 / 改写 / 选优)
- Case 案例(必须来自真实数据)

进阶项:
- 标注流程图(复杂多步骤项目)
- 排期
- 验收标准
- 知识点补充(如需专业知识)
- 操作指南(平台操作)

## 第二部分:项目执行细节(上午第二节)

### 一、人效设定

**人效不是拍脑袋**,要能讲出因果。

参考公式:
```
总数据量 ≈ 标注天数 × 人数 × 人效
```

举例:
- 一条数据标 2-3 分钟,6 小时工作制 → 一天 120-180 条
- 复杂数据(几千~1万字)一天 10 条也合理 —— **关键是能讲出原因**
- 面试官会问"你的人效怎么来的?",要能说服对方

**爬坡期(Landing/准入)**:新人前期人效低,目标是逐步达到顶峰值(如理想态 1 条/2 分钟)。
> 字节的试用期就叫 LANDING。

---

### 二、Badcase 处理:归因是核心动作

**什么是 Badcase**:
- 标注人员发现规则文档没涵盖到的数据
- 标注人员与你产生分歧的 case
- 90% 的人都标错的某类数据

**拿到 Badcase 后必做:归因**

| 原因 | 处理方式 |
|---|---|
| 标注人员没读规则文档 | 提点他,让他重读 |
| 规则文档没涵盖 | 补充规则文档 |
| 规则文档表述模糊 | 加典型案例上去 |

规则文档**前期达到 80% 完整度**就可以开始执行,后续根据实际作业不断弥补。但大致方向必须前期锚定清楚。

---

### 三、试标筛选

- **试标量**:一般 10-30 条,不要太多(检查也是负担)
- **准确率要求**:跟试标量匹配。试标 10 条要求 95% 不合理(只允许错半条),改成 80% 才合理
- **提效技巧**:把试标题做成有标准答案的问卷形式 → 自动出分,无需人工抽检
- **三级试标流程**:针对高难度项目(如美学+大模型+本项目知识三个维度),逐级筛选,降低进项后流失率
- **埋点测试**:在 3000 字数据里故意改错一小段,考察标注员是否细心
- **二次试标**:一轮 80% 但未达 90% 的,可以给二次机会

### 四、人员角色与合作模式

| 类型 | 来源 | 质量排序 |
|---|---|---|
| **内部** | 实习生、驻场、团队成员 | ⭐⭐⭐⭐⭐ 最优 |
| **标注基地** | 聚集型外包(知道是谁) | ⭐⭐⭐⭐ |
| **供应商** | BPO,按人/按数据合作 | ⭐⭐⭐ |
| **众包** | 线上社会闲散人员 | ⭐⭐ |

**供应商两种合作模式**:
- 按人:派 10-20 人,你每天分发数据
- 按数据:一批 5 万条,验收达标再付款

**字节的众包平台**:魔兜(模型的模 + 裤兜的兜)

**供应商管理常见坑**:同一标注 ID 今天 95% 准确率,明天 60% —— 可能是人请假了换人顶,需要主动协同管理。

**激励机制**:
- 供应商按准确率给系数(95% 以上 ×1.1,75% ×0.75,80% 以下不付钱)
- 实习生表现好可以发"一蹦子"(50 元 bounce)

### 五、标注全流程管理

```
任务安排 → 质检设计 → 答疑 → Badcase 收集 → 流程监控 → 规则文档优化
```

**质检比例怎么定**:
- 准确率要求 99%(如医疗):必须 100% 全检
- 普通项目:抽检 20%-30%
- 半人工时代:可以让 AI 辅助质检

**人员分组**(50 人项目):
- 5 个质检员,每人带 10 人小分队,负责答疑、培训
- 不能 1 对 100 培训

**质检评级与处理**:

| 准确率 | 评级 | 处理方式 |
|---|---|---|
| > 95% | 优秀 | 改问题数据即可 |
| 85-95% | 合格 | 改问题数据 / 自查一半 |
| < 85% | 不合格 | 全量打回重标,再抽 30% 复检 |
| < 60% | 直接淘汰该批次 | 重新找人做 |

**质检节奏**:N 日质检 N-1 日数据(轮回模式);也可以做"互检"(10 人互相检)。

**二次质检 = 验收**:针对当日所有数据再抽 200-300 条,不合格当天打回。

**质检员从哪来**:
- 从标注员里选准确率高 + 细心 + 善于沟通的人(三个条件缺一不可)
- 或直接用自己的实习生/驻场

### 六、人员替换(汰换)

⚠️ 面试雷区:被问"标注员准确率低怎么办",**不要直接说"换掉"**,会显得没人管理思维。

正确思路:
- 爬坡期准确率低 → 给余地
- 稳定期持续 3 天准确率低且态度不认真 → 适当替换
- 累计 2 次红牌可以汰换

### 七、交付与复盘

**交付文档(One Page 文档)应包含**:
- 数据来源、用途、时间
- 任务发起人、负责人、沟通群
- 任务摘要、deadline、容错程度、交付频率
- 规则文档链接
- 总工作日、总人天、产出数据量、平均合格率
- 项目成本(线上/线下)
- 相关文档与最终总结

**面试必问:项目难点 + 你怎么解决的**
> 面试官不期待你做过一模一样的项目,他考察的是**遇到问题、解决问题的能力**。

### 八、时间周期把控经验

**冗余预估原则**:
- 人员上浮 30-40%(锚定 10 人,实际准入 15 人)
- 人效跟需求方报低值(实际 150,报 100-120)
- 验收后留 3-7 天冗余

**典型周期**:
- 长期项目:前期对需求 2-3 天 → 试标 2 天 → 正式作业 + 爬坡 → 验收
- 短平快(字节常见):早上对需求 → 下午写完规则 → 次日开标 → 2-3 天交付(数据量 500-2000)

**规则文档大变动应对**:
- 暂停作业 → 先质检已标数据 → 与需求方对齐变动原因 → 培训现有人员(不重新招)→ 通知周期延长

### 四、模型调用原理速通

```
Agent = 大语言模型 + 工具调用
```

- **API 调用**:模型跑在云端服务器(伊朗服务器被炸 → 国内某些服务断)
- **本地部署**:开源模型可在本地跑,免费、私密、离线;未来手机/电脑芯片可能直接跑 8B 压缩版的 4.7 级模型
- **MCP(Model Context Protocol)**:让 AI IDE 连接其他软件工具(类似 HTTP 的协议层)
- **CLI**:比 MCP 更高权限的终端调用方式,目前比 MCP 更常用

**商业变现两条路**(以智谱为例):
- To B:把模型部署到企业服务里(智谱 80% 走这条)
- To C:订阅制(Minimax 上市靠这个)

### 七、实战案例 3:调用百度 API 识别植物 + 重命名

**思路**:不是只有 AI 大模型可以调用,百度智能云有大量传统 AI 模型 API(植物识别、人物识别、车辆识别等)。

**步骤**:
1. 百度智能云注册 → 实名认证
2. 搜"植物识别" → 开通后付费(有免费额度)
3. 创建应用 → 拿到 **APP ID / API Key / Secret Key** 三个凭证
4. 把三个凭证 + 文件夹路径 + 命名规则(如"植物-品种名-编号")给 Cursor
5. Cursor 自动生成脚本调用 API → 批量重命名本地文件夹

**结构化提示词模板**:
```
背景:我有一批植物图片需要按"植物-品种名-编号"格式重新命名
要求:调用百度植物识别 API,识别不出来的图片自动筛除
资源:
- 文件夹路径:[路径]
- APP ID:[xxx]
- API Key:[xxx]
- Secret Key:[xxx]
```

⚠️ 别让 Cursor 删你电脑文件 —— 深圳产品班有人本地文件被 OpenClaude 全删了,找不回。

### 八、Prompt Engineering(提示词工程)

#### 8.1 核心概念

- **Prompt(用户提示词)**:你输入的指令
- **System Prompt(SP / 系统提示词)**:产品内嵌的全局约束(如 Cursor 强制 Todo List 流程)
- **Memory**:产品自动记忆的用户信息
- **上下文(Context)**:Prompt + SP + Memory + 历史对话 + 参考资料,**全部一起喂给模型**

#### 8.2 提示词工程师 vs 上下文工程师

| 岗位 | 解决什么问题 |
|---|---|
| Prompt Engineer | 早期模型能力差,用结构化 prompt 精准定位能力 |
| Context Engineer | 模型能力强了,但上下文太多导致注意力分散、生成质量下降 → 给上下文"瘦身" |

**模型的能力盲区**:模型有 100% 的能力,但你的任务只需要其中一小部分。
提示词的最大作用是**精准定位**到这部分能力。

#### 8.3 优质提示词框架(ICIO / RTGO / 通用结构)

```
角色 + 背景 + 任务 + 任务拆分 + 要求 + 语气 + 输出格式 + 示例(可选)
```

**对比案例**:
- ❌ "制作一个周一到周五的食谱" → 模型会乱发挥
- ✅ 加上"角色:营养师 / 背景:已有食材xxx / 输出格式:Markdown 表格" → 精准落地

#### 8.4 写 Prompt 的进阶技巧

| 技巧 | 说明 |
|---|---|
| **简练语言** | 把模型当无脑理科生,不用客气 |
| **明确意图** | 不要太多负向约束,会束手束脚 |
| **任务拆解** | 复杂任务拆成第一步、第二步 |
| **末尾强调** | 模型对开头和结尾内容更敏感 |
| **自检机制** | 让它先列思路再生成,避免长篇跑偏 |
| **示例慎给** | 创意任务给示例会被框死;结构化任务可以给 |
| **温和派 vs 激进派** | 都行,看个人风格(老师属于激进派) |

**"奶奶激活码"梗**:早期 GPT 因模仿情感会被绕过权限。现在已经基本失效。
