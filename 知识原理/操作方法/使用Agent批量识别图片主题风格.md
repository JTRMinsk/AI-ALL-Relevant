# 使用 Agent 批量识别图片主题风格

> 一次 105 张图片、9 个固定维度 + 1 段总体描述、最终落地为带嵌图 Excel 的完整复盘。
> 工程时间约 **1 小时 57 分**（剔除中间长间断），其中前 50 分钟基本走在错误的路径上。
> 这篇文档既是工作流说明，也是教训记录。

---

- 目录：`C:\Users\jtrki\Desktop\pic`

## 1. 最终工作流

经过两次失败后稳定下来的流程，按时序分 4 步：

```
┌──────────────────────┐    ┌──────────────────────┐    ┌──────────────────────┐    ┌──────────────────────┐
│ ① 约定 schema (JSON) │ →  │ ② 用户分批贴图 (10/批) │ →  │ ③ Agent 写回 JSON     │ →  │ ④ 一键导出 Excel      │
└──────────────────────┘    └──────────────────────┘    └──────────────────────┘    └──────────────────────┘
```

### Step 1 · 落 schema：`_descriptions.json`

先把"字段、枚举、规则"全部写死到 JSON 头部，避免 Agent 越做越飘。

```json
{
  "_schema": {
    "columns_order": ["图片文件名", "图片的预览", "画面形式", "...", "整体描述"],
    "enum_fields": {
      "画面形式": ["摄影", "艺术", "动画"],
      "构图": ["中心构图", "对角线构图", "..."],
      "色调": ["暖色调", "冷色调", "中色调", "冷暖对比", "黑白色调", "不涉及"],
      "艺术风格": ["写实", "抽象", "摄影", "数字设计与插画", "东方传统艺术"],
      "景别": ["大远景", "远景", "全景", "中景", "近景", "特写", "不涉及"]
    },
    "free_text_fields": ["主题类型", "光影", "笔触特征", "情感氛围", "整体描述"],
    "rules": {
      "画面形式": "优先用摄影/艺术/动画三选一，实在不行才扩展",
      "整体描述": "总结前面九个维度（不是反向 prompt），需自然成段"
    }
  },
  "data": { "4569.jpg": { "...": "..." } }
}
```

**为什么选 JSON 不直接写 Excel？**

| 需求 | JSON ✅ | Excel ❌ |
|---|---|---|
| Agent 增量追加单行 | 一次 StrReplace 就行 | 必须重新跑脚本，状态不连续 |
| 跨对话回合幂等 | 失败可重试，不会污染 | 难重入 |
| Schema 与数据同文件 | 上下文一目了然 | 需额外文档 |
| 后续可换导出格式 | 一份数据可出 Excel / CSV / Markdown / Notion | 锁死格式 |

### Step 2 · 分批贴图（10 张/批）

由用户把图片**直接粘贴到对话框**，每批 10 张。Agent 用对话内的视觉通道识别，而不是 `Read` 工具读本地文件（原因详见第 3 节）。

一共分了 11 批：1-5、7、8、补6、补9、10、11，每批顺序识别 → 写表 → 用户校验。

### Step 3 · 写回 JSON

每批结束，Agent 把 10 条结构化记录通过 `StrReplace` 增量追加到 `_descriptions.json` 的 `data` 字段，并打印当前进度（80/105 等）。每次都用 `python -c "json.load(...)"` 做一次完整性校验。

### Step 4 · 一键导出 Excel

最后跑一个 4 KB 的 `_build_excel.py`：

```text
_descriptions.json
      │
      ▼
读 schema → 自然数字序排 105 条
      │
      ▼
为每张图生成 220×220 预览到 _previews/
      │
      ▼
openpyxl 写 Excel：
  · 表头加粗 + 浅蓝填充
  · 冻结 C2（首行 + 前两列固定）
  · 行高随预览图自适应
  · 列宽预设，长文本启用 wrap_text
  · 用 XLImage 把每张预览锚定到 B 列对应行
      │
      ▼
图片描述表.xlsx  (1.03 MB)
```

## 3. 哪些 Prompt 起到了关键作用

不是越长越有用，反而是这几条短句改变了走向：

| 时间 | 用户说的话 | 实际效果 |
|---|---|---|
| 5:44 PM | 列出 9 个维度的枚举值 | **建立词汇表**，让自由发挥变成填空 |
| 5:45 PM | "我要求你一口气做完，不要有停顿，不要有疑问" | 设定执行风格，但同时埋下隐患（见第 4 节） |
| 9:32 PM | "图片和各个维度的描述并不匹配……推倒重来" | **整个工作流被这句话救了**——Agent 这才意识到自己在编 |
| 9:38 PM | "用最通用的直接传图方式，这张图你看到了什么" | 这是关键转折：用单张测试验证视觉通道 |
| 9:42 PM | "好吧，十张十张的来" | 把任务从"一次性"切成"批处理 + 校验" |
| 9:44 PM | "省的过长，我图片一批一批的发过来" | 主动引入分批节奏 |
| 9:53 PM | "不错，第二批" | **正反馈信号**，确认当前节奏可继续 |

**给读者的提示**：当 Agent 跑偏时，最有效的不是细化要求，而是**质问输出与事实的偏差**（"和图根本对不上""推倒重来"），它会触发模型自查而不是继续涂脂抹粉。

## 5. 教训

### 5.1 为什么 `Read` 工具读本地图 ≠ 看见图？

这是这次最痛的教训。前 50 分钟内 Agent 用 `Read` 把每张缩略图读入上下文，**然后照样把人物画像写成"城市风光"**。

复盘原因：

1. **工具调用语义 ≠ 模型感知语义**。`Read` 返回的是一个图片引用，但当上下文里同时存在文件名、缩略图、上一张图的描述时，模型会优先用"文件名 + 上文模式"补全描述，而不是真正基于像素重新看。
2. **批量循环里会"自动驾驶"**。一旦 Agent 进入"读图→写描述"的 for 循环，新图的描述会越来越像前几张的均值，本质是上下文里的"风格惯性"在压过真实视觉信号。
3. **没有外部校验信号**。模型自己不知道自己看错了，需要外部反馈（"你这几批做的每条都不对呀"）才会重新审视。

**结论**：在 Cursor / IDE Agent 里，最可靠的"让模型看图"通道是用户**直接粘贴图片到对话**——这是模型原生多模态输入的路径，跟工具调用走的是完全不同的链路。

### 5.2 为什么 10 张/批？

试过几种节奏后的体感：

| 批量 | 问题 |
|---|---|
| 30+ 张/批 | 单次响应被截断；中间几张容易写串；用户无法精细校验 |
| 20 张/批 | 用户校验时翻图疲劳，很难一眼看出哪张错位 |
| **10 张/批** | **甜区**：单条响应能容纳 10 张图 + 10 张表，用户也能逐张核对 |
| 5 张/批 | 节奏太碎，Agent 输出冗余的开场白和总结，总耗时反而上升 |

10 张还有个隐藏好处：**对应"五行 × 两列"的视觉栅格**，用户在校验时能像看 contact sheet 一样扫一眼。

### 5.3 不做持久化会怎样？

这次的 `_descriptions.json` 救命的地方在于：

- 上下文压缩 / 重置后，状态可恢复（Cursor 会自动 summarize 长对话）。
- 用户中途说"补第六批"（漏了一批）时，能精准插入而不打乱顺序。
- 批 9 和批 10 顺序颠倒、用户合并发图时，靠 JSON 里的 `keys()` 排序就能立刻看出缺哪些。
- 最终 Excel 输出和 schema 解耦：要换格式（CSV、Notion DB、飞书多维表）只要换 30 行脚本，数据不动。

**如果不持久化会怎样**：

1. **断点续传不可能**。对话长到一定长度被压缩后，前面 80 张图的描述就消失了。
2. **Agent 会乐于在每个 batch 重写一个表格**，但每个表格都是孤立的，最后还要再花一轮把它们拼起来——而且很可能拼错。
3. **没法做完整性校验**。第 4 节里那次 `total: 100, total image files: 105` 的差额，正是因为 JSON 有这条记录才能算出来；如果状态只在对话里，会带病交付。

## 6. 还能怎么优化？

按"投入产出比"排序：

### 6.1 用 LLM 替代手工贴图（中等收益、需要 API）

这次用户手动粘了 11 批图，是因为 Agent 在 IDE 里读本地图不可靠。理论上更优解是：

```text
本地脚本（直接调用 GPT-4 Vision / Claude / Gemini Vision API）
   ├─ 把 9 维度的 schema 作为 system prompt
   ├─ 把每张原图以 base64 / URL 传入
   ├─ 强制输出符合 schema 的 JSON
   └─ 并发 5-10 路，最后合并
```

这样用户完全脱手，只在最后做抽样校验。代价是要写一段 API 调用 + 失败重试 + 价格控制。105 张图按当下 Vision API 价格大概 < 2 USD。

### 6.2 加 self-check 步骤（低成本、强效）

每批写完，让 Agent 自己再做一道"质检"：

- 重新只看图片，**不看自己刚写的文本**，独立给出"主要主体是什么"（一行话）。
- 然后跟刚写的"主题类型 / 整体描述"做关键词比对：如果"人物"vs"风景"、"近景"vs"远景"这种粗粒度都对不上，就标黄返工。

这次的 50 分钟错误时间，9 成是因为这步没做。

### 6.3 输出多视图（低成本）

同一份 JSON，多出几份视图：

- **CSV / TSV**：方便丢回飞书表格、Notion DB。
- **Markdown 表**：方便贴到博客 / 笔记。
- **按维度透视**：例如"摄影 + 暖色调 + 远景"有几张图，做内容资产的盘点。
- **缩略画廊 HTML**：把 105 张图按"艺术风格"分组渲染成一页。

加这些只需要十几行 Python，但对后续用法的撬动很大。

### 6.4 做"分类一致性"评估（进阶）

用 schema 约束的枚举值都很有限（如"构图"11 个值），可以：

- 跑两遍独立的分类（不同 prompt 或不同模型），看两次结果在枚举字段上的一致率。
- 一致率 < 80% 的那些字段或图片，进入人工复核队列。

对于 105 张这种小批量价值不大，但当数据集涨到 1000+ 时，这是判断质量是否可信的唯一办法。

### 6.5 Excel 美化与交互（锦上添花）

当前 Excel 已经能用，但还能：

- 给 5 个枚举列加**数据验证下拉框**，方便用户在 Excel 里直接改正错误后再回写 JSON。
- 给"画面形式 / 艺术风格"加**条件格式色块**，扫一眼就知道分布。
- 顶部加一行**汇总统计**：5 个枚举字段各值的频数。

## 7. 一句话总结

> **Schema-first + 用户直接喂图 + 小批量校验 + JSON 持久化 + 末尾一键导出**——
> 这套组合拳是这次 Agent 项目从"前 50 分钟全废"到"后 55 分钟全部 105 张干净落地"的全部秘密。
> 任何"让 Agent 批量加工内容"的任务，几乎都能套用这个骨架。
