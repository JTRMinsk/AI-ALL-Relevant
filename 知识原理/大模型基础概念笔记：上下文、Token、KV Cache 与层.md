## 一、上下文长度（Context Length）

上下文长度由 **模型架构** 和 **硬件资源** 共同决定，但**主要由模型决定**。

### 1.1 模型决定的上限

核心是**位置编码（Positional Encoding）**：

- **训练时的最大长度**：`max_position_embeddings`
  - GPT-4 Turbo: 128K
  - Claude: 200K
  - Gemini 1.5: 1M-2M

- **位置编码类型决定可扩展性**：
  - 绝对位置编码（原始 Transformer）：硬上限，无法外推
  - **RoPE（旋转位置编码）**：可通过插值/外推扩展（LLaMA 系列）
  - **ALiBi**：天然支持长度外推
  - **NoPE**：无显式位置编码

### 1.2 硬件决定的实际上限

即使模型支持 1M token，硬件不一定跑得动。瓶颈是 **KV Cache 显存占用**：

```
KV Cache 大小 ≈ 2 × num_layers × seq_len × hidden_size × num_kv_heads/num_heads × dtype_size
```

举例（LLaMA-2 70B，FP16）：

| 上下文长度 | KV Cache 占用 |
|-----------|--------------|
| 1 token | 320 KB |
| 1K token | 320 MB |
| 32K token | 10 GB |
| 128K token | 40 GB |
| 1M token | 320 GB |

### 1.3 上下文存在哪里

**存在 GPU 显存（VRAM）的 KV Cache 中**：

- 每生成一个 token，都需把之前所有 token 的 K 和 V 张量保存下来
- 这些张量存在 GPU 显存（HBM）里
- 推理时每一步都要读取整个 KV Cache 来计算注意力
- 优化方案：PagedAttention（vLLM）、量化 KV Cache、卸载到 CPU/磁盘

> **结论公式**：
> ```
> 实际上下文长度上限 = min(
>     模型训练时的 max_position_embeddings,   ← 模型决定
>     GPU 显存能容纳的 KV Cache               ← 硬件决定
> )
> ```

## 二、Token 是什么

K 和 M 后面的单位就是 **Token**：

- 128K = 128,000 tokens
- 200K = 200,000 tokens
- 1M = 1,000,000 tokens
- 2M = 2,000,000 tokens

### 2.1 Token 的本质

Token 是模型处理文本的**最小单位**，不是字符也不是单词，而是介于两者之间的"子词"（subword）。由模型的 **Tokenizer**（分词器）决定怎么切分。

### 2.2 直观换算

| 语言 | 1 token ≈ |
|------|-----------|
| 英文 | ~0.75 个单词 / ~4 个字符 |
| 中文 | ~0.5-1 个汉字（常用字 1 token，生僻字可能 2-3 token） |
| 代码 | 介于英文和符号之间 |

### 2.3 各模型实际容量

| 模型 | Token 上下文 | ≈ 英文单词 | ≈ 中文字 | ≈ 书页数 |
|------|-------------|-----------|----------|---------|
| GPT-4 Turbo | 128K | 96,000 | 80,000-128,000 | ~250 页 |
| Claude 3 | 200K | 150,000 | 130,000-200,000 | ~400 页 |
| Gemini 1.5 Pro | 1M | 750,000 | 700,000 | ~2000 页 / 1 小时视频 |
| Gemini 1.5 Pro (实验) | 2M | 1,500,000 | 1,400,000 | 整套《哈利波特》还有富余 |

### 2.4 不同模型的 Tokenizer 不一样

同一段文本，不同模型消耗的 token 数**不同**：

- **GPT 系列**：`cl100k_base` / `o200k_base`（BPE）
- **Claude**：自家 tokenizer（对中文更友好）
- **LLaMA**：SentencePiece BPE

测试方法：

```python
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4")
print(len(enc.encode("你好，世界！")))
```

或访问 [OpenAI Tokenizer](https://platform.openai.com/tokenizer)。

## 三、Token 生成速度

推理分两个阶段，瓶颈不同。

### 3.1 Prefill 阶段（处理输入 prompt）

- **计算密集型（Compute-bound）**：受 GPU 算力（FLOPS）限制
- 速度上限 ≈ GPU TFLOPS / 模型每 token 的 FLOPs
- 可以并行处理所有输入 token，所以很快

### 3.2 Decode 阶段（逐个生成输出 token）

**这是真正的瓶颈，受内存带宽限制（Memory-bound）**：

```
理论最大生成速度 ≈ 显存带宽 / 模型参数大小
```

举例（A100，LLaMA 70B FP16）：

```
A100 显存带宽 ≈ 2 TB/s
LLaMA 70B FP16 ≈ 140 GB
理论上限 ≈ 2000 / 140 ≈ 14 tokens/s（单 batch）
```

**为什么是内存带宽？**

- 每生成 1 个 token，都要把全部模型权重从显存搬运到计算单元一次
- GPU 算力其实绰绰有余，数据搬不过来才是瓶颈

### 3.3 速度上限决定因素（按重要性）

| 因素 | 影响 |
|------|------|
| **显存带宽**（HBM 带宽） | 解码速度的硬上限 |
| **模型大小** | 越大越慢（要搬运的权重多） |
| **量化精度** | INT4 比 FP16 快约 4 倍 |
| **Batch size** | 增大 batch 提升吞吐，但单请求延迟不变 |
| **KV Cache 大小** | 长上下文也要搬运，会拖慢速度 |
| **互连带宽**（NVLink/PCIe） | 多卡推理时影响通信开销 |
| **架构优化** | Flash Attention、Speculative Decoding、MoE 等 |

### 3.4 突破带宽瓶颈的方法

- **量化**：INT8/INT4 减少搬运量
- **Speculative Decoding**：小模型预测，大模型验证，1 次搬运多 token
- **MoE 架构**：每次只激活部分参数（Mixtral 8x7B 实际只激活 ~13B）
- **Continuous Batching**：服务多个请求摊薄成本（vLLM）
- **更新硬件**：H100（3.35 TB/s）→ H200（4.8 TB/s）→ B200（8 TB/s）

## 四、KV Cache 详解

### 4.1 单 token KV Cache 计算公式

```
单 token KV Cache = 2 × num_layers × num_kv_heads × head_dim × dtype_size
                    ↑                                            ↑
                  K 和 V 两份                               FP16 = 2 字节
```

### 4.2 LLaMA-2 70B 实际计算

| 参数 | 值 |
|------|-----|
| 层数（num_layers） | 80 |
| KV 头数（num_kv_heads，GQA） | 8 |
| 每个头的维度（head_dim） | 128 |
| 数据类型（FP16） | 2 字节 |

```
2 × 80 × 8 × 128 × 2 = 327,680 字节 ≈ 320 KB
```

### 4.3 为什么单 token KV Cache 这么大？

**1. 每一层都要单独存**：Transformer 是 80 层堆叠，每层都有自己独立的注意力机制，都要单独缓存自己的 K 和 V。

**2. 多头注意力（每个头独立）**：每层有多个注意力头并行工作，每个头看到的"角度"不同，K/V 也不同。

**3. K 和 V 是两份**：注意力公式 `Attention(Q, K, V) = softmax(QK^T)V` 需要 K 和 V 两个张量。

LLaMA-2 70B 用了 **GQA（Grouped Query Attention）** 优化，KV 头从 64 个降到 8 个，**已经省了 8 倍**。如果是普通 MHA：

```
2 × 80 × 64 × 128 × 2 = 2,621,440 字节 ≈ 2.5 MB / token
```

### 4.4 不同模型对比（FP16，单 token）

| 模型 | 层数 | KV 头数 | head_dim | 单 token KV Cache |
|------|-----|---------|----------|-------------------|
| LLaMA-2 7B | 32 | 32 | 128 | 512 KB |
| LLaMA-2 13B | 40 | 40 | 128 | 800 KB |
| LLaMA-2 70B (GQA) | 80 | 8 | 128 | **320 KB** |
| GPT-3 175B | 96 | 96 | 128 | 4.5 MB ⚠️ |
| Mistral 7B (GQA) | 32 | 8 | 128 | 128 KB |

> 注意：**70B 的 KV Cache 反而比 7B 小**，就是因为用了 GQA。

### 4.5 KV Cache 优化方案

| 方案 | 思路 | 效果 |
|------|------|------|
| **GQA** (LLaMA-2/3) | 多个 Q 共享一组 KV | 省 4-8 倍 |
| **MQA** (PaLM) | 所有 Q 共享一组 KV | 省到极致，但效果略降 |
| **MLA** (DeepSeek-V2/V3) | 把 KV 压缩到低秩潜空间 | 省 ~10 倍 |
| **KV 量化** | INT8/INT4 存 KV | 省 2-4 倍 |
| **PagedAttention** (vLLM) | 分页管理，减少碎片 | 省 ~2 倍利用率 |
| **滑动窗口** (Mistral) | 只保留最近 N 个 token | 上限固定 |
| **CPU/磁盘卸载** | 不活跃的 KV 换出 | 慢但能跑 |

### 4.6 为什么 KV Cache 必须在显存里

存储金字塔：

```
              访问速度
              ↑ 快
┌─────────────────────────┐
│  GPU 寄存器 (KB级)       │  ~ 几个时钟周期
├─────────────────────────┤
│  GPU L1/L2 缓存 (MB级)   │  ~ 几十纳秒
├─────────────────────────┤
│  GPU 显存 HBM (GB级)     │  ~ 几百纳秒，2-3 TB/s
├═════════════════════════┤  ← KV Cache 必须在这条线以上
│  CPU 内存 DRAM (TB级)    │  ~ 微秒级，慢 10-100 倍
├─────────────────────────┤
│  SSD (TB级)              │  毫秒级，慢 1000+ 倍
└─────────────────────────┘
              ↓ 慢
```

**带宽对比**（读 10 GB KV Cache 耗时）：

| 位置 | 带宽 | 耗时 |
|------|------|------|
| GPU 显存 (HBM3) | ~3 TB/s | **3.3 ms** ✓ |
| CPU 内存 (DDR5) | ~50 GB/s | 200 ms |
| PCIe 5.0 | ~64 GB/s | 156 ms |
| NVMe SSD | ~7 GB/s | 1.4 秒 |

**核心原因**：每生成一个 token 都要读全部 KV Cache，带宽差 100 倍意味着速度差 100 倍。

## 五、Transformer 的"层"是什么

### 5.1 一句话定义

**每一层 = 一次"让 token 重新理解自己和上下文"的运算**

### 5.2 每层做两件事

```
每一层 (Layer) = Self-Attention + Feed-Forward Network (FFN/MLP)
                    ↑                    ↑
                "看别人"             "想自己"
```

**第一步：Self-Attention（自注意力）—— "看别人"**

每个 token 主动去看上下文里的其他 token，把相关信息"吸收"进来。

例：`"小明吃了苹果，他很开心"`
- 处理 `"他"` 时，注意力机制让它去看前面所有 token
- 发现和 `"小明"` 相关度高
- `"他"` 的向量里融入了 `"小明"` 的信息

**第二步：Feed-Forward（前馈网络）—— "想自己"**

吸收完上下文后，token 自己再做一次"思考加工"，把信息转换成更抽象的表示。

### 5.3 为什么要叠 80 层 —— 理解的"深度"

每过一层，token 的理解就深一层：

| 层级 | 干的事情 | 例子（处理"苹果"） |
|------|---------|------------------|
| Layer 1-5 | 词法 | 识别这是个名词 |
| Layer 10-20 | 语法 | 它是"吃"的宾语 |
| Layer 30-40 | 局部语义 | 这里指水果，不是公司 |
| Layer 50-60 | 全局语义 | 它是小明开心的原因 |
| Layer 70-80 | 推理/抽象 | 这段话在讲温馨小场景 |

### 5.4 各模型的层数

| 模型 | 层数 |
|------|------|
| GPT-2 small | 12 |
| BERT-base | 12 |
| LLaMA-2 7B | 32 |
| LLaMA-2 13B | 40 |
| LLaMA-2 70B | 80 |
| GPT-3 175B | 96 |
| GPT-4 (推测) | ~120 |

### 5.5 为什么需要缓存每层的 K/V

生成下一个 token 时，**每一层的注意力计算都需要回看自己那一层之前所有 token 的 K 和 V**：

```
生成第 N+1 个 token 时：
  Layer 1 的注意力 → 需要 Layer 1 里前 N 个 token 的 K/V
  Layer 2 的注意力 → 需要 Layer 2 里前 N 个 token 的 K/V
  ...
  Layer 80 的注意力 → 需要 Layer 80 里前 N 个 token 的 K/V
```

如果不缓存，每生成一个 token 就要把前面所有 token 在 80 层里全部重算一遍——**计算量 O(N²) 爆炸**。

> KV Cache 的本质：**用显存（空间）换计算（时间）**。

## 六、深度 vs 宽度

### 6.1 两个容易混淆的概念

| 概念 | 对应模型参数 | 含义 |
|------|------------|------|
| **深度（Depth）** | 层数 num_layers | 思考的"轮数"、推理的"步数" |
| **宽度（Width）** | hidden_size | 每个 token 向量的"信息容量"、视角维度 |

```
       宽度 (hidden_size = 8192)
       ←——————————————————————→
    ┌──────────────────────────┐
    │   Layer 1                │  ↑
    ├──────────────────────────┤  │
    │   Layer 2                │  │
    ├──────────────────────────┤  │
    │   ...                    │  深度
    ├──────────────────────────┤  (num_layers
    │   Layer 79               │   = 80)
    ├──────────────────────────┤  │
    │   Layer 80               │  ↓
    └──────────────────────────┘
```

### 6.2 类比

**写文章**：
- 宽度 = 词汇量
- 深度 = 反复修改次数

**思考问题**：
- 宽度 = 一次能考虑多少个因素
- 深度 = 愿意往下追问几层"为什么"

```
浅 + 窄：脱口而出
浅 + 宽：见多识广但没深思
深 + 窄：钻牛角尖
深 + 宽：真正的智者  ← 大模型追求的
```

### 6.3 变大方式对显存的影响

| 变大方式 | 模型权重 | KV Cache | 计算量 |
|---------|---------|----------|-------|
| 加层（深度↑） | 线性 ↑ | 线性 ↑ | 线性 ↑ |
| 加宽（宽度↑） | 平方 ↑↑ | 线性 ↑ | 平方 ↑↑ |

例：
- 层数 40 → 80：模型权重 × 2
- 宽度 4096 → 8192：模型权重 × 4（权重矩阵是宽 × 宽）

### 6.4 不同模型的"长相"

| 模型 | 深度 | 宽度 | 形状 |
|------|-----|------|------|
| BERT-base | 12 | 768 | 又矮又瘦 |
| GPT-2 | 48 | 1600 | 中等 |
| LLaMA-7B | 32 | 4096 | 矮胖 |
| LLaMA-70B | 80 | 8192 | 又高又胖 |
| GPT-3 175B | 96 | 12288 | 巨人 |

> **层数 = 思考多少轮（深度）**
> **宽度 = 每轮思考调动多少个角度（维度）**

## 七、Token、Embedding、KV Cache 的关系

### 7.1 容易混淆的因果关系

❌ **错误说法**：token 是由模型多层的 KV Cache 组成的

✅ **正确说法**：token 是输入，KV Cache 是它经过模型时留下的"足迹/快照"

### 7.2 完整因果链

```
文本（"你好世界"）
    ↓ Tokenizer 切分
token（[你, 好, 世, 界]） ← 本质是几个整数 ID
    ↓ Embedding 查表
向量（每个 token 变成 8192 维向量）
    ↓ 进入 Layer 1
    ↓ 算出 K₁, V₁ → 存入 KV Cache  ← 副产物
    ↓ 进入 Layer 2
    ↓ 算出 K₂, V₂ → 存入 KV Cache  ← 副产物
    ↓ ...
    ↓ 进入 Layer 80
    ↓ 算出 K₈₀, V₈₀ → 存入 KV Cache ← 副产物
    ↓
输出（预测下一个 token）
```

### 7.3 三层概念

```
┌─────────────────────────────────────────┐
│  上下文 (Context)                        │
│  = 一串 token 序列                       │
│                                          │
│  ┌────────────────────────────────────┐ │
│  │  每个 token                         │ │
│  │  = 一个整数 ID                      │ │
│  │  = 词表中的一个条目                 │ │
│  └────────────────────────────────────┘ │
└─────────────────────────────────────────┘
              ↓ 跑模型推理时
┌─────────────────────────────────────────┐
│  KV Cache                                │
│  = 每个 token 在每一层的中间计算结果      │
│  = 用来加速后续生成的"备忘录"             │
│  = token 不需要它也能存在                 │
└─────────────────────────────────────────┘
```

### 7.4 关键认知

> **token 不需要 KV Cache 也存在。**
> **KV Cache 只在"运行模型推理"时才产生。**

证据：
- 硬盘里存的聊天记录 → 是 token，**没有 KV Cache**
- 发给模型 → 才开始计算，才产生 KV Cache
- 回答完，请求结束 → KV Cache 通常被释放

### 7.5 类比

**学生读书**：
- token = 书本上的字
- 模型 = 学生的大脑
- KV Cache = 学生读书时脑子里的理解和印象

字本身不是"由理解组成的"，理解是字进入大脑后产生的东西。

**简化口诀**：

> **token 是身份**（这是哪个词）
> **embedding 是含义**（这个词什么意思）
> **KV Cache 是记忆**（模型当前对它的理解状态）

### 7.6 存储 vs 推理

```
存储/传输层面：
  上下文 = [token, token, token, ...]
  每个 token 就是一个整数（几个字节而已）
  100K token 的上下文 ≈ 几百 KB（纯 token 数据）

运行/推理层面：
  上下文进入模型 → 每层算出 K, V → 缓存起来
  100K token 的 KV Cache ≈ 几十 GB（中间计算结果）
  ↑
  这才是显存压力的来源
```

## 八、KV Cache 的生命周期

KV Cache **不是和对话框绑定的**，它的生命比你想的短得多。

### 8.1 推理时的时间线（秒级）

```
T=0s    你按下回车，消息发给后台
        ↓
T=0.1s  请求路由到某张 GPU
        ↓
T=0.5s  GPU 开始 prefill：把所有历史 token 灌进模型，生成 KV Cache
        KV Cache (~20 GB) 此刻在显存里 ←─── 存在的瞬间！
        ↓
T=3s    Prefill 完成，开始生成回答
        KV Cache 还在显存，每生成一个新 token 就追加一点
        ↓
T=15s   回答生成完毕，流式输出给你
        ↓
T=15.1s 请求结束，GPU 释放显存
        KV Cache 被销毁（或部分压缩存到 CPU/磁盘做 prompt caching）
        ↓
T=15.2s ✘ KV Cache 已不存在
        ↓
   ...你看完回答，思考要不要回复...
        ↓
T=120s  这期间 GPU 早就在服务别的用户了
        ↓
T=180s  你按下回车发下一条消息
        → 又一轮新的 KV Cache 重新生成
```

> **关键点**：KV Cache 只在**模型正在处理你这条消息的那十几秒**才存在。
> 你看到回答之后，它**就已经消失了**——根本不需要等你关闭对话框。

### 8.2 等待期间什么都不占（比如三天后再聊）

| 存储位置 | 占用大小 | 形态 | 持续时间 |
|---------|---------|------|---------|
| **GPU 显存（KV Cache）** | **0 字节** | 不存在 | 回答结束就销毁 |
| **服务端 Prompt Cache** | 0 字节 | 不存在 | 5 分钟后失效 |
| **应用后台数据库** | **几百 KB** | token / 纯文本 | 直到你删除对话 |
| **客户端缓存** | 几百 KB | 文本 | 取决于客户端策略 |

> **三天等待期间真正占用的存储**：只有应用数据库里的**几百 KB 纯文本 token**。
> 没有显存、没有 GPU 资源、没有 KV Cache。

### 8.3 三天后再点击对话发生什么

```
T=3天0min  你点开对话                    📁 应用从数据库拉出历史 token
            ↓
T=3天5s    你输入新消息发送
            ↓
T=3天6s    GPU 拿到 60K+ token，从零开始 prefill
            （Prompt Cache 早已失效，不能复用）
            KV Cache (~20 GB) 在显存里重新生成 ← 临时
            ↓
T=3天20s   生成新回答
            ↓
T=3天21s   KV Cache 再次销毁              ✘
```

**关键点**：

1. **模型那边完全是"冷启动"**——不知道你之前聊过什么，需要把所有历史 token 重新跑一遍
2. **每次都要重算**，所以长对话越聊越慢、越聊越贵（前面内容每次都得重 prefill）
3. **Prompt Cache 帮不了你**——它只活几分钟，三天根本指望不上

### 8.4 60K token 大概占多少 KV Cache？

按业界一线大模型的常见参数估算：

| 假设的架构 | 单 token KV Cache | 60K token 总量 |
|-----------|------------------|---------------|
| 类 LLaMA-70B（GQA） | ~320 KB | **~19 GB** |
| 类 LLaMA-405B（GQA） | ~500 KB | **~30 GB** |
| 类 GPT-3 175B（无 GQA） | ~4.5 MB | ~270 GB ⚠️ |
| 类 DeepSeek-V3（MLA 压缩） | ~70 KB | **~4 GB** |

> 一个比较合理的中位数：**60K token 对话约占 20–30 GB 显存的 KV Cache**——光是装下"理解状态"就要一整张 A100 显存的 1/4 到 1/3。

但要记住：**这只在推理那十几秒存在**，事后立刻消失。

### 8.5 Prefill 才是真正贵的

Prefill 60K token 的计算量：

```
≈ 60,000 × 模型参数量 × 2
≈ 60K × 200B × 2
≈ 24 PFLOPs
```

H100 算力约 1 PFLOPs（FP16），单卡需要 **~24 秒**纯算 prefill（实际多卡并行更快）。

这就是为什么你每次发新消息，都要等几秒才看到回复开头——这几秒大部分是在重算所有历史 token 的 KV Cache。

### 8.6 Prompt Caching 优化

像 Anthropic 的 [Prompt Caching](https://www.anthropic.com/news/prompt-caching) 特性：

```
推理结束后：
  完整 KV Cache (显存里) → 销毁  ✓
  压缩版 KV Cache → 存到 CPU 内存或磁盘 ← 这部分能保留几分钟
                                          供下次同前缀对话复用
```

- 节省 90% 的 prefill 成本
- 但 **TTL 通常 5 分钟**，超时自动清理
- 跟你"关不关对话框"无关

### 8.7 类比：医生和病历本

| 角色 | 类比 |
|------|------|
| 你的对话 token | 你的**病历本**（一直存档案室） |
| KV Cache | 医生看诊时**脑子里**对你病情的理解 |
| 关闭对话 | 你走出诊室 |
| 三天后回来 | 你再次挂号复诊 |

> 三天后医生还记得你吗？**不记得。**
> 但他会从档案室调出病历本（token），**重新看一遍**才能继续看病——
> 医生脑子里的理解（KV Cache）是每次现场重建的。

这就是为什么大模型的"对话连续性"是个**伪连续**——每次都是把全部历史重新塞进模型再算一遍。

### 8.8 几个有趣的推论

1. **你的对话没有真正的"暂停"**：对模型来说，没有"暂停 3 天"这个概念
2. **上下文越长，每次启动越贵**：100K token 每次都要完整 prefill 一次
3. **模型权重不会因聊天而改变**：所有"记忆"都是每次现场重建
4. **删除对话只删 token**：模型那边本来也没存

## 九、LLM 应用的架构：谁在保存你的对话

### 9.1 客户端 vs 模型 API：有状态 vs 无状态

```
┌─────────────────────────────────────────────────────┐
│  Cursor / Claude App / ChatGPT 网页 / 任何 LLM 应用   │
│                                                       │
│  职责：                                              │
│  ✓ 保存对话历史（数据库/文件）                       │
│  ✓ 管理用户、会话、权限                              │
│  ✓ 每次请求时把完整历史拼好                          │
│  ✓ 调用模型 API                                      │
│  ✓ 渲染 UI、流式显示                                 │
└─────────────────────────────────────────────────────┘
                    ↕ HTTP/API 调用
┌─────────────────────────────────────────────────────┐
│  Anthropic / OpenAI / Google 等模型提供商             │
│                                                       │
│  职责：                                              │
│  ✓ 接收一次性的请求（messages 数组）                 │
│  ✗ 不记得任何历史会话                                │
│  ✓ 跑模型推理，返回回答                              │
│  ✓ 短期 prompt cache（5 分钟级别）                   │
└─────────────────────────────────────────────────────┘
```

> **核心架构原则**：
> **应用层 = 有状态的"记忆管理者"**
> **模型 API = 无状态的"推理引擎"**

### 9.2 API 调用的"无状态"本质

每次调用模型 API，请求长这样：

```json
POST https://api.anthropic.com/v1/messages
{
  "model": "claude-sonnet-4.5",
  "messages": [
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好！"},
    {"role": "user", "content": "上下文怎么决定的？"},
    {"role": "assistant", "content": "由模型和硬件决定..."},
    ...（前面所有对话）...
    {"role": "user", "content": "现在的新问题"}
  ]
}
```

**关键点**：

1. **每次请求都要把完整历史发过去**——模型 API 是无状态的（stateless）
2. 模型服务器**不会记住**你上次发过什么
3. 是应用层在每次发请求前，从自己数据库里把历史拼出来塞进 `messages` 数组

### 9.3 三种使用方式对比

```
┌────────────────────────────────────────────────────────────┐
│  方式 1: Claude.ai 网页 / Claude 桌面 App                   │
│                                                              │
│  你 → Anthropic 网页前端 → Anthropic 后端                    │
│                              │                               │
│                              ├── 数据库（存对话）            │
│                              └── 模型服务（跑推理）          │
│                                                              │
│  历史存在: Anthropic 服务器                                  │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│  方式 2: Cursor / 第三方应用                                 │
│                                                              │
│  你 → Cursor 客户端 → Cursor 后端 ──→ Anthropic API          │
│                          │                                   │
│                          └── Cursor 数据库（存对话）         │
│                                                              │
│  历史存在: Cursor 服务器                                     │
│  Anthropic 只看到瞬时请求                                    │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│  方式 3: 你自己写脚本调 API                                  │
│                                                              │
│  你的脚本 ──→ Anthropic API                                  │
│      │                                                       │
│      └── 你自己存（本地文件/数据库/啥都行）                  │
│                                                              │
│  历史存在: 你自己的存储                                      │
└────────────────────────────────────────────────────────────┘
```

| 使用方式 | 管家是谁 | 历史存在哪 |
|---------|---------|-----------|
| Claude.ai / Claude App | **Anthropic 自己** | Anthropic 数据库 |
| Cursor | Cursor | Cursor 数据库 |
| ChatGPT 网页 | OpenAI | OpenAI 数据库 |
| 自己写脚本 | 你 | 你想存哪存哪 |

> 无论哪种方式，**最底下那层"模型 API"都是无状态、健忘的**。
> 区别只在于"谁充当了那个有状态的管家"。

### 9.4 一个有趣的等价关系

> **Claude.ai 网页 ≈ Anthropic 写的"内部 Cursor"**

Claude.ai 团队和 Cursor 团队做的本质上是同一件事：

1. 做一个有状态的"管家应用"
2. 存对话历史
3. 拼 prompt
4. 调自家或别家的模型 API
5. 渲染界面

唯一区别：Anthropic 自家网页"恰好"和模型 API 在**同一家公司的服务器集群里**——但架构上仍然是分离的两个服务。

### 9.5 客户端做了多少额外的工作

以 Cursor 为例，它实际上做了不少**智能拼装**：

- 把你 `@` 的文件内容塞进 prompt
- 自动附加打开的代码、光标位置
- 注入项目相关的规则（rules）
- 决定哪些历史要保留、哪些可以省略
- 选择合适的模型（Auto / Claude / GPT 等）
- 处理工具调用循环（Agent 模式下的 Read/Write/Shell 等）

所以你看到"Cursor 很懂我的项目"——这个"懂"的功劳大半在 Cursor 工程团队，模型只是被一次次喂材料的"嘴巴"。

### 9.6 三种方式的对比

| 维度 | Claude App | Cursor | 自己调 API |
|------|-----------|--------|-----------|
| 历史存哪 | Anthropic | Cursor | 自己 |
| 项目上下文 | 没有（除非用 Project） | 有（@ 文件、代码、Rules） | 看你怎么写 |
| 工具调用 | 有限（搜索、Artifacts） | 有（Read/Write/Shell 等） | 看你怎么写 |
| 隐私 | 数据给 Anthropic | 数据给 Cursor + Anthropic | 数据只给 Anthropic |
| 模型选择 | 只能用 Claude | 可选 Claude / GPT / Gemini 等 | 看你买谁的 API |
| 成本 | 订阅制 | 订阅制 | 按 token 付费 |

### 9.7 类比：你和翻译公司

| 角色 | 类比 |
|------|------|
| **你** | 客户 |
| **Cursor / Claude App** | 你的私人秘书（知道你过去所有沟通记录） |
| **模型 API** | 翻译公司的窗口（每次都重新接待） |
| **模型本身** | 翻译公司的同声传译员 |

每次你要翻译：

1. 秘书从档案柜调出过去所有相关对话
2. 整理好递给翻译公司窗口
3. 翻译员现场看材料、给出翻译
4. 窗口把结果回传给秘书
5. 秘书展示给你，并把这次新对话**也归档到自己档案柜**

> 翻译公司从不记你是谁。你的"历史档案"始终在秘书手里。

### 9.8 几个有趣的推论

**1. 同一个对话，换个 App 也能继续**

理论上你可以：导出 Cursor 对话历史 → 用同样的 API key 自己写脚本 → 把这堆 token 喂进 Claude API。模型完全不会发现你换了客户端，因为它本来就只看到一坨 messages 数组。

**2. 模型对你"完全陌生"**

每次请求对模型 API 来说都是"全新"的。它不知道：
- 这是同一个用户的第几次对话
- 上次和你聊过什么（除非客户端把上次内容塞进这次 messages）
- 你的偏好、习惯、身份

它只看到："API key XXX 在 14:23:01 发来了一坨 60,123 tokens 的请求"。

**3. 删除对话只删 token，不影响模型**

你删除应用里的对话 → 删的是数据库里那几百 KB 纯文本。模型权重和服务你之前完全一样。

**4. "对话连续性"是客户端制造的假象**

每次的"连续感"是应用层在每次请求前帮你"重新装填记忆"造成的——模型本身永远活在"当下这一次请求"里。

### 9.9 选用 LLM 产品的本质

选用哪个 LLM 产品，本质上是在选三件事：

1. **谁当你的管家**（信任问题、隐私问题）
2. **管家有多聪明**（能不能给你接代码、调工具、搜资料）
3. **管家背后接的是谁的厨房**（Claude / GPT / Gemini……）

## 十、核心结论速查表

### 10.1 上下文与硬件

| 问题 | 答案 |
|------|------|
| 上下文长度由什么决定？ | min(模型训练上限, GPU 显存) |
| 上下文存在哪里？ | GPU 显存的 KV Cache 中（仅推理时） |
| 为什么必须在显存？ | CPU 内存带宽差几十倍，速度直接暴跌 |

### 10.2 速度

| 问题 | 答案 |
|------|------|
| Token 生成速度由什么决定？ | 显存带宽 / 模型激活参数大小 |
| 速度上限是什么？ | 显存带宽（HBM）—— Memory-bound |
| 怎么加速？ | 量化、MoE、Speculative Decoding、更换硬件 |

### 10.3 模型结构

| 问题 | 答案 |
|------|------|
| 层是干啥的？ | 让 token 反复"理解自己和上下文"，每层加深一次理解 |
| 层数和显存关系？ | KV Cache 严格线性正比 |
| 深度 vs 宽度？ | 深度=思考轮数，宽度=每轮的视角维度 |

### 10.4 概念关系

| 概念 | 角色 |
|------|------|
| Token | 身份（输入） |
| Embedding | 含义（查表后的向量） |
| KV Cache | 记忆（推理过程中的中间状态） |

### 10.5 KV Cache 生命周期

| 问题 | 答案 |
|------|------|
| KV Cache 活多久？ | **十几秒**——只在模型处理你这条消息时存在 |
| 等待期间占显存吗？ | **不占**，回答完立刻销毁 |
| 三天后再聊会怎样？ | 模型从零开始 prefill，重新生成 KV Cache |
| 关闭/删除对话影响什么？ | 只影响应用数据库里的 token 历史，KV Cache 早就没了 |

### 10.6 应用架构

| 问题 | 答案 |
|------|------|
| 谁在保存我的对话历史？ | **客户端**（Cursor / Claude App / 你自己） |
| 模型 API 会记住我吗？ | **不会**，每次请求都是全新的（无状态） |
| "对话连续性"是怎么做到的？ | 客户端每次把完整历史塞进 messages 数组 |
| 长对话为什么越来越慢？ | 每次都要重 prefill 全部历史 |

### 10.7 关键公式

```
上下文长度上限 = min(
    模型训练时的 max_position_embeddings,
    GPU 显存能容纳的 KV Cache
)

单 token KV Cache = 2 × num_layers × num_kv_heads × head_dim × dtype_size

Token 生成速度 ≈ 显存带宽 / (激活参数大小 + KV Cache 大小)

Prefill 计算量 ≈ token 数 × 模型参数量 × 2 FLOPs
```

### 10.8 总结性比喻

**比喻 1：厨师与工作台（讲推理执行）**

> **GPU 是个超级厨师，显存是他的工作台。**
> - **token** 是食材（一颗番茄）
> - **模型层** 是 80 道工序，每道工序对食材重新加工
> - **KV Cache** 是每道工序留下的中间状态
> - **CPU 内存** 是隔壁房间的冰箱（远，但容量大）
> - **SSD** 是楼下仓库（更远，巨大，但跑一趟要命）
>
> 厨师每秒要做 30 道菜（30 token/s），所有食材必须摆在伸手可及的工作台上。

**比喻 2：医生与病历本（讲对话连续性）**

> **模型是医生，对话历史是你的病历本。**
> - 病历本一直存在档案室（应用数据库）
> - 每次复诊医生都要从头看一遍病历（重新 prefill）
> - 医生脑子里对你的理解（KV Cache）每次现场重建，看完就忘
> - 你换医院，只要带上病历本，新医生也能接着看

**比喻 3：秘书与翻译公司（讲应用架构）**

> **应用是你的私人秘书，模型 API 是翻译公司的窗口。**
> - 秘书（Cursor / Claude App）保管所有对话档案
> - 你要翻译时，秘书把档案整理好递给窗口
> - 翻译员（模型）现场看材料、当场翻译、用完就走
> - 翻译公司从不记你是谁，你的"历史档案"始终在秘书手里

> **模型是无状态的瞬时引擎，记忆是客户端制造的假象。**
> **token 是上下文的"持久态"，KV Cache 是上下文的"瞬时态"。**
> **你看到的连续对话，本质上是客户端每次都在帮你"复述前情提要"。**
