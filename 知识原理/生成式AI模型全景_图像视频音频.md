# 生成式 AI 模型全景：图像、视频、音频

> 整理自 2026 年 5 月与 Cursor 的讨论。本文聚焦"生成内容"的模型——图像、视频、音频，以及它们的本地部署可行性。

---

## 一、AI Agent 是怎么"生图"的？—— 原理拆解

### 1.1 Claude / Cursor 这类 Agent 本身能"画图"吗？

**不能。它们是搬运工。**

| 能力 | 是否原生具备 |
|------|------------|
| 多模态**输入**（理解图片、PDF） | ✅ 具备（Claude/GPT/Gemini 都能） |
| 多模态**输出**（直接画出像素） | ❌ 不具备（除了 GPT-4o 那种特例） |

LLM 本质上输出的是文本（包括结构化的工具调用指令）。它"生图"是通过**工具调用（Tool Use / Function Calling）** 把任务转包给真正的图像模型完成的。

### 1.2 完整调用链路

```
用户："画一只猫"
  ↓
Agent (Claude)：理解需求 → 输出结构化的工具调用
  ↓
工具调用：GenerateImage(description="一只橘猫，扁平风格...")
  ↓
平台后端：把这个调用转发给真正的图像生成模型
  （可能是 DALL·E 3 / Imagen / Flux / Stable Diffusion）
  ↓
图像模型：生成 .png 文件
  ↓
平台：把图片返回给用户，并把"已生成"结果回传给 Agent
  ↓
Agent：基于结果继续对话
```

### 1.3 Agent 在这条链路上做的事

| 环节 | 谁做 | 含金量 |
|------|------|--------|
| 理解用户的需求 | Agent | 中 |
| 把口语翻译成图像 prompt（提示工程） | Agent | 中 |
| 决定参数（尺寸/风格/数量） | Agent | 低 |
| **真正"创作"——把噪声去噪成图像** | **扩散模型** | **几乎 100%** |
| 返回文件、展示给用户 | 平台 | 低 |

> **类比**：Agent ≈ 会写策划案但不会画画的总监 —— 自己画不出来，但能写非常清晰的设计需求文档，把文档交给画师（图像模型）。

### 1.4 反例：原生多模态生成

GPT-4o 在 2025 年推出的原生图像生成不走这条路 —— **它的图像 token 和文字 token 在同一个模型里一起预测**，叫 native multimodal generation（原生多模态生成）。

但目前**主流仍是 LLM + 外接图像模型** 的组合拳，原因：
1. 扩散模型在图像质量上仍有优势
2. 模块化、好替换（今天接 DALL·E，明天换 Flux 都行）
3. 成本可控

### 1.5 主流 AI 产品的图像生成机制对照

| 产品 | 机制 |
|------|------|
| ChatGPT 画图 | 早期 GPT-4 调 DALL·E 3 → 现在 GPT-4o 已原生化 |
| Claude 画图（在支持的平台） | 调外部图像 API |
| Gemini | 调 Imagen |
| Cursor | 调平台配置的图像服务（GenerateImage 工具） |

## 二、图像生成模型全景

### 2.1 开源派 vs 闭源派

| 模型 | 能否本地部署 | 备注 |
|------|------------|------|
| **Stable Diffusion** (1.5 / XL / 3) | ✅ 完全可以 | 开源鼻祖，社区生态最大 |
| **Flux**（Black Forest Labs） | ✅ 部分可以 | Flux.1 [schnell/dev] 开源；[pro] 闭源 |
| **SDXL / SD3** | ✅ 可以 | 权重公开 |
| **Playground / Pony / Illustrious** | ✅ 可以 | 都是 SD 衍生 |
| **DALL·E 3** | ❌ 不行 | OpenAI 闭源，只能调 API |
| **Imagen 3 / 4** | ❌ 不行 | Google 闭源 |
| **GPT-4o 原生生图** | ❌ 不行 | OpenAI 闭源 |
| **Midjourney** | ❌ 不行 | 闭源 |
| **Ideogram** | ❌ 不行 | 闭源 |

**简单规律**：
- "开源派" = Stability AI / Black Forest Labs 系
- "闭源派" = OpenAI / Google / Midjourney 系

### 2.2 反直觉真相：图像模型其实比 LLM 小很多

| 模型 | 参数量 | 类型 |
|------|--------|------|
| **Stable Diffusion 1.5** | ~0.9 B | 图像 |
| **SDXL** | ~3.5 B（base+refiner） | 图像 |
| **SD3 Medium** | ~2 B | 图像 |
| **Flux.1 dev** | ~12 B | 图像（已经算大的了） |
| ——— | ——— | ——— |
| **Llama 3 8B** | 8 B | LLM |
| **Llama 3 70B** | 70 B | LLM |
| **Qwen 2.5 72B** | 72 B | LLM |
| **DeepSeek V3** | 671 B (MoE) | LLM |
| **GPT-4 / Claude Opus** | 估计 1T+ | LLM（闭源） |

**结论：图像模型大多在 1–12 B 之间，比一线 LLM 小一两个数量级。**

#### 为什么图像模型反而"小"？

1. **LLM 要装下整个互联网的"知识"** —— 历史、科学、代码、所有语言……需要海量参数当"记忆"
2. **图像模型只需要学"视觉规律"** —— 物体长什么样、光怎么照、纹理怎么排列。规律有限，知识量小
3. **扩散模型的工作方式不同** —— 它不"记忆"图片，而是学习"如何把噪声一步步去成图"，是个**过程模型**，不是**知识模型**
4. **文本编码靠外挂** —— SD 用的 CLIP/T5 文本编码器是单独的小模型，不需要把语言能力塞进图像模型本体

### 2.3 本地部署的硬件门槛

### 2.5 为什么 OpenAI / Google 不开源图像模型？

闭源派的图像模型（DALL·E 3、Imagen、GPT-4o-image）通常：

1. **效果更好**（特别是文字渲染、prompt 理解）
2. **训练数据更"干净"**（规避版权诉讼）
3. **是商业护城河**（API 收钱）
4. **风险控制**（NSFW、deepfake、名人脸等）

### 2.6 本地能不能"接近 Midjourney"？—— 诚实对比

> 一句营销话术："一张 4090 能让你在家跑出接近 Midjourney 水平的图。"
> **真相：在特定风格下接近，全方位赶上还差一截。**

#### 本地（Flux.1 dev / SDXL + 好的 LoRA）能打的地方

| 维度 | 表现 |
|------|------|
| **写实人像/风景** | 接近甚至超过 MJ（Flux 在写实上很猛） |
| **特定垂类风格**（动漫、二次元、像素、赛博朋克） | **碾压 MJ**（社区 LoRA 太丰富了） |
| **NSFW / 无审查内容** | MJ 完全做不到，本地随便 |
| **可控性**（ControlNet、IP-Adapter、inpaint） | **吊打 MJ**（MJ 几乎无精细控制） |
| **批量生产 / 工作流自动化** | 本地完胜（ComfyUI 节点流） |
| **成本** | 一次性买卡，之后零边际成本 |

#### 本地打不过 Midjourney 的地方

| 维度 | 差距 |
|------|------|
| **"开箱即用"的审美** | MJ V6/V7 的默认出图美学就是高级感，本地需要堆 prompt + LoRA + 调参 |
| **构图与叙事感** | MJ 的镜头感、光影氛围、画面"故事性"是公认的强项 |
| **复杂 prompt 理解** | MJ V6+ 对长 prompt 的理解力很顶 |
| **文字渲染** | MJ V6/V7 和 Flux 都不错，但 MJ 略胜 |
| **风格一致性 / 角色一致性** | MJ 的 `--cref` `--sref` 体验更顺滑 |
| **平均出图质量稳定性** | MJ 的下限高，本地 SD 下限低（容易翻车） |

#### 一个准确的说法

> **本地能在"特定任务"上达到甚至超过 MJ；但要论"开箱即用、一键出大片"的综合美学，MJ 仍然是天花板。**

打比方：
- **Midjourney** = 米其林大厨做的固定套餐，端上来就是惊艳
- **本地 Flux/SDXL** = 给你一整个专业厨房 + 全套食材，**你自己得会做**，做好了不输米其林，做不好就翻车

#### Midjourney 现状（2026 年）

- 当前主力版本是 **V7**（2025 年发布）
- 强化了文字渲染、人物一致性、prompt 理解
- 仍然只能通过 **Discord / 官网**使用，**没有官方 API，完全闭源**
- 估计参数量和架构都没公开，但从效果推测应该也是几十亿参数级别的扩散模型 + 强大的训练数据 + 大量 RLHF 美学微调

### 3.4 视频生成为什么这么难？

#### 1）多了一个时间维度
图像是 H × W，视频是 H × W × T（T = 帧数）。计算量和显存都线性甚至超线性增长。

#### 2）时间一致性极难
- 角色脸不能换
- 物体不能凭空消失
- 光影、阴影要连贯
- 物理规律不能违反（水流、布料、碰撞）

这些是图像模型完全不需要考虑的问题。

#### 3）文本到运动的映射几乎没有训练数据
图像有 LAION 几十亿对（图, 文），但 **(视频, 详细描述)** 的高质量数据稀缺得多，需要用 Vision-Language 模型批量打标签。

#### 4）架构创新
当前主流是 **DiT (Diffusion Transformer)** + **3D VAE**（把视频压到时空潜空间）。Sora 是首个把这套架构做到惊艳水平的，之后大家都跟进。

### 3.7 几个关键趋势（2025–2026）

1. **"图生视频" > "文生视频" 成为主流工作流** —— 先用 SD/Flux 出关键帧，再用视频模型补动画，可控性最强
2. **音视频联合生成** —— Veo 3 开了个头，Sora 2 跟进
3. **实时生成正在到来** —— LTX-Video 这类已经能做到准实时
4. **角色一致性** —— Runway Gen-4 的角色锚定、Sora 的 Storyboard 都在解决"同一角色多镜头"问题
5. **物理仿真化** —— Sora 2 强调 "world model"，目标不只是画面好看，而是符合物理直觉

## 四、音频生成模型全景

音频生成是个"大筐"，里面装着好几个细分赛道，能力天花板和玩家完全不同。

### 4.1 五个细分赛道

| 赛道 | 干啥的 | 代表场景 |
|------|-------|---------|
| **TTS（文字转语音）** | 文本 → 人声 | 配音、有声书、客服 |
| **语音克隆** | 几秒样本 → 模仿任何人声音 | 个性化配音、deepfake |
| **音乐生成** | 文本/旋律 → 完整歌曲 | 配乐、流行歌曲 |
| **音效生成（SFX）** | 文本 → 环境音/特效音 | 游戏、影视后期 |
| **歌声合成（SVS）** | 歌词+曲谱 → 歌唱声 | 虚拟歌手、AI 翻唱 |

| 音乐（MusicGen-Large、YuE） | 16–24 GB | ✅ 能跑，慢一点 |
| 音效（Stable Audio） | 8 GB | ✅ 轻松 |

**结论：音频是三大模态里本地化最成熟的** —— 一张 4090 就能跑出商业可用的 TTS 和音乐生成。

### 4.5 几个有意思的现象

1. **TTS 已经"过拟合"到难辨真假** —— ElevenLabs / GPT-4o 已经过了恐怖谷，社会风险也跟着来（电信诈骗、伪造音频）
2. **音乐生成是 2024–2025 最大爆点** —— Suno 把"完整歌曲一键生成"这件事从科幻变成产品
3. **开源追赶最猛的是 TTS** —— CosyVoice 2 / F5-TTS / Fish Speech 已经接近 ElevenLabs 的下限
4. **音乐开源差距还较大** —— YuE / ACE-Step 出来之前，开源只能做纯器乐，做不出"带人声的完整歌"
5. **实时对话语音是新战场** —— GPT-4o-realtime、Gemini Live 把延迟压到 200ms 内，这是 ElevenLabs 都没解决好的问题

### 5.1 难度公式（粗略）

```
本地部署难度 ≈ 模型参数量 × 单次推理token数 × 时间维度 × 分辨率维度
```

- LLM：参数大 × token 多 → **大但单 token 快**
- 图像：参数中 × 单次出图 × 高分辨率 → **中等**
- 视频：参数中-大 × **时间维度爆炸** × 高分辨率 → **难**
- 音频：参数小 × 一维信号 → **简单**

### 5.2 几个反直觉的点

1. **音频比图像简单** —— 因为只有一维信号，模型也小（几 B 起）
2. **视频比图像难得多** —— 不是难一点，是难一个数量级（时间维度）
3. **顶级 LLM 比顶级视频还难本地化** —— 因为参数量碾压一切
4. **VLM 比纯 LLM 略难** —— 多了视觉编码器，显存要求略高
5. **3D 是冷门但门槛中等** —— 工具链不成熟，不是算力问题

### 5.3 最适合本地玩的"甜点区"

按"性价比 + 体验"排：

```
🥇 LLM（7B–14B） —— 几乎人人能跑，体验流畅，应用最广
🥈 TTS / ASR     —— 几乎零门槛，效果可商用
🥉 图像生成      —— 生态最成熟，可玩性最高
4️⃣ 音乐生成      —— 新兴，开源进展快
5️⃣ 3D 生成       —— 小众但门槛不高
```

### 5.4 最不建议本地搞的

```
❌ 顶级 LLM（>100B）           —— 直接用 API
❌ 顶级视频生成                —— 都闭源，用 API
❌ 实时对话语音（GPT-4o-realtime 那种） —— 闭源 + 工程难
```

### 5.5 一张图理解（文字版）

```
易 ←─────────────────────────────────────────────→ 难

Embedding ─ ASR ─ TTS ─ 小 LLM ─ 小 VLM ─ 图像生成 ─ 音乐 ─ 中 LLM ─ 3D ─ Omni ─ 视频理解 ─ 视频生成 ─ 大 LLM ─ Sora 级
   │        │      │       │        │         │        │       │      │     │       │           │           │         │
  CPU      CPU   8GB    16GB     16GB      24GB     24GB   双卡   24GB  32GB   48GB        24GB+量化     8卡集群    无解
```

## 六、一句话总览

> **能本地跑得爽的，是 LLM ≤14B、TTS、ASR、图像生成；能跑但要等的，是中型 LLM、视频生成、3D；本地基本没戏的，是 200B+ LLM 和顶级视频。**
>
> **维度越多（时间、空间），越吃硬件；模态越融合（Omni），越难；越闭源（Sora、GPT-4o），越无法本地化。**
>
> **图像模型反而是"小而专"，LLM 才是"大而全"。**
