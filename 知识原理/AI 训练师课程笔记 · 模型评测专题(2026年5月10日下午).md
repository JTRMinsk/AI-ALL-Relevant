## 一、上午遗留:评测集来源补充

### 1.1 四种来源完整版

| 来源           | 说明                                  | 面试时该不该说     |
| ------------ | ----------------------------------- | ----------- |
| **用户 query** | 真实用户提的问题(链接 / 文字 / 图片)              | ✅ 体现真实需求    |
| **开源评测集**    | GitHub / Hugging Face / Plug-case 等 | ✅ 体现技术认知    |
| **PE 构造**    | 用提示词工程让模型批量生成                       | ✅ 体现提效能力    |
| **算法提供**     | 算法直接发一份现成的给你                        | ❌ **千万不能说** |

> 老师再次强调:工作中**最常见就是算法直接给**,但面试说出来 = "你的价值在哪?"
> 必须包装成"我**主动构造**" —— 比如:"我发现算法给的数据不贴合用户真实场景,所以我打造了一批用户 Query 数据,经过 PE 处理和人工筛选,真实反映产品使用体验。"

### 1.2 开源评测集的真实样子

老师现场打开了几个开源评测集网站给大家看:

| 评测集                  | 特点                      |
| -------------------- | ----------------------- |
| **CEval**            | 国内最常用的之一,涵盖高等数学、大学化学等学科 |
| **Hugging Face 评测集** | 多家公司的评测集都挂在上面           |
| **MMLU、VMCL** 等      | 不同公司各自维护的评测集            |

**特征观察**:
- 每条题都有 "ground truth"(标准答案 / 唯一答案)
- **可以自动化跑**(直接脚本调模型 → 对比答案 → 得分)
- 评测集会**定期更新**(不是发布完就不管)
- 各家会同时维护**排行榜**(Leaderboard)

### 1.3 面试可能问到的术语

⚠️ 听到 **"x-mark / h-mark / benchmark"** 别懵 —— 意思都是**评测集 / 基础测试 / 技术标准的测试**。问到就当评测集理解就行。

### 1.4 PE 构造评测集的关键点

老师早上提了,下午再次强调:
- **PE 构造能体现你的能力**(简历加分)
- 必须**明确给模型的角色、目标、规则、生成要求**
- 一次给不到细的 → 拆维度逐个问 → 再碰撞合并
- 拿到数据后**仍然要人工筛选**才能成为评测集
- 评测集 ≠ 原始 query,是经过筛选确认的集合

### 1.5 评测集要定期更换的逻辑

**为什么要换?**
```
固定一份评测集 → 模型迭代后可能"针对评测集做优化"(过拟合)
→ 评测结果失真 → 下一次发现不出真问题
```

**怎么换?**
- 把日常做的 SFT / RM 项目里发现的 **bad case** 收集起来 → 直接转为评测集素材
- 这就是为什么平时**复盘 + 收集数据**那么重要 —— 不是仪式,是真有用

**频率参考**:
- 一般 **2-3 个月换一次**
- 不一定全换,**保留好的 + 替换被过拟合的**
- 每个公司的项目场景不同,看实际节奏

### 1.6 评测集质量准确率

> ⚠️ 评测集质量必须达到 **98-100%**,基本上 **100%** 为目标。

逻辑:你出的试卷答案要是错的,等于在用错题考模型 → 整个评测结果完全失真。

## 二、三种评测方法详解

> 上午课讲过基本概念,下午做了完整对比和"怎么选"的判断。

### 2.1 对比法(GSB / SBS)

#### 应用场景
**快速反映模型大方向好坏**,不要求精细量化。

#### 优势 / 局限

| ✅ 优点 | ❌ 缺点 |
|---|---|
| 直观感受 | 主观性强 |
| 简洁高效 | 难以量化(只能排序) |
| 快速识别优劣 | 无法反映细节差异 |

#### 面试话术
> "我们当时的需求是**要快速直观反映打磨机的优劣势**,所以采用 GSB 做快速对比。"

#### GSB 主模型对比规则

⚠️ 跑 GSB **必须有一个主模型**,不是随便比。

实际场景:
- 五个模型时:A vs B、A vs C、B vs C、B vs D、C vs D... 各种组合
- 沟通时要**问清楚是哪个模型作为主模型**

### 2.2 评分法(2/3/4/5 分制)

#### 应用场景
**需要精细量化各维度**,需要灵活性。

#### 优势 / 局限

| ✅ 优点 | ❌ 缺点 |
|---|---|
| 结果可量化 | 成本高(每维度边界都要定义) |
| 覆盖度广 | 培训成本高 |
| 可解释性高 | 项目调整时维度要重做 |
| 灵活性强 | - |

#### 面试话术
> "我们需要**结果可量化 + 知道模型具体短板**,所以采用评分法。"

#### 实际操作要点
- **5 分制最常用**,但具体几分制要看项目
- 每个分值要有**具体 case 锚点**
- **必加"问题备注"列** —— 让标注员说出"为什么打这分"
- 报告时把高分维度标绿,低分维度标红

### 2.3 二值判断法

#### 应用场景
**有明确客观答案**的题型(对/错、是/否、通过/不通过)。

#### 优势 / 局限

| ✅ 优点 | ❌ 缺点 |
|---|---|
| 简单高效 | 无法反映细节差异 |
| 结果明确 | - |
| **可以自动化跑** | - |

#### 自动化的特殊优势
> 二值判断是**唯一适合自动化**的方法。
> 跑通自动化部分 → 节省人工时间 → 剩余主观部分人工评。
> 这种"自动化 + 人工分工"是提高效率的关键。

#### 即使是对错题,仍要做问题备注

> ⚠️ 不管哪种方法,**都要让标注员写问题标签**。

理由:
- 100 条数据全是 "0"(错),你怎么向算法解释错在哪?
- 打了标签后 → 数据透视表归类 → 各类问题占比一目了然
- 这是评测报告的核心证据

### 2.4 混合标注评测法(实际常用)

老师强调:**实际工作中,评测方法不是刚性的**,会**多个方式同时用** —— 这叫**混合标注评测法**。

例子:同一个项目里:
- 大方向用 GSB
- 关键维度用 5 分制
- 客观题用二值判断

> "看你们的需求,需要快速反应又要量化,就设个分值 + 把问题指出来。"

### 2.5 双盲标注评测

复杂场景(类似奖励模型评测)会用**双盲一致性**评测:
- 多人各自标各自的,互不知道
- 评测多人一致性
- **目的:增加置信度**

跟之前学的 Reward Model 三人盲标是一个逻辑。

## 三、BOSS 直聘实地观察:AI 评测岗位行情

> 老师中途让大家直接打开 BOSS 直聘,过滤 AI 评测岗位实地看。

### 3.1 现场调查结论

```
AI 评测岗位占整体 AI 训练师岗位比例:70-80%
→ 这是简历必写的项目
```

### 3.2 岗位常见关键词

老师让大家在 BOSS 里看,每个 JD 几乎都包含:
- 大模型数据构造
- 算法需求沟通
- 图像 / 视频 / VLM 模型生成评测
- 携带优化高要完成内容评估

→ 把这些点对照之前学的就能投递。

### 3.3 推荐方向

| 方向 | 评价 |

| **多模态**(视频 + 音频) | ⭐ 老师强烈推荐,岗位最多 |

## 四、真实规则文档展示

老师展示了大量公司真实的规则文档,这一节信息密度极高。

### 4.1 阿里通用规则文档(图像 + 视频)

#### 整体结构
```
版本信息(时间、人员、版本号)
→ 项目背景
→ 评测目标(模型 + 真实需求 + 满足核心意图)
→ 评分方式(GSB + 评分法 = 混合方式)
→ 通用规则维度
→ 专项规则维度
→ 案例库(正向 + 负向)
```

#### 通用维度(9 个,会持续补充)

| 维度 | 子维度 |
|---|---|
| **安全性** | 价值观、敏感内容、对话策略 |
| **准确性** | OCR 识别错误、推理错误、知识库引用错误 |
| **全面性** | 回答视角缺失、内容缺失 |
| **权威性** | 可信度、是否权威渠道 |
| **时效性** | 是否使用最新信息 |
| **相关性** | 与图片 / 上下文是否相关 |
| **指令遵循** | 是否完成需求、部分还是完整 |
| **内容质量** | 表达、逻辑、格式 |
| **风格化** | 是否欧美化(国内产品需注意) |

### 4.2 美团 Agent 评测规则(早期版本)

#### 评测背景
- 验证 Agent 各项能力水平 + 为下阶段数据生产策略支持
- 评测集:200+ 条
- 拆分:5-6 个评测子集

#### 评测对象
- 美团 150B
- 美团 150B Plus
- GPT-4

#### 评测维度(分级)

| 一级能力 | 二级能力 |
|---|---|
| **工具调用** | 工具调用响应需求、同时调用多工具、上下游工具调用 |
| **参数能力** | 用户参数获取、参数格式、同步结果 |
| **任务规划** | 意图判断、意图识别、记忆能力 |
| **指令遵循** | 礼貌结束对话、对话风格 |

老师建议:**写 Agent 简历前去用一下市面上 Agent**(小美 / 飞猪 / 旅游 Agent),反向拆需求点会更清楚。

### 4.3 知谱多模态文生图评测(卢老师项目)

#### 评测维度(P0 / P1 优先级)

| 优先级 | 维度 |
|---|---|
| **P0(出问题直接判负)** | 安全红线、图文一致性、价值观 |
| **P1** | 图片质量、内容创造、欧美化、生成效率 |

#### 评测对象
清扬、豆包、即梦、文心 → 横向对比文生图能力

#### 评测维度细节
- **基础体验**:结果与用户是否匹配、按需求生成、图文一致性
- **产品体验**:生成效率(简单 vs 复杂场景)、稳定性
- **画面质量**:色彩、清晰度、构图、人物美观度、风格

### 4.4 视频评测规则(阿里 / 快手)

老师展示了视频生成的完整规则:

#### 一级维度
1. **指令遵循**(分四种)
   - 镜头指令
   - 主体指令
   - 动作指令
   - 场景指令

2. **崩坏**(视频专属!)
   - 画面畸形
   - 主体崩坏
   - 透视图崩坏
   - 动作崩坏
   - 背景斜歪
   - 主体一致性破坏

3. **因果常识**
   - 物理规律
   - 自然规律(转身但头没转 = 违反)
   - 时空连续性
   - 应用增雄

4. **美学表现**
   - 真实流畅度
   - 静态美学
   - 动态美学
   - **镜头叙事**(高级维度)
     - 镜头场景下进军变化
     - 推动故事发展
     - 用镜头讲故事
     - 优秀短信亲密度

5. **音效配音**
   - 动作幅度(过慢、过小、坚硬)
   - 音画不同步
   - 异常音爆
   - 配音质量(节奏感异常、语调怪异、音量异常)
   - 说话主体错误(A 角色台词 B 在说)
   - 音色不符(女声变男、儿童变成年)

6. **皮肤真实感**(剧情类很关键)

#### 关键提醒

> ⭐ 面试时**面试官会让你描述一张图 / 视频** —— 当场用你写的维度去说。
> 比如:"色彩范围(暖色调/冷色调)是什么?构图怎么样?"
> 你要能现场说出来。

**怎么练?**
1. 把一张图 + 你的规则丢给大模型
2. 让它**根据规则匹配内容**
3. **反向学习模型怎么描述的**
4. 自己练习几次

### 4.5 搜狗输入法 AI 润色评测(土味情话案例)

老师在腾讯做过的真实案例:
- 一条 prompt → 5-6 个答案
- 每个答案做维度碰撞 → 风格碰撞(土味情话 vs 高级感)
- 后面还有 6 条追问("豆包下方的 3 条提示问")
- **每条数据要看 18 条**(6 答案 × 3 追问)

#### 难点
- 当时规则定义是别人写的,**边界不清**
- 土味情话和某种风格分不开
- "两个风格一起用"是最大坑

#### 教训
- **不要太较真**,做这种又长又细的工作时要会偷
- 太认真反而被领导觉得"效率低"
- 一个人 40 个数据 / 天的人效已经够辛苦

### 4.6 豆包 AI 眼镜 · 随手记记忆库项目

最新项目展示。

#### 项目背景(老师让大家学怎么写背景)
```
眼镜的随手记功能 —— 豆包根据用户要求记录内容,存到用户信息的记忆库
记录类型:随手记、会议纪要、日程提醒、环境纪要
需要在用户需要时,帮用户提供信息
```

#### 评测维度(增删改查 + 上下文)

| 触发类型 | 含义 |
|---|---|
| **增** | 用户与 AI 眼镜交互,豆包触发随手记功能(记录) |
| **删** | 删除记忆库内容 |
| **改** | 修改记忆库内容 |
| **查** | 查询记忆库内容(随手记 / 会议纪要 / 日程提醒 / 环境纪要) |

#### 标注流程
1. 看 prompt + 图片 + 图文 + 搜索结果 + response
2. 判断用户想要什么 / AI 应该做什么
3. 结合给的标签明确大类场景
4. 选构造类型(单向 / 表格匹配)
5. 对照定义最终选择

### 4.7 文搜图 / 图搜文 / 多跳搜索

老师展示了搜索类评测规则:

| 维度 | 说明 |
|---|---|
| **单跳搜索** | 一次搜索完成(专业词汇等) |
| **多跳搜索** | 多次搜索 / 文搜切换到图搜 / 图搜切换到文搜 |
| **图多框** | 多种结构 |

**判断标准**:
- 是否两网必联(联网 + 本地)
- 时效性要求
- 是否包含隐含的时效标签

### 4.8 关键学习点

老师对所有规则文档展示的总结:

> **真实公司规则文档远比上课讲的细**
> 上课的版本是"简化版,方便理解,降低压力"
> 实际工作中要把每个维度细化、定义边界、附 case

**面试时的实战标准**:
- 维度上能说出 **3-5 个**
- 二级维度细则能说清
- 必要时拿一张图当场讲

## 五、刁钻面试题:多任务并行管理

老师抛出实战问题:**"如果多任务并行,你怎么处理?"**

### 5.1 标准回答路径(从轻到重)

```
1. 先看两个任务的紧急度 → 不都急 → 各自排期就行
        ↓
2. 都急 → 把两个需求方拉到一起讨论 → 让他们自己定优先级
        ↓
3. 讨论不出来还要做 → 找老大要人手 / 支援
        ↓
4. 要不到人 → 加班 / 加磅
        ↓
5. 加班也完不成 → 跟业务方协商任务延期
        ↓
6. 延期不接受 → 拒做一个,做另一个,明确表态
```

### 5.2 加班政策对比(老师真实经历)

| 公司 | 加班政策 |
|---|---|
| **腾讯**(大模型部门) | 加满 4 小时才算加班费,前 2 小时白干 |
| **阿里** | 相对好,15K 起,外包也能 25K |
| **字节** | 相对好 |

> "腾讯不要看他有钱 —— 钱给了赚钱部门,大模型部门给的不多,大模型才到 1-8K。"

### 5.3 管理者的核心目标

> ⭐ **管理的唯一目的:高质量交付项目**

老师反复说:
- **过程不重要,以结果为主**
- 任何手段只要能解决问题都行
- 末位淘汰、绩效不合格 → 都可以
- "合理即可"是评判标准

### 5.4 写简历时的体现

**别写"管理 5 个人"** —— 那不叫管理经验。

| 人数 | 评价 |
|---|---|
| 5 人 | 没经验,"五个人能有什么经验?" |
| **20+ 人** | 才算有管理经验 |
| 50+ 人 | 优秀 |
| 100+ 人 | 老师推荐的"刘品师兄"级别 |

**没经验怎么办?**
- 想象班主任怎么管 50-60 个学生 —— 分组管理
- 想象部队 100 人 → 分排 → 排里分班 → 班长指挥
- **分层管理 + 抓核心负责人** = 标准方案

## 六、评测报告完整结构

### 6.1 标准 5 大模块

```
1. 评测信息(任务/模型版本/数据量/人员)
2. 评分标准
3. 评测结果(GSB + 评分统计)
4. 核心结论(+ 优化方向)
5. bad case(典型案例集)
```

### 6.2 顺序优化建议

老师建议(实际工作经验):

| 优先级 | 内容 |
|---|---|
| 1️⃣ 最前面 | **数据统计 + 评测结果**(老板最想看的) |
| 2️⃣ 紧接着 | **核心结论 + 优化方向** |
| 3️⃣ 后面 | 评分标准、bad case 细节 |

理由:
- 评分标准不是报告重点,可以放后面
- 老板**翻开第一页要直接看到结论**
- bad case 是证据,放在后面支撑前面结论

### 6.3 必要图表

老师吐槽现在很多报告**只有文字、没有图**。该加的:
- 透视图
- 折线图(趋势)
- 各种维度占比的扇形图
- 数据透视表

### 6.4 报告里 case 的两大作用

```
1. 提高你报告的置信度 → 证明"这是有依据的判断"
2. 给算法做优化方向 → 下一次模型迭代根据这些 case 改
```

### 6.5 减量评测(简化版)

> 不是每次评测都要写大报告。

#### 适用场景
- 时间紧
- 老板着急看结果
- 数据量很小
- 临时性评测

#### 简化做法
```
今天做完休息一下
→ 简简单单查出结果
→ bad case 直接分析
→ 几句话总结
```

**先给数据 + 简单结论 → 详细报告第二天产出**,这是个**留有余地**的好方法。

### 6.6 美观度也是评测能力

老师强调:**输出文档的美观度 = 公司印象 = 升职机会**。

> "你输出的文档好,老大对你的印象就好。他会以你的这个标准做模板儿 —— 你就会成为一个核心员工。涉及到升职转正都会考虑到。"

## 七、评测后的算法挑战环节

> ⚠️ 写完报告**不是结束**。真正的考验在算法那关。

### 7.1 完整交付链

```
写完报告
→ 跟自己的老大讲(过自己人这关)
→ 跟需求方讲(过业务这关)
→ 跟算法讲(最难!)
```

### 7.2 算法会针对性挑战你

#### 挑战 1:针对评测里的"判错"
- "为什么这条数据你判错?"
- 你要能立刻解释每个 case 的判断逻辑

#### 挑战 2:从全部标注数据中挑刺
- ⚠️ 算法**不仅看这次报告**,还会去你**全部历史标注**里找问题
- 如果其中一条数据是某个同学瞎打的 → 突然问到你 → 你说不出来 → 死

#### 挑战 3:规则变动的争议
- 规则文档可能改过很多版
- 算法说"上次说的是 A" → 你改成 B 没留痕 → 他不承认
- 你背锅

### 7.3 防御 = 留痕!

> ⭐ **核心原则:开会录屏、文字记录、文档每版留底**

具体做法:
- **每次评测都输出一份规则文档**(可以叠加版本号)
- **开会录屏**(尤其是规则讨论会)
- **任何沟通都用文字**,不要打电话
- **大群通知 + 重要事项 @ 老板**(让他知道)

### 7.4 案例的双重作用

老师反复强调:bad case 是**保命符**。
- 算法质问 → 你拿出 case 当证据
- 算法做优化 → 你拿出 case 当方向

**所以不要懒得做 case 备注**,这是你日后的护身符。

## 十二、面试金句速查

### 12.1 评测整体流程

> "评测的话,我们会接到算法的需求,然后讨论制定规则维度,做全流程管理,最后由我做数据分析,出评测报告,分析模型优缺点。"

### 12.2 规则维度

> "我们之前主要做图像理解方向,做评测的时候,采用的是**打分 + GSB** 的混合方式。
> 通用维度有 1234,专项维度有 ABCD..."

### 12.3 评测对象类型

> "我们对比的是上下滑板 + 向上向下滑板,也做过竞品对比。"
> (能说出**版本对比 / 竞品对比 / 功能开关对比**三类即可)

### 12.4 评测报告内容

> "我们的评测报告包含:评测信息、评测结果、核心结论 + 优化方向、bad case。
> 评分标准我们放在后面,因为老板最想看的是结果。"

### 12.5 评测集来源

❌ 别说:"算法给我们的数据"
✅ 该说:"我发现算法给的数据**不够贴合真实场景**,所以我打造了一批用户 Query 数据 + 用 PE 提效构建评测集,经过筛选反映产品真实体验。"

### 12.6 数据量

❌ 别说:"评测数据上万条"
✅ 该说:"评测数据 **200-800 条**,因为评测要求小而精,准确率必须 99-100%"

### 12.7 选 GSB 的原因

> "我们当时**需要快速反映模型的优劣势大方向**,所以采用 GSB。"

### 12.8 选评分法的原因

> "我们需要**结果可量化 + 灵活分析模型短板**,所以用 5 分制评分法。"

### 12.9 项目时间起点

> "项目周期是从**算法交付数据那一天**起 5 天"(而不是开会那一天)

### 12.10 PE 构造能力

> "我会用 PE 自动化提效流程,把人工 1 天的活提到半天,这样我们一周能多做 200 条评测。"

### 12.11 通用维度优化

> "我在公司期间会**收集每期项目的通用维度**,制成通用规则文档。
> 这样下次新项目能快速对齐,标注同学也能直接复用。"

### 12.12 bad case 多种用途

> "bad case 至少有 5 个用途:作为评测集 + 加入规则文档 + 报告证据 + 培训 + 算法优化方向。"

### Q1:PE 构造评测集时,算法不给数据怎么办?(22:51)

**同学提问**:"评测集来源里说'打捞用户 query'和 'PE 构建',具体是怎么操作的?"

**老师回答**:

```
1. 第一步:跟算法提需求,让他给一批数据
2. 算法不给 → 找你领导反映
3. 自己用 PE 构建时,需求要提前沟通:
   "上一次用了算法的数据,反馈不能明显反映出模型能力,所以这次自己构造"
4. 你要主动说原因 —— 找借口、找理由
```

**为什么这么做?**
- 面试官会问"为什么用 PE 构建而不是算法数据?"
- 答案模板:"我们要保证模型质量好,实际效果和全面性,所以构造不同类别的问题。
  让算法跑成本高,且配合度低,所以我们自己来构造。"

> ⭐ 老师强调:"都是找借口,找这个理由。"
> 翻译:面试讲故事,要把"算法不配合"包装成"我主动推进"。

### Q2:质检要抽 10-30% 还是 100%?(02:45:27)

**同学提问**:"评测的质检是不是和标注一样抽 10-30%?"

**老师回答**:**评测必须 100%**。

理由:
- 标注数据量大,所以抽样
- 评测数据量小(只有 200-800 条),抽样意义不大
- 数据量小 + 准确率要求高(99-100%)→ 必须全检

### Q3:质检是边标边检还是标完再检?(02:46-02:47)

**同学提问**:不太理解什么时机做质检。

**老师回答**:

| 时机 | 适用场景 |
|---|---|
| **边标边检**(主流) | 标几条质检就开始介入,出问题立即让标注员改 |
| **标完整体检** | 项目流程不允许 / 同一批人继续做其他项目 |

#### 为什么"边标边检"更好
- 发现问题能**及时解决**
- 不然等做完之后,标注员都去做其他项目了 → 没人回头改
- 提前发现 = 节省时间成本

#### 真实经验
> "一般我们做的时候,基本上标个五六条的时候,质检就开始进行验收了。"

#### 没有固定模式
> "这个没有固定的档,两个方式都可以。你说怎么合理就行 —— 都行。"

### Q4:质检"改"的到底是什么?(02:48 — 容易混淆!)

**同学提问**:"质检的目的是改'标注员标错的结果'。但评测是评估模型好坏 —— 怎么能改模型的输出呢?"

**老师明确澄清**:

```
质检改的是:标注员判错了 → 比如某条数据应该判 5 分,他给了 3 分 → 改成 5 分
质检不改的是:模型的输出本身 → 试卷的答案是模型给的,不能改

类比:
评测 = 一场考试
模型输出 = 考生答案(模型生成的内容)
标注员评分 = 老师阅卷
质检 = 复核老师有没有判错(改的是老师,不是改考生答案)
```

> ⭐ 老师原话:"结果改了,结果不就是说试卷就变了。" → 永远不能动模型输出。

### Q5:PPT 案例的规则文档能复用到评测吗?(02:34:27)

**同学提问**:"咱们下午播放的这个案例,是属于这个评测里边的规则文档吗?"

**老师回答**:

```
✅ 不管是评测还是标注,规则文档的维度都可以参考通用
✅ 但具体使用时要根据需求改:
   - 标注的规则文档可能更全
   - 评测可能只用其中部分维度
   - 大方向类似,具体维度看需求调
```

#### 实操建议

> "比如刚刚发了一个 PPT,那你要做 PPT 的评测,就去看那些规则维度。"

→ **任何公司的真实规则文档都是好教材,关键是理解维度该细到什么程度**。

### Q6:评测的 bad case 和 SFT 的 bad case 有什么区别?(03:08)

> 这是课程最后一位同学的问题,关于"两种 bad case 是不是一回事"。

**同学提问**:"评测里面的 bad case,跟之前做 SFT 那种标注的 bad case 怎么区分?"

**老师回答**:

| 维度 | SFT 标注的 bad case | 评测的 bad case |
|---|---|---|
| **目的** | 找出好的 case,改写 / 优化数据 | 找出不好的 case,评估模型能力 |
| **结果用途** | 给模型重训学习 | 给算法看模型短板 → 下一次优化方向 |
| **规则维度** | 可能不同(SFT 看数据质量) | 可能不同(评测看模型表现) |
| **共同点** | 实际上反映的"问题点"差不太多 | 同上 |

> ⭐ 老师原话:"你感觉两个意思一样,但是目的不同、结果不同。"

**核心理解**:
- SFT 的 bad case → 改 / 优化数据本身
- 评测的 bad case → 不改数据,而是**告诉算法模型在这类问题上不行**

### Q7:评测方法要不要跟算法讨论决定?(02:42)

**同学提问**:"评测方法确定的时候,需不需要跟算法讨论?"

**老师回答**:

```
方法不用装(不需要刻意挑) —— 方法稳定就好
但有时候算法会要求"必须用 GSB 做分析" → 用他要求的就行
算法不要求时 → 你自己说"我们采用 GSB" 即可
```

**核心**:**评测方法以达到效果为准,不是政治正确**。

### B1:"卢老师从质朴转正"的真实原因

> 老师边讲规则文档边讲了卢老师的故事。

```
质朴的同事都觉得卢老师爱迟到,工作态度有问题
但他通过 web coding 写自动化工具,把"图片下载 + 表格匹配"这类
重复枯燥的工作大幅提效
他老大看到效果 → 不在乎迟到,直接转正
```

**启示**:
> "迟到不是问题,关键是你做事有能力。"
> 提效流程做出来 → 给老大汇报 → 认可度直接拉满

### B2:为什么训练师"卧底公司"传承机制重要

老师比喻这个机构是个"卧底公司":
- 每一批学员进了大厂(阿里 / 字节 / 腾讯)
- **再把内部规则文档传回来给下一批**
- 形成传承
- "你们现在能看到的,都是上一批传出来的"

→ 这就是为什么老师的真实文档不能外传 —— 一旦传出去,下一批就拿不到了。

### B3:阿里有"招聘 SOP"的有趣发现

老师当时在阿里有招聘权限时发现:

```
招聘平台上每个外包公司都会给候选人打标签:
"211 毕业 + 2 年标注经验 + 喜爱大模型近 X 年"
→ 你的简历会被打上这些标签
→ 直接影响推荐
```

**启示**:
- 简历里**主动用这些关键词** = 自动加标签 = 推荐概率高
- 千万别说"我不喜欢标注 / 不喜欢加班"→ 直接被拒
- "情绪激起 = 必拒"
