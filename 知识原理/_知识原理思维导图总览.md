## A. AI 训练师课程主线（按时间线）

### A2. 模型训练原理（2026-05-02 / 05-03，**修订版**）—— 理论核心
- 学习地图：**基础层（预训练+后训练） → 增强层（Agent/RAG/CoT） → 落地层**
- 全景三层架构图
  - 基础层 = 预训练 + 后训练（SFT / RLHF）
  - 增强层 = RAG / Agent / CoT（推理时加挂，不改参数）
  - ⚠️ 易错点：RAG/Agent/CoT 既有"训练时项目"又有"推理时系统"
- 预训练（Pre-training）
  - 海量数据 + 无监督学习 → Base Model
  - 五大必背概念
    - **涌现** Emergence：质变点不可预测，与参数量强相关
    - **参数** Parameters：长期记忆+技能（≠KV Cache）
    - **Scaling Law**：性能与"参数×数据×算力"的可预测幂律
      - 边际效应六大根因：数据见顶 / Chinchilla / 知识幂律 / 架构上限 / 经济不划算 / 评估饱和
    - **幻觉** Hallucination：数据错误 / 数据缺失硬编 / Token 链式传播
    - **过拟合 vs 欠拟合**：书呆子 vs 大傻子，训练师靠提质+多样性对抗
- 后训练（Post-training）
  - SFT（有监督微调）
    - 单轮问答
    - 多轮问答
    - CoT 项目
    - Agent 项目
    - RAG 项目
  - RLHF（人类反馈强化学习）
    - 训练 Reward Model
    - 用 RM 给主模型打分
- SFT 单轮的四大维度（必背）
  - 安全 → 指令遵循 → 内容 → 语言
- 训练师全流程 11 大类核心 Indicator
  - 需求承接 / 试标 / 正式标注 / 质检 / 训练后 / 复盘
  - 关键指标：抽检通过率 / 三人一致率 / IFEval / Arena Elo
- PE vs CE
  - PE = 调一句话激活能力
  - CE = 管整个上下文窗口的信息组装
  - Cursor / Claude Code 都是 CE 系统
- 详见 [[知识原理/AI 训练师课程笔记(2026年5月2-3日)· 修订完整版]] 与原版 [[知识原理/AI 训练师课程笔记(2026年5月2日)]]

### A3. 五大项目实操（2026-05-03 下午）—— 落地手感
- Reward Model 项目
  - 数据结构：1 prompt + N response + 三人盲标排序
  - 排序方法：两两对比擂台赛
  - 三人盲标：1 主观 / 2 打架 / **3 平衡** / 5 浪费
  - 优先级：**响应需求 > 事实正确 > 基础质量**
- CoT（思维链）项目
  - 痛点引子：strawberry 几个 R / 9.11 vs 9.9
  - 慢思考 vs 快思考
  - 三种实现：Prompt 工程 / SFT / 强化学习
  - 历史时间线：2022 谷歌提出 → 2024.9 OpenAI o1 → 2025.1 DeepSeek R1（公开技术）
  - DeepSeek R1 完整训练流程：V3 → SFT-1 → RL-1 → SFT-2 → RL-2 → R1
  - 标注 5 步法：判 prompt → 评 think → 改 think → 评 response → 改 response
  - think 五维：需求理解 / 推理完善 / 推理合理 / 信息量 / 惊喜（有效反思）
  - 有效反思 vs 无效反思：判断核心 = 有无重复 + 结论是否正确
  - 鱼缸玻璃实战案例
- Agent 项目
  - **Agent = 大模型 + 工具调用 = 野生小秘书**
  - 三大核心：Planning（规划）+ Memory（记忆）+ Tools（工具）
  - 数据结构：think + action 交替
  - 角色定义 + 标准运行规则（每个 Agent 都有）
  - 第一铁律：**信息真实性**（不能擅自构造用户没说的信息）
  - 实战：会议室预定改写
  - JSON 格式校验是最后一步
- RAG（检索增强生成）项目
  - **RAG = 给模型外挂知识库**
  - 在线 RAG（联网） vs 离线 RAG（本地知识库）
  - 四大动机：解决幻觉 / 专业领域 / 时效性 / 可解释溯源
  - 完整流程：Chunking → Embedding → 向量数据库 → Top-K 召回 → 增强 prompt → 生成
  - 数据结构：prompt + references + response
  - 三层评估：prompt 维度 / 材料维度 / 回答维度
  - ⚠️ 面试雷区："RAG 是我搭建的" → 错；正确："我做过 RAG 项目"
- 单轮 / 多轮 SFT
  - 多轮特有三维：指代理解 / 上下文一致 / 避免重复摘抄
- 详见 [[知识原理/AI 训练师项目实操笔记(2026年5月3日下午)]]

### A4. 模型评测专题（2026-05-10 上午）—— 项目类型 ≠ 训练
- 训练 vs 评测的本质区别
  - 训练 = 提供学习材料，量级万 +
  - 评测 = 出考试卷考核模型，量级 **200-800 条**
  - ⚠️ 简历踩坑："评测数据量上万条" = 完全不专业
- 评测时间点：模型上线前（出厂检测）+ 上线后（用户反馈）
- 三大类别：生成 / 理解 / 功能性
- 完整工作流（比训练多一步）
  - 需求承接 → 规则 → 试标 → 标注 → 质检 → **评测报告**
- 评测集
  - 三大要求：陌生 + 多维度 + 难易度搭配
  - 四大来源：用户 query / 开源 / Prompt 构造 / 算法提供（**面试别说**）
  - 必须定期更换（防过拟合到评测集）
- 评测三种方法
  - 对比法：GSB（三档） / SBS（五档），公式 (G + S/2)/总数
  - 评分法：5 分制最常用，必加"问题备注"列
  - 二值判断法：对/错二选一
- 高危维度：**准确性 + 安全性**（任一失败直接判负）
- 评测对象 3 类：竞品 / 同模型版本 / 同模型功能开关
- 准确率要求：99%-100%（远高于训练的 95%）
- 自动化能不能做：**大部分不能**，仅"对错明确"题型可以
- 评测报告交付链：老大 → 需求方 → **算法（最难关）**
- 详见 [[知识原理/AI 训练师课程笔记 · 模型评测专题(2026年5月10日上午)]]

## B. 大模型基础原理（独立技术文档）

### B1. 基础概念：上下文、Token、KV Cache、层
- 上下文长度
  - 模型决定上限（位置编码：RoPE / ALiBi / NoPE）
  - 硬件决定实际能用（KV Cache 显存占用）
  - 公式：**上下文上限 = min(模型 max_position, 显存能容纳的 KV Cache)**
- Token
  - 子词级最小单位
  - 1 token ≈ 0.75 英文词 ≈ 0.5-1 汉字
- Token 生成速度
  - 由显存带宽决定上限（不是算力）
- KV Cache
  - 注意力机制中的中间结果
  - 长对话累积 → 显存吃紧
- Transformer 的"层"
  - 深度 vs 宽度的权衡
- 谁在保存对话：客户端记忆 vs API 无状态
- 详见 [[知识原理/大模型基础概念笔记：上下文、Token、KV Cache 与层]]

### B2. Loss 与模型评价完全指南
- Loss 是什么
  - 模型答得有多烂的扣分值
  - 必须是连续值，不是对/错
- 常见 Loss：MSE（回归） / Cross-Entropy（分类，LLM 用）
- Train / Val / Test Loss 三兄弟
  - 学过的 / 没学过的 / 期末
- 健康判断
  - Train↑ Val↑ = 欠拟合
  - Train↓ Val↓ = 健康
  - Train↓ Val↑ = **过拟合**
- LLM 圈更常用：Perplexity（困惑度）
- Benchmark 体系
  - 通识：MMLU、MMLU-Pro、GPQA、C-Eval
  - 数学：GSM8K、MATH、AIME
  - 代码：HumanEval、SWE-Bench、LiveCodeBench
  - 长上下文：Needle in a Haystack、LongBench
  - 指令遵循：IFEval、MT-Bench
  - 安全：TruthfulQA、JailbreakBench
  - 多模态：MMMU、MathVista
  - 主观：Chatbot Arena Elo、SuperCLUE
- 业内共识：**Benchmark 是门槛，Arena 是真实**
- 训练师汇报话术升级：从"标了多少条"到"benchmark 提升幅度"
- 详见 [[知识原理/Loss 概念与模型评价完全指南 — AI 训练师视角]]

### B3. MoE 与现代 LLM 架构创新
- 稠密 vs MoE 的本质区别
  - 稠密：全部参数参与计算
  - MoE：只激活部分专家
- MoE 八大特性（按重要性）
  - ① 稀疏激活 = 大模型速度+小模型成本（**最核心**，offload 只是副产品）
  - ② 专家分工 / 涌现专业化（类比人脑功能分区）
  - ③ 容量扩展 = 解锁万亿级知识（DeepSeek V3 671B/激活 37B）
  - ④ 路由器 Router = MoE 灵魂
  - ⑤-⑧（详见原文）
- 万亿俱乐部：DeepSeek V4-Pro 1.6T、Kimi K2 ~1T
- 行业共识：**未来所有顶级模型都会是 MoE**
- 详见 [[知识原理/MoE与现代LLM架构创新]]

## C. 硬件与部署

### C1. GPU 七大维度对 LLM 的影响
- 推理重要性排序
  - ① 显存容量（能不能跑）
  - ② 显存带宽（聊天有多快）
  - ③ 算力（prompt 处理速度+并发）
  - ④ 精度支持
  - ⑤ 缓存大小
  - ⑥ PCIe 通道
  - ⑦ 互联带宽
- 一句话直觉：算力 = 眼睛读字速度 / 带宽 = 拿书页速度 / 显存 = 桌子大小
- 显存够不够公式：模型权重 × 1.2 + 上下文长度 × 0.0001 × 模型大小
- 真实硬件对照：4070 / 4090 / 5090 / H100
- 详见 [[知识原理/GPU 维度对大模型的影响完全指南]]

### C2. 大模型推理资源占用与 CPU/GPU 分工
- 三阶段拆解
  - 模型加载阶段（SSD → 内存 → 显存）
  - Prompt 处理阶段（**算力密集**）
  - Token 生成阶段（**带宽密集**）
- CPU 卸载场景的工作流
- 为什么 LLM 推理永远离不开 CPU
- 让 CPU 接近"零参与"的最佳实践
- 详见 [[知识原理/大模型推理资源占用与 CPU和GPU 分工详解]]

## D. Agent / Tooling 方向

### D1. Agent 七层架构通关手册（理论核心）
- 起点公式的演化
  - v1：Agent = LLM + 工具调用
  - v2：+ 调度循环
  - v3：+ 区分思想 vs 执行
  - v4：完整七层架构
- 七层架构（必背）
  - ① 入口/接口层
  - ② **上下文组装层 ★**（system prompt + 历史 + 工具列表 + skill 目录 + memory）
  - ③ LLM 推理引擎（这一层才是 LLM 干的活）
  - ④ 输出解析层（parser，hermes/openai/qwen 格式）
  - ⑤ 工具调度层
  - ⑥ 工具执行层
  - ⑦ 结果回喂层 → 循环回 ②
- 边界判断：**有副作用 = Agent，无副作用 = LLM**
- 工具的四种来源
  - 内置 / MCP Server / Function Calling / CLI（最强权限）
- Skill ≠ 工具
  - 工具 = 手脚（真能干活）
  - Skill = 师父笔记（按需加载的指引）
  - LLM = 工人（看笔记+拿工具）
- MCP（Model Context Protocol）
  - 类比：MCP 之于 Agent ≈ HTTP 之于浏览器
  - 三代演进：全量加载 → tool_search 懒加载 → 跨仓库发现
- 搜不到工具的四层兜底：CLI/bash → 写脚本调 API → search_mcp_registry → 诚实拒答
- System prompt 是 LLM API 层概念，不是 Agent 概念
- 概念分层全图：LLM 内部 → API 层 → Agent 框架层 → 协议层（MCP）
- 评估 Agent 的硬功夫：**分层定位**（思考层/协议层/执行层 bug 修法完全不同）
- 补充概念：Context Engineering / ReAct / Lost in the Middle / Memory / Few-shot / KV Cache
- 详见 [[知识原理/Agent 架构通关手册 — 从一个公式聊到七层结构]]

### D2. Cursor Agent 实战：音频转文字
- 任务背景：M4A 长录音转带时间轴文字（Windows + 仅 CPU）
- 整体流程
  - 摸清环境 → 装 FFmpeg → 选 ASR（faster-whisper）→ 看时长 → 跑脚本 → 交付
- 关键决策（取舍点）

  - VAD：True（跳长静音）

- 与通义听悟对比
  - 本地 Agent 方案：可复现 / 可定制 / 隐私 / 零 API 费用
  - 商业产品：一站式 / 中文优化 / 增值功能
- 详见 [[知识原理/Agent 如何帮你处理任务——以 Cursor 处理「音频转文字」为例]]

## E. 安全方向

### E1. LLM 安全：Prompt Injection 与 AI 投毒
- Prompt Injection（提示词注入）
  - 根本原因：LLM 架构上无法区分"开发者意图"和"外部内容"
  - 与 SQL 注入的本质区别：SQL 可参数化彻底解决，LLM 目前没有等价方案
- 注入两种形态
  - 直接注入：用户输入里直接覆盖 system prompt
  - 间接注入（更危险）：恶意指令藏在网页/文档/邮件里
    - 受害者本人没做错任何事
    - Agent 场景下可触发自动化工具调用
- 危害分级：聊天机器人 → Agent
- 公开记录的攻击事件
- AI 投毒（LLM Grooming）：把训练数据当战场
- Pravda 网络案例
- 现有缓解措施都不完美
  - RLHF / 输入过滤 / 角色分离 / 输出沙箱化 / Spotlighting / 双 LLM 审计
- 详见 [[LLM 安全：Prompt Injection 与 AI 投毒]]
