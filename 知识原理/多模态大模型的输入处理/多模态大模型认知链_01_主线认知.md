## 1. 起点:多模态的统一原则

### 1.1 一个朴素的问题

最开始问的是:**"向模型传文字、图片、音频、视频之后,模型内部会发生什么?这些信息模型如何读懂?"**

答案的核心只有一句话:

> **所有模态最终都要变成"和文本 Token 同一空间的向量",模型内部根本分不清你给的是字、是图、是声音。**

### 1.2 万物皆向量

不管输入是什么模态,Transformer 内部能处理的**只有一种东西**:

```
一串向量 → 多层 Self-Attention 与 FFN(Feed-Forward Network) → 输出下一个向量
```

所以多模态的关键工程问题是:

> **怎么把图片/音频/视频,变成"一串向量",并且让这串向量"长得像"文本 Token 经过 Embedding 之后的样子?**

这个过程叫 **Embedding(嵌入)**,或更专业一点叫 **Encoding(编码)+ Alignment(对齐)**。

### 1.3 "同一空间"是什么意思

文本走完 Tokenizer + Embedding 之后,每个 Token 变成一个**固定维度**的向量(比如 4096 维)。模型内部跑的就是这些向量。

多模态模型做的事是:

```
图片  → Vision Encoder(视觉编码器)  → 一堆 4096 维向量
音频  → Audio Encoder(音频编码器)   → 一堆 4096 维向量
视频  → Video Encoder(视频编码器)   → 一堆 4096 维向量
文本  → Tokenizer + Embedding       → 一堆 4096 维向量
```

注意维度都是 **4096**(举例数,实际数字取决于 LLM 的 `hidden_size`——见第 9 章)。这些向量被**拼接成一个长序列**,然后整体喂给 LLM(Large Language Model)。

模型从此刻开始**不再区分这些向量原本是什么模态**——对它来说全是"Token"。

```
[文本Token, 文本Token, <图片向量×256>, 文本Token, <音频向量×128>, 文本Token, ...]
                            ↑                          ↑
                  这两段在模型看来跟普通 Token 没区别
```

### 1.4 四模态的预处理路径

```
文字 → Tokenizer → Token ID → Embedding 查表 → 向量
图片 → 切 patch → ViT → Projector → 向量
语音 → Mel-Spectrogram → Whisper Encoder → Projector → 向量
音乐 → Mel-Spectrogram → Music Encoder → Projector → 向量
视频 → 抽帧 → ViT × N + 时序模块 → Projector → 向量
其他 → 专用 Encoder → Projector → 向量
                            ↑
                  这一步是多模态训练的核心
                  各模态最终都汇合在 LLM 的同一向量空间里
```

### 1.5 各模态简介

**文字**(回顾,你笔记《大模型基础概念》里讲过):

```
"今天天气真好"
   ↓ Tokenizer(分词器)
[Token ID: 1234, 5678, 9012]
   ↓ Embedding 查表
[向量1, 向量2, 向量3]
```

**图片**(后面第 11 章详细展开):

- 一张 1024×1024 图切成 14×14 像素的 patch,得到 5329 个 patch
- 每个 patch 经过 ViT 多层 Transformer 加工,融合全图上下文
- Projector 把 ViT 输出投影到 LLM 的向量空间
- 工程上会用 Q-Former / Perceiver Resampler 压缩到 64-256 个 token

**音频**:

```
原始波形(1秒 16000 个采样点)
   ↓ 短时傅里叶变换(STFT) → 转梅尔刻度
梅尔频谱图(Mel-Spectrogram,80 维 × N 帧的"图")
   ↓ Whisper Encoder(32 层 Transformer)
1500 个向量(30 秒音频)
   ↓ Projector
LLM Token 空间
```

**关键转换**:音频从一维时间信号变成"图"(频谱图)之后,处理逻辑就跟图片差不多。

**语音 vs 音乐的差异**:

| 维度 | 语音(说话) | 音乐 |
|---|---|---|
| **关注什么** | 语义内容、说话人、情绪 | 旋律、节奏、和声、音色 |
| **采样率** | 16 kHz(人声够) | 44.1 kHz / 48 kHz |
| **主流模型** | Whisper、Qwen-Audio | MusicGen、Jukebox |

**还有一条捷径**:很多场景直接用 Whisper 把音频转成文字再喂 LLM(ASR + LLM 流水线)——便宜够用但损失语调和情绪。完整的多模态语音才是真把音频向量直接塞进 LLM。

**视频**:

```
原视频(30fps, 2分钟)
   ↓ 抽帧(1fps 或 2fps,别每帧都算)
120 帧图片
   ↓ 每帧过 Vision Encoder
120 × 256 = 30720 个 patch token
   ↓ 时序压缩(Temporal Pooling 或 Q-Former)
压缩到几百到几千个 token
   ↓ Projector + 时间位置编码
LLM Token 空间
```

视频里的音频走音频路径,最后跟视觉 token **拼进同一个序列**。

### 1.6 其他模态:思路一致,换 Encoder 即可

| 模态 | Encoder | 输出 |
|---|---|---|
| 代码 | 同文本 Tokenizer,词表里加代码符号 | Token 向量 |
| 表格/结构化数据 | 拍平成文本,或专用编码器(如 TaPas) | Token 向量 |
| 3D 点云(自动驾驶) | PointNet / Point-Transformer | 点 Token 向量 |
| 传感器时序信号(IoT) | 1D CNN + Transformer | 时序向量 |
| 蛋白质序列(AlphaFold) | 氨基酸 Tokenizer + Evoformer | 残基向量 |
| 脑电 EEG | 1D CNN + Transformer | 时序向量 |

**通用范式**:
```
任何模态 → 专用 Encoder → 一串向量 → Projector(对齐) → 进 LLM
```

### 1.7 五个必背陌生词

| 词 | 全称 | 含义 |
|---|---|---|
| **ViT** | Vision Transformer | 把图片当 token 序列处理的 Transformer |
| **Patch** | 图块 | 图片切成的小方块,每块当一个 token |
| **Projector / Adapter** | 投影器 / 适配器 | 把 Encoder 输出投到 LLM token 空间的小 MLP,多模态对齐的灵魂 |
| **CLIP** | Contrastive Language-Image Pretraining | 让文本和图像在同一向量空间里"对齐"的训练范式 |
| **Mel-Spectrogram** | 梅尔频谱图 | 把音频从一维波形变成"图"的标准表示 |

## 2. 三段式流水线:Encode / Prefill / Decode

> 你笔记《大模型基础概念》《推理资源占用》里讲过 Prefill 和 Decode,但缺一个上游概念 Encode。三个加起来才是完整图景。

### 2.1 一句话区分

> **Encode = 把"非 Token 的东西"翻译成向量(一次性,发生在送进 LLM 之前)**
>
> **Prefill = 把"已经是向量的输入序列"在 LLM 80 层里跑一遍(发生在 LLM 内部,回答开始前)**
>
> **Decode = 逐字生成回答(发生在 Prefill 之后)**

**关键差别**:
- Encode 跟模态相关:图片、音频、视频才需要 Encode
- Prefill 和 Decode 跟模态无关:所有输入都要走

### 2.2 完整流水线对照

```
┌─────────────────────────────────────────────────────────────┐
│              用户输入:"这张图里有什么?" + 一张图              │
└─────────────────────────────────────────────────────────────┘
                              ↓
        ┌─────────────────────┴──────────────────────┐
        ↓                                            ↓
   文本路径                                     图片路径
        ↓                                            ↓
  ┌──────────┐                              ┌──────────────┐
  │Tokenizer │                              │  Vision      │
  │分词器     │                              │  Encoder     │ ← Encode
  │(CPU)    │                              │ (ViT, GPU)   │   翻译模态
  └──────────┘                              └──────────────┘
        ↓                                            ↓
  Token ID                                    Patch 向量
        ↓                                            ↓
  ┌──────────┐                              ┌──────────────┐
  │Embedding │                              │  Projector   │ ← 对齐
  │查表       │                              │  (小 MLP)    │
  └──────────┘                              └──────────────┘
        ↓                                            ↓
   4096 维向量                                 4096 维向量
        └──────────────────┬─────────────────────────┘
                           ↓
              拼接成统一的向量序列
                           ↓
        ┌──────────────────────────────────────────┐
        │  Prefill 阶段                             │ ← Prefill
        │  把整个序列在 LLM 80 层里跑一遍           │   灌进模型
        │  每层算出 K/V,存进 KV Cache              │
        │  (算力密集,GPU 跑满)                    │
        └──────────────────────────────────────────┘
                           ↓
                  输出第一个 Token
                  → TTFT (Time To First Token)
                           ↓
        ┌──────────────────────────────────────────┐
        │  Decode 阶段(逐字生成)                  │ ← Decode
        │  每次读 KV Cache,生成下一个 Token         │   吐字
        │  (带宽密集)                              │
        └──────────────────────────────────────────┘
                           ↓
                       完整回答
```

**三个阶段一目了然**:
```
Encode → Prefill → Decode
 翻译    →  灌入   →  吐字
```

### 2.3 Encode 阶段

| 输入模态 | 是否需要 Encode | 用什么 Encode |
|---|---|---|
| 纯文本 | **不需要**(Tokenizer + Embedding 就够) | — |
| 图片 | 需要 | Vision Encoder(ViT) |
| 音频 | 需要 | Audio Encoder(Whisper Encoder 等) |
| 视频 | 需要 | Vision Encoder × N 帧 + 时序模块 |

⚠️ 严格说文本走的 Tokenizer + Embedding 也是一种"编码",但业内**口语上"Encode"特指多模态那个把非文本变向量的过程**。

**Encode 阶段的特征**:
- **一次性**:每段输入只算一次,结果可以缓存
- **跟 LLM 解耦**:Vision Encoder 是独立模型,跟 LLM 是两套权重
- **可缓存**:同一张图反复用,可以存好 Encode 结果直接复用
- **耗时与输入规模强相关**:大图、长音频、高帧率视频都让 Encode 变慢
- **硬件特征**:算力密集,GPU 利用率高;不依赖 KV Cache

### 2.4 Prefill 阶段

Prefill 你笔记里讲过,本质是:

```
把整个输入序列(已经是向量了),一次性灌进 LLM 80 层
让每个 Token 互相 attend,把整个上下文"消化"一遍
副产物:每层产生 K, V → 存进 KV Cache
最终输出:第一个 Token 的概率分布
```

**关键认知**:Prefill **不输出多个 Token**,只为"开始生成"做准备。它跑完时只吐一个 Token,但 KV Cache 已经把整个上下文都消化进去了。

**Prefill 的特征**:
- **并行计算**:所有输入 Token 同时进 LLM,Tensor Core 跑满
- **算力密集**(Compute-bound)
- **耗时 ≈ Token 数 × 模型大小**:输入越长,Prefill 越慢
- **跑完产生 TTFT**:用户看到"第一个字"的等待时间就是 Prefill 时间

### 2.5 Decode 阶段

你笔记里详细讲过,这里只放对照:

- **逐字生成**:自回归,每次只能算一个 Token
- **带宽密集**(Memory-bound):每生成一个 Token 都要把整个模型权重读一遍
- **使用 KV Cache**:每步读取整个 KV Cache 算注意力
- **算力利用率低**:Tensor Core 用不满

### 2.6 三阶段对照表

| 维度 | **Encode** | **Prefill** | **Decode** |
|---|---|---|---|
| **干什么** | 把模态翻译成向量 | 把向量灌进 LLM 一次性消化 | 逐字生成回答 |
| **谁参与** | 专用 Encoder(ViT/Whisper) | LLM 主体(80 层) | LLM 主体(80 层) |
| **是否经过 LLM** | **否**(在 LLM 之前) | 是 | 是 |
| **输入** | 像素 / 音频波形 / 视频帧 | 向量序列 | 上一步生成的 Token |
| **输出** | 投影后的向量 | 第一个 Token + KV Cache | 下一个 Token + 更新 KV Cache |
| **并行性** | 一次性算完整个输入 | 所有 Token 并行 | 一次只能算一个 Token |
| **瓶颈** | 算力密集 | **算力密集** | **带宽密集** |
| **延迟贡献** | TTFT 的一部分 | TTFT 的主要部分 | 后续每个 Token 的速度 |
| **能否缓存** | 能(同图复用) | 能(Prompt Caching) | 不能 |

### 2.7 一次完整请求的时间线

**场景:给 GPT-4 一张图问"图里有什么"**

```
T=0ms      用户发送:图片 + "图里有什么?"
              ↓
T=0~10ms   [CPU] 文本 Tokenizer 切分 → 8 个 Token
              ↓
T=10~200ms [GPU] Vision Encoder Encode 图片         ← Encode 阶段
              ↓                                       约占 TTFT 20-40%
T=200ms    图片变成 1000 个向量,准备进 LLM
              ↓
T=200~800ms [GPU] LLM 跑 Prefill,消化 1008 个向量   ← Prefill 阶段
              ↓                                       约占 TTFT 50-70%
T=800ms    第一个 Token "图" 输出                    ← TTFT = 800ms
              ↓
T=825ms    Decode:"图里"
T=850ms    Decode:"图里是"
T=875ms    Decode:"图里是一"                       ← Decode 阶段
T=900ms    Decode:"图里是一只"                       每个 Token 约 25ms
...
T=2000ms   完成:"图里是一只橘猫,趴在键盘上睡觉。"
```

**TTFT 分解(典型场景)**:

```
纯文本短对话("你好"):
[Prefill: 50ms][========Decode==========]
  ↑ TTFT 50ms

带高清图:"图里有什么?":
[Encode: 200ms][Prefill: 600ms][========Decode==========]
  ↑ TTFT 800ms

带 1 分钟视频:"视频里发生了什么?":
[Encode: 8s][Prefill: 30s][========Decode==========]
  ↑ TTFT 38s ← 视频问答开头要等好久
```

### 2.8 三步分离的工程意义

#### 2.8.1 三步分离让缓存成为可能

每一步都可以**独立缓存**:

| 缓存 | 缓存什么 | 节省什么 |
|---|---|---|
| **Encoder Cache** | 同一张图的 Encode 结果 | 重复传图不用再 Encode |
| **Prompt Cache** | 同一段长 prompt 的 KV Cache | 系统提示词不用反复 Prefill |
| **KV Cache** | 当前对话的所有 K/V | Decode 时不用重算前面所有 Token |

Claude 的 Prompt Caching 功能就是把 Prefill 结果存起来,下次同 prompt 直接跳过 Prefill——**省钱省到 90%**。

#### 2.8.2 三步对应不同的硬件瓶颈

| 阶段 | 瓶颈 | 升级什么硬件最有效 |
|---|---|---|
| Encode | 算力 | 高算力 GPU(Tensor Core) |
| **Prefill** | **算力** | **高算力 GPU(4090 比 4070 快很多)** |
| **Decode** | **带宽** | **HBM 显存带宽(H100/H200 优势)** |

这就是为什么 NVIDIA 的 H100 / H200 / B200 一代比一代猛——**Prefill 要 FLOPS,Decode 要 HBM 带宽**,新卡两边都堆。

#### 2.8.3 三步可以放在不同机器上跑(PD 分离)

```
机器 A(轻量):跑 Tokenizer + Vision Encoder(Encode)
机器 B(重量):跑 LLM Prefill + Decode

或者更激进的 P/D 分离架构:
机器 A:专门跑 Prefill(高算力卡)
机器 B:专门跑 Decode(高带宽卡)
```

这叫 **PD 分离(Prefill-Decode Disaggregation)**,是 2024-2025 年大模型推理系统的热点架构(DeepSeek、Mooncake 等)。

### 2.9 速记口诀

> **Encode 是"翻译外语"——把图、音、视频翻译成 LLM 听得懂的话**
>
> **Prefill 是"看完全文"——把整段输入读一遍并记笔记(KV Cache)**
>
> **Decode 是"逐字开口"——根据笔记一个字一个字地吐出回答**
>
> 三步走完,一个 Token 才出生。后续每个 Token 只需要重复 Decode 这一步。

## 3. Token 经济学:为什么多模态烧钱

### 3.1 直觉:图片、音频、视频 Token 高得离谱

文本是人类**高度压缩过**的信息载体。"今天天气真好" 6 个汉字,承载的语义密度极高。

图片、音频、视频是**原始物理信号**,没有经过任何语义压缩——一张猫的照片,99% 的像素都在描述"毛发的纹理、光影的渐变"这些 LLM 根本不在乎的细节。但 Encoder 没法事先知道哪些重要,只能**一视同仁地都变成 Token**。

```
信息密度排序(高 → 低):
文本 >> 代码 > 表格 > 语音 > 图片 > 视频
```

密度越低,**同样的语义**需要的 Token 数越多。

### 3.2 量化对照表

按"等量信息"对比,差距非常夸张:

| 内容 | 等价描述 | Token 数 | 倍率 |
|---|---|---|---|
| 文本"一只橘猫在键盘上睡觉" | 11 个汉字 | **约 8 Token** | 1× |
| 一张这只猫的照片(1024×1024) | 同样的语义 | **约 1000 Token** | **125×** |
| 一段 10 秒说"一只橘猫..."的语音 | 同样的语义 | **约 500 Token** | **62×** |
| 一段 10 秒的猫视频 | 同样的语义 | **约 3000 Token** | **375×** |

**结论**:表达同一件事,**视频 ≈ 文本的 400 倍 Token 消耗**。

### 3.3 各家主流模型实际开销

**图片**:

| 模型 | 一张图 Token 数 | 备注 |
|---|---|---|
| GPT-4o | 85 ~ 1700 | 按分辨率档位 |
| Claude 3.5 / 4 | 约 1600 | 1.15M 像素以下 |
| Gemini 2.5 | 约 258 | 固定 |
| Qwen-VL 2.5 | 256 ~ 1280 | 按分辨率 |
| LLaVA-1.5 | 576 | 固定 |

**经验值**:一张高清图 ≈ **一本短篇小说的开头几页文字** 的 Token 量。

**音频**:

| 模型 | 每秒音频 Token 数 |
|---|---|
| Whisper Encoder | 约 50 Token/秒 |
| Qwen-Audio | 约 25 Token/秒 |
| GPT-4o 语音 | 约 10 Token/秒(端到端) |
| Gemini 音频 | 约 32 Token/秒 |

**经验值**:1 小时电话录音 ≈ **5 万到 18 万 Token**。

**视频**:

| 模型 | 每分钟视频 Token 数 |
|---|---|
| Gemini 1.5 Pro | 约 17000 Token/分钟(1 fps) |
| GPT-4o 视频 | 约 30000 Token/分钟 |
| Qwen2.5-VL | 约 6000 Token/分钟 |

**经验值**:1 小时视频 ≈ **100 万 Token**。这就是为什么 Gemini 拼命宣传"1M / 2M 上下文"——**它就是为吃视频准备的**。

### 3.4 对照你熟悉的场景

你笔记《Agent 如何帮你处理任务》里那次 **Cursor 转 118 分钟音频** 的项目:

```
118 分钟语音 ≈ 7080 秒
  ↓ 走 Whisper(ASR) 转文字路径
最终文本:约 35000 ~ 50000 字 → 约 25000 ~ 40000 Token

如果不转文字,直接喂给"端到端语音多模态"模型:
  ↓ Whisper Encoder 直接编码
约 7080 × 50 = 35.4 万 Token  ← 多了 10 倍以上
```

这就是为什么**"先转文字再喂模型"**至今仍是主流——不是技术不行,是**省钱**。

### 3.5 连锁后果

Token 多带来的不只是 API 账单变贵,还有一串麻烦:

#### 3.5.1 显存压力(KV Cache 爆炸)

你笔记里讲过:
```
KV Cache ≈ 2 × num_layers × seq_len × hidden_size × ...
```

**seq_len 是线性增长的**。一张图 1000 Token,KV Cache 就比纯文本多 1000 倍图片体量的占用。

**举例**(LLaMA-2 70B 在 FP16):
- 一张图:KV Cache 约 320 MB
- 一段 1 小时视频:KV Cache 约 **320 GB** ← 单卡装不下

#### 3.5.2 Prefill 阶段时间长(首 Token 延迟暴增)

**实测体感**:
- 纯文本提问 → 首 Token 延迟 200 ms
- 带一张高清图 → 首 Token 延迟 2 ~ 5 秒
- 带一段视频 → **首 Token 延迟 30 秒到几分钟**

#### 3.5.3 API 费用线性爆炸

按 2026 年价格,Claude 4 处理一张图约 $0.006,处理 1 小时视频约 $3 ~ $5。**视频会以 10 倍速度膨胀账单**。

#### 3.5.4 上下文窗口被快速吃光

```
Claude 4 上下文 200K Token:
  → 能装 400 页文本
  → 或 200 张图片
  → 或 1 小时音频
  → 或 12 分钟视频
```

视频是 Token 头号大胃王。

### 3.6 工业界应对策略

| 策略 | 做什么 | 例子 |
|---|---|---|
| **降采样** | 抽帧率从 30 fps 降到 1 fps | 几乎所有视频多模态模型 |
| **Token 压缩** | Q-Former / Perceiver Resampler 把几千个 patch 压成 64~256 | BLIP-2、LLaVA |
| **分辨率自适应** | 简单图低分辨率,复杂图高分辨率 | GPT-4o 的 "low/high detail" 选项 |
| **预先 ASR 转文字** | 音频 → 文字 → 普通 LLM | 通义听悟、你的 Cursor 项目 |
| **关键帧选择** | 只挑信息量大的帧 | VideoChatGPT |
| **分段处理 + 摘要** | 长视频切片处理,再汇总 | NotebookLM、各家长视频助手 |

### 3.7 速记口诀

> **文本是稀饭,图片是肉,视频是整头牛。**
>
> **稀饭一勺一个 Token,肉一块上千个,整头牛能把你的 Context 撑死。**
>
> 工程上的取舍永远是:**信息保真度 vs Token 预算 vs 推理速度 vs 钱包厚度**。

## 4. 一个常见混淆:VLM 不等于文生图

> 这是这一系列讨论里最容易踩的坑之一:**Midjourney 不是 VLM**。搞清楚之后,后面所有资料都不会再看晕。

### 4.1 两类模型的根本区别

**VLM(Vision-Language Model,视觉语言模型)** 和 **图像生成模型** 是两个完全不同的物种,方向相反、架构不同、目标不同。

```
VLM(读图模型) :      图片 + 文字 → 文字
                         ↑
                     输入图,输出话

图像生成模型 :        文字 → 图片
                         ↑
                     输入话,输出图
```

| 维度 | VLM | 图像生成模型 |
|---|---|---|
| **代表** | GPT-4V、Claude Vision、Qwen-VL、Gemini、LLaVA | **Midjourney**、DALL-E 3、Stable Diffusion、通义万相 |
| **方向** | 图 → 文 | 文 → 图 |
| **底层架构** | Transformer LLM(自回归) | **Diffusion Model(扩散模型)** |
| **能力** | 看图说话、视觉问答、文档理解 | 文生图、图生图、风格化重绘 |
| **是否预测 Token** | 是 | **否**(扩散模型不预测 Token) |

你 ACA 笔记题 15 其实已经埋下这个分类:
- **通义千问 Qwen** = 大语言模型 / VLM
- **通义万相 Wanx** = 文生图、图生图 ← **图像生成模型**

Midjourney 对标的是**通义万相**,不是 Qwen-VL。

### 4.2 扩散模型根本不是 Token 那一套

你之前学的所有东西——Token、Embedding、KV Cache、自回归、Self-Attention——讲的都是 **Transformer LLM**。但 Midjourney / DALL-E 走的是完全不同的路:**扩散模型(Diffusion)**。

扩散模型的逻辑是:

```
第 1 步:拿一张纯噪声图(满屏雪花点)
第 2 步:模型预测"如果按用户 prompt,这张雪花图应该往哪个方向去噪?"
第 3 步:去掉一点点噪声 → 图变清晰一点点
第 4 步:重复 20-50 次
第 N 步:完整的图出现
```

它**不是预测下一个 Token**,而是**在一张完整的图上反复去噪**。整个过程根本没有"上下文窗口"这个概念。

### 4.3 Midjourney 的"输入"其实非常短

你给 Midjourney 的 prompt 才是它真正的"上下文":

```
"a cat sitting on a keyboard, photorealistic, cinematic lighting, 8k --ar 16:9 --v 6"
```

这玩意儿撑死 **50-100 个 Token**。Midjourney 内部的文本编码器(通常是 CLIP 或 T5)也有上限,**通常就 75 ~ 256 个 Token,超过会被截断**。

**这就是为什么写超长 Midjourney prompt 没用**——后半截它根本读不进去。

各家文生图模型的"prompt 上下文":

| 模型 | 文本输入上限 | 备注 |
|---|---|---|
| Midjourney v6 | 约 60 ~ 80 Token | 超出截断 |
| Stable Diffusion 1.5 | 75 Token(CLIP 硬上限) | 经典限制 |
| Stable Diffusion XL | 75 + 75 = 150 Token | 双文本编码器 |
| DALL-E 3 | 约 4000 字符(用 GPT 先改写 prompt) | "作弊"了 |
| Flux | 256 Token | 用 T5 |
| 通义万相 | 约 500 字符 | |

**对照下你 Qwen / Claude 的 200K Token 上下文,差了 2000-3000 倍**。Midjourney 完全不需要长上下文,因为它不是那个工作模式。

### 4.4 真正的 VLM 上下文为什么变大

不是"VLM 一定要长上下文",而是**用户场景把它逼出来的**:

| 场景 | 需要的上下文 |
|---|---|
| **单图问答**("图里是啥?") | 不到 2K Token,普通上下文够用 |
| **多图对比**("这 5 张图哪个最好看?") | 5 × 1500 = 7500 Token |
| **长 PDF 解析**(带图表的财报) | 几十张图 × 1000 Token + 长文本 = 100K+ |
| **视频理解** | 1 小时 ≈ 100 万 Token |

**结论**:VLM 的上下文是被**长文档**和**视频**逼大的,单图本身不需要超长上下文。

**反例**:LLaVA-1.5(经典 VLM)只有 4K 上下文,但仍是 VLM。Qwen-VL-Plus 早期版本只有 8K,照样能看图回答问题。

### 4.5 对照速查表

```
┌──────────────────────────────────────────────────────────┐
│                  AI 视觉相关模型分类                       │
└──────────────────────────────────────────────────────────┘

         读图(图 → 文)              生图(文 → 图)
            │                            │
            ▼                            ▼
        VLM 家族                    图像生成模型家族
        ┌─────┐                     ┌─────────┐
        │GPT-4V│                    │Midjourney│
        │Claude│                    │ DALL-E 3 │
        │Qwen-VL│                   │   SD     │
        │Gemini │                   │ 通义万相  │
        └─────┘                     └─────────┘
            │                            │
            ▼                            ▼
       Transformer                 Diffusion Model
       自回归 Token               反复去噪 Pixel
       上下文 4K~2M               输入 prompt ≤256 Token
            │                            │
            ▼                            ▼
      上下文规模有差异              基本没有"长上下文"概念
      (单图→视频差几千倍)          (prompt 撑死几百 Token)
```

### 4.6 一个连带的认知:你 ACA 题 15 的 C 选项为什么错

题 15 的 C 选项考过:"用万相生成'日落时分'图像,包含'夕阳无限好'**准确文字**" → 错。

更深入的理解:

- 通义万相是扩散模型,输入 prompt 被 CLIP 编码成一个**整体语义向量**
- 扩散模型不"逐字生成像素",它是把"夕阳无限好"这五个字当成一个**模糊的视觉概念**去画
- 所以画出来的字往往是**像汉字但不对的图形**(缺笔画、偏旁错位)

**根本原因**:扩散模型的工作方式决定了它**不擅长精确的符号**——它擅长画"看起来像的东西",但不擅长"准确无误的东西"。这跟 LLM 处理 Token 是符号化的逻辑完全不同。

### 4.7 速记口诀

> **VLM 看图,扩散模型生图,两者底层架构不一样、对"上下文"的需求也不一样。**
>
> **Midjourney 是后者——它的 prompt 短到几乎可以忽略不计,跟"长上下文"半毛钱关系都没有。**
>
> **"看图模型"才会被多图、视频逼出长上下文;"生图模型"压根不在那个赛道上。**

## 5. 反思:不像人脑的架构

> 你最早抓到的一个直觉:**"Encode 翻译 → LLM 处理,在音频和图像视频的场景,好像不太符合人脑的处理方式。"** —— 这戳到了当前 AI 架构最深的局限。

### 5.1 LLM 的做法:语言中心主义

```
图片 ──┐
音频 ──┼─→ 各种 Encoder ─→ 翻译成"类语言空间"的向量 ─→ LLM 处理
视频 ──┘
        ↑
   注意这里"all roads lead to language"
   万物归一到 LLM 的 4096 维 token 空间
```

**本质上**:LLM 是个"语言至上主义"的架构。它把所有东西**翻译成类似语言 token 的东西**才能处理。

### 5.2 人脑的做法:模态专家并行

```
        ┌─→ 视觉皮层(V1→V2→V3→V4→IT)────┐
        │   各种独立专门硬件                │
眼睛 ───┤                                  │
        │                                  ↓
耳朵 ───┼─→ 听觉皮层(A1→A2→颞上回)─→ 联合皮层(高层概念整合)
        │   保持声音的时频结构              ↑
皮肤 ───┤                                  │
        │                                  │
身体 ───┴─→ 体感皮层、运动皮层 ────────────┘

        ↑
   注意:各模态有独立的处理通路、独立的表征格式
   语言区(Broca/Wernicke)只是其中一个专门模块
   而不是"万物归一"的中央处理器
```

### 5.3 三个核心差异

#### 5.3.1 差异 1:专用硬件并行 vs 统一翻译串行

| 维度 | 人脑 | LLM |
|---|---|---|
| **架构** | 几十个专门皮层区域**并行**工作 | 一个 Transformer **串行**处理 |
| **视觉处理** | 视觉皮层有自己的"视觉语言" | 翻译成 token 后才能"想" |
| **听觉处理** | 听觉皮层有自己的"听觉语言" | 翻译成 token 后才能"想" |
| **语言区** | 只是众多模块之一 | **整个系统的中心** |
| **共同空间** | 高层联合皮层做概念整合(amodal) | 第一步就被强行拉到 token 空间 |

**关键反例**:聋哑人没有语言,但能正常看图、识别情感、解决空间问题。**婴儿在会说话之前已经能认妈妈、记物体**。这证明人类思维**不必经过语言**。

但 LLM 的多模态版本必须经过那个"类语言"的 token 空间——**没翻译就没法处理**。

#### 5.3.2 差异 2:人脑有心象(Mental Imagery),LLM 没有

闭上眼睛想象一只橘色的猫——你脑子里会浮现某种"视觉感觉"。这就是**视觉心象**:

- fMRI(Functional Magnetic Resonance Imaging) 研究发现,**想象一只猫激活的视觉皮层和真看到一只猫激活的视觉皮层有大量重叠**
- 同样,**在脑海里"听"一首歌时听觉皮层会激活**
- 人脑可以在不同模态之间**双向自由切换**:看到 → 想到 → 说出来 → 听到 → 写下来 → 再画出来

**LLM 当前模型不行**:

- 给它一张猫图,它能描述(图 → 文)✅
- 但它不能在脑子里"保持"那张图的视觉表征做"心象旋转"
- Vision Encoder 把图压成 token 时,**大量空间精度被丢掉了**
- 想"画"出来必须调用**另一个独立的扩散模型**(如通义万相和 Qwen 是分开的)

这就是为什么 LLM 做这类任务很糟:
- "把这张图里的物体顺时针旋转 30 度想象一下" ← 心象旋转
- "在脑子里把这张图的红色和蓝色互换" ← 视觉操控
- "听这首歌然后想象下一句旋律" ← 听觉外推

#### 5.3.3 差异 3:人脑具身,LLM 离身

人理解"苹果"时调动的:
- 视觉皮层(什么样子)
- 嗅觉皮层(什么味道)
- 体感皮层(在手里的重量、温度)
- 运动皮层(怎么拿、怎么咬)
- 镜像神经元(看到别人吃苹果,自己运动皮层也激活)

**"苹果"这个概念在人脑里 = 一个跨多个皮层的分布式激活模式**

**LLM 理解"苹果"** = 一个 4096 维向量。**没有重量、没有温度、没有"咬下去的感觉"**。

哲学家 Searle 的中文房间论证讨论的就是这个:**LLM 是不是真的"理解",还是只是在符号空间里做模式匹配?**

### 5.4 为什么 LLM 走了"反人脑"的路

这条路不是没人想过,是被工程现实逼的。

**历史包袱**:
```
2017 年 ─ Transformer 诞生 ────────────→ 为文本设计
2018-2022 ─ LLM 爆发,文本能力起飞 ─────→ 文本架构成为主流
2023 ─ 需要做多模态时 ──────────────────→ "怎么办?"
        ↓
   最省事的方案:把别的模态翻译成文本能处理的格式
   于是有了 ViT + Projector 这套
```

**本质上**:**先有语言模型,后凑多模态**。所以语言被放在了中心。

这跟人脑演化史正好相反——人脑**先**有视觉听觉(爬行动物就有),**后**才长出语言(人类几百万年)。语言是大脑的"插件",不是核心。

### 5.5 当前正在尝试"更像人脑"的几个方向

#### 5.5.1 原生多模态(Native Multimodal)

GPT-4o、Gemini 2.5 Native:

- 不再"先翻译成 token 再处理"
- 训练时**同时**喂图、文、音,让模型学到一个**真正跨模态的内在表征**
- 输出端也不局限于文字
- 更接近人脑的"多模态同时进入、共同表征"

但底层还是 Transformer,离人脑还远。

#### 5.5.2 模态专属专家(Modality-Specific Experts)

借鉴 MoE(Mixture of Experts) 思想:

```
不让一个 Transformer 处理所有东西
而是:
    视觉 token → 视觉专家组(一群专门处理视觉的 FFN)
    音频 token → 音频专家组
    文字 token → 文字专家组
    联合 token → 跨模态专家组
```

更像人脑的"专门皮层"分工。代表:DeepSeek-V3、Mixtral、Gemini Pro 内部架构。

#### 5.5.3 非 Transformer 架构

| 架构 | 思路 | 类比人脑 |
|---|---|---|
| **Mamba / SSM(State Space Model)** | 不用 Attention,用状态空间建模 | 更接近神经元的"持续激活" |
| **JEPA(Joint Embedding Predictive Architecture)** | LeCun 主张:不预测 token,预测**抽象表征** | 不强求"翻译成符号" |
| **Diffusion LLM** | 把扩散模型思想用到语言上 | 模拟"思维涌现"过程 |
| **Spiking Neural Network 脉冲神经网络** | 完全模拟生物神经元 | **直接照搬大脑硬件** |

**LeCun(Meta 首席 AI 科学家)一直说**:当前 LLM 这条路是错的,未来一定要走 JEPA 这种"不通过语言中转"的架构。**他的论据跟这一节的反思几乎一模一样**。

#### 5.5.4 世界模型(World Models)

代表:李飞飞的 World Labs、LeCun 的 V-JEPA、Google DeepMind 的 Genie

- 不只是"看图说话"
- 让模型在内部建立**对物理世界的预测模型**
- 能"想象"物体如果碰一下会怎么动 ← **这就是人类心象的工程化**

### 5.6 一个有趣的悖论

**当前最强大的多模态 AI**(GPT-4o、Gemini)走的恰恰是**最不像人脑**的路。
**而最像人脑**的研究方向(JEPA、SNN、世界模型)**目前性能还远不如 LLM**。

这就引出一个深刻问题:

> **"像人脑"和"有效"是同一件事吗?**

可能不是。飞机不像鸟(鸟扇翅膀,飞机不扇),但飞机飞得更高更远。也许 AI 不需要"像大脑"才能实现智能——**只要在功能上等价就够**。

但反对派(LeCun 等)认为:当前 LLM 的局限(幻觉、不会推理、没有真正的世界模型)就是因为这种"反生物"架构。**只有走更像大脑的路,才能突破天花板**。

**这是 2024-2026 年 AI 领域最大的路线之争**。

### 5.7 几个具体例子让你体会差距

**例 1:心象旋转**

- **人脑**:闭上眼想象一个 3D 的字母 R,把它逆时针旋转 90 度。你能"看到"它旋转的过程。
- **LLM**:把 R 的图片塞给 GPT-4V → 能描述"这是字母 R" → 问"逆时针转 90 度后呢" → 经常答错,因为它没有"内在的视觉表征"可供操作。

**例 2:听音辨曲**

- **人脑**:听到一段熟悉旋律的开头,**整首歌的旋律自动在脑内继续播放**。
- **LLM**:给 GPT-4o 一段音频让它"继续这首歌"——最多能用文字描述这首歌,**生不出后续的音乐**(除非外挂 MusicGen)。

**例 3:识破"看似合理但物理不可能"的图**

- **人脑**:看到 M.C. Escher 的不可能楼梯,立刻感到"哪里不对劲"——因为视觉皮层有**内置的 3D 一致性检查**。
- **LLM**:经常被这种图骗——因为它的"视觉理解"是基于 patch token 的统计模式,**没有真正的 3D 物理理解**。

### 5.8 速记口诀

> **LLM 的多模态:万语归宗,所有模态都翻译成类语言 token,再让 LLM 主体一视同仁地处理。**
>
> **人脑的多模态:各司其职,每种感官有专门皮层并行处理,高层联合区做概念整合,语言只是其中一个模块。**
>
> **两者就像"翻译公司"和"大型医院"——翻译公司什么都翻译成同一种语言再处理;大型医院每个科室独立诊治,最后由全科会诊整合。**

## 6. Encoder 与 Decoder 本身就是大模型

> 你后来抓到的一个关键事实:**"Encode 和 Decode 也应该是很复杂的大模型吧——描述视频里的主体、背景音频、时序变化、空间信息,需要很高的'文学功底'。"** 完全正确,而且 Encoder 比你想的更大。

### 6.1 不是"前处理工具",是大模型

很多人以为 Encoder 只是个"前处理工具",像 Tokenizer 那样轻飘飘的一步。**这是巨大的误解**。

事实是:

```
Vision Encoder(如 ViT-L/14)     ≈ 300M 参数 ~ 1B 参数
Audio Encoder(如 Whisper Large) ≈ 1.5B 参数
Video Encoder(如 VideoMAE-Large)≈ 300M ~ 1B 参数

LLM 主体(如 Qwen2-7B)           ≈ 7B 参数
```

注意:**Vision Encoder 单独就比很多小型 LLM 还大**。

更夸张的对比:

| 模型 | Vision Encoder | LLM 主体 | Encoder 占比 |
|---|---|---|---|
| LLaVA-7B | CLIP ViT-L (300M) | Vicuna-7B (7B) | 4% |
| **Qwen2-VL-2B** | **675M** | **1.5B** | **31%** |
| InternVL-Chat-V1.5 | InternViT-6B | LLaMA-20B | **23%** |
| **InternVL2-Llama3-76B** | **InternViT-6B** | **Llama3-70B** | **8%** |

**InternViT-6B 是一个 6B 参数的视觉 Encoder**——它单独就比 Qwen-3B、Phi-3 这种"小型 LLM"还大。

### 6.2 视觉 Encoder 的"文学功底"

你说的"文学功底",工程上叫**表征能力(Representation Capacity)**。一个视觉 Encoder 要同时编码多个层级的信息。

看一张猫坐在键盘上的图片,Encoder 需要同时编码:

**低层(前几层)**:
- 边缘、纹理、颜色梯度
- 光照方向、阴影
- 物体轮廓

**中层(中间几层)**:
- 这是动物(不是文字、不是建筑)
- 有毛发、有耳朵、有四条腿
- 背景是个矩形物体(键盘)

**高层(最后几层)**:
- 这是一只橘猫
- 它趴在键盘上
- 表情看起来很慵懒
- 这个场景常见于"程序员的猫"类图片
- 暗示家居 / 工作场景

**空间关系**:
- 猫在键盘上方
- 键盘在桌面上
- 视角是俯视的
- 透视关系符合物理

**所有这些信息**最后要塞进 256 个 4096 维向量里——这就是 Encoder 要做的"文学功底"。

**一张图的信息密度对比**:

```
一段 8 个 token 的描述:"一只橘猫趴在键盘上睡觉"
= 8 × 4096 维 = 32K 个数字

一张图片的 Encoder 输出:
= 256 × 4096 维 = 1M 个数字(信息量是描述文字的 32 倍)
```

**Encoder 必须把这些信息合理地"压缩"进向量空间,又不能损失关键细节**——跟把《战争与和平》写成 280 字的微博一样难。

### 6.3 视觉 Encoder 的能力清单

| 能力 | 具体体现 |
|---|---|
| **物体识别** | 区分 1000+ 类物体(ImageNet 类目) |
| **空间感** | 知道"上下左右前后"、深度、3D 关系 |
| **数量感** | 能数清图里有几个人、几个苹果 |
| **细节捕捉** | 能看到背景小字、远处人脸 |
| **风格识别** | 油画 vs 摄影 vs 卡通 |
| **OCR(Optical Character Recognition)** | 把图里的字也读出来 |
| **情绪/氛围** | 暖色调温馨 / 冷色调忧郁 |
| **常识推理** | "穿西装的人在演讲" → 推测是会议场合 |

**这就是为什么 Vision Encoder 要那么大**——上面每一项都需要参数。

### 6.4 视频 Encoder 的功底(更难)

视频 Encoder 在图片基础上还要做时间维度的处理:

| 时间维度的能力 | 具体体现 |
|---|---|
| **运动追踪** | 同一个物体跨帧识别 |
| **动作识别** | "在跑步" vs "在走路" |
| **因果推理** | "球被踢飞了" 而不是"球自己飞走了" |
| **事件分段** | 视频里"切菜→炒菜→装盘"是三个动作 |
| **场景变化检测** | 镜头切换 vs 同一场景内移动 |
| **时序一致性** | "前一秒戴帽子,后一秒没戴" → 注意到变化 |

**视频 Encoder 比图片 Encoder 难一个数量级**——参数往往更多。

### 6.5 音频 Encoder 的功底

Whisper Large-v3 就是 1.5B 参数。它在干什么:

| 能力 | 具体体现 |
|---|---|
| **语音识别** | 把声波转成文字 |
| **多语言** | 99 种语言识别 |
| **口音适应** | 印度英语、苏格兰英语都能听懂 |
| **噪声鲁棒性** | 嘈杂环境下还能听清 |
| **说话人区分** | 多人对话不混 |
| **情绪识别** | 听出是开心还是生气 |
| **背景音乐识别** | 区分人声、音乐、环境音 |
| **音乐结构理解** | 节拍、调性、乐器 |

**1.5B 参数全砸在"听"这一件事上**——这就是为什么 Whisper 比传统 ASR 强那么多。

### 6.6 Encoder 也需要大规模训练

**Encoder 不是手写规则,它是模型,需要训练**——而且训练成本极高:

| 模型 | 训练数据 | 参数量 | 训练成本 |
|---|---|---|---|
| **CLIP**(OpenAI, 2021) | 4 亿对图文 | 400M | $10M+ |
| **DINO v2**(Meta, 2023) | 1.4 亿张图 | 1.1B | $5M+ |
| **SigLIP**(Google, 2023) | 100 亿对图文 | 400M | $20M+ |
| **InternViT-6B**(OpenGVLab, 2024) | 多源数据 | 6B | $50M+ |
| **EVA-CLIP-18B**(2024) | 数十亿对图文 | 18B | $100M+ |

**Whisper Large-v3**:**68 万小时**多语言音频 ≈ **77 年**不间断的录音 → 训练成本 $10M+

**这就是为什么它的"文学功底"那么强**——77 年的"听书经验"压缩进 1.5B 参数里。

### 6.7 Decoder 端也是大模型

#### 6.7.1 文字 Decoder(流派 A 的情况)

如果是 Qwen-VL、Claude Vision 这种只输出文字的模型,**"Decoder" 就是 LLM 本身**——也就是说,那 7B/70B/200B 的 LLM 参数,**全部都是"文字 Decoder"**。

```
LLM 主体 = 一个超大的文字 Decoder
专门负责"把内部向量翻译成连贯的文字回答"
```

这就是为什么 LLM 那么大——**生成自然语言比理解多模态更难**。

#### 6.7.2 图像 Decoder(流派 B / 扩散模型)

如果模型要输出图像(GPT-4o 原生模式、通义万相),需要一个图像 Decoder:

| 图像生成模型 | Decoder 参数 |

| Stable Diffusion 1.5 | 860M |

| **Stable Diffusion 3** | **8B** |
| **FLUX.1** | **12B** |
| **DALL-E 3(推测)** | 数 B 到 10B+ |

#### 6.7.3 音频 Decoder

| 模型 | 参数 |
|---|---|
| **MusicGen Large** | 3.3B |
| **AudioGen** | 1.5B |
| **Bark** | 1B |
| **Suno v3(估)** | 数 B |

#### 6.7.4 视频 Decoder

| 模型 | 参数 |
|---|---|
| **Sora** | 估计 30B+ |
| **可灵 KLING** | 不公开,估计 30B+ |
| **Veo 2** | 不公开 |

**视频 Decoder 是当前最大、最贵的 Decoder**——因为生成视频要解决时间一致性,是地狱难度。

```

┌──────────────────────────────────────────────────┐
```

### 6.9 三个反直觉的事实

#### 6.9.1 Encoder 的幻觉

你以为模型说错图片内容是 LLM 的锅?**很多时候是 Encoder 的锅**:

- Encoder 没看清细节 → LLM 拿到的向量本身就错 → LLM "尽职"地生成了错误的描述
- 这叫 **Visual Hallucination**,业界发现 60%+ 的多模态幻觉来自 Encoder 端

#### 6.9.2 Encoder 限制了整个系统的天花板

```
如果 Vision Encoder 看不出"图里有 5 个苹果"
那么再大的 LLM 也救不了——它根本拿不到这个信息
```

这就是为什么 2024-2026 年大家拼命堆 Encoder 参数(从 ViT-L 的 300M 卷到 InternViT 的 6B 再到 EVA-CLIP 的 18B)。

#### 6.9.3 Encoder 的训练比 LLM 还讲究

| 阶段 | 数据 | 难度 |
|---|---|---|
| LLM 预训练 | 互联网文字(几乎免费) | 数据好找,但要清洗 |
| Vision Encoder 预训练 | 图文对(需要质量配对) | **数据贵很多,对齐质量直接决定 Encoder 上限** |

LAION-5B(50 亿图文对)是开源界最大的视觉训练集——**它的整理本身就是一个 PhD 级别工程**。

### 6.10 速记口诀

> **Encoder 不是简单的翻译官,它是一个**专门读图/听音/看视频的大模型**,参数量动辄几亿到几十亿。**
>
> **Decoder 也不是简单的吐字机,它是一个**专门画图/合成音乐/生成视频的大模型**,规模能匹敌或超过 LLM 主体。**
>
> **整个多模态系统是 "Encoder 大模型群 + LLM 大模型 + Decoder 大模型群" 的复合体——你看到的"一个多模态模型",其实背后是一支由七八个大模型组成的乐队。**

## 7. 软 Token 的本质

> 这一系列讨论的终点,也是最精妙的部分。你最终抓到的精确表述:**"生成了 token 在模型中对应的 embedding 常量,离 token 很近,但中间没有 token。"** 这一句话价值千金。

### 7.1 Encoder 输出不是"文字 Token"

最容易踩的坑:以为 Encoder 把图变成了"文字 token"。**不是。**

**对照表**:

| 维度 | 文字 Token | Encoder 输出向量 |
|---|---|---|
| 什么形态? | 整数 ID(如 12345) | 浮点向量(4096 维) |
| 来源? | Tokenizer 切分文字 | 神经网络计算 |
| 对应关系? | Token 12345 = "猫" | 这个向量 = "某种视觉模式" |
| 能否反查回去? | 能(查词表得"猫") | ❌ 不能(不在词表里) |
| 人能读懂吗? | 能(解码回字符串) | ❌ 不能(就是一堆数字) |
| 在词表里吗? | 在 | ❌ 不在 |

**关键认知**:

> **Encoder 的输出是一种"无法翻译回文字"的向量**——它存在的全部意义就是**直接被 LLM 当作"Embedding 之后的状态"来用**。

### 7.2 业内对这些向量的几个叫法

| 叫法 | 含义 |
|---|---|
| **Visual Embedding** | 视觉嵌入向量(最准确) |
| **Visual Token** | 视觉 Token(口语化叫法,**容易和文字 Token 混淆**) |
| **Soft Token** | 软 Token(强调它不是离散的) |
| **Image Patch Embedding** | 图像块嵌入 |

⚠️ 关键区分:

```
文字 Token  = 离散的、有词表对应、能查回字符串       —— "硬 Token"
视觉 Token  = 连续的浮点向量、无词表、查不回任何东西  —— "软 Token"
```

"视觉 Token"这个词在业内常用,但它和文字 Token 是两种东西——只是因为长得像(都是进入 LLM 的"序列元素"),所以借用了 Token 这个词。

### 7.3 "离 token 很近"的几何含义

这是你最终抓到的精确表述。在 LLM 的 4096 维 Embedding 空间里:

```
LLM 的 Embedding 空间(4096 维)里:

  "猫"这个文字 Token 的 Embedding 在某个位置 ━━●
                                              │
                                              ↓ (距离很近)
  Encoder 处理猫图后输出的向量 ━━━━━━━━━━━━━━●
                                              │
                                              ↓ (距离稍远)
  "狗"这个文字 Token 的 Embedding ━━━━━━━━━●
                                              │
                                              ↓ (距离更远)
  "汽车"这个文字 Token 的 Embedding ━━●
```

**这就是 CLIP 训练范式做的事**——通过 4 亿对图文,把图像 Encoder 的输出**拽到对应文字 Token 的附近**。

### 7.4 "中间没有 token"的工程意义

这个判断**最深刻**。它精确指出了:**Encoder → LLM 这条路径里,并没有一个"先翻译成文字、再 Embedding"的中间步骤**。

```
❌ 错误理解:
图 → Encoder → 文字("一只猫")→ Tokenizer → Token ID → Embedding → 进 LLM

✅ 正确理解:
图 → Encoder → 向量(直接在 Embedding 空间里)→ 进 LLM
                                         ↑
                              跳过了"变成文字"这一步
```

#### 7.4.1 为什么"经过 token"会损失信息

假设走错误路径(图 → 文字描述 → Token → 进 LLM):

```
原始图片信息量:图里有 100 种细节
   ↓ Encoder 强行用文字描述
"一只橘猫趴在键盘上"(10 个 token)
   ↓ Token 化 → Embedding
LLM 拿到的信息:约等于 10 个文字 Token 的语义

问题:
- 猫毛的精确花纹?没了
- 键盘是什么品牌?没了
- 光线角度?没了
- 猫眼睛是否睁着?没了
- 背景里那只老鼠?根本没提
- 整体构图风格?语言难以描述
```

**人类语言是一种有损压缩**——文字描述天生就过滤掉了大量视觉细节。

#### 7.4.2 跳过 token 保留了什么

走正确路径(图 → 向量 → 直接进 LLM):

```
原始图片信息
   ↓ Encoder 压成 256 个向量
256 × 4096 = 100 万个浮点数

LLM 拿到的信息:
- 不局限于"能用文字描述"的部分
- 包含人类没词汇形容的视觉模式
- 包含连续的、渐变的、模糊的信息
- 保留远多于 10 个 token 的信息量
```

**这就是为什么 GPT-4V 能看出文字描述里没说的细节**——它没经过"文字"这个有损压缩瓶颈。

### 7.5 容易混淆的点:Encoder 输出 ≠ KV Cache

另一个常踩的坑:以为 Encoder "直接生成了 KV Cache 放进 LLM"。**不是。**

正确流程:

```
图 → Encoder → 输入级向量(等同于"Embedding 查表后的状态")
                  ↓ 拼进 LLM 输入序列
                  ↓
              进入 LLM Layer 1
                  ↓ Self-Attention + FFN
              产生 K₁, V₁ → KV Cache 第 1 层 ★
                  ↓ 重复 80 次
              KV Cache 完整生成
                  ↓
              开始 Decode
```

**关键认知**:

> **Encoder 输出是 KV Cache 的"远房原料",中间还差 80 层 LLM 计算。**

为什么不能让 Encoder 直接生成 KV Cache?
- KV Cache 必须由 LLM 自己一层一层算出来(每层依赖上一层)
- KV Cache 的形状完全由 LLM 架构决定(num_layers × seq_len × hidden_size × ...)
- Encoder 不知道 LLM 有几层、每层多宽,**根本算不出** LLM 风格的 KV Cache

**业界确实有一种和"预先生成 KV Cache"接近的技术**——**Prompt Caching**:
- 不是"Encoder 直接给 KV Cache"
- 而是"之前算过的 KV Cache 存起来下次用"

详见第 2.8.1 节。

### 7.6 软 Token vs 硬 Token:两条路径

有一种做法**真的把图像变成了"硬 Token"**——以 **Chameleon、Emu3、Janus** 为代表的**全离散多模态**。

#### 7.6.1 两种路径对比

```
路径 A(主流,连续向量,"软 Token"):
图片 → Encoder → 256 个连续向量(4096 维浮点)→ 进 LLM
                    ↑
                  软 Token,查不回字符串

路径 B(前沿,离散 Token,"硬 Token"):
图片 → VQ-VAE 编码器 → 256 个离散 ID(如 [4521, 8923, 12, ...])→ 进 LLM
                    ↑
                  硬 Token,**真的在词表里**,能"反查"
```

#### 7.6.2 VQ-VAE 怎么实现"硬 Token"

**VQ-VAE(Vector Quantized Variational Autoencoder)** 的核心:

1. 训练一个图像 Encoder,把图像编码成向量
2. 准备一个**视觉词表**(比如 8192 个视觉"码本",每个对应一个 1024 维向量)
3. Encoder 输出的每个向量,**强制对应到词表里最近的那个码本**
4. 于是图片变成了 256 个**整数 ID**(每个 ID 是 0-8191 之间的数)

```
视觉词表(学习出来的):
  ID 0 = 向量[0.1, -0.3, ...](对应某种"草地纹理")
  ID 1 = 向量[0.5, 0.2, ...](对应某种"天空蓝色")
  ID 2 = 向量[-0.4, 0.8, ...](对应某种"猫毛黄色")
  ...
  ID 8191 = 向量[...]
```

**于是图像真的被"翻译成"一种"视觉文字"了**——只不过这种文字人类看不懂,只有模型懂。

#### 7.6.3 两种路径的优劣

| 维度 | 路径 A(连续向量) | 路径 B(离散 Token) |
|---|---|---|
| **信息保真度** | 高(连续值精度高) | 低(量化损失) |
| **架构统一性** | 低(要单独处理视觉部分) | **高(图、文统一在 Token 层面)** |
| **生成能力** | 难(不能用自回归生成图像) | **强(可以自回归吐图像 Token)** |
| **当前主流** | ✅ 是(GPT-4V、Claude、Qwen-VL) | ❌ 实验性(Chameleon、Emu3) |
| **图像质量** | 不涉及生成 | 目前不如扩散模型 |

### 7.7 Decode 阶段的两大流派

#### 7.7.1 流派 A:只能输出文字的多模态模型(当前 95%)

代表:Qwen-VL、Claude Vision、GPT-4V(早期)、LLaVA、Gemini Vision

```
任何模态输入 → Encode → 统一向量
                          ↓
                      Prefill
                          ↓
                  Decode(只吐文字 Token)
                          ↓
                       文字回答
```

**特点**:进来时啥都能吃(图、音、视频),出来时**只能吐文字**。

#### 7.7.2 流派 B:任意模态都能输出的原生多模态

代表:GPT-4o(原生模式)、Gemini 2.5 Native、Chameleon、Emu3、Janus、Qwen-Omni

```
任何模态输入 → Encode → 统一向量
                          ↓
                      Prefill
                          ↓
                  Decode(吐多种 Token)
                     ↓        ↓        ↓
                 文字Token  图像Token  音频Token
                     ↓        ↓        ↓
                   直接显示  图像解码器  音频解码器
                              ↓         ↓
                             像素图    音频波形
```

**特点**:词表里**同时有**文字 Token、图像 Token、音频 Token。Decode 时模型决定下一个 Token 是哪种类型。

#### 7.7.3 对称美——Encoder 和 Decoder 是镜像

一个完整的原生多模态模型,Encoder 端有什么,Decoder 端往往就镜像配一个:

```
        Encode 端(输入侧)            Decode 端(输出侧)
        ──────────────                  ──────────────
图片  → Vision Encoder(ViT)    │   图像 Token → Image Decoder → 像素
                                │       (类似 VQ-VAE 的解码器)
音频  → Audio Encoder(Whisper) │   音频 Token → Audio Decoder → 波形
                                │       (类似 SoundStream 的解码器)
视频  → Frame Encoder + 时序    │   视频 Token → Video Decoder → 帧序列
                                │
文本  → Tokenizer + Embedding  │   文本 Token → Detokenizer → 字符串
```

### 7.8 主流模型归位

| 产品 | 输入模态 | 输出模态 | 属于哪派 |
|---|---|---|---|
| **Qwen-VL** | 文字 + 图 | 文字 | 流派 A |
| **Claude Vision** | 文字 + 图 | 文字 | 流派 A |
| **Gemini Vision** | 文字 + 图 + 音 + 视频 | 文字 | 流派 A |
| **通义听悟** | 音频 | 文字(转写) | 流派 A 的极简版 |
| **GPT-4o(原生模式)** | 文字 + 图 + 音 | 文字 + 图 + 音 | **流派 B** |
| **Gemini 2.5 Native Image** | 文字 + 图 | 文字 + 图 | **流派 B** |
| **通义万相**(文生图) | 文字 | 图 | **不是 LLM 架构**,是扩散模型 |
| **Midjourney** | 文字 | 图 | **不是 LLM 架构**,是扩散模型 |

### 7.9 速记口诀

> **Encoder 不是翻译机,是嵌入机。**
>
> **它不把图像"翻译"成文字,而是把图像"嵌入"到文字 Token 共享的语义空间里——成为一种 LLM 能理解但人类读不出来的"软 Token"。**
>
> **少数前沿模型(Chameleon、Emu3)走的是另一条路:用 VQ-VAE 把图像真的离散化成"硬 Token",让图像和文字在词表层面完全统一。但这是少数派。**

### 7.10 终极一句话

> **Encoder 没有把图像变成"文字 Token"——它把图像变成了"和文字 Token 共享同一个语义空间的连续向量"。这些向量在 LLM 内部被一视同仁地处理,但它们本身不在词表里、不能反查、不能解码回字符串。少数前沿模型(路径 B)通过 VQ-VAE 真的把图像变成"硬 Token",但目前的主流(GPT-4V、Claude Vision、Qwen-VL)走的都是"软 Token"路线。**

## 第一部小结

读到这里,应该已经对多模态大模型有了**直觉级**的把握:

- **统一原则**:万物皆向量,所有模态在 LLM 内部都被一视同仁地处理
- **三段式**:Encode 翻译模态、Prefill 灌进 LLM、Decode 逐字吐字
- **Token 经济学**:多模态 50-400 倍的 Token 消耗,是被信息密度差异逼出来的
- **分类辨析**:VLM 读图、扩散模型生图,两个物种,不要混为一谈
- **人脑对比**:LLM 的"语言中心主义"vs 人脑的"模态专家并行",是当前路线之争的根源
- **大模型乐队**:Encoder、LLM 主体、Decoder 都是大模型,一个多模态系统是七八个大模型的复合体
- **软 Token 精髓**:Encoder 不把图变成文字 Token,而是把图嵌入到 Token 共享的语义空间——离 Token 很近,但中间没有 Token
