> 前面讲的都是"概念怎么工作",这一部分讲"概念长什么样"——把抽象的 Token、Embedding 变成你能在代码里打印出来看的具体东西。

## 8. Token 长什么样

### 8.1 一句话:Token 就是一个整数

**Token 在 LLM 内部就是一个整数 ID**——具体说是个无符号整数。

```
"猫" → Token ID: 28392
"hello" → Token ID: 15043
" the" → Token ID: 262
"," → Token ID: 3001
```

**就这么朴素**。一个 Token = 一个数字。

### 8.2 数据类型

通常是 **INT32**(4 字节)或 **INT64**(8 字节)的无符号整数:

```
INT32:32 bit = 4 字节
       能表示 0 ~ 约 42 亿
       足够装下任何词表(通常 5 万 ~ 25 万)
```

**LLaMA、Qwen 等都用 INT32**。

### 8.3 Token ID 的"含义"

Token ID 本身**完全没有语义**——它只是词表里的索引位置:

```
词表(一个长长的列表):
  [0]    <PAD>
  [1]    <BOS>
  [2]    <EOS>
  [3]    "the"
  [4]    " "
  ...
  [262]  " the"
  ...
  [15043] "hello"
  ...
  [28392] "猫"
  ...
  [149999] 最后一个 token
```

**Token ID 28392 = "查词表第 28392 行 = '猫'"**

ID 数字大小本身不代表任何东西:"猫"是 28392 还是 5 都无所谓,只要词表和模型保持一致就行。

### 8.4 一个"句子"在内存里长什么样

```
"你好,世界"
   ↓ Tokenizer
[14990, 3001, 15917]    ← 3 个整数,12 字节
   ↓ 查 Embedding 表
[[0.02, -0.18, ...],    ← 第 1 个向量
 [0.34, 0.11, ...],     ← 第 2 个向量
 [-0.21, 0.55, ...]]    ← 第 3 个向量
                          总共 3 × 8 KB = 24 KB
```

**Token 阶段**:12 字节
**Embedding 阶段**:24 KB(放大 2000 倍)

### 8.5 对话历史在硬盘里存什么

你笔记里讨论过"应用数据库里的对话历史"——它存的就是**Token ID 序列**:

```
你和 Claude 的整个对话历史(假设 5 万 Token)
  ↓ 在数据库里存储的形态
[14990, 3001, 15917, 262, 1834, 9921, ..., 5621]
   ↑
50000 个整数 = 200 KB
```

**这就是为什么你笔记说"应用数据库里存几百 KB 纯文本 token"**——字面意义上就是一长串整数。

不是字符串、不是向量、不是 KV Cache——**就是整数列表**。

### 8.6 Tokenizer 是什么程序

**Tokenizer = 一个预先训练好的"切词规则" + 一张固定的词表**

- 不是死程序(规则不是人手写的)
- 也不是神经网络(不做推理,不需要 GPU)
- 而是一种**统计学习出来的算法**,跑起来很快(CPU 毫秒级)

它本质上是**两个文件**:

```
1. vocab.json(词表文件)
   {
     "the": 262,
     " the": 1996,
     "cat": 3797,
     "猫": 28392,
     ...
     共 15 万行
   }

2. merges.txt 或类似的规则文件(切词规则)
   定义"看到什么样的字符序列,切成哪个 token"
```

**加起来通常 1-10 MB**——比模型权重小得多。

### 8.7 主流算法:BPE(Byte Pair Encoding)

GPT、LLaMA、Qwen、Claude **绝大多数现代 LLM 都用 BPE 或其变种**。

#### 8.7.1 训练阶段(构建词表的过程)

```
Step 1:把训练语料拆成最小单位(单字符)
        "low lower lowest" → [l, o, w, _, l, o, w, e, r, _, l, o, w, e, s, t]

Step 2:统计哪些"相邻对"出现最频繁
        发现 "l + o" 出现 3 次  ← 最频繁
        合并成新单元 "lo"

Step 3:重新统计
        发现 "lo + w" 出现 3 次  ← 最频繁
        合并成 "low"

Step 4:继续重复
        发现 "low + e" 出现 2 次
        合并成 "lowe"

... 重复几万次,直到词表达到目标大小(如 15 万) ...
```

**结果**:常见的字符组合(如 "the"、"ing"、"猫")变成单个 token,罕见的组合保持拆开。

#### 8.7.2 推理阶段(切词的过程)

**用训练好的合并规则反复合并**:

```
输入:"lowest"
   ↓ 拆成字符
[l, o, w, e, s, t]
   ↓ 应用规则:l+o → lo
[lo, w, e, s, t]
   ↓ 应用规则:lo+w → low
[low, e, s, t]
   ↓ 应用规则:e+s → es(如果词表里有)
[low, es, t]
   ↓ 应用规则:es+t → est
[low, est]
   ↓ 没有更多规则可用,停止
最终 token:[low, est] → [3083, 395]
```

**全程不需要"理解",只是机械地按规则合并**。

### 8.8 几个直观的例子(GPT 实际切分)

```
"Hello, world!"
   → [Hello, ,, _world, !]
   → [15496, 11, 995, 0]

"低速发动机"
   → [低, 速, 发动机]   或   [低速, 发动机]
   → 看模型词表训练时的数据分布

"antidisestablishmentarianism"(罕见词)
   → [anti, dis, est, abl, ish, ment, arian, ism]
   → 拆得很碎,因为整词不在词表里
```

**这就是你 ACA 笔记题 1 那个考点**——"8500 字中文 < 8K Token" 的原因:**常见中文词被合并成 1 个 token,所以字符数 > token 数**。

### 8.9 不同模型的 Tokenizer 不一样

| 模型 | Tokenizer | 词表大小 | 中文友好度 |
|---|---|---|---|
| GPT-4 | tiktoken (cl100k_base/o200k_base) | 10万/20万 | 中等 |
| Claude | 自家 BPE | ~15万 | 较好 |
| LLaMA | SentencePiece BPE | 3.2万 | 一般 |
| Qwen | tiktoken 变种 | 15万 | **最好** |
| DeepSeek | 自家 BPE | 10万 | 好 |

**同一句话,不同 Tokenizer 切出来的 Token 数不一样**——这就是为什么"同样上下文,不同模型消耗 Token 数不同"。

### 8.10 Tokenizer 几个变种

| 算法 | 代表 | 特点 |
|---|---|---|
| **BPE** | GPT 系列、LLaMA | 字符级合并 |
| **WordPiece** | BERT | 类似 BPE,合并策略略不同 |
| **SentencePiece** | LLaMA、T5 | 把空格也当字符处理 |
| **Tiktoken** | GPT-4、Qwen | OpenAI 的 BPE 实现,更快 |
| **Unigram** | 部分多语言模型 | 概率化切分 |

### 8.11 确定性承诺

**同一句话、同一个 Tokenizer、跑一万次,输出的 Token 序列永远一样。**

因为 Tokenizer 的工作就是**纯查表 + 按固定规则合并**,里面:
- 没有随机数
- 没有概率采样
- 没有时间因素
- 不依赖任何外部状态
- 不跟 GPU/CPU 调度有关

这是 Tokenizer 对整个 LLM 系统的硬承诺——**所有后续优化(计费预估、Prompt Caching、可逆性)都依赖这个承诺**。

**与 LLM 推理的对比**:

| 组件 | 是否确定性 | 原因 |
|---|---|---|
| **Tokenizer** | ✅ **永远确定** | 纯规则查表 |
| Embedding 查表 | ✅ 确定 | 查固定的表 |
| LLM 前向计算(数学上) | ✅ 确定 | 矩阵乘法是确定的 |
| LLM 前向计算(工程上) | ⚠️ 几乎确定 | 浮点误差可能差最后几位 |
| **LLM 生成 Token(带采样)** | ❌ **不确定** | 有 temperature / top-p 随机性 |

**所以 Claude 同一个问题每次回答不一样**——不是 Tokenizer 在变,而是**最后那一步 "从概率分布里采样"** 有随机性。

### 8.12 Encode 和 Decode 严格互逆

```python
text = "你好世界"
tokens = tokenizer.encode(text)        # [14990, 3001, 15917]
restored = tokenizer.decode(tokens)    # "你好世界"
assert text == restored                # 永远成立
```

这是 Tokenizer 的硬承诺。

### 8.13 它运行在哪里

回到你笔记《大模型推理资源占用》:

```
Tokenizer 跑在 CPU 上:
  → 不需要 GPU
  → 速度:几毫秒
  → 占用:几乎可忽略

所以在你笔记的"CPU/GPU 分工表"里:
  Tokenizer 分词 = CPU 全包
  Embedding 查表 = GPU 全包
```

### 8.14 速记口诀

> **Token = 一个整数 ID = 词表里的索引位置 = 4 字节的"门牌号"**
>
> **它本身没有任何语义,含义全在"查词表"和"查 Embedding 表"这两个动作里。**
>
> **Tokenizer = "训练出来的查表程序"——训练阶段在海量文本上统计常见字符组合并合并成 token;推理阶段拿到文字按训练好的规则机械合并,输出整数 ID 序列。CPU 毫秒级,永远确定。**

## 9. Embedding 长什么样

### 9.1 一句话:一坨数字

一个 Embedding 向量,**字面意义上**,就是这样一个东西:

```
"猫" 这个 Token 的 Embedding(假设是 4096 维):

[0.0234, -0.1827, 0.4521, 0.0091, -0.3344, 0.7812, -0.0567, 0.2103,
 -0.1098, 0.4456, 0.0712, -0.2891, 0.5023, -0.0334, 0.1672, -0.4187,
 0.2890, -0.0556, 0.3344, 0.1029, -0.6712, 0.0445, 0.2218, -0.1990,
 ... (中间还有 4072 个数字) ...
 -0.0823, 0.1556, -0.3401, 0.2789]
```

**就这么一坨数字**。4096 个浮点数,没了。

### 9.2 用代码"看一眼"

```python
import torch
embedding = model.get_input_embeddings()
cat_token_id = tokenizer.encode("猫")[0]  # 假设是 28392
cat_embedding = embedding(torch.tensor([cat_token_id]))

print(cat_embedding.shape)
# torch.Size([1, 4096])  ← 一行 4096 列的数字

print(cat_embedding)
# tensor([[ 0.0234, -0.1827,  0.4521, ..., 0.1556, -0.3401, 0.2789]])
```

**这就是"猫"在 LLM 眼里的样子**——一行 4096 个浮点数,仅此而已。

### 9.3 数学概念:高维空间里的一个点

#### 9.3.1 类比从低维开始

```
1 维向量(1 个数字):
[3.5]  ← 数轴上一个点,位置 3.5

2 维向量(2 个数字):
[3.5, 2.1]  ← 平面上一个点,横 3.5、纵 2.1

3 维向量(3 个数字):
[3.5, 2.1, -0.8]  ← 立体空间里一个点

4096 维向量:
[0.0234, -0.1827, ..., 0.2789]  ← 4096 维空间里的一个点
                                 每个坐标是一个维度
                                 人脑无法可视化,但数学上完全合法
```

#### 9.3.2 关键认知

> **每个 Token 的 Embedding = 4096 维空间里的一个"点",或者说"位置坐标"。**

整个词表(约 15 万个 Token)= 这个 4096 维空间里散布着 15 万个点。

```
4096 维空间(想象成一个超级巨大的"宇宙"):

  ●"猫"             ●"狗"

              ●"动物"
                              ●"汽车"
   ●"猫咪"
                    ●"宠物"               ●"飞机"
                                                   ●"火车"
              ●"哺乳动物"
   ●"feline"
                                  ●"交通工具"
```

**相近的概念,点在空间里靠得近;不相关的概念,点离得远**。

#### 9.3.3 这才是"语义"的物理形式

LLM 的"理解",本质上就是**把概念组织到这个空间里的相对位置**:

```
"猫" 和 "狗" 距离:0.18
"猫" 和 "动物" 距离:0.22
"猫" 和 "宠物" 距离:0.25
"猫" 和 "汽车" 距离:0.89    ← 离得远
"猫" 和 "民主" 距离:0.94    ← 几乎完全无关
```

**这些距离不是人工定义的,是模型在训练时自己学出来的**。这就是 LLM "懂语义"的物理实现。

### 9.4 关键数学性质

#### 9.4.1 维度(Dimension)

```
Embedding 维度 = 这个空间有多少坐标轴

GPT-2 small:    768 维
LLaMA-7B:      4096 维
LLaMA-70B:     8192 维
GPT-3 175B:   12288 维
GPT-4(估计):  ~12288 维或更高
```

**对应你笔记里的"宽度(hidden_size)"概念**——这就是 LLM 的"宽度"。

```
宽度越大 = 每个 Token 用越多坐标来表达
        = 表达能力越强
        = 但显存代价是平方增长
```

#### 9.4.2 元素类型(详见第 10 章)

每个数字是什么精度的浮点数?这决定了显存占用:

| 数据类型 | 每个数字占多少字节 | 用在哪 |
|---|---|---|
| FP32 | 4 字节 | 训练时常用 |
| **FP16/BF16** | **2 字节** | **推理标配** |
| INT8 | 1 字节 | 推理压缩 |
| INT4 | 0.5 字节 | 极致压缩 |

**一个 4096 维 FP16 向量占用**:4096 × 2 = **8192 字节 = 8 KB**

#### 9.4.3 数字的范围

每个数字通常在 **-1 到 +1 之间**,绝大多数靠近 0:

```
典型分布:
  约 95% 的数字落在 [-0.5, 0.5] 之间
  少数数字会大一些,到 ±2 左右
  几乎不会有超过 ±5 的极端值
```

为什么不会有特别大的数字?因为 **Layer Normalization(层归一化)** 等机制会把数值拉回正常范围——否则计算会爆炸。

#### 9.4.4 单个数字没有"含义"

**重要认知**:

```
第 1 个数字 0.0234   不代表"猫的颜色"
第 2 个数字 -0.1827  不代表"猫的体型"
第 3 个数字 0.4521   不代表"猫的可爱度"
...
```

**每个数字单独看,都没有人类可解释的含义**。"猫"的语义是这 4096 个数字**整体**形成的位置,不是某个数字单独表达的。

**类比**:
- 你在地球上的 GPS 坐标 (39.9087, 116.3975) → 这代表"天安门"
- 但 39.9087 这个数字单独看,不代表"北京"或"中心"或别的什么
- 含义在**两个数字组合**里,不在单个数字里

LLM 的 4096 维向量同理——含义在**4096 个数字的组合模式**里。

### 9.5 维度的纠正

⚠️ **常见误解**:"每个数字有正负两个维度"——错。

精确表述:

```
4096 个数字 = 4096 个维度
              ↑
        "维度数 = 数字个数",这才是"维度"的标准用法

每个数字 = 一个可正可负的浮点数(取值范围大约 -2 到 +2)
              ↑
        "可正可负"不是另外两个维度
        是同一个维度里的取值范围(数轴的方向)
```

**精确类比**:

```
你的位置坐标 (北纬 39.9, 东经 116.4)
  → 是 2 个维度
  → 每个维度的值可以是正(北纬/东经)或负(南纬/西经)
  → 但"南北"和"正负"不是新维度,是纬度这一个维度的取值

Embedding (0.0234, -0.1827, ..., 0.2789)
  → 是 4096 个维度
  → 每个维度的值可正可负
  → 但"正负"不算独立维度,只是每个维度的取值方向
```

### 9.6 几何运算:为什么向量能"计算"语义

#### 9.6.1 经典例子:词向量算术

Word2Vec 时代的著名发现:

```
向量("国王") - 向量("男人") + 向量("女人") ≈ 向量("女王")
```

**字面意义上**:

```
[0.5, -0.2, 0.7, ...]   ← "国王"
- [0.3, -0.1, 0.4, ...] ← "男人"
+ [0.2, 0.1, 0.5, ...]  ← "女人"
= [0.4, 0.0, 0.8, ...]  ← 算出来的向量
≈ [0.41, 0.02, 0.79, ...] ← "女王"的真实向量
```

**两个向量近不近?用距离衡量**:
```
余弦相似度 = (A·B) / (|A| × |B|)
欧式距离 = sqrt(Σ(A_i - B_i)²)
```

这就是为什么 LLM 能做类比推理——**因为语义关系在向量空间里是真实的几何关系**。

#### 9.6.2 RAG 的本质就是几何最近邻

你 ACA 笔记题 5 里那个标准 RAG 流程:

```
"如何开通 ECS 实例?" ──→ Embedding向量 A
                              │
                              ↓ 计算距离
知识库里所有文档块的Embedding向量 ──→ B₁, B₂, B₃, ..., Bₙ
                              ↓
                       找出离 A 最近的 Top K 个
                              ↓
                       这些就是"最相关的文档块"
```

**RAG 的"检索"本质上就是高维空间里的"找最近邻"**——你笔记里学的"向量相似度",字面意义上就是计算这些 4096 维向量的几何距离。

### 9.7 Embedding 表(Embedding Matrix)

"Embedding 查表"——表是什么?

```
词表大小:约 15 万个 Token
向量维度:4096

Embedding 表 = 一个 (150000 × 4096) 的大矩阵:

           维度1   维度2   维度3   ...   维度4096
Token_0    0.01    -0.23   0.45    ...   0.12
Token_1    -0.34   0.56    0.78    ...   -0.05    ← "猫"对应的那一行
Token_2    0.22    -0.11   -0.67   ...   0.34
...
Token_149999  ...
```

**这个表的大小**:150000 × 4096 × 2字节 = **约 1.2 GB**

**它是 LLM 权重的一部分**——和那 80 层 Transformer 一起保存在模型文件里。

**"查表"就是字面的查表**:
```
Token ID 28392 ("猫") → 取第 28392 行 → 得到那 4096 个数字
```

### 9.8 Embedding 是怎么"学"出来的

```
模型刚初始化时:
  "猫" 的 Embedding:[随机数1, 随机数2, ..., 随机数4096]
  "狗" 的 Embedding:[随机数1, 随机数2, ..., 随机数4096]

  此时它们在空间里随机分布,没有任何语义结构

训练过程(在海量文本上做"预测下一个 token"):
  看到 "猫吃鱼" → 模型预测错了 → 调整 "猫" 的 Embedding 数字
  看到 "狗汪汪" → 模型预测错了 → 调整 "狗" 的 Embedding 数字
  看到 "猫和狗都是宠物" → 微调让它们更靠近
  ... 重复几万亿次 ...

训练完成后:
  "猫" 和 "狗" 的向量自动变得相近
  "猫" 和 "汽车" 的向量自动变得疏远

  ★ 没人告诉模型"猫和狗是宠物" ★
  ★ 它从海量文本的统计规律里"自己学出来的" ★
```

**这就是 LLM 神奇的地方**——这 4096 个数字的位置,是通过万亿次梯度下降**自动调整**到能反映人类语义结构的位置上的。

对应你笔记里的"涌现":**语义在向量空间里的几何结构,就是从大量训练中"涌现"出来的**。

### 9.9 hidden_size 不固定

⚠️ **重要纠正**:前面一直用"4096 维"举例,但**4096 不是固定的**。

每个模型有自己的"宽度",业界叫 **hidden_size**(隐藏层维度)或 **embedding_dim**:

| 模型 | hidden_size(宽度) | 备注 |
|---|---|---|
| BERT-base | **768** | 又矮又瘦 |
| GPT-2 small | 768 | 早期 |
| GPT-2 XL | 1600 | |
| **LLaMA-7B** | **4096** | 前面一直用这个举例 |
| LLaMA-13B | 5120 | |
| **LLaMA-70B** | **8192** | 又高又胖 |
| **GPT-3 175B** | **12288** | 巨人 |
| Qwen-7B | 4096 | |
| Qwen-72B | 8192 | |
| GPT-4(推测) | 12288 ~ 18432 | 不公开 |
| **DeepSeek-V3** | **7168** | |

**这个数字"一旦训练完就锁死"**——同一个模型的所有 Token 都用同一个宽度。

### 9.10 宽度的连锁影响

你笔记《大模型基础概念》第六章"深度 vs 宽度"讲过。串起来看:

| 维度数变化 | 影响 |
|---|---|
| **Embedding 表大小** | 线性增长(150000 × hidden_size) |
| **每层权重矩阵** | **平方增长**(hidden_size × hidden_size) |
| **KV Cache 大小** | 线性增长(hidden_size × seq_len × layers) |
| **每个 Token 的"信息容量"** | 线性增长 |

**举例对比**:

```
模型 A:hidden_size = 4096
  Embedding 表:150000 × 4096 = 6.1 亿参数 ≈ 1.2 GB(FP16)

模型 B:hidden_size = 8192(翻倍)
  Embedding 表:150000 × 8192 = 12.3 亿参数 ≈ 2.5 GB

模型 C:hidden_size = 12288(×3)
  Embedding 表:150000 × 12288 = 18.4 亿参数 ≈ 3.7 GB
```

但更恐怖的是**每一层的权重矩阵**:

```
hidden_size = 4096:每层 4096 × 4096 = 1700 万参数
hidden_size = 8192:每层 8192 × 8192 = 6700 万参数(×4)
hidden_size = 12288:每层 12288 × 12288 = 1.5 亿参数(×9)
```

**这就是你笔记里"加宽 = 平方 ↑↑"的来源**。

### 9.11 宽度的"贯穿性"

宽度不只在"输入 Embedding"层。**从输入到输出,整个 LLM 内部所有的中间向量都是同一宽度**:

```
输入 Embedding:    4096 维
Layer 1 输出:     4096 维
Layer 2 输出:     4096 维
...
Layer 80 输出:    4096 维
最终输出(送到词表头):4096 维 → 投影到词表大小(15万)→ 选 Token
                              ↑
                        最后这一步才"变形"
```

**整个 LLM 主体就是个"4096 维向量进、4096 维向量出"的转换器**——宽度从头贯穿到尾。

### 9.12 几种"宽度变种"

#### 9.12.1 GQA(Grouped Query Attention)

LLaMA-3 70B 用了:

```
Query(Q):8192 维(完整宽度)
Key(K):1024 维(压缩了)  ← KV Cache 只存这个,省显存
Value(V):1024 维(压缩了)

→ KV Cache 体积砍到 1/8
→ 你笔记里 KV Cache 公式里那个 "num_kv_heads/num_heads" 就是这个
```

**所以严格说**:KV Cache 里向量的宽度,有时**比 Embedding 窄**。

#### 9.12.2 MoE(Mixture of Experts)

```
普通 dense 模型:
  Token 经过一个 4096 维的 FFN

MoE 模型(如 DeepSeek-V3、Mixtral):
  Token 经过 64 个 4096 维的"专家"中的 2-8 个
  每次选不同的子集

→ 总参数量爆炸,但单次推理只激活一小部分
```

#### 9.12.3 不同 Encoder 的宽度也不同

```
CLIP ViT-L:     宽度 1024
DINOv2-G:       宽度 1536
SigLIP-L:       宽度 1024
InternViT-6B:   宽度 3200

→ 都不一样
→ 都得经过 Projector 才能对齐到 LLM 主体宽度
```

### 9.13 为什么不无脑加宽

如果加宽这么好,为什么不直接做 hidden_size = 100000 的模型?

**因为代价是平方级的**:

```
hidden_size = 4096:每层 4096² = 1700 万参数
hidden_size = 40960:每层 40960² = 17 亿参数(×100)

整个 80 层模型:从 14 亿参数 → 1400 亿参数

而能力提升不是平方的——是边际递减的
```

业界的实践:

| 策略 | 代表 |
|---|---|
| 加深度而不是宽度 | Mistral 7B(32 层、4096 宽) |
| 平衡深度+宽度 | LLaMA 系列 |
| 加宽但用 MoE 控制激活量 | DeepSeek V3、Mixtral |
| 极限宽度+深度 | GPT-4 这种巨头(贵到飞起) |

### 9.14 宽度怎么"选"

宽度选择参考几个原则:

1. **能整除注意力头数**(hidden_size = num_heads × head_dim)
   - 常见:head_dim = 64 或 128
   - 所以 hidden_size 常是 64 / 128 的倍数(768、1024、4096、8192...)

2. **配合硬件**(GPU 的矩阵运算单元有偏好尺寸)
   - NVIDIA Tensor Core 对 128 倍数友好

3. **配合显存预算**

4. **配合训练数据量**(Chinchilla scaling law:模型大小和数据量要匹配)

### 9.15 KV Cache 里的向量

#### 9.15.1 你的核心理解

你的精确表述:"Token 的 Embedding 是一个浮点数组,有 4096 个数。进了 KV Cache,也是这么一个结构,根据上下文变换。"

**结构上完全正确**。需要精修两个点。

#### 9.15.2 修正点 1:Embedding 本身固定,中间状态才变

```
输入 Embedding(永远不变):
  "猫" → 查表得到 [0.0234, -0.1827, ..., 0.2789]
        无论上下文是什么,查出来都是这串数字
        这串数字是"猫"在 Embedding 表里的固定坐标

中间状态(随上下文变化):
  Layer 1 加工后:[0.05, -0.21, ..., 0.31]  ← 融合了周围 Token 的信息
  Layer 2 加工后:[0.08, -0.18, ..., 0.34]  ← 进一步融合
  ...
  Layer 80 加工后:[0.12, -0.15, ..., 0.38] ← 最终的"上下文化向量"

  这 80 层的中间状态,每层都存一份 K 和 V → KV Cache
```

**精确说法**:

> **Embedding 本身是固定的("猫"的 Embedding 永远是那串数字)。但 Embedding 进入 LLM 后,每一层会算出一个"融合了上下文的新向量"——这些新向量逐层加深理解,每层的 K 和 V 存进 KV Cache。**

**所以"根据上下文变换"的精确表述**:

```
❌ "Embedding 根据上下文变换"
   → 不对。Embedding 是查表得到的,固定。

✅ "Token 在 LLM 内部的表示,根据上下文逐层变换"
   → 对。这些变换的结果存在 KV Cache 里。
```

**类比**:

```
你的身份证号(一辈子不变) ← Embedding
你在不同场合的角色(公司里是同事、家里是父亲、球场上是队长) ← 上下文相关表示
所有这些角色记录(你的人生足迹) ← KV Cache
```

#### 9.15.3 修正点 2:1 个 Token 在 KV Cache 里有 160 份

```
1 个 Token 输入 LLM
       ↓
经过 80 层,每层产生 2 个向量(一个 K,一个 V)
       ↓
所以 1 个 Token → 80 × 2 = 160 个 4096 维向量

这就是这个 Token 在 KV Cache 里的"全部足迹"
```

**对比清单**:

| 层级 | 是什么 | 数量 |
|---|---|---|
| 1 个 Token 的输入 Embedding | 1 个 4096 维向量 | 1 个向量 |
| 1 个 Token 在 KV Cache 里 | 80 层 × (K + V) | **160 个**向量 |
| 1 个 Token 占的 KV Cache 大小 | 160 × 4096 × 2字节 | **≈ 1.3 MB** |

### 9.16 完整对照表

| 概念 | 是什么 | 数量 | 是否随上下文变 | 占用空间 |
|---|---|---|---|---|
| **Token ID** | 整数 | 1 个数 | ❌ 固定 | 4 字节 |
| **Embedding** | 浮点向量 | 1 个 4096 维向量 | ❌ 固定(查表的) | 8 KB |
| **第 1 层 K, V** | 浮点向量 | 2 个 4096 维向量 | ✅ 上下文相关 | 16 KB |
| **第 2 层 K, V** | 浮点向量 | 2 个 4096 维向量 | ✅ 上下文相关 | 16 KB |
| ... | ... | ... | ✅ | ... |
| **第 80 层 K, V** | 浮点向量 | 2 个 4096 维向量 | ✅ 上下文相关 | 16 KB |
| **KV Cache(80 层全部)** | 浮点向量集合 | 160 个 4096 维向量 | ✅ 上下文相关 | **1.3 MB** |

**比例关系**:
- ID → Embedding:放大 **2000 倍**(4 字节 → 8 KB)
- Embedding → KV Cache:再放大 **160 倍**(8 KB → 1.3 MB)

这就是为什么你笔记里讲"KV Cache 几十 GB"——**每个 Token 都要在 80 层里留 160 个向量,序列长一点就爆了**。

### 9.17 速记口诀

> **Embedding = 4096 个浮点数 = 高维空间里的一个固定坐标 = Token 的"标准语义位置"**
>
> **KV Cache = 这个 Token 经过 LLM 80 层加工后的 160 个上下文相关向量 = "语义位置在当前上下文里被丰富后的足迹"**
>
> **结构上同一物种(都是 4096 维浮点向量),数量上 KV Cache 是 Embedding 的 160 倍,含义上 KV Cache 包含上下文信息而 Embedding 不包含。**

## 10. 数据类型与精度

### 10.1 命名规则

**FP32 里的 "32" 是"位数(bit)"——一个数字用 32 个二进制位存储。**

```
8 bit = 1 字节
32 bit = 32 ÷ 8 = 4 字节
```

**所以**:
- FP32 → 32 bit → 4 字节
- FP16 → 16 bit → 2 字节
- INT8 → 8 bit → 1 字节
- INT4 → 4 bit → 0.5 字节(两个 INT4 挤一个字节)

### 10.2 命名拆解

每个名字由两部分组成:

```
FP   32
↑    ↑
类型  位数

FP = Floating Point(浮点数,能表示小数)
INT = Integer(整数)
```

**完整对照**:

| 名字 | 类型 | 位数 | 字节 | 能表示什么 |
|---|---|---|---|---|
| **FP32** | 浮点 | 32 bit | 4 字节 | 小数,精度高 |
| **FP16** | 浮点 | 16 bit | 2 字节 | 小数,精度中 |
| **BF16** | 浮点 | 16 bit | 2 字节 | 小数,精度中(另一种格式) |
| **FP8** | 浮点 | 8 bit | 1 字节 | 小数,精度低 |
| **INT8** | 整数 | 8 bit | 1 字节 | 整数 |
| **INT4** | 整数 | 4 bit | 0.5 字节 | 整数(量化用) |

### 10.3 为什么是 32/16/8/4

都是 **2 的幂**:

```
32 = 2⁵
16 = 2⁴
 8 = 2³
 4 = 2²
```

**原因**:计算机内存按 2 的幂对齐最高效。CPU/GPU 的硬件电路是按这些规整的位数设计的。

### 10.4 位数决定什么

位数越多 → 能表示的数字越精细,但占的空间也越大:

```
FP32:每个数字 32 bit
  能精确表示约 7 位有效小数(如 3.1415926)
  范围:极大极小都行

FP16:每个数字 16 bit
  只能精确表示约 3 位有效小数(如 3.14)
  范围:被压缩了

INT8:每个数字 8 bit
  只能表示 -128 到 +127 的整数
  本身没有小数概念

INT4:每个数字 4 bit
  只能表示 -8 到 +7 的整数
  极度粗糙
```

### 10.5 BF16 为什么不叫 FP16

**FP16 和 BF16 都是 16 位浮点**,但内部分配不同:

```
FP16(IEEE 标准):
  1 位符号 + 5 位指数 + 10 位小数
  → 精度高,但能表示的数值范围小(容易溢出)

BF16(Google Brain 设计):
  1 位符号 + 8 位指数 + 7 位小数
        ↑ 这里和 FP32 一样
  → 精度低,但数值范围大(不容易溢出)
  → "Brain Float 16" 缩写 BF16
```

**业界用途**:
- **训练用 BF16**(不溢出更重要)
- **推理用 FP16**(精度更重要)

### 10.6 量化的本质

对照你笔记里的本地部署项目——"Qwen-14B Q4 模型"中的 **Q4 就是 INT4 量化**:

```
Qwen-14B 原版(FP16):
  14B × 2 字节 = 28 GB
  → 你的 4070 12GB 根本装不下

Qwen-14B Q4(INT4 量化):
  14B × 0.5 字节 = 7 GB
  → 4070 可以舒服跑

代价:精度从 FP16 降到 INT4,模型变"笨"一点,但能跑起来
```

**这就是你笔记里"量化"的本质**——把每个数字从大类型换成小类型,**用精度换空间**。

### 10.7 几个不常见的名字

偶尔会在前沿模型里看到:

| 名字 | 含义 |
|---|---|
| **FP4** | 4 位浮点(NVIDIA 新硬件支持) |
| **FP8 E4M3 / E5M2** | 8 位浮点的两种变体(指数位/小数位分配不同) |
| **NF4** | NormalFloat 4-bit(QLoRA 用的特殊量化格式) |

### 10.8 速记口诀

> **FP = 浮点(小数),INT = 整数,后面跟着的数字就是占的 bit 数,÷8 就是字节数。**
>
> **常见组合:FP32(4 字节,高精度训练)、FP16/BF16(2 字节,推理标配)、INT8(1 字节,量化)、INT4(0.5 字节,极致压缩)。**
>
> **位数 = 精度 = 显存代价,三者一损俱损一荣俱荣。**

## 11. ViT 与 Projector 详解

### 11.1 一句话直觉

```
ViT      = "图片版的 Transformer,专门用来'看'图"
Projector = "一个小翻译官,把 ViT 看到的东西翻译成 LLM 能懂的格式"
```

### 11.2 ViT(Vision Transformer)

#### 11.2.1 一句话定义

**ViT = Vision Transformer = "处理图片的 Transformer"**

它和 LLM Transformer **几乎一模一样**,只是输入从"文字 Token"换成"图片 patch"。

#### 11.2.2 跟 LLM Transformer 的对照

你笔记里熟悉的 LLM Transformer:

```
文字 → Tokenizer → Token ID → Embedding → 多层 Transformer → 输出
                                            ↓
                                    Self-Attention + FFN
                                    反复 32-80 层
```

ViT:

```
图片 → 切 patch → patch ID → patch Embedding → 多层 Transformer → 输出
                                                  ↓
                                          Self-Attention + FFN
                                          反复 12-24 层
                                          ★ 跟 LLM 同款架构 ★
```

**核心认知**:ViT 不是什么新东西,**就是把 Transformer 这套架构搬来处理图片**。Self-Attention、FFN、多层堆叠——你笔记里学的概念全用得上。

#### 11.2.3 ViT 内部流程

```
Step 1:把图切成 patch
  一张 224×224 图 → 切成 16×16 = 256 个小块
  每个小块 14×14 像素

Step 2:每个 patch 投影成向量
  patch(一堆像素值)→ 线性变换 → 1024 维向量
  ↑ 这就是图片版的"Embedding"

Step 3:加位置编码
  告诉 ViT 这个 patch 在图的哪个位置

Step 4:进入 Transformer 层(12-24 层)
  每层:Self-Attention(patch 互相看)+ FFN(自己加工)
  ↑ 跟 LLM 一模一样的操作,只是处理 patch 而不是 token

Step 5:输出
  256 个"加工过的向量"(每个 1024 维)
  这些向量已经包含了"对图片的理解"
```

#### 11.2.4 它"看图"的方式

举例处理一张猫的图片:

```
ViT 第 1 层:每个 patch 只看附近几个 patch
  → "我旁边有橘色像素和毛发纹理"

ViT 第 6 层:每个 patch 看到更远的 patch
  → "我和那边的眼睛、鼻子一起构成猫脸"

ViT 第 12 层:每个 patch 看到全图
  → "我是一只趴在键盘上的橘猫的左耳"
```

**这就是"看懂"的物理实现**——通过反复让 patch 互相看,每个 patch 都拿到了全图上下文。

#### 11.2.5 几个数字

| 模型 | 层数 | 宽度 | 参数量 |
|---|---|---|---|
| ViT-Base | 12 | 768 | 86M |
| ViT-Large | 24 | 1024 | 307M |
| ViT-Huge | 32 | 1280 | 632M |
| **CLIP ViT-L/14** | 24 | 1024 | **300M** |
| **InternViT-6B** | 48 | 3200 | **6B** |

**典型的 ViT 大小**:300M 到几个 B 参数。**就是个独立的大模型**,跟一个小型 LLM 规模相当。

#### 11.2.6 ViT vs LLM Transformer 的关键差异

虽然架构同款,但有几点不同:

| 维度 | LLM Transformer | ViT |
|---|---|---|
| 输入单位 | Token(文字单元) | Patch(图块) |
| Attention 方向 | 单向(只看前面) | **双向**(看全图) |
| 输入数量 | 任意长度 | 固定数量(如 256) |
| 用途 | 生成文字 | **理解图像** |
| 层数 | 多(32-80 层) | 较少(12-48 层) |

最关键的差异:**LLM 是"生成式"(一边看一边吐),ViT 是"理解式"(看完一张图后输出表征向量)**。

### 11.3 Projector(投影器)

#### 11.3.1 一句话定义

**Projector = 一个小型神经网络,把 ViT 的输出"翻译"成 LLM 能直接吃的格式**

它的全部职责就是**对齐两个不同模型之间的"语言"**。

#### 11.3.2 为什么需要它

矛盾在这里:

```
ViT 的输出:1024 维向量(ViT 自己的"宽度")
LLM 的输入:4096 维向量(LLM 自己的"宽度")

→ 维度不匹配,直接拼不上
→ 需要一个"翻译官"做转换
```

不只是维度问题,**语义空间也不一样**:

```
ViT 训练时学的"语言" ≠ LLM 训练时学的"语言"

ViT 输出向量在"ViT 的语义宇宙"里
LLM 期待的输入在"LLM 的语义宇宙"里

→ 需要做"语义对齐"
```

Projector 同时解决这两个问题。

#### 11.3.3 它长什么样

**最简单的实现**(LLaVA 用的):

```python
class Projector(nn.Module):
    def __init__(self):
        self.linear1 = Linear(1024, 4096)   # 升维
        self.gelu = GELU()                   # 激活函数
        self.linear2 = Linear(4096, 4096)   # 再过一层

    def forward(self, vit_output):
        x = self.linear1(vit_output)
        x = self.gelu(x)
        x = self.linear2(x)
        return x  # 4096 维,可以喂给 LLM 了
```

**就这么简单**——两层 MLP(Multi-Layer Perceptron),加起来几百万参数。

#### 11.3.4 几种 Projector 类型

| 类型 | 复杂度 | 代表 |
|---|---|---|
| **线性层**(1 层 Linear) | 最简单 | LLaVA v1 |
| **MLP**(2-3 层 Linear + 激活) | 简单 | **LLaVA v1.5、最主流** |
| **Q-Former**(带 Attention 的小 Transformer) | 较复杂 | BLIP-2 |
| **Perceiver Resampler** | 较复杂 | Flamingo |
| **Cross-Attention** | 较复杂 | 部分模型 |

**最常用的就是 MLP**,简单粗暴有效。

#### 11.3.5 参数量

```
两层 MLP(1024 → 4096 → 4096):
  Layer 1:1024 × 4096 = 420 万参数
  Layer 2:4096 × 4096 = 1700 万参数
  总计:约 2000 万参数 = 20M

对比:
  ViT-L:300M 参数
  LLaMA-7B:7B 参数
  Projector:20M 参数
```

**Projector 是整个多模态系统里最小的部件**——但它的作用关键到不可替代。

### 11.4 两者协作的完整流程

```
📷 一张 224×224 的猫图
  ↓
切成 16×16 = 256 个 patch
  ↓
每个 patch 投影成 1024 维向量(ViT 的输入格式)
  ↓
┌─────────────────────────────────────────────┐
│  ViT(24 层 Transformer,300M 参数)          │
│  ─────────────────────                       │
│  每层:Self-Attention + FFN                   │
│  patch 互相看,逐层加深对全图的理解             │
└─────────────────────────────────────────────┘
  ↓
输出:256 个 1024 维向量("我已经看懂这张图了")
  ↓
┌─────────────────────────────────────────────┐
│  Projector(2 层 MLP,20M 参数)              │
│  ────────────────────                        │
│  把每个 1024 维向量 → 4096 维向量              │
│  对齐到 LLM 的语义空间                         │
└─────────────────────────────────────────────┘
  ↓
输出:256 个 4096 维向量(LLM 能直接吃的格式)
  ↓
和文字 Embedding 拼接,送进 LLM
  ↓
LLM 80 层 Prefill → KV Cache → Decode → "图里是一只猫..."
```

### 11.5 训练时这俩怎么学出来的

#### 11.5.1 ViT 的训练

**两阶段**:

1. **预训练阶段**:用 4 亿对图文(如 LAION-5B)做 CLIP 式对比学习
   ```
   让"猫图"的 ViT 输出 ←靠近→ "猫"的文字向量
   让"猫图"的 ViT 输出 ←远离→ "汽车"的文字向量
   ```
   这一步 ViT 学会"看图"和"理解视觉语义"。

2. **冻结**:训练多模态模型时,**ViT 通常被冻结(不更新参数)**,因为它已经训练得足够好。

#### 11.5.2 Projector 的训练

**这才是多模态训练的核心**:

```
固定 ViT 不动
固定 LLM 不动(或部分微调)
只训练 Projector!

训练数据:图片 + "请描述这张图" + 标准答案
让 Projector 学会"把 ViT 的语言翻译成 LLM 听得懂的话"
```

**惊人的事实**:

> **训练一个能看图的 LLaVA,主要工作就是训练那个 20M 参数的小 Projector。LLM 和 ViT 都是现成的,只需要训练这个小翻译官。**

这就是 LLaVA 用很小代价做出多模态模型的秘密——**站在两个巨人肩膀上,只补一个翻译官**。

### 11.6 三个工程理由

为什么这么设计?

1. **复用现有 LLM**:不用为图片重新训练一个 LLM,省钱
2. **复用现有 ViT**:CLIP/DINO 等开源 ViT 已经训得很好,拿来就用
3. **只训练 Projector**:小、快、便宜,是"穷人版多模态"的关键

**LLaVA 项目的故事**:作者用一张 8×A100 的机器,**几小时**就把 LLaMA 改造成能看图的模型——靠的就是这个"训练小 Projector"的策略。

### 11.7 几个常见误解澄清

**误解 1**:"ViT 把图变成文字"
❌ 不对。ViT 输出的是**向量**,不是文字。

**误解 2**:"Projector 是简单的格式转换"
⚠️ 部分对。维度转换是表面,**语义对齐才是核心**——它要让视觉向量落在文字 token 空间的合理位置上。

**误解 3**:"ViT 输出直接进 LLM"
❌ 不行。维度不匹配、语义空间不一致——必须过 Projector。

**误解 4**:"只要换 Projector 就能换 ViT 或 LLM"
✅ 对。这就是 Projector 设计的目的——解耦视觉模型和语言模型。

### 11.8 速记口诀

> **ViT = "图片版的 Transformer",专门用 Self-Attention 让 patch 互相看、看懂全图,输出 256 个语义丰富的向量。**
>
> **Projector = "一个 2 层 MLP 的小翻译官",把 ViT 输出的向量翻译成 LLM 能直接吃的格式(维度对齐 + 语义对齐)。**
>
> **两者协作 = 给 LLM 装上"眼睛"——ViT 看,Projector 翻译,LLM 思考。**
>
> **训练成本:ViT 已经在 4 亿图文对上预训练好(贵但一次性),Projector 是真正需要为每个多模态项目定制训练的部分(便宜、快)。**

## 第二部小结

读到这里,第一部那些抽象词都"落地"了:

- **Token** = 一个 4 字节整数 ID,词表里的索引位置,本身没有任何语义
- **Tokenizer** = 训练出来的 BPE 查表程序,纯规则、CPU 跑、永远确定
- **Embedding** = 一个 4096 维浮点向量,LLM 高维语义空间里的一个固定坐标,从查表得到
- **KV Cache** = 同样的浮点向量,但是 1 个 Token 在 LLM 80 层里有 160 份(K + V × 80),随上下文变化
- **hidden_size** = LLM 的"宽度",从 BERT 的 768 到 GPT-3 的 12288 都有,平方影响代价
- **FP32/FP16/INT4** = 命名规则简单:类型(浮点/整数) + bit 位数,÷8 是字节数
- **ViT** = 图片版的 Transformer,12-24 层 Self-Attention 让 patch 互相看
- **Projector** = 一个 2 层 MLP 小翻译官,把 ViT 输出对齐到 LLM 输入空间——多模态训练的真正主角

到这里你已经能在脑子里"打开"任何一个多模态模型,知道它内部每个张量是什么形状、什么类型、多少字节。
