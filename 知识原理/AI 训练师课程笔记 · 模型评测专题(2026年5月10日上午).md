## 一、什么是模型评测?

### 1.1 同学们日常用模型的"主观评测"

老师提问:"你们现在最好用的大模型是哪个?"
- 同学:"Claude。"
- 老师:"为什么觉得 Claude 好?"
- 同学:"用得多 / 对比过。"

> 你们日常这种"用一下觉得好" = **主观评测**,但不算公司里的真正评测。

每个模型都有自己的**优势和劣势**(比如 Claude 在生活类问题不如某些国产模型),问清楚优势劣势就是评测的过程。

### 1.2 模型评测的正式定义

> **系统化、客观化、全面性**地对大模型的性能质量,进行量化和质化评估的过程。

### 1.3 拆解关键词

| 关键词 | 含义 | 反例 |
|---|---|---|
| **系统化** | 有计划、有流程、有方案 | 单测一道题就下结论 |
| **客观化** | 不能太主观、要让别人信服 | 故意挑对模型有利的题 |
| **全面性** | 各角度各方向都覆盖 | 只测自己擅长方向 |
| **量化 + 质化** | 既要分数也要质性分析 | 只说"还不错"没有数据 |
| **性能 + 质量** | 速度、准确率、推理能力 + 内容是否符合要求 | 只看输出对错 |

### 1.4 比喻:评测 = 给模型出考试卷

> 老师反复用这个比喻,贯穿全课:

```
学生考试  →  考核学生学了多少
模型评测  →  考核模型训练得多好

考试要素:
  - 考试安排(系统化)
  - 试卷内容(全面性)
  - 难易度搭配(客观)
  - 打分方式(量化)
  - 反馈到底哪门偏科(质化分析)
```

**反馈机制对比**:
- 学校:老师反馈给学生,学生自己加强(以前没那么负责的老师)
- 模型评测:**反馈给领导/算法,下一次模型优化的方向**

### 1.5 训练 vs 评测 —— 必须区分清楚

> ⚠️ 很多同学交简历时写"评测数据量上万条" → 老师当场说"不合理"。

| 维度 | 训练阶段(SFT/RLHF) | 评测阶段 |
|---|---|---|
| **目的** | 提供优质数据让模型学 | 考核模型学得好不好 |
| **任务** | 筛选/构建优质数据 | 出试卷 + 打分 + 分析 |
| **数据量** | 上千上万条 | **200-800 条**(评测要小) |
| **持续性** | 一次性筛选完就交付 | 每个版本上线前都要做 |
| **简历写法** | 数据筛选项目 | 模型评测项目 |

> 如果听快或没听懂的地方,**一定要举手**(老师反复强调)。

## 二、什么时候做模型评测?

### 2.1 时间点:模型上下线前后

```
模型训练阶段
  │
  │  [训练阶段:数据筛选]
  ↓
模型上线前 ← ⭐ 评测点 1(出厂检测)
  │
模型正式上线
  │
  │  [线上运行,产生用户反馈]
  ↓
模型上线后 ← ⭐ 评测点 2(用户反馈分析)
```

### 2.2 类比:汽车出厂

汽车要出厂给用户开 → 必须做出厂检测。
模型上线前也要做一次评测,**确认达标才能让用户用**。

### 2.3 上线后的评测怎么做?

**触发场景**:
- 用户反馈不好(比如客服投诉)
- 后台调出投诉数据
- AI 训练师做评测分析

**任务**:
- 划分问题类型
- 统计**问题占比**
- 找出 **TOP 2 高频问题**
- 反馈给算法 → 下一次针对性优化

### 2.4 评测的双重目的

| 目的 | 含义 |
|---|---|
| **质量校验** | 模型是否达标可以上线 / 是否发现新问题 |
| **优化方向** | 比如豆包一开始只有对话 → 后来加视频/音频/Agent/深度思考 → 都靠评测发现需求 |

## 三、评测什么?三大类别

```
模型能力
  ├── 生成方向(基础)
  ├── 理解方向
  └── 功能性方向(辅助)
```

### 3.1 生成方向(最基础)

| 子类 | 评测要点 | 例子 |
|---|---|---|
| **文本生成** | 真实性、准确性、幻觉、逻辑(数据前后一致) | "写 2000 字产品报告" → 看数据是否真实、有没有幻觉、有没有"前面说上升后面说下降" |
| **图片生成** | 指令契合度、物理空间合理性、细节统一 | "橘黄色猫趴在咖啡馆窗前看外面,阳光打进来" → 猫的颜色统一吗?阳光逻辑对吗?物理空间对吗? |
| **视频生成** | 指令契合 + 镜头切换 + 运镜 + 物体连贯 | "人从椅子站起走向门外" → 站起来时身体有没有变形/方块?走着突然变三条腿? |
| **音频生成** | 音色、角色扮演、多音字 | TTS 多音字处理、声音音色匹配 |

### 3.2 理解方向

| 子类 | 评测要点 | 老师亲身经历 |
|---|---|---|
| **OCR** | 识别一张图的文字内容 | "我做的换课的能力,对多种字体识别效果差,但平台不支持调整" |
| **图像理解** | 物理常识 / 数人 / 反常识 | 画面里几个人?如果出现"两个脑袋""六个手指"能不能识别? |
| **图像理解(多轮)** | 多轮对话中带图理解 | 给一张图后聊天,模型能不能理解上下文?能不能基于图改答案? |
| **视频理解** | 整段画面在讲什么故事 | 给视频片段,模型能否理解情节 |
| **音频理解** | 一句话的语义判断 | 这句话什么意思 / 情绪如何 |
| **深度思考(慢思考)** | 思考方式真不真 / 流程对不对 / 速度合理吗 | 看 CoT 是否有效 |
| **MCP** | 调用协议是否正确 / 是否必要调用 | 评测的还比较少,场景小 |

### 3.3 功能性方向

| 子类 | 评测要点 |
|---|---|
| **性能 / 生成速度** | 用户多了之后会不会变慢?生成质量与速度的平衡 |
| **解析能力** | 上传 Word / Excel / PDF 能不能解析 |
| **资源消耗** | Token 消耗大小,关系到成本 |
| **上下文长度** | 最大上下文容量是多少 |

> Claude 早期能解析 Word,但解析 Excel 表格不行,后来才补强 → 这就是功能性维度迭代的过程。

### 3.4 垂类方向(必聊)

```
通用模型           垂类模型(医疗/法律/教育/金融...)
  ↓                       ↓
什么都答             只答自己领域
做着做着差不多         做得越来越精
   ↓
  会变成稀缺人员
```

#### 老师的建议

> **未来通用大模型差不多以后,会让每个垂类做更精** → 垂类训练师将成为稀缺人才,**人少但价格高**。

- 如果你有自身专业方向(财务、法律、医疗等)→ 写简历时匹配上,大加分
- 但目前找工作,**还是优先视频 / 多模态 / Agent** 这种主流方向(岗位多)
- 不要一开始就搞冷门方向 → 岗位少,匹配度差

## 四、模型评测的完整工作流

### 4.1 与之前训练流程对照

老师提问:之前做训练项目的工作流是什么?

```
需求承接 → 制定规则 → 预估排期 → 试标 → 标注 → 质检 → 数据交付
```

**评测流程几乎一致,但多了一个关键步骤**:

```
需求承接 → 制定规则 → 预估排期 → 试标 → 标注 → 质检 → 评测报告 ← 新增!
```

为什么多个**评测报告**?
- 训练阶段:交付优质数据就结束了
- 评测阶段:必须**总结结果反馈给领导/需求方**,告诉他们这个模型方向上有什么优缺点、哪些数据产出反映了什么问题

### 4.2 第一步:需求承接

#### 简历常见错误

> ⚠️ 很多人简历写"通过 5W2H 方法承接需求" → **不要再这么写**了。

#### 简化的承接思路

> 抓两个核心点就够了:**项目背景 + 项目目标**。

继续往下展开:
- 他们要什么样的数据?
- 数据有多少?
- 人员有多少?
- 时间多少?

#### 实际场景

正常对接需求 = **拉个会** + **共享屏幕讲需求**(口述 / 文档都可能)。

#### 关键技巧:开会**录音**

> 如果对方没给文档,**一定要录音**!
> 录完之后利用大模型帮你整理需求、分析、写到钉钉文档里。
> 这是非常重要的一个习惯。

#### 评测排期:不能当场答

```
对方:"会议结束了,什么时候给到我?"
错误回答:"3 天 / 5 天"(乱拍脑袋)
```

**正确做法**:
1. 拿到数据后先看一下数据
2. 看数据难度
3. 看人员够不够
4. **试标**得到一个真实时效
5. **再回复**

#### 计时起点的坑

> 算法说"今天给数据" → 实际上是**他写代码生成数据**,可能要到第二天甚至更晚才真正交付。
> ⭐ **计时起点应该是"算法把数据交付给你的那一天"**,不是开会那一天。

#### 给时间留 buffer

```
评测耗时 = 标注时间 + 数据分析时间(可能半天到一天)
```

不要算"两天刚好搞完",一定要给自己留分析时间,**否则你会做到凌晨 12 点**(老师亲身经历)。

#### 谈判技巧

```
你说:5 天
对方:"急,能不能 3 天?"
应对方法:
  1. 先报半个月 → 对方砍价就到一周左右(常用谈判技巧)
  2. 拿数据说话:"我有 X 人,有 Y 数据量,具体时间是 Z 天"
  3. 数据摆出来,他没法说
```

如果对方还是要催:
- 找你老大协调更多人手
- 实在协调不到 → 不用想了,按你的节奏来

#### 管理者要避免人员空转

> 比如试标 / 等需求 / 梳理规则阶段,标注同学**没活干** → 要给他们找别的事。
> 实在没活就让他们去支援别的组。
> ⚠️ **千万别让领导发现你的人在闲置**,否则你直接背锅。

### 4.3 第二步:数据类型分析

不同公司数据交付方式不同:
- **直接导平台** → 数据格式比较明确
- **给一份资料文档** → 你要自己整理,把待标注字段都准备好

> 复杂项目可能要花 1-2 小时整理数据。

### 4.4 第三步:数据量(评测的关键差异点)

> 老师反复强调:**评测数据量是小的,不是大的**。

#### 为什么评测数据量小?

类比:
- 学生**日常学习** → 题做得多
- 学生**考试** → 题相对少(几十几百道,已经能反映水平)

#### 标准量级

| 项目类型 | 数据量 |
|---|---|
| 一般评测 | **200-800 条** |
| 一些热品评测 | 50-100 条 |
| 复杂项目可达 | 800-1000 条 |
| 多个评测维度叠加 | 800+ 条(如四个底座 × 200 = 800) |

#### 老师的真实案例

```
做的项目:四个底座
  - OCR 识别
  - 图像理解
  - 图像反应
  - 图像解题

每个底座 200 道题 → 共 800 条
项目周期:约 1 周
```

#### 周期参考

| 项目类型 | 周期 |
|---|---|
| 一般评测 | **2-3 天**(占大多数) |
| 复杂多维度评测 | **1 周** |
| 快速热品评测 | 每天评一次(C-4 那种项目) |

---

### 4.5 第四步:验收准确率

> ⚠️ 评测项目准确率要求 **99%-100%**,不是标注的 95%。

#### 为什么?

```
评测数据量小(只有 100 道题)
  ↓
你给个 95%,等于 5 道错
  ↓
基数小 → 误差占比大
  ↓
这个评测结果**不可信**
  ↓
下游决策会出错
```

#### 等同效应

```
你 100 道题做了 95% 的正确率
  =
你模型上万道题最多就能反映 95% 的能力
```

→ 评测**准确率必须高**(因为它是模型质量的"代言人")。

---

### 4.6 ⚠️ 第五步:能不能自动化评测?

#### 老师的提问

"模型评测这个阶段能不能用自动化跑?"

#### 标准答案:**大部分不能**

#### 为什么?

```
评测的是模型好坏 → 涉及主观判断
  ↓
自动化(代码)= 让另一个大模型来判
  ↓
但这个"裁判模型"怎么知道好坏?
  ↓
需要给它一个非常客观、非常明确的规则
  ↓
但实际评测有很多主观维度,无法全部规则化
```

#### 哪些情况下可以自动化?

> **唯一能自动化的:对错明确的题**(对/错二值判断)。

老师的真实案例:
```
评测对象:某个有标准答案的项目
判断维度:答案对错(只有两个值)
量级:每个版本估价 1000 条
做法:写代码扫描 → 自动打标签
结果:成功做出自动化平台
```

#### 主观维度只能靠人工

```
你要看"内容好不好"、"风格搭不搭"、"逻辑通不通"
→ 必须人工
```

### 4.7 第六步:制定规则(专项规则)

#### 面试时的失败回答

老师吐槽:模拟面试常问"你这个项目的规则维度是什么?"——

```
错误回答:
"安全维度、指令遵循维度、内容维度、语言维度..."
(大家都背的标准答案,听起来太空)
```

#### 正确回答模板

```
"我们这个项目背景是 X,目标是筛选 Y 类数据。
当时定规则维度时,我们考虑了:
- 通用维度:[安全、指令遵循、内容、语言]
- 专项维度:[针对项目的具体维度]
通过这种 ABCD 的方式去考虑..."
```

#### 关键原则

- **通用维度 + 专项维度** 一定要分开讲
- 专项维度才能体现你做过这个项目的真实经验
- 把范围缩小到具体业务,显得更可信

#### 简历准备小提醒

> 下周准备简历时,把每个项目的**专项维度**重新捋一下,通用维度不能全靠"安全、指令、格式"这种空话。

---

### 4.8 评测报告的对象 = 评测对象

评测对象有三种类型(很重要,经常混淆):

| 评测对象类型 | 含义 | 例子 |
|---|---|---|
| **竞品之间评测** | 不同模型横向对比 | 豆包 vs 千问 vs Gemini |
| **同一模型版本对比** | 同一模型上线前后 / 老版本 vs 新版本 | 二月份训练的模型 vs 十月份训练的新模型 |
| **同一模型功能开关对比** | 开/关某个能力 | 深度思考开 vs 关 |

#### 模型 ID 别犯傻

> 公司里模型经常以一串代码出现(比如 `0908_1908`、`v75`)→ 你看不懂代码不要紧,**沟通时一定要问清楚这个 ID 代表哪个模型**。

老师的提醒:
> "公司里来人太多了,大家不会觉得你是小白。所以不懂就要问。
> 你不问,后期就吃亏 —— 想改改不了,你就背锅。"

## 六、评测集怎么构造?

### 6.1 评测集的定义

> **模型训练结束后,正在评估模型综合能力的一个数据集。**

### 6.2 评测集的三大要求

| 要求 | 含义 |
|---|---|
| **陌生** | 模型在训练阶段**完全没见过**(否则等于看过答案再考试) |
| **多维度丰富** | 像真实试卷,有不同题型 |
| **难易度搭配** | 不能全是难题或全是简单题(否则反映不出真实水平) |

### 6.3 思考题:K12 教育评测怎么构造?

老师抛出实操题:**"我们要做一个 K12 教育的评测集构造,你怎么设计?"**

#### 老师引导的拆解过程

**第一步:按年级分层**
```
K12 = 1-12 年级
  → 小学(1-6 年级)
  → 初中(7-9 年级)
  → 高中(10-12 年级)
```

**第二步:按题型区分难易度**

| 题型 | 难度 | 占比 |
|---|---|---|
| 奥数题 | 高(基本拉满) | 少 |
| 应用题 | 中 | 中 |
| 计算题 | 中等偏低 | 高 |
| 填空 / 选择 | 低 | 高 |

**第三步:每个细分还要再细分**
```
小学应用题  →  按年级再分
小学计算题  →  按年级再分
初中应用题  →  按年级再分
......
```

#### 启示

> 真实做的时候,评测集的设计**远比你想象的复杂**。
> 你想得越细,评测越准确。

---

### 6.4 评测集的四大来源

| 来源 | 说明 | 面试可不可以说 |
|---|---|---|
| **用户 query** | 真实用户提的问题 | ✅ 可以说,体现真实需求 |
| **开源评测集** | GitHub / Kaggle / Plug-case 等网站上的公开数据集 | ✅ 可以说,但要做筛选 |
| **Prompt 构造** | 你用 PE 让模型自动生成评测题 | ✅ 可以说,体现技术能力 |
| **算法直接提供** | 算法给一份现成的 | ⚠️ **面试千万别说这个** |

#### ⚠️ 关于"算法提供"

老师特别强调:

> 工作中确实最常见的就是算法直接给你数据,但**面试时不能这么说**。
> 面试官会想:"那你的价值在哪?"
> 必须说自己**主动构造** —— 比如:"我发现算法给的数据不贴合用户场景,所以我让产品打造了一批用户真实数据,再做筛选,真实反映产品使用体验。"

#### 用户 Query 的形态

- 文字 query 最常见
- 图片 query(链接形式 / 图片 URL)
- 多模态混合

#### 提效技巧:自动化筛选

```
用户 Query 数据
  ↓
插件 / PE 自动跑
  ↓
图片形式输出
  ↓
人工筛选优质条目
```

简历可以写"通过 PE 提效流程优化"。

---

### 6.5 ⚠️ 关键认知:用户 query ≠ 评测集

老师特别提醒:

```
原始用户 query
  ↓ 你以为这就是评测集了?
  ↓ 不是!这只是数据来源
  ↓
理解需求 → 制定规则 → 试标 → 筛选优质数据
  ↓
这才是真正的评测集
```

> 评测集本身就是一个**独立的数据标注项目**(类似你之前做的训练数据筛选)。

---

### 6.6 评测集要"定期更换"

> 评测集**不是一次性的**,需要**持续迭代**。

#### 为什么要更换?

```
固定一份评测集
  ↓
模型迭代了几次后
  ↓
模型可能"针对评测集"做优化(过拟合到评测集)
  ↓
评测结果失真
```

#### 怎么换?

- **保留**那些已经达标的、覆盖维度好的题目
- **替换**模型已经过拟合的题目
- 替换的同时**补充新维度** → 又是一个评测集构造的小循环

> 评测集是一个**不断迭代、不断复杂化**的过程,而不是做完一次就完事。

```
百科 · 奥数 · 逻辑 · 阅读 · 汉语之子(可能是汉语)·
医疗 · 数学(K12)· 法律 · 金融 · 产品...
```

## 七、评测的三种方法

```
评测方法
  ├── 对比法(GSB / SBS)
  ├── 评分法(2/3/4/5 分制)
  └── 二值判断法(对错 / 通过不通过)
```

---

### 7.1 对比法

#### 定义

> 两个或两个以上的模型进行**两两比较**的方法。

#### 7.1.1 GSB(三档对比)

| 标识 | 英文 | 含义 |
|---|---|---|
| **G** | Good | 主模型(A)更好 |
| **S** | Same | 一样好 / 一样差 / 差不多(都用 S) |
| **B** | Bad | 主模型(A)更差 |

> 主模型 A 是你想评测的目标,B 是参照。

#### 7.1.2 SBS(Side by Side,五档对比)

```
模型 A 明显更好(更好得多)
模型 A 略好
一样好
模型 A 略差
模型 A 明显更差(更差得多)
```

> 比 GSB 多了"略好/略差"的细分,数据更细。

#### 7.1.3 GSB 的计算公式

```
胜率 = (G + S/2) / 总数
```

**为什么 S 要 ÷ 2?**
- S 表示"一样" → 我们无法判断到底胜负
- 各让一半 → S 数量的一半算给主模型

#### 7.1.4 GSB 评分标准示例

| 等级 | 维度差异 | 标识 |
|---|---|---|
| A 明显好于 B | A 在 3 个以上维度更好 | G |
| A 略好 | A 在 1-2 个维度略好 | S(其实是细分到 SBS 时的"略好") |
| A 严重不如 B | A 在**准确性 / 安全性**(高危维度)失败 | B |

> ⚠️ **准确性 + 安全性是高危维度** —— 这两个维度任何一个出问题,直接判 A 不好(无视其他维度)。

#### 7.1.5 GSB 真实案例

老师演示了几道医疗 query 的对比:
- 用户问感冒、专业医疗问题
- B 模型回答:"吃点感冒药就好了" → ❌ 不专业
- 应该:"给个建议 + 让用户去看医生"
- A 模型在 8 个维度都更优 → 全是 G

#### 7.1.6 报告里的指标

```
体感更优率 = 测试环境(向上)体感更优 + 略更优
```

老师举例:
```
测试环境体感更优 = 19% + 7% = 26%
向上(已上线)体感更优 = 还要把"向上"的也加起来
```

#### 7.1.7 优缺点

| ✅ 优点 | ❌ 缺点 |
|---|---|
| 速度快 | 难以量化(只是排序) |
| 大方向好坏立判 | 主观性太强 |

---

### 7.2 评分法(主流方法)

#### 定义

> 给每个维度打分(2/3/4/5 分制),综合算出加权分数。

#### 7.2.1 几分制怎么选?

| 分制 | 适用场景 |
|---|---|
| 2 分制 | 等同二值判断 |
| 3 分制 | 简单分类 |
| 4 分制 | 中度细分 |
| **5 分制** | 公司中**最常用** |

#### 7.2.2 5 分制示例

```
1分:非常糟糕
2分:糟糕
3分:一般 / 部分糟糕(★ 难界定的边界)
4分:良好
5分:非常好
```

#### 7.2.3 ⚠️ 关键挑战:边界要清楚

> 比如"非常糟糕 vs 糟糕"之间还有一些"创造不出来"的灰色数据 → 这就是规则定义有问题。

**做法**:
- 每个维度的边界**必须定义清晰**
- 每个分值要找**具体案例**作为锚点
- 否则标注员根本不知道怎么打分

#### 7.2.4 必加列:**问题备注 / 问题类型**

> 不要只打分 → 一定要让标注员**写出"为什么这分"**。

为什么?
- **方便定位 bad case**(知道为什么模型差)
- **方便最终数据分析**(可以统计各类问题的占比)

#### 7.2.5 报告示例

```
某模型评测后统计:
- 5 分占比 X%
- 4 分占比 Y%
- 3 分占比 Z%
- 1-2 分占比 W%
  - 其中"未给结果"占 X%
  - 其中"幻觉"占 Y%
  - 其中"格式问题"占 Z%
```

→ 你这样分析,**领导会觉得你做得很细**。

#### 7.2.6 计算公式

```
加权平均值 = Σ(分值 × 占比) / 总数
满意度 = (非常满意 + 满意) / 总数
```

#### 7.2.7 优缺点

| ✅ 优点 | ❌ 缺点 |
|---|---|
| 结果可量化 | 成本高(每个维度边界都要定义清楚) |
| 覆盖度广 | 培训成本高 |
| 灵活性强 | 项目调整时要重新定义维度 |
| 可解释性高 | - |

---

### 7.3 二值判断法

#### 定义

> 最简单 —— **两个值的判断**:1/0、对/错、通过/不通过、是/否。

#### 适用场景

- 有明确标准答案的题
- 客观题
- 数学计算题

#### 但仍要做问题备注!

> 即使是最简单的"对错判断",也要让标注员标注问题类型。

老师的建议:
```
做新项目时:
  - 如果发现新问题类型 → 把它变成一个新的问题标签
  - 让所有标注员后续统一使用这个标签
  
最终统计时:
  - 用数据透视表归类
  - 各类问题占比一目了然
```

---

### 7.4 三种方法的选择

```
快速判断模型大方向好坏     →  对比法(GSB / SBS)
精确量化各维度表现         →  评分法
有明确对错答案的题         →  二值判断法
```

实际工作中:**经常组合使用**(同一个项目不同维度用不同方法)。

### 8.1 必须有的要素


### 8.2 报告呈现技巧

| 颜色 | 含义 |
|---|---|
| 🟥 标红 | 模型出问题大的地方 |
| 🟩 标绿 | 模型表现好的地方 |

- 老板喜欢一眼看出问题
- 表格高亮 + 文字描述结合,**比纯文字效率高很多**
- "怎么方便领导看你报告就怎么写"

### 8.3 自动化分析的工具

老师建议:
- 把统计表给大模型 → 让它分析
- ⚠️ **要人工验证**(尤其阿里那些受限模型,GPT 版本可能很低,会出现误差)
- 字节内部用的模型可能更好,可以做模型分析
- 老师亲身经历:试过一些模型分析,**还不如自己做**

## 十二、面试关键话术

### 12.1 项目数据量(避坑)

❌ "我做的评测项目数据量上万条"
✅ "我做的评测项目数据量 200-800 条,因为评测要求小而精"

### 12.2 项目规则维度

❌ "安全、指令遵循、内容、语言"(背书式回答)
✅ "我们这个项目背景是 X,目标是 Y。当时定规则维度时,通用维度有 ABC,**专项维度**还有 DE,因为...."

### 12.3 评测集来源

❌ "算法直接给我们的"
✅ "我发现算法给的数据不贴合用户真实需求,**所以我们打造了一批用户 Query 数据**,经过 PE 处理 + 人工筛选,真实反映产品使用体验。"

### 12.4 数据时间起点

❌ "项目周期 5 天"(对方追问"从哪天算?")
✅ "项目周期是从**算法交付数据那天**起 5 天"(显得专业)

### 12.5 难点描述(STAR 法则)

```
Situation:项目背景是 X
Task    :遇到什么难点
Action  :我做了哪些事(用 ABCDE 列出)
Result  :最终达到什么效果(具体数据 / 占比)
```

> "评测是给模型出考试卷,训练是给模型学习材料 —— 两个是完全不一样的。"

> "评测数据量上万条 = 你根本不知道自己在做什么。"

> "汽车出厂要做出厂检测,模型上线也要做评测。"

> "公司中以结果为主,过程不重要。"

> "新人不懂就问、嗓门要大。"

> "你被领导骂'你都不主动问' → 你就说'我说了你这个不说,我就干不下去了' → 他就没办法了。"

> "面试时千万别说'算法给我们数据'—— 你就显得没价值。"

> "上海培训机构肯定也有这个东西,你抄都行,但抄完要落地。"(老师对作业的态度)

> "**做评测,准确率不是 99% 就是 100%。**"

> "**算法给到的数据没有贴合用户需求,所以我去打造了一批用户 Query 数据**" —— 这是面试金句模板。

> "公司里来人太多,大家不会觉得你是小白。所以不懂就问,你不问就吃亏。"

> "新人保护期不是新手保护期,这就是一个考验。"
