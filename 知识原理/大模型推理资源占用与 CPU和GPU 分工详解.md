## 1. 模型加载阶段

### 1.1 你执行 `ollama run qwen3-14b` 后发生了什么

#### 第 1 步：从硬盘读权重

```
SSD 上的 .gguf 文件（9GB）
    ↓ 通过 SATA/NVMe 读取
内存（RAM）作为临时中转站
```

- **使用资源**：SSD + 内存
- **速度瓶颈**：SSD 读速度（NVMe 约 3-7 GB/s）
- **耗时**：9GB 模型大约 2-5 秒

#### 第 2 步：决定哪些层放显存

推理框架（llama.cpp/Ollama）会自动判断：

- 显卡有多少显存？
- 模型有多少层？每层多大？
- 还要给 KV cache 留多少空间？

**自动决策示例 A**（4070 12GB 跑 14B Q4）：

```
模型总共：48 层
每层大小：约 190 MB
全部装下：48 × 190 = 9.1 GB
还要留：3 GB 给 KV cache + 系统

结论：48 层全部装显存 ✅
```

**自动决策示例 B**（4070 12GB 跑 30B MoE）：

```
模型总共：60 层
每层大小：约 280 MB
全装需要：16.8 GB → 显存不够

结论：前 35 层放显存（9.8 GB）
      后 25 层放内存（7 GB）
```

#### 第 3 步：通过 PCIe 把权重从内存搬到显存

```
内存（RAM）
    ↓ PCIe 总线（4070 是 PCIe 4.0 x16，32 GB/s）
显存（VRAM）
```

- **使用资源**：PCIe + 内存 + 显存
- **速度瓶颈**：PCIe 带宽
- **耗时**：9GB 数据约 0.3-1 秒

#### 第 4 步：留在内存里的部分（如果有卸载）

```
内存中保留：
├─ 卸载到 CPU 的层（如 7 GB）
├─ Tokenizer 和模型配置（约 100 MB）
└─ KV cache 在 CPU 部分对应的存储
```

### 1.2 加载完成后的资源分布

**例子 1：4070 12GB 跑 Qwen3-14B Q4_K_M（全 GPU 推理）**

```
显存（12 GB）：
├─ 模型权重：9 GB ████████████████████░░░░
├─ KV cache 预留：2 GB ████░
└─ 系统/框架：1 GB ██

内存（22 GB 可用）：
├─ Ollama 进程：~500 MB
├─ Tokenizer：~100 MB
└─ 其余：空闲
```

**例子 2：4070 12GB 跑 Qwen3-30B-A3B MoE（CPU 卸载）**

```
显存（12 GB）：
├─ 前 35 层：9.8 GB ████████████████████░░
└─ KV cache（GPU 部分）：2 GB ████

内存（22 GB 可用）：
├─ 后 25 层：7 GB ████████████░░░░░░
├─ KV cache（CPU 部分）：1.5 GB ███
└─ 系统占用：1 GB ██
```

## 2. 处理 Prompt 阶段（算力密集）

假设你输入"帮我写一首关于秋天的诗"。

### 2.1 第 1 步：Tokenizer 分词（CPU 干活）

```
"帮我写一首关于秋天的诗"
    ↓ Tokenizer（运行在 CPU）
[101, 2345, 6789, 1234, 5678, 102]  ← 6 个 token
```

- **使用资源**：CPU（很少量）
- **耗时**：几毫秒（可忽略）

### 2.2 第 2 步：生成 Embedding（GPU 干活）

把每个 token ID 查表变成向量（一般是 4096 维或 5120 维）：

```
[101] → [0.21, -0.45, 0.78, ...]（4096 维向量）
[2345] → [-0.13, 0.92, 0.04, ...]
...
```

- **使用资源**：GPU（轻量）
- **耗时**：< 10 毫秒

### 2.3 第 3 步：并行处理所有 token（算力密集的关键阶段）

**Prompt 处理特点：所有 token 一起算**

```
输入的 6 个 token 同时通过模型的 48 层：

第 1 层：6 个 token 并行计算 → Tensor Core 跑满
第 2 层：6 个 token 并行计算 → Tensor Core 跑满
...
第 48 层：6 个 token 并行计算 → Tensor Core 跑满
```

**这一步的特点**：

- **算力密集**：所有 token 同时算，Tensor Core 利用率接近 100%
- **带宽不是瓶颈**：每个权重读一次能服务所有 token
- **谁强谁快**：4090 算力是 4070 的 3 倍，这一步快 3 倍

**为什么长 prompt 时算力差异能拉开**：

| Prompt 长度            | 4070 vs 4090 速度差 |
| -------------------- | ---------------- |
| 短 prompt（10 token）   | 几乎没差             |
| 中 prompt（500 token）  | 慢 2 倍            |
| 长 prompt（5000 token） | 慢 3-5 倍          |

### 2.4 第 4 步：写入 KV cache

每一层算完后，会把"key"和"value"两个中间结果存进 KV cache（在显存里），方便后面生成 token 时复用。

```
KV cache 内容：
├─ 第 1 层的 K 和 V
├─ 第 2 层的 K 和 V
├─ ...
└─ 第 48 层的 K 和 V
```

**Prompt 处理完，KV cache 里存了 6 个 token 的状态**。

### 2.5 第 5 步：生成第一个 token

最后一层输出一个概率分布，选出概率最高的 token：

```
"秋"  ← 第一个 token 出来了！
```

到这里，**首 token 延迟（TTFT, Time To First Token）** 结束。

## 3. 持续生成 Token 阶段（带宽密集）

### 3.1 关键认知：生成阶段是"逐个吐字"

跟 prompt 阶段的"批量并行"不同，生成阶段每次只能算一个 token：

```
出了"秋"，要算下一个：

第 1 步：把"秋"的 embedding 算出来
第 2 步：跑 48 层
    │
    ├─ 每一层都要把整个权重矩阵从显存读出来
    ├─ 跟"秋"的当前状态算
    └─ 跟前面 6 个 token 的 KV cache 算
    
第 3 步：选出下一个最可能的 token → "天"

继续：
"秋天"出来了 → 算下一个
"秋天的"出来了 → 算下一个
"秋天的风"出来了 → 算下一个
...
```

### 3.2 为什么生成阶段是带宽密集

**每生成一个 token，要把整个模型的权重从显存读一遍。**

```
14B Q4 模型 = 9 GB
生成 1 个 token 需要读取 9 GB 数据

4070 带宽 504 GB/s
理论速度上限 = 504 ÷ 9 = 56 token/s
```

**算力够用吗？** 单 token 计算量很小，4070 的 Tensor Core 根本用不满（利用率 < 30%）。

**这就是为什么单用户聊天，4090 比 4070 没快太多**：

- 算力差 3 倍 → 没用
- 带宽差 2 倍 → 速度差 2 倍

## 4. CPU/GPU 分工全流程

### 4.1 分工总览表

| 阶段 | CPU 负责 | GPU 负责 |
|------|---------|---------|
| 模型加载 | 读硬盘、协调内存→显存传输 | 接收数据 |
| Tokenizer 分词 | **全部** | 不参与 |
| Embedding 查表 | 不参与 | **全部** |
| Prompt 并行处理 | 协调 | **绝大部分** |
| Token 逐个生成 | 协调 | **绝大部分** |
| KV cache 读写 | 不参与 | **全部**（在显存里） |
| 输出 detokenize | **全部** | 不参与 |
| 网络/API 通信 | **全部** | 不参与 |

**关键认知**：模型本身的计算 99% 在 GPU 上做，CPU 主要做"周边工作"。

### 4.2 全 GPU 推理时 CPU 在干嘛

```
CPU 核心利用率：通常 5-15%
    └─ 做的事：
        ├─ 接收用户输入
        ├─ Tokenizer 分词
        ├─ 调度 GPU 任务
        ├─ 把生成的 token 转回文字
        └─ 网络通信（如果有 API 服务）
```

**结论**：单卡 LLM 推理时，CPU 几乎是闲着的。**多核 CPU 对 LLM 推理几乎没帮助**。

## 5. CPU 卸载场景下的工作流

当模型超过显存，框架会做"分层卸载"。这时 CPU 才真正参与计算。

### 5.1 卸载时的数据流（每生成一个 token）

```
输入 token
    ↓
[显存] 第 1 层 → 算（GPU 跑）
[显存] 第 2 层 → 算（GPU 跑）
...
[显存] 第 35 层 → 算（GPU 跑）
    ↓
（中间结果通过 PCIe 传到内存）
    ↓
[内存] 第 36 层 → 算（CPU 跑）  ← 这里慢
[内存] 第 37 层 → 算（CPU 跑）
...
[内存] 第 60 层 → 算（CPU 跑）
    ↓
（结果通过 PCIe 回到 GPU）
    ↓
输出 token
```

### 5.2 为什么卸载会大幅降速：三个累积惩罚

#### 惩罚 1：内存带宽远低于显存带宽

| 类型 | 带宽 | 比 |
|------|------|---|
| 显存（4070） | 504 GB/s | 1× |
| 内存（DDR5-6000） | 48 GB/s | 0.1× |

**内存里的层，单层算时间是显存里的 10 倍。**

#### 惩罚 2：CPU 算力远低于 GPU

| 计算单元 | FP16 算力 |
|---------|-----------|
| 4070 GPU | 117 TFLOPS |
| Ryzen 7 7700（8核） | ~0.5 TFLOPS |

**CPU 计算速度是 GPU 的 1/200。**

但因为内存带宽是真瓶颈（不是 CPU 算力），实际差距没这么夸张。

#### 惩罚 3：PCIe 传输开销

每次跨设备都要走 PCIe（32 GB/s），中间结果传输也耗时。

### 5.3 卸载后的实际速度

**举例：4070 跑 Qwen3-30B-A3B（17GB），卸 7GB 到 CPU：**

```
全 GPU 理论速度（如果显存够）：30 tok/s
实际带卸载速度：18-25 tok/s
速度损失：约 30-40%
```

> **MoE 模型卸载损失小**，因为每次只激活一部分专家。dense 模型卸载损失大。

### 5.4 CPU 卸载时硬件利用率

```
GPU 利用率：30-60%（处理 GPU 那部分时高，传数据时空闲）
CPU 利用率：60-100%（计算分配的层）
内存带宽：跑满
PCIe：周期性高峰
```

## 6. 完整时序图

### 6.1 场景 A：4070 12GB 跑 Qwen3-14B Q4，全 GPU 推理

```
时间线（生成"秋天的风很凉"6 个 token）

T=0ms     用户输入"写一首秋天的诗"
T=2ms     [CPU] Tokenizer 分词，得到 7 个 token
T=5ms     [GPU] Embedding 查表
T=10ms    [GPU] 7 个 token 并行通过 48 层（Prompt 处理）
T=80ms    [GPU] 写入 KV cache
T=85ms    [GPU] 生成 token "秋"            ← TTFT = 85ms

T=110ms   [GPU] 读取 9GB 权重 + KV cache，生成 "天"
T=135ms   [GPU] 读取 9GB 权重，生成 "的"
T=160ms   [GPU] 读取 9GB 权重,生成 "风"
T=185ms   [GPU] 读取 9GB 权重，生成 "很"
T=210ms   [GPU] 读取 9GB 权重，生成 "凉"

每个 token 间隔约 25ms = 40 token/s

整个过程：
- CPU 利用率：5-10%（基本闲着）
- GPU 利用率：60-80%
- 显存带宽：~80% 利用率
- 内存带宽：几乎不用
```

### 6.2 场景 B：4070 12GB 跑 30B MoE 卸载

```
T=0ms     用户输入
T=2ms     [CPU] Tokenizer
T=10ms    [GPU] Embedding
T=15ms    [GPU] 前 35 层 Prompt 处理
T=50ms    [PCIe] 中间结果传到内存
T=55ms    [CPU] 后 25 层 Prompt 处理      ← 慢
T=180ms   [PCIe] 结果传回显存
T=185ms   [GPU] 生成第一个 token         ← TTFT = 185ms（慢一倍多）

每个 token 间隔约 50ms = 20 token/s

整个过程：
- CPU 利用率：60-90%（参与计算了）
- GPU 利用率：40-50%（等数据时间多）
- 显存带宽：跑满
- 内存带宽：跑满
- PCIe：周期性高峰
```

## 7. 硬件资源监控与健康指标

### 7.1 监控命令

**看 GPU 状态**：

```bash
nvidia-smi              # 查看显存占用、GPU 利用率
nvidia-smi -l 1         # 每秒刷新一次
nvidia-smi dmon         # 监控带宽、温度等
```

**看 CPU/内存**：

```bash
htop                    # 综合监控
free -h                 # 内存占用
```

### 7.2 各场景的"健康指标"

**全 GPU 推理（理想状态）**：

```
GPU 利用率：60-90% ✅
显存占用：80-95% ✅
GPU 显存带宽：60-80% ✅
CPU 利用率：5-15% ✅
内存占用：20-30% ✅
```

**正常的 CPU 卸载**：

```
GPU 利用率：40-60% ⚠️
显存占用：90-99% ⚠️
CPU 利用率：50-90% ⚠️（在干活）
内存占用：60-80% ⚠️
速度：比全 GPU 慢 30-50%
```

**异常状态（要警惕）**：

```
❌ GPU 利用率 < 20%   → 模型在 CPU 跑，配置错了
❌ 内存占用 > 95%     → 快 OOM 了
❌ 速度 < 5 tok/s     → 在用 swap，立刻停
❌ SSD 读写灯狂闪    → 模型在硬盘 swap，会写坏 SSD
```

### 7.3 实时诊断瓶颈

```bash
# 一个终端跑模型
# 另一个终端开 nvidia-smi dmon
nvidia-smi dmon

# 观察输出列：
#   sm   - GPU 利用率
#   mem  - 显存带宽利用率
#   pwr  - 功耗
```

**判断瓶颈**：

- `mem` 接近 100%：带宽瓶颈（正常状态）
- `sm` 接近 100%、`mem` 不高：算力瓶颈（少见）
- 都很低：被 CPU 拖累了（CPU 卸载严重）

## 8. 完全不依赖 CPU 是否可能？

**简短回答：完全不依赖 CPU 是不可能的，但可以让 CPU 几乎闲着。**

### 8.1 CPU 必须做的事（GPU 做不了）

#### 操作系统层面的事

```
- 进程管理（启动/停止推理程序）
- 内存分配（malloc/free）
- 文件系统操作（读模型文件）
- 网络通信（HTTP API 接收请求）
- 中断处理（响应硬件信号）
- 驱动调度（CUDA driver 本身跑在 CPU）
```

**为什么 GPU 做不了**：GPU 是"加速器"不是"主控芯片"，没有操作系统能跑在 GPU 上。所有计算机都是 **"CPU 主控 + 协处理器辅助"** 的架构。

#### CUDA Driver 本身

```
你写的代码：
    cuda_kernel<<<blocks, threads>>>(args);
    ↓
CPU 上的 CUDA Driver：
    - 编译 PTX 字节码
    - 把 kernel 上传到 GPU
    - 调度 GPU 执行
    - 等待结果
```

**关键事实**：每次启动一个 GPU 计算任务，CPU 都要"指挥"一下。GPU 不能自己决定下一步算什么。

#### 控制流（if/else/循环）

GPU 极其不擅长分支判断。LLM 推理中的"采样"步骤就有大量分支：

```python
# 这个逻辑在 CPU 上跑
if temperature > 0:
    next_token = sample_from_distribution(probs, temperature)
elif top_k > 0:
    next_token = top_k_sample(probs, top_k)
else:
    next_token = argmax(probs)

# 然后判断要不要继续
if next_token == EOS_TOKEN:
    break
if len(generated) >= max_length:
    break
```

GPU 能做矩阵乘法这种"对所有数据做同一件事"，做不了"看情况选不同分支"。

#### Tokenizer

分词是字符串处理 + 查表，是典型的 CPU 任务：

```
"你好世界" → CPU 查 BPE 词表 → [101, 234, 567]
```

虽然有人尝试做 GPU tokenizer，但**性能不如 CPU**，因为字符串处理本来就不适合并行化。

#### 数据预处理 / 后处理

```
输入：JSON 解析、字符编码转换 → CPU
输出：UTF-8 解码、流式发送 → CPU
```

### 8.2 GPU 能做的事的边界

GPU 擅长：**对大量数据做相同的简单运算**（SIMD：单指令多数据）

```
✅ 矩阵乘法（10000 × 10000 个数同时算）
✅ 向量加法
✅ 元素级激活函数（ReLU、Softmax）
✅ 卷积运算
```

GPU 不擅长：**复杂逻辑、串行依赖、分支**

```
❌ if/else/while
❌ 字符串处理
❌ 文件 I/O
❌ 网络通信
❌ 内存分配
❌ 复杂数据结构（树、图）
```

**结论**：LLM 99% 的计算量是矩阵乘法（适合 GPU），但 **1% 的"调度+控制"必须 CPU 做**。

### 8.3 那些"看起来不依赖 CPU"的方案

#### 数据中心的 H100/H200 集群

H100 有自己的 SM（流多处理器）能跑一些"调度逻辑"，但仍然需要 CPU 做：

- 启动 CUDA 进程
- 管理多卡通信（NVLink 调度）
- 接收用户请求

**单台 8 卡 H100 服务器仍然有 1-2 颗强力 CPU**（如 AMD EPYC 64 核）。

#### 苹果 M 系列（统一内存）

很多人误解："M3 Max 跑 LLM 不用 CPU 啊？"

实际是：

- M 芯片是 SoC（系统级芯片），CPU + GPU + NPU 在一颗芯片里
- 用统一内存共享数据，不需要 PCIe 传输
- **CPU 仍然在干所有"调度类"工作**

苹果只是把 CPU 和 GPU 放得很近，没有消除 CPU。

#### NPU / TPU 专用 AI 芯片

谷歌 TPU、华为昇腾、Groq LPU 这些"AI 专用芯片"：

- 优化了矩阵运算速度
- 但**仍然需要 CPU 做控制**（叫做"主机 CPU"）
- TPU 板上有 ARM 协处理器做基础调度，但大型推理仍依赖外部 x86 服务器

**Groq LPU** 算最激进的——它把 LLM 推理硬编码在芯片里，但用户访问时仍然要走 CPU 服务器。

#### NVIDIA GPUDirect 技术

NVIDIA 有个 GPUDirect 技术：

- GPU 直接读 NVMe 硬盘（不经过 CPU）
- GPU 直接走网络（GPUDirect RDMA）

**但这只是减少了 CPU 在数据搬运中的角色**，**计算调度仍然是 CPU 的事**。

### 8.4 未来会有"无 CPU LLM 设备"吗？

**短期（1-3 年）**：不会。技术上做不到。所有 AI 加速器都需要主机 CPU 控制。

**中期（3-5 年）**：可能出现"嵌入式 AI 芯片"。像 Groq LPU 这样的方向——把 CPU 和 AI 加速器深度集成成单芯片，对外看起来像"无 CPU 设备"。但芯片内部仍然有控制核心。

**长期**：理论上可能。如果未来有"自主调度的 AI 芯片"——能自己解析模型、自己决定计算流程，那确实可能不需要传统 CPU。但这需要芯片架构的根本性革命，目前看不到苗头。

## 9. 让 CPU 接近"零参与"的最佳实践

虽然消除不了 CPU，但可以让它降到最低。

### 9.1 模型完全装进显存

```
✅ 全 GPU 推理：CPU 利用率 5-15%
❌ CPU 卸载推理：CPU 利用率 60-90%
```

### 9.2 用 GPU 友好的推理框架

| 框架 | CPU 占用 | 备注 |
|------|---------|------|
| **vLLM** | 极低 | CUDA Graph 减少 CPU 调度 |
| **TensorRT-LLM** | 极低 | NVIDIA 官方优化 |
| **llama.cpp** | 中等 | 通用框架 |
| **Ollama** | 中等 | llama.cpp + 进程管理 |
| **Transformers (原生)** | 高 | Python GIL 卡得厉害 |

**vLLM 的杀手锏：CUDA Graph**

把多个 GPU 操作"录制"成一个图，整个图一次性提交给 GPU，CPU 不用每步都参与。这能让单步推理的 CPU 调度开销降低 90%。

### 9.3 用 Continuous Batching

vLLM 的另一个优化：CPU 一次提交多个请求给 GPU，GPU 自己调度执行顺序。

### 9.4 关闭花里胡哨的功能

```bash
# llama.cpp 高效配置
./llama-server \
  -m model.gguf \
  -ngl 99 \              # 全部到 GPU
  --no-warmup \           # 跳过预热
  --no-mmap \             # 不映射文件（一次性加载）
  --numa distribute \     # 优化 NUMA
  -t 1                    # CPU 只用 1 线程（反正不干活）
```

### 9.5 绕过 Python（极致优化）

Python 的 GIL 锁导致单线程性能差，CPU 经常成为瓶颈。

```
Python (transformers)：CPU 占用 30-50%
Rust/C++ (llama.cpp)：  CPU 占用 5-15%
```

**如果你看到 CPU 占用很高但 GPU 利用率不高**，多半是被 Python 卡了。

### 9.6 极限场景的 CPU 占用对照

#### 单用户聊天，全 GPU 推理

```
我的 4070 跑 Phi-4-reasoning（全装显存）：

CPU 利用率：3-8%
    ├─ Tokenizer：< 1%
    ├─ CUDA Driver：2-3%
    ├─ HTTP 服务：1-2%
    └─ 进程管理：1-2%

GPU 利用率：60-80%
显存带宽：70%
内存：几乎不用
```

这个状态下，**16 核 CPU 和 4 核 CPU 几乎没区别**——都是闲着。

#### CPU 卸载推理

```
4070 跑 Qwen3-30B-A3B（卸 7GB）：

CPU 利用率：60-85%（参与计算）
    ├─ 矩阵乘法（卸载层）：50-70%
    ├─ 数据搬运：5-10%
    └─ 调度：5%

GPU 利用率：40-60%（等数据时间多）
内存带宽：跑满
```

这种场景，**CPU 性能直接影响速度**：

| CPU | 速度 |
|-----|------|
| Ryzen 9 7950X | 18 tok/s |
| Ryzen 5 5600 | 12 tok/s |
| 老 i5 | 5 tok/s |

#### 大并发服务

```
vLLM 跑 100 个并发请求：

CPU 利用率：30-50%（调度 + 网络）
GPU 利用率：95%+
```

并发场景 CPU 又开始忙了——要管理大量请求。

## 10. 常见疑问 FAQ

### Q1：为什么我的 GPU 利用率只有 60-70%？

**A**：这是正常的。LLM 推理是带宽密集型，不是算力密集型。GPU 经常在"等数据从显存搬过来"，不是计算不过来。看显存带宽利用率才有意义。

### Q2：为什么模型加载很慢但运行很快？

**A**：加载阶段瓶颈是 SSD（3-7 GB/s）+ PCIe（32 GB/s）。运行阶段权重已经在显存里了，走显存带宽（504 GB/s），快得多。

### Q3：多核 CPU 能加速 LLM 吗？

**A**：全 GPU 推理时几乎没用。CPU 只在做 CPU 卸载时才重要，这时核心数和内存带宽都有影响。但即使 16 核 CPU，速度也远不如 GPU。

### Q4：上下文越长，为什么速度越慢？

**A**：KV cache 越来越大，每生成一个 token，要读的数据量也越来越多：

- 第 1 个 token：读 9GB（仅模型权重）
- 第 1000 个 token：读 9GB + 1GB KV cache = 10GB
- 第 8000 个 token：读 9GB + 4GB KV cache = 13GB

速度从 50 tok/s 跌到 35 tok/s 是正常的。

### Q5：为什么有时候内存被占满了，但显存还没满？

**A**：你可能在跑 dense 大模型卸载。dense 模型每层大小相近，卸载到内存的部分会占大量内存。换 MoE 模型能改善（MoE 大部分专家是闲置的）。

### Q6：多个模型同时加载会怎样？

**A**：各占各的显存/内存。如果总和超过物理容量，先加载的不动，后加载的报 OOM。Ollama 默认会自动卸载不用的模型。

### Q7：完全不用 CPU 有可能吗？

**A**：不可能。CPU 必须做：操作系统调度、CUDA Driver 控制、采样逻辑、Tokenizer、网络通信。但全 GPU 推理时 CPU 利用率能压到 5% 以下。

## 11. 实战优化建议

### 11.1 让 GPU 利用率最大化

```bash
# llama.cpp 参数
./llama-server \
  -m model.gguf \
  -ngl 99 \              # 所有层放 GPU
  --flash-attn \          # 开启 Flash Attention（省显存）
  --cache-type-k q8_0 \   # KV cache 用 Q8（省一半显存）
  --cache-type-v q8_0 \
  -c 8192                 # 上下文设合适大小，别贪多
```

### 11.2 让 CPU 卸载尽量少痛

如果必须卸载：

1. **优先选 MoE 模型**（卸载惩罚小）
2. **手动指定 GPU 层数**（让 GPU 装到 95%）
   ```bash
   -ngl 35  # 手动指定放 35 层到 GPU
   ```
3. **关闭其他占内存的应用**
4. **保证内存频率高**（DDR5 比 DDR4 卸载快一倍）

### 11.3 不同场景的 CPU 选购建议

**只关心推理速度**：

- 4070 全 GPU 推理时，i3 和 i9 没区别
- 把钱花在显卡上，不要堆 CPU

**做 CPU 卸载**：

- CPU 性能开始重要
- 优先**多核 + 高内存带宽**
- AMD Ryzen 7000/9000 系列性价比好
- 内存上 DDR5-6000 或更高

**做并发服务**：

- CPU 核心数要够
- 单 GPU 服务建议 8 核以上
- 多 GPU 服务建议 16 核以上

## 附录 A：资源占用速查表

```
显存装：模型权重 + KV cache + GPU 计算缓冲（绝对主角）
内存装：被卸载的模型层 + KV cache 卸载部分 + 临时数据
GPU 干：99% 的实际计算
CPU 干：分词、调度、被卸载的层（仅在卸载时）
PCIe 走：模型加载时 + 卸载推理时的中间结果
SSD 用：仅模型加载时（运行中不读）
```

## 附录 B：理想 vs 妥协状态

**全 GPU 推理（理想状态）**：

- 模型完全装显存
- GPU 持续计算
- CPU 几乎闲置
- 内存只占一点点
- 速度达到带宽上限的 70-85%

**CPU 卸载（妥协方案）**：

- 显存装一部分，内存装其余
- GPU 和 CPU 交替计算
- PCIe 反复传输
- 速度损失 30-70%

**核心要点回顾**：

> 1. **LLM 推理是带宽密集型**，不是算力密集型——这决定了显存带宽比 GPU 算力更重要
> 2. **Prompt 处理（首 token）和 Token 生成是两个截然不同的阶段**——前者吃算力，后者吃带宽
> 3. **全 GPU 推理时 CPU 几乎闲着**——多核 CPU 对单用户 LLM 帮助有限
> 4. **CPU 卸载会带来 30-70% 速度损失**——能装进显存就别卸载
> 5. **完全不依赖 CPU 不可能**——但可以压到 5% 以下
> 6. **LLM 推理就像演出，GPU 是台上演员，CPU 是后台导演**——导演戏份很少，但完全没了戏就演不了
