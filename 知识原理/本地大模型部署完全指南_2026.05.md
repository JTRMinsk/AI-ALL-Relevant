# 本地大模型部署完全指南（2026.05 版）

> 整理自与 Cursor 的讨论。本文聚焦 **如何在 Ubuntu + RTX 4070 12GB + 32GB RAM 这类消费级硬件上跑本地 LLM**：从看懂模型名字、选量化级别，到挑工具栈、避开 Ollama 的坑、用 LM Studio 实操。

## 二、量化是什么？—— 完全指南

### 2.1 一句话定义

> **量化 = 把模型权重从"高精度小数"压缩成"低精度数字"，换取更小体积和更快速度，代价是一点点精度损失。**

### 2.2 形象比喻

想象你要描述一群人的身高：

| 精度 | 怎么记 | 占多少字节 | 误差 |
|------|--------|----------|------|
| FP32 | 1.7234567 米 | 4 字节 | 几乎无 |
| FP16 | 1.72 米 | 2 字节 | 极小 |
| INT8 (Q8) | "172"（cm） | 1 字节 | 小 |
| INT4 (Q4) | "高/中高/中/矮" 16 档 | 0.5 字节 | 中 |
| INT2 (Q2) | "高/中/矮/极矮" 4 档 | 0.25 字节 | 大 |
| INT1 | "高/矮" | 0.125 字节 | 巨大 |

**模型也一样**：每个权重就是一个数，从 16-bit 压到 4-bit，体积变成 1/4。

### 2.3 怎么实现的？（技术原理）

#### 基本公式

```
量化:    int_value = round(float_value / scale + zero_point)
反量化:  float_value ≈ (int_value - zero_point) × scale
```

简单说：把一段连续的小数（比如 -2.5 到 +2.5）**线性映射**到 16 个整数（4-bit 能表示的范围）。

#### 主流量化算法

| 算法 | 特点 | 适合 |
|------|------|------|
| **RTN** (Round-to-Nearest) | 最简单，直接四舍五入 | 不推荐 |
| **GPTQ** | 用校准数据集逐层量化，最小化误差 | 服务器场景 |
| **AWQ** (Activation-aware) | 保护"重要权重"不量化 | 主流推荐 |
| **GGUF / K-quant** | llama.cpp 体系，按重要性分块 | 本地部署 |
| **bitsandbytes (BNB)** | HF 生态，nf4 量化 | 训练/微调 |
| **HQQ** | 极快的量化，无需校准 | 快速部署 |
| **SmoothQuant** | 平滑激活分布 | 8-bit 主流 |

### 2.4 GGUF 命名规则（最容易搞混）

格式：`Q<位数>_<变体>_<尺寸>`

```
Q4_0      → 简单 4-bit，旧版
Q4_K_S    → 4-bit K-quant，小块（Small）
Q4_K_M    → 4-bit K-quant，中块（Medium）  ← 最推荐
Q4_K_L    → 4-bit K-quant，大块（Large）
Q5_K_M    → 5-bit，质量更好
Q6_K      → 6-bit，接近无损
Q8_0      → 8-bit，几乎无损
IQ4_XS    → "重要性量化"，4-bit 但更省（imatrix）
IQ2_XXS   → 2-bit 极限压缩，质量明显下降
```

`_K_` 系列比 `_0` 旧版更聪明：把不同重要性的层用不同精度。

### 2.5 各级别对比（7B 模型实例）

| 量化 | 文件大小 | 显存占用 | 质量保留 | 速度 | 推荐度 |
|------|---------|---------|---------|------|--------|
| **FP16** | ~14 GB | ~16 GB | 100% | 1× | ⭐⭐ 太大 |
| **FP8** | ~7 GB | ~9 GB | 99% | 1.5× | ⭐⭐⭐ |
| **Q8_0** | ~7.2 GB | ~9 GB | 99% | 1.5× | ⭐⭐⭐ |
| **Q6_K** | ~5.5 GB | ~7 GB | 98% | 1.7× | ⭐⭐⭐⭐ |
| **Q5_K_M** | ~4.8 GB | ~6 GB | 97% | 1.8× | ⭐⭐⭐⭐ |
| **Q4_K_M** | **~4.1 GB** | **~5 GB** | **95%** | **2×** | **⭐⭐⭐⭐⭐ 黄金点** |
| **Q4_K_S** | ~3.9 GB | ~4.8 GB | 93% | 2× | ⭐⭐⭐⭐ |
| **Q3_K_M** | ~3.3 GB | ~4 GB | 88% | 2.2× | ⭐⭐⭐ |
| **Q2_K** | ~2.6 GB | ~3.2 GB | 75% | 2.5× | ⭐⭐ 仅极限场景 |
| **IQ1_S** | ~1.5 GB | ~2 GB | 50%? | 3× | ⭐ 实验性 |

### 2.6 量化的"代价"

| 影响 | 程度 | 说明 |
|------|------|------|
| 数学/推理能力 | **下降明显** | 精度敏感，量化越狠越蠢 |
| 编程能力 | **轻微下降** | Q4 一般无感，Q2 会犯小错 |
| 中文 / 日语 | 中等下降 | 多字节语言更敏感 |
| 长上下文 | 中等下降 | 远端信息容易"忘" |
| 创意写作 | 几乎无影响 | 主观任务最耐量化 |
| **多模态（看图）** | **下降更明显** | 视觉编码器对精度更敏感，Q4 可能损失 10-15% |

### 2.7 黄金法则

> **Q4_K_M 是消费级的最佳平衡点**：体积小 4 倍，质量损失 5%，几乎人人都用它。
>
> 如果你显存够，**优先 Q5_K_M 或 Q6_K**。
>
> 如果硬件极限，**最低不要低于 Q3_K_M**。
>
> **Q2 以下基本就是"能跑但不好用"**。

## 三、模型选型：4070 12GB + 32GB RAM 在 2026.05 的最优解

### 3.1 我的硬件画像

```
RTX 4070 = 12 GB 总显存
├─ 系统/驱动占用 ~ 0.8-1 GB
└─ 实际可用 ~ 10.8-11.2 GB

系统 RAM = 32 GB
```

### 3.2 路线对比：多模态 vs 纯文本 vs 统一

#### 2025 中之前的二选一：
- 选稠密 9B 多模态（Qwen2.5-VL-7B 等）
- 选 30B-A3B 纯文本 MoE（Qwen3-30B-A3B）

#### 2026.02–03 的关键变化：**Qwen3.5 系列把多模态和 LLM 统一了**

```
Qwen3.5 全系都是统一多模态（同一权重既是 LLM 又是 VLM）：
0.8B / 2B / 4B / 9B / 27B / 35B-A3B / 122B-A10B / 397B-A17B
                  ↑       ↑
              你的甜点    需要 16GB+
```

**这意味着不用再权衡——一个模型搞定所有事。**

### 3.3 主力推荐：Qwen3.5-9B（2026.03 发布）

```
架构：稠密 9B，统一多模态（文本+图像+视频）
```

### 3.5 ⚠️ MoE offload 的真相（重要更正）

> **过去常听到的说法**："4070 + 32GB RAM 跑 35B-A3B MoE，把不活跃专家放内存，速度 10-20 tok/s"。
>
> **2026.05 实测真相**：把大 MoE offload 到 32GB 内存，**速度只有 0.5-1 tok/s**。原因是 PCIe 带宽瓶颈，专家来回切换的代价远超想象。
>
> **结论：能跑，但不可用。**

## 四、量化级别决策：Q5_K_M 还是 Q6_K？

### 4.1 4070 12GB 跑 Qwen3.5-9B 的真实账本

| 量化 | 权重大小 | 视觉编码器 | KV Cache 余量 | 上下文 | 质量保留 | 4070 速度 |
|------|---------|-----------|--------------|--------|---------|----------|
| **Q4_K_M** | ~5.5 GB | ~0.6 GB | ~4.5 GB | **64K-100K 轻松** | ~95% | 55+ tok/s |
| **Q5_K_M** | ~6.5 GB | ~0.6 GB | ~3.5 GB | **32K-64K 舒服** | ~97-98% | 50+ tok/s |
| **Q6_K** | ~7.5 GB | ~0.6 GB | ~2.5 GB | 16K-32K 够用 | **~99%** | 45+ tok/s |
| Q8_0 | ~9.5 GB | ~0.6 GB | <1 GB | 4K 紧张 | ~99.5% | 40+ tok/s |

### 4.2 为什么不选 Q4_K_M（虽然名义上是黄金点）

#### 1）显存有富裕，没必要省
12GB 是预算，Q5_K_M 只用 ~7.5 GB（含视觉），剩 3.5 GB 给上下文 —— 够日常 95% 场景。省下的那 1 GB 显存只能换"更长上下文"，但日常聊天写代码用得到 64K+ 上下文吗？大概率用不到。

#### 2）多模态模型比纯 LLM 更怕量化
- 纯 LLM 量化到 Q4：质量损失约 5%
- **多模态量化到 Q4：图像理解可能损失 10-15%**

视觉编码器对精度敏感，因为它要把像素映射到与文本对齐的空间。**量化越狠，图像识别精度掉得越快**。

#### 3）Qwen3.5 的强项是推理 / 数学，**这些最怕量化**
GPQA 81.7、MathVision 78.9 这些跑分都是在原始精度（FP16）下的成绩，量化越狠掉得越多。Q5_K_M 几乎保留全部能力，Q4_K_M 在难题上**会肉眼可见地变笨**。

#### 4）速度差异忽略不计
4070 跑 9B 模型瓶颈是显存带宽不是算力，Q4 vs Q5 的速度差 < 10%，不到 5 tok/s 的差距，**人眼几乎察觉不到**。

### 4.3 最终选择：Q6_K（"几乎无损"代名词）

```
Q6_K：
├─ 大小：~7.5 GB（含视觉 ~8.1 GB）
├─ 显存余量：~2.5-3 GB
├─ 上下文：稳跑 16K-32K（够 99% 用）
├─ 质量保留：~99%（接近 FP16 原版）
└─ 速度：45+ tok/s（依然飞快）
```

唯一代价是上下文从 64K 缩到 32K，但 **32K 已经能装一本中篇小说了**。

### 4.4 决策树

| 问题 | 是 → | 否 → |
|------|------|------|
| 经常处理 >32K 超长文本 / 视频？ | **Q4_K_M**（用质量换上下文长度） | 看下一题 |
| 对图像 / 视频识别精度敏感？（OCR、读图表、看复杂截图） | **Q6_K**（多模态最稳） | 看下一题 |
| 想保留更多显存做其他事？（同时跑别的小模型、ComfyUI、显示游戏等） | **Q5_K_M**（平衡之选） | **Q6_K**（质量党） |

### 4.5 拍板方案

```
默认方案（推荐 90% 的情况）：
└─ Q6_K        ← 你硬件完全吃得下，质量最接近原版

保守方案（不想冒险）：
└─ Q5_K_M     ← 稳妥的"业界标准"

特殊场景方案：
└─ Q4_K_M     ← 只在你明确要长上下文/同时跑其他模型时
```

## 五、部署工具：Ollama 还能用吗？

### 5.1 Ollama 在 2026 年被诟病的真实原因

#### 1）性能拉胯（最致命）

2026 年实测对比：

```
Qwen3.5-35B 在同一台机器上：
  llama.cpp：47-53 tok/s
  Ollama：   28-32 tok/s

完成同一任务时间：
  llama.cpp：12 分 50 秒
  Ollama：   20 分 03 秒（慢 57%）
```

抽象层加了无谓开销，模型越大差距越明显。

#### 2）默认上下文 4096 token（坑）

Qwen3.5 原生 262K 上下文，Ollama 默认只给 **4K**——你大概率不知道这事，模型一旦输入超过 4K 直接被截断，**得手动改环境变量才能解锁**：

```bash
OLLAMA_CONTEXT_LENGTH=32768   # 你得自己设
```

很多人抱怨"模型记性差"，实际上是 Ollama 默认配置的问题。

#### 3）开源伦理争议

- README 里**一年多没提 llama.cpp**，明明是 llama.cpp 的封装
- 二进制分发**漏装 MIT 许可证**（违反开源协议）
- 2024 年社区施压后，**只在 README 加了一行**致谢
- 2025 年中**直接抛弃 llama.cpp**，自己基于 ggml 搞了一套
- 不回贡献给上游

简单说：**靠人家代码起家的，做大了之后想撇清关系**。

#### 4）GGUF 文件搞特殊化

Ollama 下载的模型**不是标准 GGUF**，文件名和元数据被改过，**没法直接给其他工具用**。等于把你"锁"在它的生态里。

#### 5）开始商业化"夹带私货"

- 2025 年加了 "Ollama Cloud" 功能
- 把云端付费模型混进本地工具里
- 二进制变臃肿、增加遥测可能
- **从"纯本地隐私"路线偏离**

#### 6）输出质量被吐槽

Reddit / Medium 上有用户报告：同一模型在 Ollama 跑，数学错得离谱、格式化输出经常崩、重复输出问题严重。**部分原因是 Ollama 的默认采样参数和 chat template 处理**，不一定是模型本身问题。

### 5.2 但 Ollama 也不是一无是处

| 优点 | 说明 |
|------|------|
| **安装最简单** | curl 一行命令搞定 |
| **生态丰富** | Open WebUI / Dify / AnythingLLM 都默认接它 |
| **新模型上得快** | 官方仓库更新及时 |
| **CLI / API 体验丝滑** | 适合写脚本 |

> **结论：Ollama 适合"快速尝鲜"，不适合"长期主力"。**

### 6.5 新手常踩的坑

## 七、Ubuntu 上 Docker 还是原生？

### 7.1 三种部署路线对比

| 路线 | 优点 | 缺点 | 适合 |
|------|------|------|------|
| **原生安装**（Native） | 性能最好、配置简单、显存利用率高 | 依赖冲突可能 | 单机个人用 ⭐⭐⭐⭐⭐ |
| **Docker** | 干净、可复现、易迁移 | 需要 NVIDIA Container Toolkit、有 RAM 开销 | 多服务、生产 |
| **Conda / venv** | Python 项目隔离 | 不隔离系统依赖 | Python 工具 |

> 对"4070 12GB 单机自用"的场景：**原生 + 少量 Docker** 是最佳搭配。

### 7.2 各组件的真实部署方式

#### 🟢 LLM 运行时（推荐原生）

| 工具 | 推荐方式 | 难度 | 备注 |
|------|---------|------|------|
| Ollama | 原生（一行命令）| ⭐ | 自动配 GPU |
| LM Studio | 原生 .AppImage / .deb | ⭐ | GUI 友好 |
| llama.cpp | 原生编译 | ⭐⭐ | 最灵活 |
| vLLM | pip 或 Docker | ⭐⭐⭐ | 生产推荐 Docker |
| text-generation-webui | 原生 install.sh | ⭐⭐ | 老牌全功能 |

#### 🟡 前端 / WebUI（Docker 友好）

| 工具 | 推荐方式 | 备注 |
|------|---------|------|
| Open WebUI | **Docker** 或 pip | Docker 是官方首推 |
| AnythingLLM | Docker 或 .AppImage | 都行 |
| LobeChat | Docker | 多服务 stack |
| SillyTavern | 原生 npm | 角色扮演社区 |

Open WebUI 在 Docker 里跑特别合适：

```bash
docker run -d \
  --network=host \
  -v open-webui:/app/backend/data \
  -e OLLAMA_BASE_URL=http://localhost:11434 \
  --name open-webui \
  --restart always \
  ghcr.io/open-webui/open-webui:main
```

#### 🟢 Agent 框架（多数原生）

| 工具 | 部署方式 |
|------|---------|
| Hermes Agent | pip / 原生 |
| OpenClaw | 原生 CLI 安装 |
| Cline (VS Code 插件) | VS Code 内 |
| Continue | VS Code / JetBrains 插件 |
| Aider | `pip install aider-chat` |
| Open Interpreter | `pip install open-interpreter` |
| CrewAI / LangGraph / LangChain | pip（用 venv 强烈推荐） |

### 7.3 为什么 Docker 不是首选？

#### 1）NVIDIA GPU 在 Docker 里要"绕一道弯"

需要装 NVIDIA Container Toolkit：

```bash
distribution=$(. /etc/os-release;echo $ID$VERSION_ID)
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
  sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
# ... 还有几步
sudo systemctl restart docker
```

跑容器时还要加 `--gpus all`。**多了几个故障点**。

#### 2）显存吃紧时 Docker 会让你抓狂

Docker 会消耗 ~500 MB - 1 GB 系统内存、一点点显存、PCIe 带宽（可忽略）。**4070 这种显存紧张的，建议把所有 GB 都交给模型。**

#### 3）文件 IO 路径变复杂

Docker 里改个配置、看个日志、调个模型路径，都要 mount volume，比直接编辑文件麻烦。

### 7.4 什么时候该用 Docker

✅ **强烈推荐用 Docker 的场景**：
1. **多服务编排** —— 比如 LLM + 向量数据库 + 前端 + 反向代理
2. **想随时干净卸载 / 重装**
3. **多个项目要不同的 Python 版本 / CUDA 版本**
4. **生产部署 / 服务器**
5. **某些工具官方只支持 Docker**（比如某些向量数据库）
6. **跟着教程跑，教程用 Docker**（少踩坑）

❌ **没必要用 Docker 的场景**：
1. 单机自用 LLM
2. 已经有成熟的原生包（Ollama、LM Studio）
3. 想榨干硬件性能
4. 显存非常吃紧

### 7.5 Ubuntu + 4070 12GB 的最佳推荐栈

### 7.6 Ubuntu 特有的几个建议

#### NVIDIA 驱动用官方 PPA 或 CUDA Toolkit

#### 用 `uv` 替代 pip（速度快 10-100 倍）

2024-2026 Python 圈的"事实标准"，比 pip 快得离谱。

#### 模型放专用 SSD 或独立分区

```bash
# 设置 Ollama 模型存放路径
```


### 7.7 一个常见的混乱：通信方式

很多新手以为"装在哪就只能在哪用"。其实**这些工具都通过 HTTP API 互通**：

```
原生 LM Studio / Ollama   监听 :1234 / :11434（OpenAI 兼容）
                                ↓ HTTP
Docker 里的 Open WebUI    通过 host.docker.internal:11434 连接
                                ↑ HTTP
原生的 Aider / Hermes      通过 localhost:11434 连接
                                ↑ HTTP
另一台机器                 通过 你的IP:11434 连接（开放端口后）
```

**所以"LLM 后端原生 + 其他都 Docker"或"全部原生"都行，它们之间用 HTTP 沟通，不在意彼此装在哪。**
