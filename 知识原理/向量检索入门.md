# 向量检索入门：从概念到 pgvector 实战

> 给"想用 RAG，但想搞懂底层在干嘛"的人。

---

## Part 1 · 务虚：概念与全景

### 为什么需要向量检索

传统数据库擅长**精确匹配**：

```sql
SELECT * FROM products WHERE name = '蓝牙耳机';
```

但 LLM 时代的查询往往是**语义模糊**的：
- "降噪效果好的便携音频设备" —— 没有任何关键词能精确匹配
- "客户上次问的那个问题" —— 数据库不知道"那个"指什么

**向量检索解决的就是"按意思找"的问题**，而不是按字符串匹配。

### 它怎么做到的

```
Embedding（向量化）：把文本变成一串数字 [0.23, -0.12, 0.87, ...]
                    意思越近 → 数字越接近
                            ↓
Vector Store（向量存储）：把这些数字存起来
                            ↓
ANN（近似最近邻检索）：算两串数字的"距离"，找最近的几个
```

### 一个反直觉的视角：向量检索像"数据库的图灵测试"

> 数据库靠**显式定义的结构**（外键、索引、规则）回答问题。
> 向量检索靠**隐式学到的语义**（embedding 模型从海量训练数据偷学到的统计规律）回答问题。
>
> 两条路走出的结果"看起来差不多"——但向量这条路**没走数据库逻辑**，靠的是"数字距离碰巧反映了语义关系"。

所以它的根本特性是：**结果是概率近似的，不是确定的**。后面会再深入。

### 业界主流的工程实现

| 流派 | 代表 | 特点 |
|---|---|---|
| **专用向量库** | Pinecone, Qdrant, Weaviate, Milvus, Chroma | 向量性能强、大规模快，但功能单一 |
| **通用数据库 + 向量扩展** | **PostgreSQL + pgvector**, MongoDB Atlas, Elasticsearch/OpenSearch | 一库多用、能 join、运维省事 |

**选型经验：**
- 中小规模 + 已有 PG → **pgvector**（默认选择）
- 搜索场景重（电商、客服）→ **Elasticsearch/OpenSearch**
- 文档型数据 → **MongoDB Atlas**
- 亿级以上向量、极致性能 → **Pinecone / Milvus**

下面以 **PostgreSQL + pgvector** 为例，把整套机制拆透。

## Part 2 · 务实：PostgreSQL + pgvector

### 2.1 四个角色，谁干什么

```
你的程序         ─── 协调者，把下面三者串起来
Embedding 模型   ─── 翻译官，把文本变成数字（懂语义）
PostgreSQL + pgvector ─── 仓库，存数字 + 算距离（不懂语义）
LLM              ─── 读者，看检索结果生成回答
```

**特别要澄清**：pgvector **不调用** embedding 模型，也不知道 embedding 是什么。它只负责存你给它的向量、按距离排序。语义理解完全在 embedding 模型那一侧。

### 2.2 数据库里存的是什么 —— **chunk 和向量存在同一行里**

这是最关键也最容易被忽略的事实：**chunk 原文 + 向量 + 元数据是同一行的三个字段，不是分开存的**。

一条记录长这样：

```
┌─ knowledge_chunks 表里的一行 ────────────────────────┐
│                                                       │
│  id:        42                                        │
│  content:   "RAG 是通过检索增强生成的技术..."          │  ← 给 LLM 读
│  embedding: [0.23, -0.12, 0.87, ...]                  │  ← 给检索用
│  metadata:  {"source": "manual.pdf", "page": 5}       │  ← 过滤+溯源
│                                                       │
└───────────────────────────────────────────────────────┘
        ↑ 三件套必须同行，缺一不可
```

| 字段 | 作用 | 缺了会怎样 |
|---|---|---|
| content | 给 LLM 读的原文 | 检索出来一串数字，LLM 读不懂 |
| embedding | 用来算距离的向量 | 没法做语义检索 |
| metadata | 过滤、引用出处、权限 | 检索结果像黑盒，无法定位来源 |

类比：图书馆里**索书号（向量）和书本身（chunk）必须配对存放**——只有索书号找到了书但读不了；只有书知道有书但找不到。

### 2.3 整体流程

```
入库阶段（一次性）：
  原始文档 → [切块] → [向量化] → [存储] → [建索引]
                                              ↓
                                          数据库 ready
                                              ↓
查询阶段（每次提问）：
  用户问题 → [向量化] → [向量检索] → [拼上下文] → [LLM 生成] → 回答
```

下面把这 8 步**每一步都按统一格式**拆开。

---

### 2.4 每一步详解：谁/做什么/为什么/产生什么/存哪里

#### ① Chunking（切块）

- **谁做**：你的程序（通常用 LangChain / LlamaIndex 等库的切块工具）
- **做什么**：把长文档切成几百字的小段
- **为什么**：
  - embedding 模型有输入长度限制（一般 8000 token）
  - 一整本书变成一个向量，语义被严重稀释
  - 检索时只需要相关段落，不需要整本书
- **产生什么数据**：一堆文本块（chunk）
- **存哪里**：临时在内存里，等下一步处理

> 切块有讲究——按段落 / 按标题 / 按语义 / 滑动窗口……切不好直接影响检索效果。这是 RAG 工程的核心调参点之一。

#### ② Embedding（向量化）

- **谁做**：Embedding 模型（OpenAI `text-embedding-3`、Cohere、本地的 BGE / Jina 等）
- **做什么**：把每个 chunk 翻译成一串数字（一般是 1536 维向量）
- **为什么**：向量是数字，可以算距离；意思越近的文本，向量距离越近
- **产生什么数据**：每个 chunk 对应一个向量
- **存哪里**：临时在内存里，等下一步存入数据库

> ⚠️ 入库和后面查询时**必须用同一个 embedding 模型**——不同模型生成的向量在不同的"语义空间"，混用就完全对不上。

#### ③ Storing（存储）

- **谁做**：PostgreSQL（用 pgvector 提供的 `vector` 数据类型）
- **做什么**：把 chunk 原文 + 对应向量 + 元数据**作为同一行**塞进表
- **为什么**：三件套必须配对存在（见 2.2）
- **产生什么数据**：数据库表里的一行行记录
- **存哪里**：**PostgreSQL 的表数据文件**（磁盘上）

```sql
INSERT INTO knowledge_chunks (content, embedding, metadata)
VALUES ('RAG 是...', '[0.23, -0.12, ...]', '{"source":"manual.pdf"}');
```

#### ④ Indexing（建索引）

- **谁做**：pgvector（用 HNSW 或 IVFFlat 算法）
- **做什么**：把所有向量按"邻近关系"组织成一个加速结构（分层图或聚类）
- **为什么**：没索引时查询要算**所有**向量的距离，量大就卡死；有索引能"跳着算"，快几千倍
- **产生什么数据**：一份"导航数据"（向量之间的邻接关系）
- **存哪里**：**和表数据分开，存在 PostgreSQL 的独立索引文件里**

```
PostgreSQL 数据目录（磁盘）
│
├─ 表数据文件                          ← ③ 存这里
│   存所有行：content + embedding + metadata
│
└─ 索引文件                            ← ④ 存这里（独立！）
    存 HNSW 邻接图或 IVFFlat 簇结构
```

> **关于索引几个反直觉的事实：**
> - 索引可能比原数据还大（HNSW 要存大量邻居指针）
> - 索引很吃内存，理想情况要整个放进内存才快
> - 数据 INSERT/UPDATE 时索引会自动同步，但写入会变慢
> - 删索引不影响原数据，只是查询变慢

---

#### ⑤ Query Embedding（问题向量化）

- **谁做**：Embedding 模型（**必须和入库时同一个模型**）
- **做什么**：把用户问题翻译成向量
- **为什么**：要在同一个"语义空间"里才能算距离
- **产生什么数据**：一个查询向量
- **存哪里**：内存里

#### ⑥ Vector Search（向量检索）

- **谁做**：pgvector
- **做什么**：算"查询向量"和"数据库所有向量"的距离，返回最近的 K 个（通常 K=5）
- **为什么**：距离近 = 语义近 = 最相关
- **产生什么数据**：K 行记录（带 content、距离、metadata）
- **存哪里**：查询结果，临时返回给程序

```sql
SELECT content, metadata, embedding <-> '[0.22, ...]' AS distance
FROM knowledge_chunks
ORDER BY embedding <-> '[0.22, ...]'    -- ← 用 <-> 算距离
LIMIT 5;                                  --   自动走索引加速
```

> ⚠️ **不精确性来了**：这一步用的是 **ANN（近似最近邻）算法**，不保证 100% 找到最近的几个——可能漏掉真正最近的，但能保证大约 95-99% 召回率。**用 5% 准确率损失换 1000 倍速度**，是工程上的标准 trade-off。

#### ⑦ Augment（拼上下文）

- **谁做**：你的程序
- **做什么**：把检索出的 chunks 拼到 prompt 模板里
- **为什么**：LLM 没法直接看数据库，需要把相关内容塞进它的上下文窗口
- **产生什么数据**：一段完整的 prompt 字符串
- **存哪里**：内存

```
prompt = """基于以下资料回答问题：
{检索到的 5 个 chunk}

问题：{用户问题}"""
```

#### ⑧ Generation（生成回答）

- **谁做**：LLM（GPT / Claude / 本地模型）
- **做什么**：基于 prompt 里的资料生成自然语言回答
- **为什么**：LLM 负责"理解 + 表达"，前面所有步骤是为它准备"参考资料"
- **产生什么数据**：自然语言回答
- **存哪里**：返回给用户

> 这就是 RAG 三个字母的由来：**R**etrieval（②⑥ 检索）+ **A**ugmented（⑦ 增强）+ **G**eneration（⑧ 生成）。

### 2.5 pgvector 究竟"加"了什么

PostgreSQL 原本不认识向量。pgvector 这个扩展给它加了三样东西：

1. **新的数据类型** `vector(N)` —— 让表能有"向量列"
2. **新的距离运算符** `<->`（欧氏）`<=>`（余弦）`<#>`（内积）—— 让 SQL 能按向量距离排序
3. **新的索引算法** HNSW / IVFFlat —— 让向量查询变快

注意 pgvector **不算 embedding**，也不"懂"向量代表什么意思——它只负责存和算。

### 2.6 真正的威力：向量搜索 + SQL 混用

这是 pgvector 比 Pinecone 这类专用向量库更强的地方——**一句 SQL 同时做结构化过滤和向量排序**：

```sql
SELECT content
FROM knowledge_chunks
WHERE metadata->>'department' = '财务部'     -- 结构化过滤
  AND metadata->>'version' = 'v2'
ORDER BY embedding <-> q_vector              -- 向量排序
LIMIT 5;
```

也能 join 业务表：

```sql
SELECT a.title, c.content
FROM knowledge_chunks c
JOIN articles a ON c.metadata->>'article_id' = a.id::text
WHERE a.author = '张三'
ORDER BY c.embedding <-> q_vector LIMIT 5;
```

**向量搜索和 SQL 能力是合一的**，这是"通用数据库 + 向量扩展"流派的核心价值。

### 2.7 关于"不精确性"的再思考

向量检索的不精确性其实有**两层**：

- **第一层 · 索引算法层面**：ANN 可能漏掉真正最近的（前面提到的 95-99% 召回）
- **第二层 · 语义近似层面**：即使找到了"向量距离最近"的，也不等于"答案最对的"——因为 embedding 模型对语义的理解本来就是统计近似

这就是为什么向量检索**不能替代精确查询**，只能在"模糊语义匹配"场景下用。问"客户A订单 12345 的金额"应该走 SQL，问"和退款政策相关的内容"才适合走向量。

业界主流的 **Hybrid RAG** 就是这个意思——精确事走 SQL，语义事走向量，互补使用。

## Part 3 · Legacy 数据如何向量化

大多数团队不是从零开始，面对的是"已经有一堆数据的旧库"。

### 3.1 推荐设计模式：原表不动，新建 chunks 表

```
原系统（不动）              新增（RAG 专用）
┌──────────────┐           ┌──────────────────────────┐
│  products    │           │  knowledge_chunks        │
│  orders      │ ───外键──→ │  ├── source_type         │
│  customers   │           │  ├── source_id           │
└──────────────┘           │  ├── content             │
                           │  ├── embedding           │
                           │  └── metadata            │
                           └──────────────────────────┘
```

**为什么不直接在原表加 `embedding` 列？**

- ✅ 零侵入：原系统代码、报表、权限都不动
- ✅ 可独立演进：换模型、换向量库都只动 chunks 表
- ✅ 可独立运维：向量索引吃内存，可以单独部署
- ✅ 失败可回滚：RAG 出问题不影响业务系统

短字段（商品名、标签那种）也可以直接在原表加列，但长文本一定要分表。

### 3.2 回填流程

```
步骤 1：建 chunks 表（先不建向量索引）
步骤 2：分批读老数据 → 切块 → 调 embedding 模型 → INSERT 到 chunks 表
        循环直到处理完所有数据
步骤 3：所有数据有向量后，一次性建 HNSW 索引
步骤 4：改业务代码，让新数据写入时同步写 chunks 表
```

**关键工程细节：**

| 细节 | 怎么处理 |
|---|---|
| 成本 | 100 万条 ≈ $4（OpenAI），可控；本地模型免费 |
| 时间 | 100 万条约 1-2 小时，可并发加速 |
| 失败重试 | `WHERE embedding IS NULL` 天然支持断点续传 |
| 数据清洗 | 脏数据进 → 垃圾向量出，回填前先清洗 |
| 增量同步 | 业务代码写时同步 / 定时全量重建 / 监听 binlog |
| 建索引时机 | 最后再建，避免回填中每次写入都触发索引更新 |

### 3.3 常见的坑

⚠️ **入库和查询必须用同一个 embedding 模型** —— 换模型必须重建所有向量。

⚠️ **数据更新需要重新向量化** —— 改了文本不重算向量，向量代表的还是旧内容。

⚠️ **chunk 拼接要有上下文** —— 把相关字段拼成一段语义完整的文本再向量化，比单字段单独向量化效果好得多。

## 一页速查表

```
向量检索 = 把"按意思找"转化为"算数字距离"

完整流程（8 步，归两个阶段）：
  入库   切块 → 向量化 → 存储 → 建索引
  查询   问题向量化 → 检索 → 拼上下文 → LLM 生成

存储分布：
  表数据文件     chunk + 向量 + 元数据（同一行）
  索引文件       HNSW 邻接图 / IVFFlat 簇（独立文件）

四个角色：
  你的程序        协调
  Embedding 模型  懂语义（向量化）
  pgvector       傻仓库 + 加速索引
  LLM            读检索结果，生成回答

特性：
  快、模糊、概率性
  不能替代精确查询 → 与 SQL 互补使用（Hybrid RAG）
```

## 延伸阅读方向

本文只覆盖了 **Hybrid RAG 的一个分支**（关系数据库 + 向量检索）。完整 RAG 全景还有：

- **文档型 RAG**：处理 PDF / Word / 网页等非结构化文档
- **Text-to-SQL**：让 LLM 写 SQL 查结构化数据
- **GraphRAG**：用知识图谱处理复杂关系
- **检索质量优化**：Hybrid Search、Reranker、Query Rewriting、HyDE
- **评估与监控**：RAGAS、TruLens、LangSmith
- **Agentic RAG**：让 Agent 自己决定怎么检索

但底层机制相通——**切块 / 向量化 / 索引 / 检索 / 解耦设计**这套思维在所有分支中都通用。
