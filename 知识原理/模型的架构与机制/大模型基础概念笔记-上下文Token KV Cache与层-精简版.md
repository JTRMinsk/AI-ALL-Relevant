## 一、上下文长度（Context Length）

聊大模型时常说的「能塞多长」，其实不是单一数字：**模型架构**和**硬件**一起在掐上限，只是平日里我们更先听到模型标称的 128K、200K、1M——那通常是「训练/设计层面」的故事；真正落地时，还要问过 GPU：**KV Cache 装不装得下、带宽跟不跟得上**。

### 1.1 模型决定的上限

核心是**位置编码（Positional Encoding）**：

- **训练时的最大长度**：`max_position_embeddings`（例如 GPT-4 Turbo 128K、Claude 200K、Gemini 1.5 的 1M–2M 量级）。
- **编码类型决定能不能「拉长」**：
  - 绝对位置编码（早期 Transformer）：硬上限，不好外推；
  - **RoPE**：常用插值/外推思路扩展（LLaMA 系）；
  - **ALiBi**：相对更易长度外推；
  - **NoPE**：无显式位置编码的一类路线。

### 1.2 硬件决定的实际上限

即便模型「宣称」百万 token，机器也可能跑不动：推理时历史都要参与注意力，**KV Cache 跟序列长度近似线性膨胀**，往往最先撞上显存墙。

```
KV Cache 大小 ≈ 2 × num_layers × seq_len × hidden_size × num_kv_heads/num_heads × dtype_size
```

举例（LLaMA-2 70B，FP16）：

| 上下文长度 | KV Cache 占用 |
|-----------|--------------|
| 1 token | 320 KB |
| 1K token | 320 MB |
| 32K token | 10 GB |
| 128K token | 40 GB |
| 1M token | 320 GB |

### 1.3 上下文「存在哪里」

直觉上我们说的是「这一段对话文本」，但在 GPU 里真正占地方的，往往是：**为了让下一步还能 attend 到前面每一个 token，而把每一层算出来的 K/V 张量留在显存里**。这就是 KV Cache。常见优化包括 PagedAttention（vLLM）、KV 量化、以及把一部分 KV 卸到 CPU/磁盘（代价通常是延迟）。

> **结论公式**：
> ```
> 实际上下文长度上限 = min(
>     模型训练时的 max_position_embeddings,
>     GPU 显存能容纳的 KV Cache
> )
> ```

## 二、Token 是什么

规格里的 **K / M**，指的就是 **Token** 的数量级：128K、200K、1M、2M……它不是「字符数」，也不是严格的「词数」，而是这套模型** tokenizer 切出来的片段**。

### 2.1 Token 的本质

Token 是模型处理文本的**最小单位**，介于字符与整词之间的「子词」（subword）。同一段话在不同模型上可能被切成不同的 token 序列——因此**计费、上下文占用、速度**，都以各家 tokenizer 为准。

### 2.2 直观换算与各模型容量（保留量级直觉）

| 语言 | 1 token ≈ |
|------|-----------|
| 英文 | ~0.75 个单词 / ~4 个字符 |
| 中文 | ~0.5–1 个汉字（生僻字可能更多 token） |
| 代码 | 介于英文与符号之间 |

| 模型 | Token 上下文 | ≈ 英文单词 | ≈ 中文字 | ≈ 书页数 |
|------|-------------|-----------|----------|---------|
| GPT-4 Turbo | 128K | 96,000 | 80,000–128,000 | ~250 页 |
| Claude 3 | 200K | 150,000 | 130,000–200,000 | ~400 页 |
| Gemini 1.5 Pro | 1M | 750,000 | 700,000 | ~2000 页 / ~1 小时视频 |
| Gemini 1.5 Pro（实验） | 2M | 1,500,000 | 1,400,000 | 量级上可覆盖超长读物 |

### 2.3 Tokenizer 不一样，会发生什么？

同一段文本，不同模型的 token 数可能差一截：GPT 系常用 `cl100k_base` / `o200k_base`（BPE）；Claude 自有 tokenizer；LLaMA 常用 SentencePiece BPE。若要较真，可用 tiktoken 或各家控制台估算：

```python
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4")
print(len(enc.encode("你好，世界！")))
```

亦可试用 [OpenAI Tokenizer](https://platform.openai.com/tokenizer)。

## 三、Token 生成速度

推理可以粗分成两个阶段：**Prefill**（把整段 prompt 吃进去）与 **Decode**（一个接一个往外蹦 token）。它们各自的瓶颈不一样——这也是为什么「首 token 延迟」和「每秒生成多少个 token」常常拆开讨论。

### 3.1 Prefill：算力更像瓶颈

输入 token 可以并行处理，阶段整体更像 **Compute-bound**：上限大致跟 GPU 算力、以及模型每个 token 需要的计算量有关。

### 3.2 Decode：带宽更像瓶颈

生成阶段往往是 **Memory-bound**：每产出 1 个 token，通常要把大量权重（以及逐步变长的 KV）从显存带宽路径上走一遍。粗直觉：

```
理论最大生成速度 ≈ 显存带宽 / 模型参数大小
```

举例（A100，LLaMA 70B FP16）：带宽 ~2 TB/s，权重 ~140 GB → 粗算上单一请求的解码上限约在十余 tokens/s 量级（真实系统还受实现、KV、batch、内核等影响）。关键点在于：**算力常常够用，搬运跟不上**。

### 3.3 常见影响因素与减负思路（压缩列举）

| 因素 | 影响 |
|------|------|
| **显存带宽（HBM）** | 解码的重要上限之一 |
| **模型大小 / 激活参数** | 需要搬运的量 |
| **量化精度** | INT4 相对 FP16 往往显著减负 |
| **KV Cache 体量** | 越长上下文，搬运与缓存压力越大 |
| **架构与实现** | Flash Attention、Speculative Decoding、MoE、Continuous Batching 等 |

## 四、KV Cache 详解

KV Cache 是大模型推理里最「常识级」的工程概念：**为了不重复计算历史位置的注意力键值**，把每层每个位置的 **K、V** 缓存下来；代价是显存与带宽。

### 4.1 单 token 的计算样貌

```
单 token KV Cache = 2 × num_layers × num_kv_heads × head_dim × dtype_size
                    ↑                                            ↑
                  K 和 V 两份                               FP16 = 2 字节
```

以 LLaMA-2 70B（FP16）为例：80 层、GQA 下 `num_kv_heads = 8`、`head_dim = 128` →  
`2 × 80 × 8 × 128 × 2 ≈ 320 KB / token`。

### 4.2 为什么「单 token」也能这么大？

第一，**每一层都要各自一份**：Transformer 是堆叠模块，层与层的表示不同，注意力在各层回顾历史时用的是**该层**历史上的 K/V。  
第二，**多头 / GQA / MQA**在「KV 头数」上玩法不同，但直觉不变：**KV 头越多，缓存越大**。  
第三，注意力本来就用到 **K 与 V 两份**张量：`Attention(Q,K,V)=softmax(QK^T)V`。

这也是为什么 **GQA**（例如把 KV 头从 64 收到 8）能把 KV 开销砍掉倍数级；若退回稠密 MHA，同样是 70B 量级，单 token KV 会涨到约 **2.5 MB** 这一档。

### 4.3 几款模型的量级对照（FP16，单 token）

| 模型                | 层数  | KV 头数 | head_dim | 单 token KV Cache |
| ----------------- | --- | ----- | -------- | ---------------- |
| LLaMA-2 7B        | 32  | 32    | 128      | 512 KB           |
| LLaMA-2 70B (GQA) | 80  | 8     | 128      | **320 KB**       |
| GPT-3 175B        | 96  | 96    | 128      | 4.5 MB ⚠️        |
| Mistral 7B (GQA)  | 32  | 8     | 128      | 128 KB           |

> **同类参数下，70B 的 KV 未必比 7B「更重」**——架构（例如 GQA）会把 KV 头压下去。

### 4.4 优化路线图（保留原文的工程抓手）

| 方案 | 思路 |
|------|------|
| **GQA / MQA** | 共享或极致共享 KV 头 |
| **MLA**（DeepSeek-V2/V3） | 低秩/压缩表示 KV |
| **KV 量化** | INT8/INT4 减体积 |
| **PagedAttention** | 缓解碎片，提高利用率 |
| **滑动窗口** | 只保留最近片段 |
| **CPU/磁盘卸载** | 换延迟换容量 |

### 4.5 为什么 KV Cache「总想」待在显存里

```
              访问速度
              ↑ 快
┌─────────────────────────┐
│  GPU 寄存器 / L1/L2      │
├─────────────────────────┤
│  GPU 显存 HBM            │  ← KV Cache 理想位置：带宽高、延迟低
├═════════════════════════┤
│  CPU 内存 DRAM           │  慢一个量级（乃至更多）
├─────────────────────────┤
│  SSD                     │  再慢几个量级
└─────────────────────────┘
```

读同样大小的 KV：HBM 可能在毫秒以内量级扫完；DDR/NVMe 则可能拉到人类可感的延迟。**解码步步都要触碰 KV**，因此带宽差距会直接翻译成吞吐差距。

## 五、Transformer 的「层」

### 5.1 一句话定义

**每一层 = 一次「让 token 重新理解自己与上下文」的运算。**

### 5.2 每层两件事：看别人 & 想自己

```
每一层 (Layer) = Self-Attention + Feed-Forward Network (FFN/MLP)
                    ↑                    ↑
                「看别人」              「想自己」
```

**Self-Attention**：每个位置会去「看齐」序列里其它位置，把相关信息揉进自己的向量。举例：`「小明吃了苹果，他很开心」`——处理「他」时，注意力会倾向于与前文的「小明」建立关联。  
**FFN**：在吸收上下文之后，对每个位置再做一轮非线性变换，得到更抽象的表示。

### 5.3 为什么要叠很多层？

这不是玄学刻度，而是工程上的分层归纳：**浅层更像形态与局部搭配；深层更像语义整合与推理线索**。下面这张「苹果」的例子，用来建立直觉即可（真实模型未必严格对齐层号）：

| 层级（示意） | 直觉 | 例子（处理「苹果」） |
|-------------|------|---------------------|
| 较早 | 词法/局部 | 识别名词 |
| 中层 | 语法/局部语义 | 它是「吃」的宾语；更像水果而非公司名 |
| 较晚 | 全局语义/推理 | 与情绪、事件结构相关联 |

### 5.4 模型有多「深」（层数举例）

| 模型 | 层数 |
|------|------|
| GPT-2 small | 12 |
| BERT-base | 12 |
| LLaMA-2 7B / 13B / 70B | 32 / 40 / 80 |
| GPT-3 175B | 96 |

### 5.5 为何每层都要自己的 K/V Cache？

生成第 **N+1** 个 token 时：**每一层的注意力**都要使用该层前 **N** 个位置的 K/V。若不缓存，就要反复把历史在各层重算一遍，复杂度爆炸。

> KV Cache 的本质：**用显存（空间）换计算（时间）。**

## 六、深度 vs 宽度

深度（层数）与宽度（hidden_size）都「变大模型」，但**账单长得不一样**：

| 概念 | 对应 | 含义（直觉） |
|------|------|-------------|
| **深度** | `num_layers` | 「轮流想几遍」 |
| **宽度** | `hidden_size` | 「每一步向量有多宽、表达容量有多大」 |

写文章类比：**宽度**像词汇与句式储备；**深度**像修改润色的轮数。  
思考问题类比：**宽度**像一次并列考虑的因素维度；**深度**像追问「为什么」的层数。

```
浅 + 窄：脱口而出      深 + 窄：钻牛角尖
浅 + 宽：见多识广      深 + 宽：强模型的常见形状（直觉）
```

**对账单的影响（直觉）**：深度 ↑，权重与 KV 往往近似线性跟着涨；宽度 ↑，不少矩阵是「宽高相乘」的关系，**权重规模更接近平方级抬头**，计算也更重——这也是为什么「变宽」通常比「加深」更「贵」。

## 七、Token、Embedding、KV Cache

### 7.1 先澄清因果

❌ **错误**：token 是由多层 KV Cache「构成」的。  
✅ **正确**：token 是输入侧的离散单元；KV Cache 是推理过程中为了加速而缓存下来的**中间计算状态**。

### 7.2 因果链（保留主线）

```
文本
  → Tokenizer → token ID 序列
  → Embedding → 向量序列
  → 逐层：每层计算注意力时需要 K/V → 写入 KV Cache（按层、按位置累积）
  → 末尾输出下一 token 的分布
```

### 7.3 三层概念并排理解

- **上下文**：本质上是 token 序列（外加角色、工具返回等结构化包装）。  
- **KV Cache**：模型「此刻如何处理这段上下文」的中间快照；**离开推理就不该想当然地认为它还活着**。  
- **存储**：数据库里往往是 **token/文本**（体积小）；显存里爆炸的是 **KV**（体积大、寿命短）。

**学生读书类比**：字（token）还在书上；读完脑子里留下的理解与追踪（KV）是过程产物——**字不是由「理解」组成的**。

**口诀**：

> **token = 身份；embedding = 含义入口；KV Cache = 推理当下的工作记忆。**

## 八、KV Cache 的生命周期

KV Cache **不等价于「对话框」**；它更像是 GPU 处理某一趟请求时的**短期驻留物**。

### 8.1 一趟请求的秒级时间线（保留叙事）

```
按下回车 → 路由到 GPU → Prefill：为历史 token 构建 KV Cache（体积可达数十 GB 量级）
→ Decode：边生成边追加 KV → 流式结束 → 请求收尾释放显存 → KV 通常即刻消失
→ 你下次再发消息：新的一趟请求，再建一轮 KV（除非命中短期的前缀缓存服务）
```

> **要点**：KV Cache 往往只在**处理这条消息的数十秒量级**内完整存在于显存；你看到回复后，它多半已经没了——与你是否关闭窗口无关。

### 8.2 「等了三天」占不占 GPU？

| 位置 | 等什么 | 典型体量 |
|------|------|---------|
| GPU（KV） | 不占：会话静置时没有这轮 KV |
| 应用数据库 | 占：**文本/token 历史**（常为 KB–MB 级） |
| Prompt Cache（若启用） | 短命缓存（常见分钟级 TTL），不能当永久记忆 |

### 8.3 三天后再聊：发生了什么？

应用会从库里读出历史 token；模型侧仍是 **cold start**：需要把这些 token **重新跑一遍 prefill** 来再生 KV。于是：**上下文越长，每次开口的第一段等待往往越重**——这不只是「模型记性不好」，而是架构上的无状态重复计算。

**60K token KV 的量级（估算）**：类 LLaMA-70B（GQA）约 ~19 GB；类 GPT-3 175B（无 GQA）可到数百 GB 量级吓人的档位；若引入强压缩（如 MLA），则可能明显下降。**但它们仍然是「那一小段推理时间里」的临时高峰**。

**Prefill 昂贵**：粗量级 `≈ token 数 × 模型参数 × 2 FLOPs`（系数依实现而变），长上下文会把这一阶段拉长——所以你体感上的「首字延迟」，常常主要在啃历史。

**Prompt Caching（例如 Anthropic 的方案）**：可在服务端保留一段可复用的前缀 KV，显著节省下一次同类请求的 prefill；但 TTL 通常很短，与「关不关对话框」不是一回事。[Prompt Caching](https://www.anthropic.com/news/prompt-caching)

**医生与病历本**：病历（token）在档案室；医生当下的诊断心智（KV）每次现场重建——这与「伪连续对话」的工程学图景是同构的。

## 九、LLM 应用的架构：谁在保存你的对话

### 9.1 有状态的壳 vs 无状态的核

```
┌ 应用（Cursor / 网页 / 桌面端）────────────────────┐
│ 保存历史 · 组装 messages · 调工具 · 渲染 UI          │
└───────────────────────────────┬─────────────────────┘
                                │ HTTP/API
┌ 模型提供商 API ────────────────────────────────────┐
│ 单次请求进 · 单次回答出；不记得「你上一次是谁」      │
│ 可能有短命前缀缓存；不负责替你永久存档会话          │
└────────────────────────────────────────────────────┘
```

**架构口诀**：**应用层是管家；模型 API 是瞬时推理引擎。**

### 9.2 无状态到底意味着什么？

典型请求会把**到目前为止完整对话**塞进 `messages`——不是因为它「记得」，而是因为客户端**每次都要复述一遍前情提要**：

```json
POST https://api.anthropic.com/v1/messages
{
  "model": "claude-sonnet-4.5",
  "messages": [
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好！"},
    {"role": "user", "content": "现在的新问题"}
  ]
}
```

### 9.3 三种用法：管家是谁？

| 用法 | 历史存在哪 | 备注 |
|------|-----------|------|
| Claude.ai / Claude App | 提供商一侧常见方案 | 与模型服务常在同一生态，但职责仍可拆分理解 |
| Cursor 等第三方 | 第三方数据库 | 模型只看到拼装后的请求 |
| 自建脚本 | 你自己的存储 | 自由度最高，拼装逻辑也由你承担 |

**等价观察**：Claude.ai ≈ 「官方出品的管家 App」；与 Cursor 同类——差别往往在隐私边界、工具链、以及下游接哪家的「厨房」。

### 9.4 Cursor 多做了什么（示例）

例如注入 `@` 文件、编辑器上下文、规则文件、对话裁剪策略、模型路由与 Agent 工具循环——所以你感受到的「懂项目」，**很大程度是产品在替你策展上下文**，模型负责在被投喂的材料上推理。

### 9.5 维度对比（保留表格骨架）

| 维度 | Claude App | Cursor | 自建 API |
|------|-----------|--------|---------|
| 历史归属 | 提供商 | Cursor | 你 |
| 代码仓库上下文 | 依功能而定 | 强（文件/Rules 等） | 取决于实现 |
| 工具生态 | 依产品而定 | Agent 工具链 | 你来接 |

**秘书 vs 翻译窗口**：秘书归档与整理材料；窗口接单当场翻译；**档案始终在秘书那边**。

## 十、核心结论速查

### 10.1–10.6 问答表（合并呈现）

| 类别 | 问题 | 答案要点 |
|------|------|---------|
| 上下文 | 上限谁说了算？ | `min(模型位置上限, KV 显存)` |
| 上下文 | 推理时占内存的大头？ | KV Cache（随序列变长） |
| 速度 | Prefill / Decode | 算力 vs 带宽（后者常为解码瓶颈） |
| 结构 | 层做什么？ | Attention（看齐上下文）+ FFN（加工自身） |
| 结构 | 深度 / 宽度 | 层数 vs hidden；变宽常更「平方级」贵 |
| 概念 | Token / Emb / KV | 输入身份 / 向量语义入口 / 推理中间态 |
| 生命周期 | KV 活多久？ | 多为单次请求的短时窗口 |
| 架构 | 谁保存会话？ | 客户端/应用；API 通常无状态 |

### 10.7 关键公式（合集）

```
上下文长度上限 = min(max_position_embeddings, GPU 能承载的 KV Cache)

单 token KV Cache = 2 × num_layers × num_kv_heads × head_dim × dtype_size

Decode 粗直觉 ∝ 显存带宽 / 需要搬运的权重与 KV

Prefill 粗量级 ≈ token 数 × 模型参数 × 常数量级的 FLOPs
```

### 10.8 三个总结比喻（原文精神的缩短版）

1. **厨师与工作台**：token 像食材；层像工序链；KV 像每道工序必须在手边的半成品——工作台（显存）够近够快，出菜才顺。  
2. **医生与病历**：病历（数据库里的文本/token）长期存档；诊断心智（KV）每次现场重建。  
3. **秘书与翻译**：秘书拼装历史；翻译窗口只做这一轮；连续性来自**反复的上下文重装**，不是模型「私下记得你」。

## 终极一句话总结

> **模型是无状态的瞬时引擎，连续性多半来自应用的「前情提要」。**  
> **token 更像持久载荷；KV Cache 更像瞬时的工作记忆。**  
> **你感受到的同一条长对话，往往在每一次发送里都被整套重新计算过一遍（除非你命中工程上的缓存优化）。**
